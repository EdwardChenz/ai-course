#### 1. 全双工语音对话的固定链路是哪六段？音频格式怎么定？

<div class="upper-alpha" markdown>

1. 音频输入 → VAD → ASR → Agent 推理 → TTS → 音频输出；麦克风侧固定 16 kHz 单声道 16 bit PCM、扬声器侧固定 24 kHz 或 48 kHz 立体声，两侧不一致必须重采样，那次重采样会引入额外延迟并让首包变小
2. 音频输入 → ASR → VAD → Agent 推理 → TTS → 音频输出；两侧统一 44.1 kHz 即可
3. 六段固定不变，采样率可以任选，由 ASR 侧自动适配
4. 音频输入 → VAD → Agent 推理 → ASR → TTS → 音频输出，先理解意图再转写

</div>

??? question "查看答案"
    正确答案是 **A**。语音与文本的根本差别只有一句话：用户说话的时机不由你控制，而文本请求一旦发出就不会中途变卦——所以接口是"双向字节流"，架构必须从流开始设计。选 B 把 VAD 挪到 ASR 之后，会让打断检测白等识别结果，用户已经多听了半秒废话。选 D 同样错在顺序：VAD 必须先于 ASR。

    **考查概念：** Realtime语音架构

    **参见：** [章节首页](../13-multimodal-apps/index.md)

#### 2. 语音工具调用的三级分档依据是什么？各级延迟代价多大？

<div class="upper-alpha" markdown>

1. 按工具的重要性分档：重要工具要确认，不重要工具直接执行
2. 按调用频率分档：高频工具要确认，低频工具直接执行
3. 按能不能回滚分档：读类（无副作用、耗时小于 500 毫秒）直接执行、写类（有副作用但可回滚）执行后口播结果、不可逆类（涉及金钱、外发、删除）必须口播复述参数并等用户明确说"是"；延迟代价依次是 0、0、多一轮 8 到 12 秒
4. 按保密等级分档：公开工具直接执行、内部工具需确认

</div>

??? question "查看答案"
    正确答案是 **C**。分级依据是"能不能回滚"，不是"重不重要"。把"改备注"和"转账"放在同一档要求确认，会让用户被无意义的确认折磨到放弃；反过来把"转账"当读类直接执行，出一次事就够赔一整年的工具调用优化收益。选 A 和 D 都是用一个与风险无关的维度代替"能不能回滚"，选 B 则把用户体验绑在了流量上。

    **考查概念：** 语音工具调用

    **参见：** [章节首页](../13-multimodal-apps/index.md)

#### 3. barge-in 打断要真正生效，必须同时满足哪四个条件？

<div class="upper-alpha" markdown>

1. 只需要清空输出队列即可，检测方式不重要
2. 暂停播放、用户说完后接着播完，是最自然的交互
3. 等 ASR 出结果再停播，这样可以保证上下文完整
4. 在音频帧层检测而不等 ASR、丢弃而不是暂停、做回声消除否则会自己打断自己、丢弃后把"未播完"写回上下文

</div>

??? question "查看答案"
    正确答案是 **D**。四个条件缺一个用户就会觉得"它没听见我"。选 B 尤其危险：暂停意味着用户说完后系统要把没播完的半句接着播，而用户插嘴通常意味着他改了主意。选 C 的半秒延迟足以让人生气——打断检测只依赖 VAD 的当前帧能量，不依赖任何识别结果。判断做得好不好只有一个指标：打断响应成功率（300 毫秒内实际停播的次数除以打断总次数），基线 0.94、优化后 0.985，门禁不低于 0.98。

    **考查概念：** 语音打断处理

    **参见：** [章节首页](../13-multimodal-apps/index.md)

#### 4. 首音频延迟的默认合计与门禁余量是多少？为什么不能只压 VAD？

<div class="upper-alpha" markdown>

1. 默认五段合计 1,300 毫秒、距 1,500 毫秒门禁余量 200 毫秒（13.3%），余量偏薄是因为实测 P95 为 1,680 毫秒；只把 VAD 压到 200 毫秒下限在算术上最优（合计 1,000 毫秒），却把打断误触发率从 3.5% 抬到 11.2%
2. 首音频延迟必须等整段回答播完才结算，所以余量看不出来
3. 五段之间存在并行空间，应该尽量并行
4. VAD 的 500 毫秒是机器处理耗时，可以随意压低

</div>

??? question "查看答案"
    正确答案是 **A**。正确顺序是"先动别处，最后动 VAD"：三步联合优化（VAD 到 300、ASR 到 180、TTS 到 140）合计 1,020 毫秒，余量 480 毫秒、P95 落到 1,420 毫秒，只比只压 VAD 慢 20 毫秒，却保住了 3.5% 的误触发率。选 C 违反了本章的拆法前提——五段之间没有一处能并行，公式就是严格串行求和。

    **考查概念：** 语音延迟优化

    **参见：** [章节首页](../13-multimodal-apps/index.md)

#### 5. ffmpeg 合成链的三条纪律是什么？

<div class="upper-alpha" markdown>

1. 归一化可以在拼接之后统一补救，拼接前不用管
2. 归一化必须在拼接之前（分辨率、帧率、像素宽高比、采样率四项一致性检查，`-vf scale=...,setsar=1` 保住构图并把像素宽高比拉回 1:1）；拼接前先跑 `ffprobe` 探测流参数；成片还要过四项体检（规格、音画时长差不超过 40 毫秒、响度落在 -23 到 -14 LUFS、无黑帧）
3. 只要统一编码器为 `libx264`，其余归一化步骤都可以省
4. `-movflags +faststart` 是可选优化，上传平台会自行处理 moov 位置

</div>

??? question "查看答案"
    正确答案是 **B**。多模态项目里 60% 以上的线上事故不在生成环节而在合成环节，而合成事故的成因只有两个：归一化没做、时间轴靠估。这个坑本章踩过一次——花屏改了一天提示词，最后发现是某个分镜是 25 fps。选 D 会在上传后出现进度条卡在 90% 的现象，moov 在文件末尾意味着播放器必须下完整个文件才能开始播。

    **考查概念：** ffmpeg合成链

    **参见：** [章节首页](../13-multimodal-apps/index.md)

#### 6. 字幕时间轴的唯一合法时间源是什么？烧录字幕时有哪些必做参数？

<div class="upper-alpha" markdown>

1. 可以按字数与语速估算，估算值与实际偏差通常在 100 毫秒内
2. `subtitles` 滤镜必须排在 `scale` 之前，否则缩放后字幕会变形
3. SRT 时间戳的毫秒分隔符用句点即可，逗号是可选写法
4. 唯一合法时间源是配音的实际时长：先生成配音再用 `ffprobe` 读时长；SRT 毫秒分隔符是逗号；每条字幕不低于 800 毫秒、单条不超过 15 个汉字；烧录时 `subtitles` 必须排在 `scale` 之后且 `force_style` 里 `Outline=1` 描边不可省

</div>

??? question "查看答案"
    正确答案是 **D**。字幕按字数估算必然偏短，因为配音的语速是模型决定的——这条偏差正是合成链里最高频的错误来源之一，实测 640 毫秒。选 B 把滤镜顺序说反了：滤镜链按书写顺序执行，字幕在低分辨率下渲染完再被放大，边缘发虚。另外 `Outline=1` 不能省，字幕压在浅色画面上会完全看不见。

    **考查概念：** 字幕与配音合成

    **参见：** [章节首页](../13-multimodal-apps/index.md)

#### 7. 视频生成的三个参数各自是什么？调参的判断口径是什么？

<div class="upper-alpha" markdown>

1. 三个参数都有拐点：引导强度主峰在 6.0 到 8.5、可用率峰值 0.71，高于 11.0 回落到 0.55；步数 30 到 50 提升 0.02 后持平，默认取 30；种子不提升质量只保证可复现，进入成片交付的镜头必须记录
2. 引导强度越大越好，取区间上限 15.0 时可用率最高
3. 步数越多越精细，应一律取上限 60
4. 种子应当每次随机，避免画面重复

</div>

??? question "查看答案"
    正确答案是 **A**。判断参数好坏只有一个口径：整批镜头的可用率，不是单条镜头看着顺不顺眼。选 B 是最常见的误判——画面过度贴合文字但动作僵硬，可用率反而从 0.71 掉回 0.55。选 D 会让三个月后改一句台词时无法复现原来的画面，种子是成片可交付性的前提，不是可选项。

    **考查概念：** 生成参数调优

    **参见：** [章节首页](../13-multimodal-apps/index.md)

#### 8. 内容审核的三层结构是什么？抽检发现问题时应该怎么处理？

<div class="upper-alpha" markdown>

1. 机审应覆盖所有内容类型且漏检率为零才算合格
2. 人审抽检发现 1 条问题后修补那一条即可，不需要扩大抽检
3. 三层是机审前置 100% 全量、人审按类型与风险分层抽检（资讯 5%、观点 15%、带货 30%，机审得分低于 0.6 的 100% 人审）、发布后前 24 小时与前 7 天巡检；发现问题的处理方式是扩检而不是单条修补，漏检率的分母是全量不是抽检量
4. 抽检应完全随机，风险分层会带来抽样偏差

</div>

??? question "查看答案"
    正确答案是 **C**。扩检的理由是统计上的：抽检 1 条发现问题时真实问题率至少是 1/14 = 7.1%，扩检 2 倍能把问题率的估计误差从 ±7 个百分点压到 ±4 个百分点。选 B 相当于只修症状。漏检率的分母这点也必须写清——本章 100 条里最终隔离 5 条，5/100 = 0.05 正好是基线值，如果拿抽检条数当分母，验收时必然扯皮。

    **考查概念：** 内容审核机制

    **参见：** [章节首页](../13-multimodal-apps/index.md)

#### 9. 短剧单条 60 秒成片的成本里哪两项最大？降本应该先做哪一条？

<div class="upper-alpha" markdown>

1. 配音合成 0.60 元占 3.9%，应优先砍这一项
2. 视频生成占 78.4%，唯一值得投入优化精力的是可用率——把废片率从 40% 降到 25%，计费时长 100 秒降到 80 秒、视频生成 12.00 元降到 9.60 元、单条 15.30 元降到 12.90 元；而混音段改用 `-c:v copy` 是唯一零代价的改动，必须最先做
3. 人工抽检摊销 2.40 元是刚性成本，直接取消即可
4. 画质增强与转码 0.24 元占比最小，转码环节最容易砍，优先砍它

</div>

??? question "查看答案"
    正确答案是 **B**。可用率 0.75 与废片率 0.25 是同一个数的两种表述，所以"提升可用率"同时改善质量门禁和成本两个方向。降本最常见的错误是从最便宜的成本项开始砍——把配音单价从 0.60 元砍到 0.30 元只省 0.30 元（占 2.0%），而动废片率能省 2.40 元。选 C 的问题不只是省钱：抽检摊销 15.7% 排第二且不随生成质量下降而下降，是刚性成本，比例每次调整都要拿数据说话。

    **考查概念：** 生成成本核算

    **参见：** [章节首页](../13-multimodal-apps/index.md)

#### 10. 批量生成里"失败的粒度"应该怎么定？最大的一类失败又该怎么处理？

<div class="upper-alpha" markdown>

1. 按批次为单位重试即可，一次提交 6 个镜头失败 2 个就整批重跑，逻辑更简单
2. 内容审核拒（403）应归入可重试类，换个提示词重试可能就过了
3. 参数错误（400）也应重试，多次尝试总有一次能成
4. 失败的粒度必须比成功的粒度细——整批重跑会让已付的 4 个镜头（占本批 66.7%）费用作废；重试分类的依据是"重试有没有可能成功"，最大的失败来源不是报错而是"没报错但不能用"（占 62%），只能由可用率预算决定，单条内容重试预算 2 次，超过就降级为人工重做

</div>

??? question "查看答案"
    正确答案是 **D**。参数错误重试一万次也一样，审核拒则要转人工改脚本，这两类重试纯属烧钱。真正需要警惕的是"结果不可用"这一类：它在监控里完全隐形，只能靠人工或模型判定，却是唯一由预算而不是重试次数决定要不要重试的失败。三条纪律要配合着用——幂等键防重复计费、退避加抖动防重试风暴、预算熔断防单条内容吃完整天预算。

    **考查概念：** 失败重试补偿

    **参见：** [章节首页](../13-multimodal-apps/index.md)
