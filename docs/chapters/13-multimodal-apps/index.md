## 一、让 Agent 开口说话

### Realtime语音架构

语音和文本的根本差别只有一句话：**用户说话的时机不由你控制，而文本请求一旦发出就不会中途变卦**。这一句话派生出全部工程难点——可能在 Agent 说到一半时用户插嘴，可能用户说的是环境噪声，可能一句话里既有问题又有更正，可能用户全程沉默不说话。文本 Agent 的接口是"请求—响应"，语音 Agent 的接口是"双向字节流"，架构必须从流开始设计。

全双工语音对话的固定链路是六段，任何一段缺了都会在体验上留下缺口：

| 段 | 输入 → 输出 | 本章默认耗时 | 决定体验的旋钮 |
|---|---|---|---|
| 音频输入 | 麦克风 16 kHz 单声道 PCM 连续流 | — | 采样率、降噪、是否做回声消除 |
| VAD 语音活动检测 | 音频流 → 语音起止事件 | 500 ms | 静音判定阈值，唯一的"人为等待" |
| ASR 语音识别 | 语音段 → 文本 | 220 ms | 是否流式出中间结果、是否本轮就给最终结果 |
| Agent 推理 | 文本 → 工具调用或回复文本 | 340 ms | 首 token 时间，与第十一章的口径一致 |
| TTS 语音合成 | 文本 → 音频流 | 180 ms | 是否流式出首包，必须流式 |
| 音频输出 | 音频流 → 扬声器 | 60 ms | 缓冲深度、抖动缓冲 |

音频格式要先钉死，否则后面所有时间都会被重采样偷走。麦克风侧固定 16 kHz 单声道 16 bit PCM，这是识别侧的甜点区间；扬声器侧固定 24 kHz 或 48 kHz 立体声，这是合成侧的输出档位。两侧不一致就必须在中间做一次重采样，那次重采样会引入额外延迟并且让首包变小。下面这段是能跑通最小会话的骨架，接口名与事件名在不同版本间调整过，**版本差异以官方文档为准**。

```python
import asyncio
from dataclasses import dataclass, field

PCM_IN_RATE = 16_000          # 麦克风侧固定，与 ASR 训练档位一致
PCM_OUT_RATE = 24_000         # 扬声器侧固定，与 TTS 输出档位一致
FRAME_MS = 20                 # 每帧 20 毫秒，按 20 ms 切分是 VAD 的常用粒度


@dataclass
class Turn:
    """一次用户发言的完整生命周期；从 VAD 判定语音开始，到音频播完为止"""
    turn_id: str
    audio_chunks: list[bytes] = field(default_factory=list)
    text: str = ""
    interrupted: bool = False       # 被打断则为真，播完则为假


class RealtimeSession:
    def __init__(self, session_id: str, agent, vad, asr, tts):
        self.session_id = session_id
        self.agent, self.vad, self.asr, self.tts = agent, vad, asr, tts
        self.out_queue: asyncio.Queue[bytes] = asyncio.Queue()   # 待播音频，未播的随时可丢
        self.playing = False
        self.turn = None

    async def handle_frame(self, pcm: bytes) -> None:
        """每 20 毫秒调一次；打断判定必须在这一层，不能等到 ASR 结束"""
        speech = self.vad.is_speech(pcm)            # 只看当前帧，不看整段
        if speech:
            if self.turn is None:                   # 连续多帧只建一个 turn，否则一个词建八次
                self.turn = Turn(turn_id=next_id())
            self.turn.audio_chunks.append(pcm)
        elif self.turn is not None and self.vad.silence_ms() >= self.vad.threshold_ms:
            # 静音超过阈值判定"说完了"，这是本章 500 毫秒预算的去处
            await self._finish_turn(self.turn)
            self.turn = None

    async def _finish_turn(self, turn: Turn) -> None:
        turn.text = await self.asr.transcribe(b"".join(turn.audio_chunks))
        reply, tool_calls = await self.agent.run(turn.text, self.session_id)
        if tool_calls:
            # 语音场景的工具调用必须走确认闸门，见"语音工具调用"一节
            reply = await self.agent.confirm_then_run(tool_calls, turn)
        for chunk in self.tts.stream(reply):        # TTS 必须流式出首包
            await self.out_queue.put(chunk)
```

链路能跑通只值一半的钱，另一半在"五段各自多快"。下面这张表是本章延迟部分全部数字的唯一来源，后面的算例和图表都从它推导：

| 段 | 默认值 | 优化后 | 可压下限 | 压它的代价 |
|---|---|---|---|---|
| VAD 静音判定 | 500 ms | 300 ms | 200 ms | 低于 300 ms 会显著增加误触发打断 |
| ASR 识别尾包 | 220 ms | 180 ms | 80 ms | 换更重的识别模型会抬高服务端延迟 |
| Agent 首 token | 340 ms | 300 ms | 120 ms | 与第十一章同源，靠提示缓存压 |
| TTS 首包 | 180 ms | 140 ms | 60 ms | 换音色档位会牺牲音质 |
| 传输与编码 | 60 ms | 40 ms | 20 ms | 基本压不动 |
| 合计 | 1,300 ms | 960 ms | 480 ms | 门禁 1,500 ms |

### 语音打断处理

**barge-in 是语音体验的第一杀手**。它的定义只有一句：用户开始说话时，立刻停止播放 TTS，并把还没播出去的音频全部丢弃。听起来是显然的，实现起来有四个必须同时满足的条件，缺一个用户就会觉得"它没听见我"。

第一个条件是**检测必须在音频帧层，不能等 ASR 出结果**。等到识别出文本再停播，用户已经多听了半秒的废话，这一秒半的延迟足以让人生气。所以打断检测只依赖 VAD 的当前帧能量，不依赖任何识别结果。

第二个条件是**丢弃，不能只是暂停**。暂停意味着用户说完之后系统要把没播完的那半句接着播，这在对话上是错的——用户插嘴通常意味着他改变了主意，接着播旧内容会让对话彻底乱掉。所以正确做法是清空输出队列，并给这一轮打上"未播完"标记，让 Agent 知道上一句没说完整。

第三个条件是**回声消除，否则会自己打断自己**。扬声器播出去的声音会被麦克风收回来，如果不做回声消除，VAD 会把自己的 TTS 当成用户发言，于是刚开口就自己停下来。工程上的做法是在播放期间把 VAD 灵敏度调低，或者干脆在播放期间冻结打断判定，等播放缓冲低于某个水位再恢复。

第四个条件是**丢弃之后不能留半句在上下文里**。被播了一半的回复文本，用户只听到了前半句，但上下文里是完整的一句，下一轮模型会以为自己已经说过了，于是重复或漏掉关键信息。正确做法是把被截断的位置写回上下文，比如追加一条"（未播完）"标记，让模型知道这句话用户没听到。

```python
async def on_barge_in(self) -> None:
    """VAD 判定用户开始说话时立刻调用；本函数必须非阻塞地跑在每 20 毫秒一帧的循环里"""
    self.playing = False
    dropped = 0
    while not self.out_queue.empty():          # 条件二：丢弃而不是暂停
        self.out_queue.get_nowait()
        dropped += 1
    if self.current_reply is not None and self.played_chars:
        # 条件四：把"用户没听到"这件事写回上下文，否则下一轮模型会以为说过了
        self.session.append(
            role="assistant",
            text=self.current_reply[:self.played_chars] + "（未播完，用户已打断）",
        )
    self.played_chars = 0
    metrics.inc("barge_in.dropped_chunks", dropped)
    metrics.inc("barge_in.count")
```

打断处理得好不好，只用一个指标判断：打断响应成功率，定义为"用户打断后 300 毫秒内实际停止播报的次数"除以"打断总次数"。本章基线 0.94，优化后 0.985，门禁不低于 0.98。低于 0.95 基本等于用户每次插嘴都要再说一遍。

!!! mascot-tip "打断是必须自己实现的能力"
    ![墨墨提示技巧](../../img/mascot/tip.png){ class="mascot-admonition-img" }
    有些实时接口提供一个开关就能打开打断，但它往往只帮你停掉输出，不帮你清空已排队的音频，也不帮你把"没播完"写回上下文。这三件事都得自己补，省掉任何一件，用户都会觉得"它没听见我"。

### 语音工具调用

文本 Agent 的工具调用是静默执行的，用户盯着屏幕上跳出的参数卡片，他知道系统正在做什么。语音场景完全不同：没有屏幕、没有卡片、用户也没法回滚一段已经说出口的话。所以语音工具调用必须**说出来确认**而不是静默执行，而"哪些工具需要确认"要按副作用分三级来定，不能一刀切。

| 级别 | 判定标准 | 语音策略 | 本章例子 | 延迟代价 |
|---|---|---|---|---|
| 读类 | 只读、无副作用、耗时 < 500 ms | 直接执行，不打断播报 | 查订单状态、查保单余额、查天气 | 0，可与播报并行 |
| 写类 | 有副作用但可回滚 | 执行后口播结果，不预先确认 | 加备注、建草稿、存草稿偏好 | 0，多一句口播 |
| 不可逆类 | 涉及金钱、外发、删除，无法自动回滚 | 必须口播复述参数，等用户明确说"是" | 转账 5,000 元、发送短信、注销保单 | +1 轮，8 到 12 秒 |

分级的依据是"能不能回滚"，不是"重不重要"。把"改备注"和"转账"放在同一档要求确认，会让用户被无意义的确认折磨到放弃；反过来把"转账"当成读类直接执行，出一次事就够赔一整年的工具调用优化收益。

```python
# 工具分三级写在注册表里，闸门逻辑与具体工具解耦；新增工具只改这张表
TOOL_TIERS = {
    "query_claim_status": "read",                # 读类：直接跑
    "add_claim_note": "write",                   # 写类：跑完口播结果
    "transfer_premium": "irreversible",          # 不可逆：先复述再等确认
    "send_sms_to_user": "irreversible",
}

CONFIRM_WORDS = ("是", "对", "确认", "嗯", "好的")   # 只认这五个词，其余一律重问


def requires_confirmation(tool: str, args: dict) -> bool:
    """不可逆工具必须复述关键参数并等待明确肯定；模糊应答一律按未确认处理"""
    return TOOL_TIERS.get(tool) == "irreversible"


async def confirm_then_run(self, tool_calls: list[dict], turn: Turn) -> str:
    for call in tool_calls:
        if not requires_confirmation(call["name"], call["args"]):
            continue
        # 口播复述时只念最关键的两个参数，念全了用户会走神
        spoken = f"{call['args']['title']}，{call['args']['amount']} 元，确认吗？"
        for chunk in self.tts.stream(spoken):
            await self.out_queue.put(chunk)
        reply = await self.asr.transcribe(collect_until_silence())
        if reply.strip() not in CONFIRM_WORDS:
            return f"好的，已取消{call['name']}。还有别的需要吗？"
        await self.agent.execute(call)
    return "已完成。"
```

不可逆工具的确认轮有个容易被忽略的成本：它把一次工具调用变成两轮识别加一次完整合成，会让整通对话多花 8 到 12 秒。本章的语音客服里这类工具占比只有 6%，但因为它落在通话末尾，直接拉长了平均通话时长 6.4 秒——按 8,000 通/月算，一个月多花约 51,200 秒机时。

### 语音延迟优化

语音延迟只有一个指标：**首音频延迟**，即从用户停止说话的那一刻起，到用户听到第一个音频样本为止。它和第十一章的端到端延迟不是一回事——端到端延迟要把整段回答播完才算，首音频延迟只要开头响了就算，因为用户对"开始说话"的敏感度远高于"说完"。本章的目标是把这个数压进门禁 1,500 毫秒。

它能被拆成五个互不重叠的串行段，拆法必须严格按串行来，因为五段之间没有一处能并行：

\[
T_{\text{first-audio}} = T_{\text{vad}} + T_{\text{asr}} + T_{\text{ttft}} + T_{\text{tts}} + T_{\text{net}}
\]

按默认值的算例：\(500 + 220 + 340 + 180 + 60 = 1{,}300\) 毫秒，距 1,500 毫秒的门禁还剩 200 毫秒余量，余量占比 \(200 / 1{,}500 = 13.3\%\)。这个余量偏薄，因为 P95 会比 P50 高出约 380 毫秒（本章实测 P95 为 1,680 毫秒），也就是说默认配置在 5% 的请求上会破门禁。所以默认配置不能直接上线，必须先做联合优化。

三步优化的顺序也有讲究，按"收益除以风险"排：

| 步 | 动作 | 改动量 | 改动后合计 | 风险 | 为什么先做 |
|---|---|---|---|---|---|
| 1 | VAD 静音判定 500 降到 300 ms | −200 ms | 1,100 ms | 低，增加误触发打断 | 纯本地参数，改一行代码 |
| 2 | ASR 换流式最终结果加更轻档位 | −40 ms | 1,060 ms | 低，字准率掉约 0.01 | 服务端换档，不动前端 |
| 3 | TTS 固定音色走预热连接 | −40 ms | 1,020 ms | 低，首次调用略慢 | 消除建连抖动 |

三步做完合计 1,020 毫秒，余量 480 毫秒（32.0%），P95 落到 1,420 毫秒，门禁 1,500 毫秒通过。反过来只做第一步是最常见的错误选择：把 VAD 一路压到 200 毫秒下限，合计是 1,000 毫秒，比三步联合只多省 20 毫秒，却把打断误触发率从 3.5% 抬到 11.2%。**先动别处，再动 VAD**，这条顺序值得写进你们的代码规范。

!!! mascot-warning "VAD 阈值是唯一一个人为加的等待"
    ![墨墨提醒注意](../../img/mascot/warning.png){ class="mascot-admonition-img" }
    四段延迟都是机器的真实耗时，只有 VAD 的 500 毫秒是你自己"决定再等等看用户是不是说完了"。压它最容易、看起来收益最大，代价却是打断体验崩掉。这个坑我替你踩过：把它压到 200 毫秒省下 300 毫秒，投诉量翻了三倍。

**Prerequisites:** 首音频延迟、VAD 静音判定、ASR 识别尾包、模型首 token、TTS 首包、串行分段求和、余量占比（均已在本块上方的"Realtime语音架构"与"语音延迟优化"两节定义）。

**Evidence of Mastery:** 学习者先拖动五条滑块观察堆叠形状，再手写三道挑战题的答案；三题数值全部与标准值一致、且第三题答出"只压 VAD 反而抬高打断误触发率"这一取舍时算掌握。只拖动不提交不算证据。

**Misconceptions:** (1) VAD 静音阈值是机器处理耗时，可以随意压低。(2) 首音频延迟要等整段回答播完才结算。(3) 五段之间存在可以并行的地方。

**Instructional Rationale:** Analyze 层级要求先用公式建立假设再用数值验证，因此三题必须先锁定再揭晓；第 3 题与第 2 题构成刻意设计的对照——第 2 题里"压 VAD 到下限"看起来是最优解（省 300 毫秒），第 3 题揭示三步联合只多省 20 毫秒却把打断误触发率从 3.5% 抬到 11.2%，练的是"最优解与可接受解要分开算"。

**Content:**

学习者可调节五段预算，每段有各自的取值范围、步长与默认值：

| 分段 | 最小 | 最大 | 步长 | 默认 | 单位 |

| VAD 静音判定 | 200 | 900 | 20 | 500 | 毫秒 |

| 模型首 token | 120 | 900 | 10 | 340 | 毫秒 |
| TTS 首包 | 60 | 500 | 10 | 180 | 毫秒 |

图表以堆叠条形显示五段与总首音频延迟，默认合计 1,300 毫秒，右侧读数区实时显示合计值、与 1,500 毫秒门禁的余量、以及余量占比。

余量占比 = （1,500 − 合计）÷ 1,500 × 100%，保留一位小数，判定容差 ±0.1 个百分点。门禁判定用合计与 1,500 毫秒比较，合计不超过 1,500 毫秒为通过，等于 1,500 毫秒按通过计。

三道挑战题（固定顺序，每题先预测再揭晓）：

| 序号 | 题干 | 标准值 | 答错时的提示 |
|---|---|---|---|
| 1 | 默认取值下，五段合计的首音频延迟是多少毫秒，与 1,500 毫秒门禁的余量与余量占比各是多少 | 1,300 毫秒，余量 200 毫秒，余量占比 13.3% | 五段串行相加：500 + 220 + 340 + 180 + 60 = 1,300 毫秒。余量 1,500 − 1,300 = 200 毫秒，占比 200 ÷ 1,500 = 13.3%。余量偏薄，因为实测 P95 是 1,680 毫秒，默认配置会在 5% 的请求上破门禁。 |
| 2 | 只把 VAD 静音判定从 500 毫秒压到可压下限 200 毫秒，其余四段不动，合计是多少毫秒、相对默认节省多少毫秒 | 合计 1,000 毫秒，节省 300 毫秒 | 200 + 220 + 340 + 180 + 60 = 1,000 毫秒，比默认少 300 毫秒。但 VAD 低于 300 毫秒会把打断误触发率从 3.5% 抬到 11.2%，省下的 300 毫秒要用三倍投诉量换。 |
| 3 | 三步联合优化（VAD 到 300、ASR 到 180、TTS 到 140）后的合计与余量各是多少，与第 2 题相比多省了多少毫秒 | 合计 1,020 毫秒，余量 480 毫秒，比第 2 题少省 20 毫秒 | 300 + 180 + 340 + 140 + 60 = 1,020 毫秒，余量 1,500 − 1,020 = 480 毫秒，占比 32.0%。与只压 VAD 的 1,000 毫秒相比，联合方案反而慢 20 毫秒，但打断误触发率保持在 3.5%，P95 落在 1,420 毫秒，门禁通过且留足余量。 |

答题反馈文案：第 1 题说明默认配置不是"够用"，它只是"平均够用"，13.3% 的余量会被 P95 的抖动吃掉。第 2 题是全块的核心陷阱：只压 VAD 到下限在算术上最优，在体验上最差。第 3 题给出正解——同样的目标用三处各压一点达成，代价可以接受，收益几乎一样；首音频延迟的优化顺序应当是"先动别处，最后动 VAD"。

**Provenance:** 五段默认值与合计 1,300 毫秒出自本块上方的"Realtime语音架构"一节链路表与"语音延迟优化"一节的算例；门禁 1,500 毫秒、余量 200 毫秒与余量占比 13.3% 出自同节算例；P95 1,680 毫秒与三步优化后 P95 1,420 毫秒出自"语音延迟优化"一节正文；三步目标值 300 / 180 / 140 出自同节三步优化表；可压下限 200 / 80 / 120 / 60 / 20 与各段步长为教学设定，构成合成数据集，随机种子 20261013。打断误触发率 3.5% 与 11.2% 为合成数据（生成规则：VAD 阈值不低于 300 毫秒时固定 3.5%，低于 300 毫秒时按每降 50 毫秒抬升 3.9 个百分点生成），随机种子 20261013。

**Rules:** 首音频延迟 = 五段当前值之和，单位毫秒，实时更新，容差 ±0 毫秒。五段严格串行，不存在并行重叠。余量 = 1,500 − 合计，负值显示为超出额度并标红。合计不超过 1,500 毫秒判为通过，等于 1,500 毫秒按通过计。挑战题 3 的"多省多少毫秒"以第 2 题的 1,000 毫秒为基准，允许为负值，负值表示联合方案比只压 VAD 更慢。滑块取值必须落在步长网格上，VAD 步长 20 毫秒，其余四段步长 10 毫秒。三题无并列，容差 ±0 毫秒，余量占比容差 ±0.1 个百分点。

### 语音客服实战

语音客服是语音四节的收口，它把架构、打断、工具调用、延迟四件事同时压在一条通话上，任何一环松掉整通通话就崩。本章的场景是保险理赔报案电话：8,000 通/月、平均 3.4 轮、平均 96 秒一通。

这个场景最难的地方不是延迟，是**方言与噪声**。城市口音的字准率（CER，定义为替换加删除加插入除以参考字数）比标准普通话低 8 到 14 个百分点，而理赔场景的关键词（车牌号、保单号、金额）恰恰是最容易错的那类。所以这个场景的第一个动作不是调 VAD，而是加一层**关键词兜底**：当 CER 超过 0.7 时，把识别文本里的数字与关键实体单独送给一个判别模型重判一次。

第二个动作是**改口处理**。理赔电话里最常见的一句话是"不是这个，我说的是那个"，它是两轮意图而不是一轮。处理办法是在意图层加一个修订槽位：只要本轮输入包含纠正类模式词（"不是"、"我是说"、"搞错了"），就把上一轮的槽位全部作废重采，而不是在旧槽位上打补丁。这一条能救回约 41% 的转人工通话。

第三个动作是**转人工的判定要前置**。不要等 Agent 绕满 3.4 轮才判断，两种信号任一命中立刻转：用户说出"转人工"类关键词，或者本通对话里累计两次 CER 高于 0.7。前者耗时 0.3 秒，后者要等两次识别完成，代价是让用户多等 2 到 4 秒，但省下的是一整通白跑的电话时长。

| 指标 | 基线 | 优化后 | 门禁 | 归因 |
|---|---|---|---|---|
| 首音频延迟 P95 | 1,680 ms | 1,420 ms | <= 1,500 ms | VAD 与 TTS 联合优化 |
| 打断响应成功率 | 0.94 | 0.985 | >= 0.98 | 丢弃队列加回声消除 |
| ASR 字准率 CER | 0.15 | 0.11 | <= 0.12 | 关键词兜底加领域热词表 |
| 自助解决率 | 0.51 | 0.62 | >= 0.60 | 改口处理加槽位作废重采 |
| 平均通话时长 | 102 s | 96 s | <= 100 s | 自助解决减少无效兜底轮 |

### 数字人集成

数字人常被当成"语音的贴图版"，这个理解会让你在架构上做错两件事：把录制型当成直播型，把驱动当成渲染。数字人集成实际是三层，各层的规格、成本和延迟完全不同，选错层比写错代码贵十倍。

| 类型 | 首帧延迟要求 | 单次驱动时长上限 | 分辨率档位 | 驱动单价（示意） | 适用 |
|---|---|---|---|---|---|
| 录制型数字人 | 可容忍 2,000 ms | 60 s | 1080×1920 / 25 fps | 0.05 元/秒 | 培训视频、课程、口播带货 |
| 直播型数字人 | < 400 ms | 10 s | 720×1280 / 25 fps | 0.28 元/秒 | 实时客服、直播中控 |
| 合成型数字人 | 可容忍 5,000 ms | 300 s | 1920×1080 / 30 fps | 0.09 元/秒 | 短剧角色、成片补拍 |

单价一栏是示意数据，实际以服务商官方文档为准。本章的语音客服用的是录制型，因为客服回答是从库里拼出来的、时长可预估，用直播型纯浪费；本章的短剧角色用的是合成型，因为成片要 60 秒且需要 1080p。**先确定延迟要求，再选类型**——这是数字人集成唯一需要记住的选型顺序。

集成时三个必须实测的量：口型同步误差（音频起音到唇形开始动作的时差）门禁不超过 80 毫秒，同步误差超标在观感上非常明显；首帧延迟录制型不超过 2,000 毫秒；驱动稳定性要求连续 300 次驱动无崩溃。下面这段是录制型的最小驱动封装，成本按秒累加。

```python
import os, json, time, urllib.request

DRIVE_ENDPOINT = os.environ["DIGITAL_HUMAN_ENDPOINT"]     # 端点随服务商与版本变化，以官方文档为准
DRIVE_TOKEN = os.environ["DIGITAL_HUMAN_TOKEN"]
SCENE_ID = os.environ["DIGITAL_HUMAN_SCENE"]             # 形象与场景由平台侧配置，代码只引用


def drive_once(audio_path: str, out_dir: str) -> dict:
    """一次驱动只做一件事：把一段配音音频变成一段带口型的视频。
    上传的音频采样率必须是 16 kHz，否则平台会静默重采样并让口型偏移 40 到 90 毫秒"""
    with open(audio_path, "rb") as fh:
        payload = fh.read()
    req = urllib.request.Request(
        f"{DRIVE_ENDPOINT}/v1/drive",
        data=payload,
        headers={
            "Authorization": f"Bearer {DRIVE_TOKEN}",
            "X-Scene-Id": SCENE_ID,
            "X-Output-Fps": "25",
            "X-Sample-Rate": "16000",            # 与配音侧输出严格一致
        },
        method="POST",
    )
    with urllib.request.urlopen(req, timeout=120) as resp:
        job = json.load(resp)                   # 平台返回的是任务，不是视频
    return poll(job["task_id"], out_dir)


def poll(task_id: str, out_dir: str, interval: float = 3.0) -> dict:
    """异步任务的三段式：提交、轮询、取回；轮询上限 40 次即 120 秒，超时按失败补偿处理"""
    for _ in range(40):
        time.sleep(interval)
        with urllib.request.urlopen(
            f"{DRIVE_ENDPOINT}/v1/tasks/{task_id}", timeout=20
        ) as resp:
            body = json.load(resp)
        if body["status"] == "succeeded":
            dest = os.path.join(out_dir, f"avatar_{task_id}.mp4")
            urllib.request.urlretrieve(body["result_url"], dest)
            return {"task_id": task_id, "path": dest,
                    "lip_error_ms": body["metrics"]["lip_sync_error_ms"]}
        if body["status"] == "failed":
            return {"task_id": task_id, "path": None, "error": body["error_code"]}
    return {"task_id": task_id, "path": None, "error": "poll_timeout"}
```

## 二、从一段文字到一段视频

### Seedance视频生成

视频生成和文本生成的根本差别在于**输出不是一段可审阅的字符串，而是一段需要逐帧检查的像素**。文本生成错了改提示词重跑一次，成本是一次 token；视频生成错了你得等 45 秒才知道，而且这一次的 45 秒和钱已经花掉了。所以视频接入的第一个工程决定不是选哪个模型，而是**把"抽卡"这件事从人工挪到自动**：一个分镜一次生成，成功率 60% 左右是常态，剩下 40% 必须自动重试或自动降级，不能靠人盯。

文本生视频和图生视频的差异必须先分清，它们的适用边界几乎不重叠：

| 维度 | 文本生视频 | 图生视频 |
|---|---|---|
| 输入 | 一段提示词 | 一张首帧图加一段运动描述 |
| 控制力 | 弱，只能靠提示词描述画面 | 强，首帧确定后构图与人物已锁定 |
| 一致性 | 差，同一角色每次生成的脸都不一样 | 好，角色与场景天然继承 |
| 典型用途 | 转场空镜、氛围镜头、开场 | 有角色出镜的剧情镜头、商品展示 |
| 本章用量占比 | 18% | 82% |

本章的短剧流水线里 82% 的镜头走图生视频，原因很实际：一个 6 镜的短剧要保持同一张脸，纯文生视频每镜换一张脸的可能性接近 100%，而图生视频靠同一张角色定妆图作为首帧能把一致率提到 0.93。这一条就是"为什么本章示例是一致性优先"的答案。

规格档位是视频接入必须显式管理的第二件事，因为不同档位的时长与价格直接决定后面的成本模型。以下档位与单价均为示意数据，**实际规格与计费以官方文档为准**：

| 档位 | 分辨率（竖 / 横） | 帧率 | 可选时长 | 单价（元/秒，示意） | 本章用途 |
|---|---|---|---|---|---|
| 标准档 | 720×1280 / 1280×720 | 24 fps | 5 s / 10 s | 0.12 | 试片与分镜验证 |
| 高清档 | 1080×1920 / 1920×1080 | 24 fps | 5 s / 10 s | 0.21 | 成片交付 |
| 高帧档 | 1920×1080 | 48 fps | 5 s | 0.32 | 运动镜头与升格 |

按标准档 0.12 元/秒算，5 秒镜头 0.60 元、10 秒镜头 1.20 元；高清档 0.21 元/秒对应 1.05 元与 2.10 元；高帧档 0.32 元/秒对应 1.60 元。三个数字在后文的成本算例里会反复出现，所以这里先算清。

提示词的组织方式是本章要沉淀下来的通用方法论，它跨产品通用。结构固定为五段，顺序不能乱：**主体 + 动作 + 镜头 + 光线 + 风格**。这个顺序背后的逻辑是后面的词会覆盖前面的词，把风格放最后它才不会被中途改写。

```text
主体：一名 28 岁东亚女性，齐肩黑发，米白色针织衫，戴细框眼镜
动作：从沙发上起身，右手拿起桌上的马克杯，走向窗边
镜头：中景，跟拍，缓慢左移，浅景深
光线：清晨侧逆光，窗棂阴影落在地面
风格：写实电影感，35mm 胶片颗粒，冷色低饱和
```

比提示词技巧更重要的是**首帧图规范**。图生视频的首帧质量直接决定成片质量，而首帧图通常由人准备，所以要定死一套规范：主体占比画面 40% 到 60%、主体完整不被裁切、光源方向单一、人脸正对或侧 30 度以内、无文字水印。这五条不合规的首帧，下游模型基本救不回来，而事后你只会看到"生成质量差"这个笼统结论。

### Minimax H3生成

同一个产品族里，选型往往不是看"谁更强"，而是看谁在你的失败模式下更省事。本章把 Minimax H3 当作 Seedance 的对照组，理由是它在**多镜头一致性**和**快速运动稳定性**这两项上表现不同，而这个差异恰好对应短剧里两类不同的镜头。

| 维度 | Seedance | Minimax H3 |
|---|---|---|
| 本章观察到的强项 | 单镜头运动幅度大、镜头语言丰富 | 多镜头之间的角色服装与场景陈设保持得更稳 |
| 本章观察到的弱项 | 跨镜头角色脸型漂移明显 | 快速运动镜头偶尔出现肢体畸变 |
| 适配的镜头类型 | 情绪镜头、动作镜头、运镜空镜 | 对话镜头、双人同框、产品特写 |
| 本章 82 个镜头中的实际分工 | 34 个（41.5%） | 48 个（58.5%） |
| 接口形态 | 提交任务后异步返回 | 提交任务后异步返回 |

这张表的真正用途是给后面的"分镜路由"一条规则：**按镜头类型选产品，而不是按产品选镜头类型**。本章的做法是先对分镜脚本做一次自动分类（动作强度、人物数、是否有特写），再按分类路由到不同产品，这一步让短剧的一次通过率从 0.60 提到 0.71。

请求体字段是接入时最容易踩坑的地方，因为产品迭代会改字段名。下面这份结构用于说明"哪些字段必须显式填、哪些填错会静默降级"，**字段名与取值以官方文档为准**：

```json
{
  "model": "video-gen-standard",
  "prompt": "一名 28 岁东亚女性，齐肩黑发，从沙发起身走向窗边，中景跟拍，清晨侧逆光，写实电影感",
  "first_frame_image_id": "img_7f31a9",
  "duration_seconds": 5,
  "resolution": "720x1280",
  "fps": 24,
  "seed": 20261013,
  "guidance_scale": 7.5,
  "steps": 30,
  "watermark": false,
  "safety_check": "strict"
}
```

`first_frame_image_id` 缺省会退化成纯文本生视频，而退化是静默的——接口不报错，只是结果不一致。`seed` 必须固定，否则同一个分镜重跑三次得到三个不同的动作，你无法判断"这次更好"还是"只是随机"。`safety_check` 在批量场景里要显式设为严格并自行记录拒审原因，因为平台拒审时返回的是通用错误码，你无法从错误码反推是哪条规则触发的，而这条信息决定内容要怎么改。

### 生成参数调优

参数调优的目标不是把单条调到最好看，而是**把平均可用率调上去**，因为可用率每提高 5 个百分点，单条成本就降一截（后面成本一节会给算例）。三个参数按影响从大到小排：引导强度、步数、种子。

引导强度（guidance scale）控制模型多贴提示词。它和可用率的关系不是单调的，是一条带拐点的曲线：低于 4.0 时模型自由发挥，产物往往动作漂亮但内容不对口，可用率从 60% 掉到 41%；在 6.0 到 8.5 这个区间达到峰值 0.71；高于 11.0 时画面过度贴合文字但动作僵硬，可用率回落到 0.55。所以调参不是越大越好，而是要找出这条曲线的拐点。

步数（steps）只影响细节精度，不影响构图。本章的实测结论是：30 步到 50 步之间可用率提升 0.02，耗时增加 66%；50 步以上可用率不再提升（0.71 到 0.715）。所以 30 步是本章的默认，50 步只在"人物特写"这类高频糊掉的镜头上临时启用。

种子（seed）不提升质量，只保证可复现。本章的纪律是：**进入成片交付的镜头必须记录种子**，否则三个月后客户要改一句台词，你无法复现原来的画面。

| 参数 | 默认 | 可调区间 | 步长 | 对可用率的影响 | 本章取值理由 |
|---|---|---|---|---|---|
| `guidance_scale` | 7.5 | 3.0 到 15.0 | 0.5 | 主峰在 6.0 到 8.5，峰值 0.71 | 取 7.5，兼顾动作自然与语义贴合 |
| `steps` | 30 | 20 到 60 | 10 | 30 到 50 提升 0.02，之后持平 | 取 30，细节够用且耗时最低 |
| `seed` | 固定 | 0 到 2^31 − 1 | 1 | 无直接影响，决定可复现性 | 成片镜头必须记录 |

按上表做一轮 82 镜的 A/B 对照，是本章参数调优的全部工作内容：

```python
# A/B 对照：只改一个变量，其余全同；每组 82 个镜头，与基线同分镜同种子
# 版本差异以官方文档为准：计费字段名与用量字段随版本调整过
EXPERIMENTS = [
    {"name": "baseline",      "guidance_scale": 7.5,  "steps": 30, "usable_rate": 0.60, "seconds": 100},
    {"name": "guidance_low",  "guidance_scale": 4.0,  "steps": 30, "usable_rate": 0.41, "seconds": 100},
    {"name": "guidance_high", "guidance_scale": 11.0, "steps": 30, "usable_rate": 0.55, "seconds": 100},
    {"name": "steps_50",      "guidance_scale": 7.5,  "steps": 50, "usable_rate": 0.62, "seconds": 166},
    {"name": "guidance_65",   "guidance_scale": 6.5,  "steps": 30, "usable_rate": 0.68, "seconds": 100},
]


def pick_config(experiments: list[dict]) -> dict:
    """选型只看可用率与耗时的权衡，不看单项最高可用率；
    steps_50 的 0.62 低于 guidance_65 的 0.68，多花的 66% 耗时买不到 0.02 可用率"""
    return max(experiments, key=lambda e: e["usable_rate"] - 0.002 * (e["seconds"] - 100))
```

结果把默认值定在 `guidance_scale=7.5`、`steps=30`、可用率 0.60，同时留下一条明确的优化路径：把引导强度固定 6.5 后可用率升到 0.68，废片率从 40% 降到 32%。这就是后文成本一节里"废片率从 40% 优化到 25%"的中间台阶。

!!! mascot-neutral "参数不是调得越大越好"
    ![墨墨说明情况](../../img/mascot/neutral.png){ class="mascot-admonition-img" }
    引导强度和步数都有拐点，超过某个值之后画面会变得过度贴合文字而动作僵硬，可用率反而往下掉。判断参数好坏只有一个口径：整批镜头的可用率，不是单条镜头看着顺不顺眼。

### RunningHub云任务

自己买 GPU 跑视频模型只在两种情况下成立：日调用量稳定超过 2,000 次，或者有明确的模型微调需求。除此之外，把生成任务外包给云端工作流几乎总是更划算，因为 GPU 的年折旧、空转率和运维人力都摊进了你的成本里。RunningHub 这类平台的价值就是让你用"按次计费"换掉"按卡年计费"。

云任务真正的学习成本不在调用接口，而在**异步任务的三段式模型**：提交、轮询、取回。它的工程含义是必须为每个任务持有一份可恢复的状态，因为轮询途中进程可能重启、任务可能超时、结果可能过期。

```python
import time, uuid

POLL_INTERVAL = 5.0          # 轮询间隔，不要低于 3 秒，否则容易被平台限流
POLL_LIMIT = 60               # 上限 300 秒，超时按失败补偿处理，不无限等

RETRYABLE = {"RATE_LIMIT", "UPSTREAM_TIMEOUT", "NODE_EXECUTION_FAILED"}


def submit(workflow_id: str, params: dict) -> str:
    """提交云端工作流，返回 task_id。幂等键必须带上，
    否则网络重试会提交出两个任务并收两份钱"""
    body = dict(params)
    body["client_task_id"] = uuid.uuid4().hex     # 幂等键：同一内容重提不会重复计费
    resp = post_json("/api/openapi/task/submit", {
        "apiKey": settings.RUNNINGHUB_KEY,
        "workflowId": workflow_id,
        "nodeInfoList": body,
    })
    return resp["data"]["taskId"]


def wait_task(task_id: str) -> dict:
    for _ in range(POLL_LIMIT):
        time.sleep(POLL_INTERVAL)
        d = post_json("/api/openapi/task/outputs", {
            "apiKey": settings.RUNNINGHUB_KEY, "taskId": task_id,
        })["data"]
        if d["status"] == "SUCCESS":
            return {"ok": True, "outputs": d["outputs"]}
        if d["status"] == "FAILED":
            # 失败原因码要落库：只有错误码能支撑下一节的补偿策略分类
            return {"ok": False, "reason": d["errorCode"],
                    "retryable": d["errorCode"] in RETRYABLE}
    return {"ok": False, "reason": "poll_timeout", "retryable": True}
```

云工作流相比直接调模型 API，多了一个能力也带来一个义务。多出来的能力是**工作流可以把多步串起来**：取首帧、生成视频、放大、抽帧封面、做安全检测，全部在一个工作流里完成，你只提交一次。带来的义务是**你失去了中间可观测性**：工作流里哪一步慢、哪一步错，平台只给你一个总耗时和一个错误码，所以必须要求平台返回逐节点耗时，否则第十一章那套延迟分段分析在这一段是瞎的。

### 失败重试补偿

批量生成里最贵的浪费不是重试本身，而是**整批重来**。一次提交 6 个镜头，成功 4 个失败 2 个，此时正确动作是只重试那 2 个；如果按"批次为单位"重跑，你已经付掉的 4 个镜头的费用（占本批 66.7%）就白扔了。这是本章所有补偿策略的第一原则：**失败的粒度必须比成功的粒度细**。

失败必须先分类再重试。分类的依据是"重试有没有可能成功"，而不是"错误看起来严不严重"：

| 失败类型 | 典型错误 | 可重试 | 策略 | 本章占比 |
|---|---|---|---|---|
| 限流 | 429、`RATE_LIMIT` | 是 | 指数退避 1 s / 2 s / 4 s，加 0 到 500 ms 抖动，上限 3 次 | 18% |
| 上游超时 | 504、`UPSTREAM_TIMEOUT` | 是 | 同上，但只重试 1 次后转排队 | 9% |
| 内容审核拒 | 403、`SAFETY_REJECT` | 否 | 立刻转人工改脚本，不重试 | 4% |
| 参数错误 | 400、`INVALID_PARAM` | 否 | 立刻报 bug，重试一万次也一样 | 2% |
| 平台故障 | 5xx、`NODE_FAILED` | 是 | 退避重试 3 次，之后熔断该工作流 | 5% |
| 结果不可用 | 无错误码，可用率判定失败 | 视预算 | 按可用率预算决定是否再来一次 | 62% |

最后一行是视频场景特有的：**最大的失败来源不是报错，是"没报错但不能用"**。这类失败在监控里完全隐形，只能靠人工或模型判定。它也是唯一一类由预算而不是重试次数决定要不要重试的失败——本章给它一条硬规则：单条内容的可用率重试预算为 2 次，超过就把这条降级为"人工重做"，不再消耗生成预算。

```python
import random, time
from dataclasses import dataclass

BACKOFF = (1.0, 2.0, 4.0)        # 指数退避基数，单位秒


@dataclass
class Shot:
    shot_id: str
    status: str = "pending"      # pending / ok / failed / unusable
    attempts: int = 0
    cost_cny: float = 0.0


def retry_shot(shot: Shot, generate, unit_price: float, retry_budget: int = 2) -> Shot:
    """只重试这一个镜头；单条内容累计成本超过该条预算 2 倍即停止并转人工"""
    while shot.attempts <= retry_budget:
        shot.attempts += 1
        try:
            result = generate(shot.shot_id)
            shot.cost_cny += unit_price
            if judge_usable(result):             # 可用率判定，不可用也算失败
                shot.status = "ok"
                return shot
            shot.status = "unusable"
        except RetryableError:
            if shot.attempts > len(BACKOFF):
                shot.status = "failed"
                return shot
            time.sleep(BACKOFF[shot.attempts - 1] + random.uniform(0, 0.5))
        except (SafetyReject, InvalidParam):
            shot.status = "failed"              # 不可重试，立刻停，不烧钱
            return shot
        if shot.cost_cny >= unit_price * retry_budget * 2:
            shot.status = "failed"              # 成本熔断优先于重试次数
            return shot
    return shot
```

三条纪律必须配合着用：**幂等键防重复计费、退避加抖动防重试风暴、预算熔断防单条内容吃完整天预算**。少任何一条，批量场景都会在某个下午出事——前两条对应技术故障，第三条对应业务故障，而后者更常见也更难发现。

## 三、合成链：ffmpeg 是本章的硬核

### ffmpeg合成链

生成只是原料，成片是合成出来的。多模态项目里 60% 以上的线上事故不在生成环节，而在合成环节，而合成环节的所有问题最后都落在 ffmpeg 上。所以这一节不讲"视频处理框架"，只讲 ffmpeg 的参数语义与链路纪律。

先把会反复出现的术语一次定清，后面所有命令都按这套定义写：**容器**是文件的封装格式（`.mp4`、`.mov`、`.webm`），**流**是容器里的一条独立轨道（一条视频轨加一条音频轨），**编码**是流数据的压缩方式（`libx264` 是 H.264 软编码器）。**帧率**是每秒多少帧，`fps=30` 表示每秒 30 帧。**采样率**是音频每秒取样次数（`48000` 表示 48 kHz），**声道**是音频的独立通道数。**crf** 是恒定质量模式下的质量参数，取值 18 到 51，**数值越小质量越高体积越大**。

用一句话记住 crf 的档位：18 是"肉眼看不出编码损失"，23 是默认档（本章全链路用 23），28 以上肉眼能看出块状伪影。**preset** 是编码速度与压缩效率的权衡，`-preset medium` 是本章的默认，往快走体积涨 15% 到 25%，往慢走体积降 8% 到 12% 但耗时成倍。

| 参数 | 本章取值 | 语义 | 写错的后果 |
|---|---|---|---|
| `-c:v libx264` | 全链路 | H.264 软编码，兼容性最好 | 用 `libx265` 体积小 30% 但部分平台转码失败 |
| `-crf 23` | 全链路 | 恒定质量，18 到 51，越小越好 | 随意改成 18，体积翻倍 |
| `-preset medium` | 全链路 | 编码速度与压缩率折中 | `veryslow` 会让合成段成为批量场景的瓶颈 |
| `-pix_fmt yuv420p` | 全链路 | 像素格式，决定播放器兼容性 | 缺这一项在部分移动端变黑屏 |
| `-r 30 -fps_mode cfr` | 全链路 | 固定帧率、恒定帧模式 | 混用不同帧率片段时画面卡顿；`-fps_mode` 是较新写法，旧版本用 `-vsync`，**以 ffmpeg 官方文档为准** |
| `-c:a aac -b:a 192k -ar 48000 -ac 2` | 全链路 | AAC 立体声 192 kbps 48 kHz | 采样率与视频侧不一致会造成音画偏移 |
| `-movflags +faststart` | 所有上传文件 | moov 原子前置，支持边下边播 | 缺这一项上传平台后进度条卡在 90% |
| `-vf scale=...,setsar=1` | 竖屏成片 | 统一分辨率并把像素宽高比拉回 1:1 | 不统一会导致拼接花屏 |

合成链的第一条纪律是**归一化必须在拼接之前**，而不是在拼接之后补救。下面这条命令是六个分镜合并成一条竖屏成片的标准写法，每一段参数都能对上上面这张表：

```bash
#!/usr/bin/env bash
# 六个分镜合成一条 1080x1920 竖屏成片；归一化在前，拼接在后
set -euo pipefail
mkdir -p out tmp

# 第一步：逐个分镜归一化到同一套规格。这一步不能省，省了就是在给后面的花屏埋雷。
# -vf 里 scale 用 force_original_aspect_ratio=decrease 保住原构图比例，
# 再用 pad 把短边补黑边到 1920 高；setsar=1 把像素宽高比拉回 1:1，
# 否则不同来源素材的像素宽高比不同，播放器会按各自比例拉伸，画面比例就乱了。
for f in raw/shot_*.mp4; do
  base=$(basename "$f" .mp4)
  ffmpeg -y -i "$f" \
    -vf "scale=1080:1920:force_original_aspect_ratio=decrease,pad=1080:1920:(ow-iw)/2:(oh-ih)/2:color=black,setsar=1" \
    -r 30 -fps_mode cfr \
    -c:v libx264 -crf 23 -preset medium -pix_fmt yuv420p \
    -c:a aac -b:a 192k -ar 48000 -ac 2 \
    -video_track_timescale 90000 \
    -movflags +faststart \
    "tmp/${base}_norm.mp4"
done

# 第二步：用 concat 拼接。concat 分两种——滤镜版与 demuxer 版。
# 滤镜版（-f concat 滤镜）会重新编码，能保证片段之间绝对无缝，推荐；
# demuxer 版（concat 文本加 -c copy）不重编码、秒级完成，但要求所有片段的
# 流参数完全一致，只要有一个对不上就会音画不同步。本章一律用滤镜版。
printf "file '%s'\n" tmp/shot_*_norm.mp4 > tmp/list.txt
ffmpeg -y -f concat -safe 0 -i tmp/list.txt \
  -c:v libx264 -crf 23 -preset medium -pix_fmt yuv420p -r 30 \
  -c:a aac -b:a 192k -ar 48000 -ac 2 \
  -movflags +faststart \
  out/episode.mp4
```

第二条纪律是**拼接之前必须先探测流参数**，因为 concat 滤镜版也不能替你修正"一条片段缺音轨"这类问题。下面这条探测命令会把每条流的编码、帧率、采样率、时长、帧数一次性打出来，任何一项与其他片段不同就该在归一化阶段处理：

```bash
# ffprobe 探测：合成前必跑一次。-show_entries 只取需要的字段，
# -of csv 把结果压成一行，方便跨片段比对
ffprobe -v error -select_streams v:0 \
  -show_entries stream=codec_name,width,height,r_frame_rate,duration,nb_frames \
  -of csv=p=0 tmp/shot_01_norm.mp4
ffprobe -v error -select_streams a:0 \
  -show_entries stream=codec_name,sample_rate,channels,duration \
  -of csv=p=0 tmp/shot_01_norm.mp4

# 一致性检查：音频时长与视频时长之差超过 40 毫秒就报警，不要等成片后才发现
for f in tmp/shot_*_norm.mp4; do
  vd=$(ffprobe -v error -select_streams v:0 -show_entries stream=duration -of csv=p=0 "$f")
  ad=$(ffprobe -v error -select_streams a:0 -show_entries stream=duration -of csv=p=0 "$f")
  awk -v v="$vd" -v a="$ad" -v n="$f" 'BEGIN{d=(v-a)*1000; if(d<0)d=-d;
    printf "%s 偏移 %d ms\n", n, d}'
done
```

第三条纪律是**成片必须过一次体检**，四个检查项缺一不可：分辨率与帧率是否等于目标值、音画时长差是否不超过 40 毫秒、音量是否落在 -23 到 -14 LUFS（响度标准，过低平台会压、过高会被限流）、画面是否有黑帧（探测黑帧用 `blackdetect` 滤镜）。下面这条命令把体检四项串在一起，可以直接进 CI：

```bash
# 成片体检四项：规格、时长差、响度、黑帧。任何一项不过就阻断发布。
SPEC=$(ffprobe -v error -select_streams v:0 \
  -show_entries stream=width,height,r_frame_rate -of csv=p=0 out/episode.mp4)
VD=$(ffprobe -v error -select_streams v:0 -show_entries stream=duration -of csv=p=0 out/episode.mp4)
AD=$(ffprobe -v error -select_streams a:0 -show_entries stream=duration -of csv=p=0 out/episode.mp4)

echo "规格：$SPEC（应为 1080,1920,30/1）"
awk -v v="$VD" -v a="$AD" 'BEGIN{d=(v-a)*1000; if(d<0)d=-d;
  if(d>40){printf "音画偏移 %d ms 超 40 ms，阻断\n", d; exit 1}
  printf "音画偏移 %d ms，通过\n", d}'

# 响度：-23 到 -14 LUFS 是平台通用的安全区间，超出会被平台二次处理
ffmpeg -hide_banner -i out/episode.mp4 -af ebur128=peak=true -f null - 2>&1 \
  | grep -A 4 "Integrated loudness" | tail -3

# 黑帧检测：连续黑帧超过 0.5 秒即判失败（片尾留白单独人工确认）
ffmpeg -hide_banner -i out/episode.mp4 -vf "blackdetect=d=0.5:pix_th=0.10" -f null - 2>&1 \
  | grep black_start || echo "无黑帧，通过"
```

### 字幕与配音合成

字幕时间轴的**唯一合法时间源是配音的实际时长**，不是字数、不是语速估算、不是模型返回的预估时间。这条纪律看起来朴素，但它是合成链里最高频的错误来源——上面诊断块序号 3 那条 640 毫秒的偏移就是这么来的。

正确做法是先生成配音，再用 `ffprobe` 读它的实际时长，然后把字幕按语音边界切分。字幕格式用 SRT，时间戳的毫秒分隔符是逗号（`00:00:01,200`）而不是句点，这一点写错的话播放器会当纯文本显示。两条必须遵守的细节：一是每条字幕时长不低于 800 毫秒，否则来不及读；二是单条不超过 15 个汉字，否则会挤成两行。

烧录字幕（硬字幕，进画面）与外挂字幕（软字幕，进文件不占画面）是两种做法，选错会让成片无法二次编辑。硬字幕用 `subtitles` 滤镜，它需要系统装好 `libass` 支持；软字幕用 `-c:s mov_text`，参数上简单得多。烧录时还有一个必做的参数：`force_style` 里的 `Outline=1` 是描边，没有它字幕压在浅色画面上会完全看不见。

```bash
# 字幕与配音合成三步：探测实际时长、烧录硬字幕、混背景音乐
# 第一步：读配音真实时长，这是字幕时间轴的唯一来源
DUR=$(ffprobe -v error -show_entries format=duration -of csv=p=0 out/voiceover.wav)
echo "配音实际时长 ${DUR} 秒"

# 第二步：烧录硬字幕。滤镜链顺序是书写顺序，所以 subtitles 必须排在 scale 之后，
# 否则字幕会在低分辨率下渲染完再被放大，边缘发虚（诊断块序号 6 的成因）。
# force_style 里 Fontsize 按成片高度给，Outline 是描边，用来保证浅色背景下可读。
ffmpeg -y -i out/episode_novoice.mp4 -i out/voiceover.wav \
  -vf "scale=1080:1920,setsar=1,subtitles=out/sub.srt:force_style='Fontsize=18,Outline=1,MarginV=60'" \
  -map 0:v:0 -map 1:a:0 \
  -c:v libx264 -crf 23 -preset medium -pix_fmt yuv420p -r 30 \
  -c:a aac -b:a 192k -ar 48000 -ac 2 \
  -shortest -movflags +faststart \
  out/episode_final.mp4

# 第三步：混背景音乐。amix 的第一个参数是参与混音的流数量，写错会直接报错。
# -af 后依次做三件事：把音乐采样率对齐到 48 kHz（aresample）、
# 把音量压到人声的 0.18 倍（volume）、再混合（amix）。
# -c:v copy 是刻意的：背景音乐混完不需要重编码视频，copy 省掉整条链里最贵的一段编码，
# 这一条能省下合成段约 40% 的耗时。
ffmpeg -y -i out/episode_final.mp4 -i out/bgm.mp3 \
  -filter_complex "[1:a]aresample=48000,volume=0.18[bg];[0:a][bg]amix=inputs=2:duration=first[a]" \
  -map 0:v:0 -map "[a]" \
  -c:v copy -c:a aac -b:a 192k -ar 48000 -ac 2 -movflags +faststart \
  out/episode_master.mp4
```

`-shortest` 在第二步里不能少：它让输出按最短的那条流结束，避免视频播完了音频还在响。`-c:v copy` 在第三步里同样是刻意的，它能省下合成段约 40% 的耗时，是整条合成链里性价比最高的一个参数。

### 画质增强流程

生成出来的素材普遍偏软，原因是模型输出分辨率受限加上压缩编码的损失。画质增强是一条三段流水线，**顺序不能换**：放大去噪 → 锐化 → 补帧 → 编码。锐化必须在补帧之前，因为补帧会生成插值出来的软边缘，插值之后再锐化只会把插值痕迹一起放大。

放大这一步不要用单纯的双三次插值，要用带锐化的缩放。双三次放大出来的画面会糊，因为高频细节已经丢了；`scale` 加 `unsharp` 相当于先补一层伪高频再锐化，观感上明显更实。

```bash
# 画质增强流水线：一次命令里串完四段。分四次转码会让每一步都重新编码一次，
# 合成段耗时翻四倍，而且每转一次就多一次编码损失。
ffmpeg -y -i raw/shot_01.mp4 \
  -vf "scale=1920:1080:flags=lanczos,hqdn3d=1.5:1.2:6:6,unsharp=5:5:0.8:5:5:0.0,minterpolate=fps=48:mi_mode=mci:mc_mode=aobmc:me_mode=bidir:vsbmc=1,setsar=1" \
  -r 48 -c:v libx264 -crf 20 -preset medium -pix_fmt yuv420p \
  -c:a aac -b:a 192k -ar 48000 -ac 2 \
  -movflags +faststart \
  enhanced/shot_01.mp4

# 四个关键参数的取值说明：
# scale=...:flags=lanczos   放大用 Lanczos 插值，双三次的细节保留明显更差
# hqdn3d=1.5:1.2:6:6       高斯降噪，四个数依次是亮度降噪、色度降噪、时域降噪、时域色度
#                          时域降噪取 6 是上限附近，再高会让运动物体拖出残影
# unsharp=5:5:0.8:5:5:0.0   半径、半径、振幅、阈值、阈值、亮度，只振幅 0.8，
#                          振幅给到 1.5 以上边缘会出现明显白边
# minterpolate=...          24 帧补到 48 帧，mc_mode=aobmc 是运动补偿块匹配，
#                          比默认方式慢约 4 倍但运动画面不抖
# crf 从 23 降到 20         因为经过了重编码，再压一次会二次损失；这一档是"只做一次"的补偿
```

补帧有一个必须知道的限制：它是**时间维度的猜测**，在快速运动或镜头切换处会生成不存在的中间帧，表现为"果冻感"。所以补帧只用在两类镜头上——慢速运镜和静态特写；快速动作镜头补帧的观感损失大于它带来的顺滑收益。用 ffmpeg 探测镜头切换点可以把这条规则自动化：

```bash
# 用 scene 滤镜统计镜头切换点；pts_time 是切换发生的时间点（秒）
# 镜头数决定合成链要拼接几段，切点密度决定哪些镜头值得补帧
ffmpeg -hide_banner -i out/episode_master.mp4 -vf "select='gt(scene,0.4)',showinfo" -f null - 2>&1 \
  | grep -o "pts_time:[0-9.]*" | cut -d: -f2

# 若某段输出 48 fps 而成片要求 24 fps，输出前必须降回，否则平台转码会插黑帧
ffmpeg -y -i enhanced/shot_01.mp4 -vf "minterpolate=fps=24" \
  -c:v libx264 -crf 21 -preset medium -pix_fmt yuv420p -r 24 \
  enhanced/shot_01_24fps.mp4
```

## 四、三条业务流水线

三条流水线共用同一套底座（生成、合成、审核），但业务目标完全不同，所以**节奏、批量、抽检比例三项参数必须分别设**，不能一套参数走天下。这一节按这个原则把三条线各自的差异化设计讲清，而不是重复讲底座。

### 短剧流水线实战

短剧是三条线里最重的一条，特点是**镜头多、一致性要求高、交付周期短**。本章的规格是：一条 60 秒成片、6 个分镜、每镜 10 秒、日产 4 条。

流水线固定七步，每一步的产出物都要落盘，因为下游任何一步失败都要能单独重跑那一步而不重跑整条：

```text
分镜脚本 → 首帧图生成 → 视频生成 → 配音生成 → 字幕生成 → ffmpeg 合成 → 审核发布
   ↓           ↓            ↓           ↓          ↓           ↓           ↓
script.json  frame_*.png  shot_*.mp4  voice.wav  sub.srt   episode.mp4  publish.json
```

三条短剧特有的设计。第一，**分镜脚本先冻结再生成**，脚本里定死每个镜头的时长（10 秒）、人物、动作、景别、台词，生成阶段只允许改提示词措辞不允许改结构。理由是结构一改，六个镜头的时长之和就不再是 60 秒，合成段的对齐全部作废。

第二，**配音与视频分离生成，用时长回填对齐**。因为视频是固定 10 秒而配音长度不定，所以流程是先生成 10 秒视频、再生成配音、再把多出来的配音尾巴裁到 10 秒，同时把字幕时间轴按裁剪后的实际时长重写。这样做的代价是台词被裁的风险，所以台词字数上限要卡在 10 秒可读完的量（正常语速约 4.2 字/秒，即 42 字以内）。

第三，**一致性用首帧图锁定而不是靠提示词**。六个镜头共用一套角色定妆图（正面、侧面、四分之三侧三张），每镜生成前先按景别裁切这张定妆图作为首帧。这样做的收益可以量化：角色一致率从纯文本生视频的 0.29 提到 0.93，素材可用率从 0.60 提到 0.71。

### 电商带货实战

带货切片和短剧在四个点上完全不同，混着做必然两头不讨好。

第一，**节奏密度差一个量级**。短剧 60 秒 6 个镜头，带货 15 秒 3 个镜头，平均单镜 5 秒。5 秒镜头的提示词必须更短更具体，因为运动幅度大的镜头在 5 秒内还没做完动作就被切走了，可用率因此下降——带货场景的实测可用率只有 0.70，比短剧低 10 个百分点。

第二，**卖点必须来自商品详情而不是编**。带货视频的话术三段式（痛点、卖点、行动号召）里，卖点必须逐字对应商品详情页的字段，这是合规硬要求，编造功能属于虚假宣传。所以流程上多了一步"卖点抽取与比对"：用模型从详情页抽取结构化卖点，再逐条与话术做一致性校验，不一致的话术直接拦住。

第三，**分发的成本结构不同**。同一条 15 秒切片要分发到 4 个平台，而平台规格各不相同。所以合成链要输出**多个规格的母版**，而不是一个成片分发四份——靠平台侧二次转码会丢掉字幕精度。

| 平台 | 规格要求 | 字幕样式 | 合成动作 |
|---|---|---|---|
| 主短视频平台 | 1080×1920 / 30 fps | 底部居中，白字黑描边，字号 20 | 直接用母版 |
| 第二平台 | 720×1280 / 30 fps | 底部居中，字号按高度折算 | 缩放后重烧字幕（不能 copy，字幕会随画面一起缩放而变糊） |
| 视频号 | 1080×1920 / 30 fps | 需带账号水印 | 叠加水印层后重编码 |
| 图文平台 | 需 3 张封面图 | 无 | 从母版抽 3 帧做封面 |

### 自媒体矩阵实战

矩阵的核心不是"多发几个平台"，而是**用同一份内容资产派生多个变体**，把边际成本压到接近零。它的前提是批量生产，而批量生产的三个约束是：幂等、失败隔离、成本上限。

矩阵的差异化设计有三条。第一，**选题与生成彻底分离**。选题来自热点追踪（下一节的打分模型），生成只消费一个结构化的选题对象，不关心这个选题是怎么来的。这样替换选题来源不影响产线。

第二，**人工抽检是不可省的，但比例可以按内容类型分**。矩阵日产的 30 条里，资讯解读类（事实密度低、风险低）12 条抽检 5%，观点评论类（涉及主观判断、风险中等）10 条抽检 15%，带货切片类（涉及商业承诺、风险最高）8 条抽检 30%。按这套比例，期望抽检条数是 \(0.05 \times 12 + 0.15 \times 10 + 0.30 \times 8 = 0.6 + 1.5 + 2.4 = 4.5\) 条，约 5 条。这个数字要写进排班表，因为它是矩阵运营里唯一不可自动化的人力，也是"按风险分层"比"统一 10%"更省人力的证据——统一 10% 要抽 3 条，覆盖不到风险最高的带货切片。

第三，**变体派生的四种手法与它们的成本**。这四种是矩阵里"一份资产变五条"的全部手段，成本依次递增：同一素材换文案（0.11 元，只重配音）、换首帧换景别（0.60 元一镜）、换 BGM 与调色（0.05 元）、重生成整条（5.10 元）。所以派生的默认顺序是从便宜往贵试，试到不达标为止，不要一上来就重生成整条。

| 派生手法 | 增量成本 | 触达增量（示意） | 什么时候用 |
|---|---|---|---|
| 换 BGM 与调色 | 0.05 元 | +5% | 需要规避重复内容判定 |
| 换文案 | 0.11 元 | +8% | 同一素材的第二次发布 |
| 换首帧与景别 | 0.60 元/镜 | +21% | 平台判定同质化 |
| 重生成整条 | 5.10 元 | +63% | 平台限流且前三种无效 |

### 热点追踪选品

选品的本质是**在有限产能下挑出单位投入回报最高的那几个题目**，所以它是一个排序问题而不是一个预测问题。做法是把热度、商品匹配度、竞争度三个分量归一化到 0 到 100，再加权求和：

\[
\text{score} = 0.40 \times H + 0.35 \times M + 0.25 \times (1 - C)
\]

其中 \(H\) 是热度分，\(M\) 是商品匹配分，\(C\) 是竞争分。竞争分是**反向**的——竞争越高越不该做，所以要先取 \(1 - C\) 再加权。这个反向处理极易写反，写反了会让矩阵全去追最红最挤的题目。

三个分量的来源必须区分清楚：热度分来自外部热榜（抓取后按品类归一化，注意热榜有付费推广位，必须去广告再算）；商品匹配分来自自有商品库与热榜关键词的语义匹配（这一项是自有数据，别人抄不走）；竞争分来自关键词下已有内容的数量与互动率。四个候选的打分算例：

| 候选 | 热度分 | 商品匹配分 | 竞争分 | 综合分 | 决策 |
|---|---|---|---|---|---|
| 1 深秋保温杯 | 82 | 90 | 0.30 | 81.8 | 选，当天出片 |
| 2 桌面加湿器 | 61 | 78 | 0.42 | 66.2 | 备，排第 2 位 |
| 3 露营折叠椅 | 74 | 65 | 0.55 | 63.6 | 备，排第 3 位 |
| 4 智能手表 | 95 | 40 | 0.88 | 55.0 | 弃，热度最高但库里无货且竞争白热化 |

逐项验算第一行：\(0.40 \times 82 + 0.35 \times 90 + 0.25 \times (1 - 0.30) = 32.8 + 31.5 + 17.5 = 81.8\)。第四行是最值得讲的一行：它热度分 95 是全场最高，却因为竞争分 0.88 直接被压到末位。**选品不是追热点，是躲开红海里的热点。**

!!! mascot-tip "热榜上的第一名往往是陷阱"
    ![墨墨提示技巧](../../img/mascot/tip.png){ class="mascot-admonition-img" }
    综合分里竞争度是反向的，热度 95 分的智能手表因为竞争 0.88 被压到 55.0 分垫底，而热度只有 82 的保温杯拿了 81.8 分第一。算式里那个 \(1 - C\) 写反了，整个矩阵的选题会全部撞进红海。

### 批量生产调度

批量调度只有三条铁律，缺一条就会在某个下午出事：**幂等**（同一份输入重复提交不产生重复产物也不重复计费）、**失败隔离**（一条失败不影响同批其他条）、**成本上限**（熔断优先于任何重试逻辑）。

先看本章矩阵产线的规模：日 30 条、每条平均 6 次生成调用、合计 180 次调用/日；账号级并发上限设为 4（示意，实际以服务商配额为准）；单次生成调用平均耗时 45 秒。一天的理论跑批时间 \(180 / 4 \times 45 = 2{,}025\) 秒，约 34 分钟。这个数说明一件事：**批量生成不是"跑得慢"的问题，是"限流与失败率"的问题**，所以调度的设计重心必须放在并发控制与补偿，而不是在压单次耗时。

```yaml
# 批量调度配置：三个约束（并发、熔断、幂等）集中在这一份文件，改一处两处生效
batch_scheduler:
  queue: redis_stream                  # 任务队列；用 Stream 不用 List 是因为需要消费确认
  concurrency:
    video_gen: 4                       # 账号级并发上限，示意值，实际上限以服务商配额为准
    tts: 16                            # 文本转语音是无状态服务，并发可以开大
    compose: 2                         # ffmpeg 吃满 CPU，与生成并发必须错开，否则互相抢资源
  idempotency:
    key: "sha256(script_json + model + params)"   # 幂等键只由内容与参数决定，不含时间戳
    ttl_days: 30                       # 30 天内重复提交直接返回既有产物，不重复计费
  cost_guard:
    daily_budget_cny: 800              # 日预算上限；实际日均 240 元，余量 3.3 倍
    per_item_budget_cny: 60            # 单条上限，超出即降级为人工，不允许继续烧钱
    on_breach: pause_queue              # 熔断动作是暂停队列而不是只报警
  retry:
    max_attempts: 3
    backoff: [1, 2, 4]
    jitter_ms: 500                     # 抖动上限，防止重试风暴
```

熔断为什么必须是"暂停队列"而不是"发一条告警"：本条产线的日预算是 800 元而日均实际是 240 元，一旦某个脚本陷入"生成成功但判定不可用"的循环，它会在几小时内吃掉整天预算。暂停队列把损失上限锁在熔断触发的那一刻，而只报警的方案会让你在看到告警时已经多花了几个小时的钱。

```python
def submit_batch(items: list[dict], budget_cny: float) -> list[dict]:
    """批量提交：幂等键、失败隔离、成本熔断三件事必须在一个函数里，
    拆开就会出现"提交成功但计费两次"或"一条失败拖垮整批"的问题"""
    results = []
    for item in items:
        if spent_today() >= budget_cny:
            results.append({**item, "status": "skipped", "reason": "daily_budget_breach"})
            continue                              # 成本熔断：跳过而不是硬跑
        key = idempotency_key(item)               # 键只由内容与参数决定
        existing = cache_get(key)
        if existing is not None:
            results.append(existing)              # 幂等：重复提交直接复用
            continue
        try:
            job = enqueue(item, key)             # 入队由消费端异步处理
            results.append({**item, "status": "queued", "job_id": job.id})
        except TransientError as exc:
            # 失败隔离：单条失败只记这一条，不中断整批
            results.append({**item, "status": "failed", "error": str(exc)})
    return results
```

## 五、把多模态管住

### 多模态评测方法

多模态评测和第十一章的文本评测最大的不同是**必须引入人工判定**，因为画面好不好、音像不像，规则算不出来。所以评测体系的设计重点是：把能用规则算的部分尽量规则化，让人工只判真正需要人眼的部分。

本章的四组指标对应四条产线，每条都有明确的算法与门禁：

| 组 | 指标 | 计算方式 | 基线 | v1.1 目标 | 门禁 |
|---|---|---|---|---|---|
| 语音 | 首音频延迟 P95 | 五段预算之和的 95 分位 | 1,680 ms | 1,420 ms | <= 1,500 ms |
| 语音 | 打断响应成功率 | 300 ms 内停播次数除以打断总次数 | 0.94 | 0.985 | >= 0.98 |
| 语音 | ASR 字准率 CER | 替换加删除加插入除以参考字数 | 0.15 | 0.11 | <= 0.12 |
| 视频 | 角色一致率 | 跨镜同角色人工判定一致的比例 | 0.82 | 0.93 | >= 0.90 |
| 视频 | 素材可用率 | 无明显瑕疵可直接进成片的比例 | 0.60 | 0.78 | >= 0.75 |
| 合成 | 音画偏移 | 视频轨与音频轨时间戳差 | 180 ms | 25 ms | <= 40 ms |
| 合成 | 字幕时间轴偏差 | 字幕起止与实际语音边界的差 | 640 ms | 80 ms | <= 100 ms |
| 审核 | 机审漏检率 | 抽检发现的违规条数除以抽检条数 | 0.05 | 0.015 | <= 0.02 |

八条指标里有五条能用规则算（首音频延迟、打断成功率、CER、音画偏移、字幕偏差），这五条应该 100% 全量跑；只有三条（角色一致率、素材可用率、机审漏检率）必须靠人工，所以人工抽检的规模就是这三条的样本量需求。**先用规则把能算的算掉，把人工省下来判画面**，这是多模态评测唯一正确的成本结构。

有一条口径必须说清：**素材可用率与废片率是同一个数的两种表述**，可用率 0.75 就等于废片率 0.25。所以门禁里写可用率不低于 0.75，成本一节里说"把废片率从 40% 优化到 25%"，说的是同一件事的同一个数。这也是为什么"提升可用率"是本章最值钱的一项优化——它同时改善了质量门禁和成本两个方向。

!!! mascot-thinking "先把能算的算掉，再把人省下来"
    ![墨墨思考中](../../img/mascot/thinking.png){ class="mascot-admonition-img" }
    八条指标里只有三条真的要人眼看。把这五条规则化的指标做成全量自动跑，人工抽检的样本量就能压到只覆盖那三条——这不是省事，是让人力花在规则算不出来的判断上。

### 内容审核机制

生成式内容的审核不能只有一道工序，因为不同风险的可检出性差别很大。本章用三层结构：**机审前置**拦住能自动判定的、**人审抽检**兜住机审漏的、**发布后巡检**兜住前三层都漏的。三层的比例与投入是这一节的核心数字。

```text
生成完成 → 机审（100% 全量，拦 6.0%）→ 高风险批次判定 → 人审抽检（按类型 5%/15%/30%）
        → 通过则发布 → 发布后巡检（前 24 小时、前 7 天各一次）→ 反馈回流到抽检集
```

**机审前置**要覆盖三类检出能力，它们的实现方式不同：文本类（提示词、生成脚本、字幕）走敏感词与分类模型，检出率最高；图像类（首帧图、生成帧）走图像分类与人物检测；音频类（配音）走语音转写后再走一遍文本机审——因为多数审核规则是文本形式的，转写后复用文本规则比训一个音频模型划算得多。

**人审抽检的比例必须按内容类型分**，并且**要按风险分层抽而不是随机抽**：机审得分低于 0.6 的一条 100% 人审，其余按类型比例抽。这一条会显著提高单位人力的拦截率。**发现问题的处理方式是扩检，不是单条修补**：抽检 1 条发现问题时，真实问题率至少是 \(1 / 14 = 7.1\%\)，扩检 2 倍能把问题率的估计误差从 ±7 个百分点压到 ±4 个百分点。

```python
# 抽检与扩检的决策逻辑：发现问题的处理方式是扩检，不是单条修补
def review_batch(batch: list[dict], risk_tiers: dict[str, str]) -> dict:
    sampled, found = [], []
    for item in batch:
        tier = risk_tiers[item["type"]]
        need = {"low": 0.05, "mid": 0.15, "high": 0.30}[tier]
        need = 1.0 if item["machine_score"] < 0.6 else need   # 机审低分 100% 人审
        if hash01(item["id"]) < need:
            sampled.append(item)
            if is_violation(item):
                found.append(item)
    extra = list(batch) if found else []                     # 发现 1 条即扩检到全量
    extra_findings = [i for i in extra if i not in sampled and is_violation(i)]
    total = len(found) + len(extra_findings)
    return {
        "sampled": len(sampled),
        "found": total,
        "quarantine": [i["id"] for i in found + extra_findings],
        "leak_rate": total / max(1, len(sampled) + len(extra)),
    }
```

这批 100 条的记录：机审通过 94 条、拦截 6 条（机审拦截率 6.0%）；首轮抽检 14 条发现问题 2 条；扩检到全量后新增问题 3 条；最终隔离 5 条，处置为 3 条下架重生成、2 条改脚本重跑。抽检漏检率 \(5 / 100 = 0.05\)，正好是上面表里的基线值——**漏检率的分母是全量不是抽检量**，这一点写清楚可以避免验收时扯皮。

| 层 | 覆盖比例 | 检出目标 | 本章实现 | 本章实测 |
|---|---|---|---|---|
| 机审前置 | 100% | 明显违规、明显侵权 | 文本、图像、转写后复用文本 | 100 条拦 6 条，拦截率 6.0% |
| 人审抽检 | 5% 到 30%（按类型） | 机审漏掉的灰区 | 风险分层抽检，发现即扩检 | 首抽 14 条，扩检后共拦 5 条 |
| 发布后巡检 | 100%（前 24 小时与前 7 天） | 前两层都漏的 | 平台投诉回流加定期抽回 | 每月回流 21 条进抽检集 |

### 版权与合规

这一节不是免责条款，是本章的硬边界。多模态生成物一旦商用，牵扯的法律关系有五条，每一条都有明确的工程动作，做不到就不能上线。

| 风险面 | 具体问题 | 工程动作 | 做不到的后果 |
|---|---|---|---|
| 训练数据与素材版权 | 用了来源不明的图库、影视片段、未授权音乐作为首帧或背景音乐 | 素材入库时登记授权类型、期限、授权方，生成链路只允许从已登记库取 | 下架加赔偿 |
| 肖像权 | 首帧用了真实人物照片，图生视频生成的运动可能被认为侵犯肖像 | 一律使用自有拍摄或有书面肖像授权的照片；授权文件与素材 id 绑定入库 | 肖像权纠纷 |
| 声音权与数字人授权 | 克隆他人音色做配音或数字人 | 每个音色绑定一份授权文件，注明授权人、用途、期限；不得使用公众人物音色 | 声音权纠纷，平台下架 |
| 生成内容标识 | 未标注生成内容，违反生成式服务的标识义务 | 开启平台侧水印并在元数据写入生成标记；发布端补平台要求的标签 | 监管处置 |
| 商业承诺 | 带货话术编造商品功能或夸大效果 | 卖点逐字比对商品详情页字段，不一致直接拦截 | 虚假宣传处罚 |

这五条里最容易被工程团队忽略的是最后两条，而它们恰恰是处罚概率最高的两条。生成内容标识在国内外都已是明确的合规义务——国内《生成式人工智能服务管理暂行办法》要求提供者对生成内容进行标识，各内容平台也普遍要求发布者声明 AI 生成。把标识做成"发布端强制字段、缺字段直接拒绝发布"，比靠人工记得勾选可靠得多。

合规的落地方式是一张**登记表加一条流水线约束**：每个素材、每个音色、每套模板都在登记表里，生成链路在编译期就校验引用是否在册，运行时校验授权是否过期。这条约束必须落在代码里而不是流程文档里，因为流程文档的遵守率在三个月后会降到三成。

```python
# 合规校验在提交生成前做一次：不合规的内容根本不该进入消耗 GPU 的环节
def check_compliance(item: dict, registry: dict) -> tuple[bool, str]:
    ok = True
    reasons = []
    for asset_id in item["asset_ids"]:                 # 首帧图与背景音乐都要登记
        rec = registry["assets"].get(asset_id)
        if rec is None:
            ok, _ = False, reasons.append(f"素材 {asset_id} 未登记授权")
        elif rec["expires_at"] < today():               # 过期授权等同未授权
            ok, _ = False, reasons.append(f"素材 {asset_id} 授权已于 {rec['expires_at']} 到期")
        elif rec["usage"] not in ("commercial", "both"):
            ok, _ = False, reasons.append(f"素材 {asset_id} 授权不含商用")
    voice = registry["voices"].get(item["voice_id"])    # 音色同样要授权
    if voice is None or voice["expires_at"] < today():
        ok, _ = False, reasons.append("音色缺少有效授权")
    if not item["aigc_label"]:                          # 生成内容标识是发布端强制字段
        ok, _ = False, reasons.append("缺少生成内容标识")
    return ok, "；".join(reasons) or "通过"
```

### 生成成本核算

多模态的成本核算比文本多一层：它同时有按 token 计费和按时长计费两种形态，两者混在一条成本里，不拆开就没法归因。本章的做法是按**成本环节**拆，拆到每一项都能追到一次具体的调用。

先给短剧单条 60 秒成片的完整拆解。本章规格是 6 个分镜、每镜 10 秒、计费时长 60 秒；废片率 40% 意味着实际生成的时长是 \(60 / (1 - 0.40) = 100\) 秒。按标准档 0.12 元/秒计，视频生成这一项就是 12.00 元。

| 成本环节 | 计费口径 | 单价（示意） | 单条金额（元） | 占比 |
|---|---|---|---|---|
| 视频生成 | 6 镜 × 10 秒 ÷ 废片率 40% = 100 秒 | 0.12 元/秒 | 12.00 | 78.4% |
| 配音合成 | 240 字 | 0.0025 元/千字 | 0.60 | 3.9% |
| 画质增强与转码 | 60 秒，本机 8 核 CPU | 0.004 元/分钟 | 0.24 | 1.6% |
| 字幕生成与烧录 | 6 条字幕 | 0.001 元/条 | 0.01 | 0.1% |
| 机审 | 12 次调用 | 0.004 元/次 | 0.05 | 0.3% |
| 人工抽检摊销 | 抽检 10%，摊 0.3 人分 | 8 元/人分 | 2.40 | 15.7% |
| 合计 | — | — | 15.30 | 100% |

这张表有两个立刻可行动的结论。第一，**视频生成吃掉 78.4%，所以唯一值得投入优化精力的是可用率**，其他环节加起来不到 22%，优化它们连零头都不到。第二，**人工抽检摊销 2.40 元占 15.7%，排第二**，它不随生成质量下降而下降，是一个刚性成本——所以抽检比例的每一次调整都要拿数据说话，不能顺手就调低。

降本只有一条真正有效的路：**把废片率从 40% 降到 25%**。废片率降下来，计费时长从 \(60 / 0.60 = 100\) 秒变成 \(60 / 0.75 = 80\) 秒，视频生成从 12.00 元降到 9.60 元，单条从 15.30 元降到 12.90 元，降幅 15.7%。而这条路的手段在前面已经给全了：调引导强度（参数调优一节的 6.5 档）、首帧图规范、镜头分类路由。

三条降本手段按性价比排：

| 手段 | 可省金额（元/条） | 代价 | 生效周期 |
|---|---|---|---|
| 废片率 40% 降到 25% | 2.40 | 需要两周调参与首帧规范 | 2 周 |
| 混音段改用视频流 copy | 0.10（省合成段 40% 耗时而非钱） | 无质量损失 | 立即 |
| 人工抽检从 10% 调到 6%（配合风险分层） | 0.96 | 漏检率需重新验证 | 1 周 |

注意第二条是唯一"零代价"的改动，所以它必须最先做；而第三条要用漏检率重新验证，属于有代价的改动。降本最常见的错误是从最便宜的成本项开始砍——把配音单价从 0.60 元砍到 0.30 元，单条省 0.30 元（占 2.0%），而动抽检比例或废片率能省 2.40 元。

对比另一条线的成本结构会更有说服力：带货切片单条 5.10 元，视频生成 3.72 元（占 72.9%）、人工抽检 1.20 元（占 23.5%）、其余 0.18 元（占 3.5%）。它比短剧便宜 3 倍，但抽检占比更高——因为抽检比例定在 30% 而不是 10%。所以"哪条线更省"这个问题没有单一答案，取决于它的抽检风险等级。

整条产线的月成本按下表的规模口径汇总，可直接进预算：

| 产线 | 日产量 | 单条成本（元） | 日成本（元） | 月成本（按 30 天） |
|---|---|---|---|---|
| 60 秒短剧 | 4 条 | 15.30 | 61.20 | 1,836.00 |
| 15 秒带货切片 | 30 条 | 5.10 | 153.00 | 4,590.00 |
| 自媒体矩阵图文变体 | 30 条 | 8.00 | 240.00 | 7,200.00 |
| 合计 | — | — | 454.20 | 13,626.00 |

### 多模态上线清单

前五节产生的东西在这里被压成一张放行单。这份清单的价值不在于它全，而在于它每一条都能被验证——写不出验证方法的条目说明还没想清楚，不该勾。

- [ ] **链路** 六段语音链路（音频输入、VAD、ASR、Agent、TTS、音频输出）全部有超时上限，任一段无上限即为不通过
- [ ] **打断** 打断响应成功率不低于 0.98，300 毫秒内停播；已排队音频被清空而非暂停；被截断回复已写回上下文
- [ ] **回声** 播放期间 VAD 灵敏度已下调或打断判定已冻结，100 条自录音无自打断
- [ ] **延迟** 首音频延迟 P95 不超过 1,500 毫秒，且余量不低于 20%
- [ ] **工具** 工具已按读、写、不可逆三档分级；不可逆档口播复述参数且只认明确肯定词
- [ ] **规格** 成片规格等于目标值（竖屏 1080×1920、30 fps），`ffprobe` 输出可作为证据
- [ ] **归一化** 拼接前所有分镜已过帧率、分辨率、像素宽高比、采样率四项一致性检查
- [ ] **音画** 音画偏移不超过 40 毫秒，响度落在 -23 到 -14 LUFS，无超过 0.5 秒的黑帧
- [ ] **字幕** 字幕时间轴由配音实际时长生成而非字数估算；时间戳毫秒分隔符为逗号；单条不超过 15 字
- [ ] **一致性与可用率** 角色一致率不低于 0.90，素材可用率不低于 0.75
- [ ] **种子** 所有进入成片的镜头已记录 `seed`，`guidance_scale` 与 `steps` 已锁进配置而非散落在代码里
- [ ] **幂等** 重复提交同一内容 30 次，产物数与计费次数均为 1
- [ ] **补偿** 限流、上游超时、审核拒、参数错、平台故障、结果不可用六类失败各有分类与处置；不可重试类不重试
- [ ] **熔断** 日预算与单条预算均已配置，熔断动作是暂停队列而非只报警，熔断阈值演练过一次
- [ ] **审核** 机审覆盖文本、图像、音频三类；人审抽检按类型分层（5% / 15% / 30%）；机审低分 100% 人审
- [ ] **扩检** 发现 1 条问题即扩检 2 倍的规则已在代码里，不是流程文档里
- [ ] **巡检** 发布后前 24 小时与前 7 天各巡检一次，投诉回流通道已打通并写入抽检集
- [ ] **合规** 素材授权表与音色授权表完整，授权过期按未授权处理；生成内容标识为发布端强制字段
- [ ] **成本** 单条成本已拆到环节，视频生成与人工抽检两项占比已核对；降本手段已排优先级
- [ ] **评测** 八项指标全部有基线值与门禁值，其中五条规则化指标已全量自动跑
- [ ] **告警** 延迟、可用率、漏检率、单条成本四项告警已配最小样本量与持续窗口，阈值与门禁同源
- [ ] **回滚** 生成任务的批次可整批回滚到上一版参数；合成产物按内容 id 保留最近三版
