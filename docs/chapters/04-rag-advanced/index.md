## 一、先造一把尺子：评测集与失败归因

RAG 出错时大多数团队的第一反应是"改提示词"。这个顺序几乎总是错的，因为一个答错的样本背后可能是四种互斥的病因，而提示词只能治其中一种。要让评测集能定责，标注粒度就必须比"对 / 错"更细——每一道题要记下"正确答案应该出现在哪个文件的哪一段"。

评测集的生产规模起点是 200 题，分三块：典型问题 120 道、边界问题 40 道（信息不全、问法模糊、指代未消解）、拒答题 40 道。拒答题占到两成不是凑数：一个能答对的系统在拒答上几乎不需要训练就能及格，而"该说不知道"必须被单独教会、单独度量。第二章给的 50~100 题适合验证管线能不能跑通，不足以做版本之间的显著性判断。

四个指标先定义清楚，本章后面每一节都复用它们：

| 指标 | 回答什么问题 | 计算方式 | 本章基线门禁 |
|---|---|---|---|
| 召回命中率 | 该找的资料找到了吗 | 正确块进入 Top50 候选的题数 / 评测集总题数 | >= 90% |
| 忠实度 | 答案句句有出处吗 | 可被引用块支撑的断言数 / 断言总数 | >= 93% |
| 拒答准确率 | 该沉默时沉默了吗 | 40 道拒答题中正确拒答的题数 / 40 | >= 90% |
| 上下文精确率 | 送到模型手里的是不是净料 | 最终 5 条引用块中正确的条数 / 5 | >= 0.6 |

注意这四个指标定位不同：召回命中率是天花板，它低说明后面全是白干；忠实度和拒答准确率是生成侧的安全带；上下文精确率是中间量，它掉下来会同时推高输入 token 和幻觉概率。

有了尺子还要有刻度。一次基线评测跑出 200 题里 40 题错，按下面四类归因拆开，这四类决定了后面所有的优化顺序：

| 失败类型 | 判定方法 | 根因位置 | 典型药方 |
|---|---|---|---|
| 资料缺失 | 人工翻遍知识库也找不到依据 | 运营侧，库本身没有 | 补文档，排期认领 |
| 切分断裂 | 依据存在但被切成两块，正确块没进 Top50 | 数据侧，切分参数或解析 | 改切分粒度、加结构前缀 |
| 检索失配 | 正确块在库里但没进 Top50 | 检索侧，嵌入或召回策略 | 换嵌入模型、加混合检索、调 TopK |
| 生成漂移 | 块进了候选但答案没照抄，或凭空补充 | 生成侧，提示词与约束 | 加引用约束、加阈值拒答 |

归因顺序是固定的：先看召回命中率。召回没中的题（本章基线里 18 道：切分断裂 11 道、资料缺失 7 道）不要去动提示词，改提示词对它们零收益。召回到却答错的 22 道（生成漂移 14 道、忠实度不足 8 道）才轮到下一节。把 40 道错题按这个顺序切开，你会看到通常前两类占大头——这正是新手最容易调错方向的原因。

!!! mascot-warning "只标对错的评测集没有用"
    ![墨墨提醒注意](../../img/mascot/warning.png){ class="mascot-admonition-img" }
    只标"对 / 错"你只能知道系统在变好还是变坏，看不出该改哪儿。标注要落到"哪份文档哪一段"，多花的那半天会在第一次归因时直接赚回来。这个坑我替你踩过：没有块级标注的评测集，最后总会退化成凭感觉改提示词。

### 幻觉抑制策略

幻觉是"答案里出现了检索块中没有的事实"。它有三个来源，对应三道不同的防线，别指望一道防线全挡：块里根本没有（靠检索侧和证据门槛），块里有但表述被扭曲（靠生成约束和二次校验），块里没写但模型按世界知识补了一句（同样靠二次校验）。

第一道防线是**证据门槛**，它必须发生在任何生成之前。做法是拿重排后的 Top1 分数当闸门：低于阈值就直接拒答，连提示词都不给模型看。本章的阈值取 0.62（重排分数落在 0 到 1 之间）。举个例子，某次查询重排后 Top5 分数依次是 0.71、0.66、0.63、0.58、0.55，按 0.62 卡掉后只剩 3 条进入上下文；若 Top1 就低于 0.62，整轮拒答。一个容易忽略的收益是：证据变少会同时省下输入 token 和延迟，所以这道防线在省钱这一栏也是正的。

第二道防线是**引用约束**：提示词里给每条证据编号，硬性要求答案里的事实性陈述必须带编号，不许自由发挥。第三道防线是**二次校验**：把生成的断言逐条与证据做核对（规则匹配或让一个便宜模型判定蕴含关系），对不上就改成"资料未提及"。三层代码写在一起是这样：

```python
RERANK_FLOOR = 0.62       # 重排分数低于此值视为"没有证据"
ANSWERABLE_FLOOR = 0.62   # Top1 低于此值直接拒答，连提示词都不给

async def answer_with_evidence(question: str):
    hits = await vector_search(question, k=50)      # 第一段：召回 50 条
    ranked = await rerank(question, hits, top_n=5)  # 第二段：重排收敛到 5 条
    if not ranked or ranked[0].score < ANSWERABLE_FLOOR:
        return REFUSAL                              # 第三层前置于一切生成
    evidence = [h for h in ranked if h.score >= RERANK_FLOOR]
    prompt = EVIDENCE_PROMPT.format(                # 每条证据带编号 [1] [2] ...
        question=question,
        evidence="\n\n".join(f"[{i+1}] {h.text}"
                             for i, h in enumerate(evidence)),
    )
    answer = await llm.ainvoke(prompt)
    return attach_citations(answer, evidence)        # 编号对齐，宁可留空也不错引
```

三层全开的效果和代价是可以量出来的。下表是同一份 200 题评测集上的四组对照，每格都是实测值，不是估计值：

| 配置 | 忠实度 | 拒答准确率 | P95 延迟 | 每次成功问答成本 | 卡在哪个门禁 |
|---|---|---|---|---|---|
| 裸 RAG，不做任何抑制 | 82% | 55% | 3.2 s | 0.011 元 | 忠实度、拒答准确率双低 |
| 只加引用约束 | 89% | 55% | 3.3 s | 0.012 元 | 忠实度 89% 仍低于 93%，拒答完全没改善 |
| 只加阈值拒答 | 82% | 81% | 3.2 s | 0.011 元 | 拒答提到 81% 但离 90% 还差，忠实度纹丝不动 |
| 只加二次校验 | 94% | 88% | 4.6 s | 0.019 元 | P95 超 4.5 s，拒答仍差 2 个百分点 |
| 三层全开 | 96% | 92% | 4.9 s | 0.021 元 | 成本 0.021 元超 0.02 元，P95 超 4.5 s |
| 高风险意图开全部三层，其余只开引用约束加阈值拒答 | 94% | 92% | 3.9 s | 0.016 元 | 全部达标 |

这张表的读法比数字本身更重要：三层各自只解决一种病因，谁也替代不了谁，所以"三层全开"的效果最好；但它同时把成本推到 0.021 元、P95 推到 4.9 秒，两条门禁都破了。真正可上线的答案是最后一行——按意图分级开关。高风险意图（涉及金额、承诺、投诉）承担全部校验成本，其余意图只走便宜的引用约束加阈值拒答，整体成本回落到 0.016 元，忠实度和拒答准确率却和全开时一样。

!!! mascot-thinking "先问是哪一种病，再决定开哪副药"
    ![墨墨思考中](../../img/mascot/thinking.png){ class="mascot-admonition-img" }
    把幻觉想成三种不同的病：查无实据（检索没找到）、看错病历（模型曲解了找到的证据）、凭空补全（模型掺进了世界知识）。阈值拒法治第一种，引用约束治第二种，二次校验治第三种——它们不是强度不同的同一招，而是三味不同的药。所以"我把提示词改了三版还是幻觉"这句话本身就是诊断错误。

### 用户反馈闭环

用户反馈是唯一来自真实分布的信号，评测集永远只是它的抽样。生产系统要采四类信号：显式的赞和踩、隐式的追问（同一问题被换问法再问一遍）、转人工（最强的负反馈）、以及用户主动填写的会话结束原因。它们要挂在同一个 `trace_id` 上，否则人工归因时无法回放当时的召回结果。

闭环的运转节奏是定死的：负反馈进归因队列 → 人工把它归到第一节那四类失败类型之一 → 修复 → 回归评测 → 进评测集固化成回归用例。本章基线的量级是日均 1200 次会话、负反馈率 6%，即每天约 72 条、每周约 500 条负反馈待归因；前三类原因通常占其中六成左右。目标闭环周期不超过 7 天，超过这个周期反馈就变成了抱怨而不是数据。

```python
async def record_feedback(feedback: FeedbackIn):
    """负反馈不只是一颗星星，它是一条评测集候选"""
    session = await load_session(feedback.session_id)   # 带完整检索轨迹
    await store.save({
        "session_id": feedback.session_id,
        "kind": feedback.kind,      # 踩 / 追问 / 转人工 / 会话结束原因
        "question": session.last_question,
        "cited_ids": session.cited_ids,
        "trace_id": session.trace_id,   # 供人工归因时原样回放召回与重排
    })
    if feedback.kind == "踩":
        await queue.push("attribution", feedback.session_id)
```

### 知识库运营指标

评测指标回答"准不准"，运营指标回答"这套系统值不值得继续投"。它是给老板和知识运营同事看的，必须能落到一个具体的动作上，否则看板上全是没人负责的曲线。分三层，每层都要能按场景标签和部门切片：

| 层级 | 指标 | 定义 | 本章基线 | 掉了该找谁 |
|---|---|---|---|---|
| 效果层 | 自助解决率 | 未转人工且未点踩的会话数 / 总会话数 | >= 60%（本章全站基线 61%） | 检索与知识运营 |
| 效果层 | 知识覆盖率 | 有效提问意图中库里有答案的比例 | >= 85% | 知识运营（补文档） |
| 效果层 | 负反馈率 | 点踩会话数 / 总会话数 | <= 6% | 检索与生成 |
| 成本层 | 每次成功问答成本 | 总花费 / 成功问答数 | <= 0.02 元 | 架构与限流 |
| 成本层 | 检索调用量 P95 | 每日 Top50 召回的调用次数 | <= 12000 次 | 缓存与网关 |

## 二、三种会把检索打穿的资料形态

前面几节假设知识库是一堆干净的段落。真实的库里总有三样东西会把朴素 RAG 打穿：超长文档、表格、图片。它们各有各的失败方式，也各有各的处理套路。

### 长文档处理

一份 120 页的产品手册大约 8.6 万字。按第二章的默认块大小 800 字、块重叠 120 字切，会得到约 108 块；问题不在数量而在边界——手册里"安装前置条件"和"安装步骤"被切成相邻两块时，用户问"装之前要准备什么"，召回可能只捞到后半块。

更糟的是"整篇直塞"这种偷懒做法：8.6 万字折合约 5.7 万 token，塞不进常见的 32768 上下文窗口；有人改成截前 20 页（约 1.6 万字、1.07 万 token），占掉三分之一预算却大概率答非所问，因为用户在问第 90 页的内容。

长文档的正解是分层：先按结构把文档切成一级章节（这份手册是 12 章，平均每章 7200 字），对 12 章各生成一段摘要（共约 2400 字），在摘要层做第一次检索挑出相关章节；再在被选中的章节里按小节标题切块（每块 800 字、重叠 120 字，共仍是 108 块，但边界落在小节上），每块前面拼上标题路径如"产品手册 > 第 7 章 安装部署 > 3.2 环境要求"（约 30 字），在块层做第二次检索取 Top5。这样既不爆窗口，又让每一块都自带定位信息。

| 方案 | 上下文占用 | 召回粒度 | 主要风险 |
|---|---|---|---|
| 整篇直塞 | 约 5.7 万 token，爆窗口 | 无检索，全量 | 直接失败，或截断后答非所问 |
| 固定窗口截前 N 页 | 截 20 页约 1.07 万 token | 页级 | 漏掉后 5/6 的内容 |
| 固定块切分 | Top5 块约 4000 字 | 块级 | 块边界切断语义 |
| 分层检索（摘要层加块层） | 摘要 2400 字一次性，块 5 条约 4000 字 | 章节级加块级 | 摘要失真，需要一次额外检索 |

```python
async def long_doc_answer(question: str, doc_id: str):
    chapters = await load_chapter_sections(doc_id)   # 120 页按一级标题拆成 12 章
    outline = await summarize_sections(chapters)     # 摘要层：12 段共约 2400 字
    picked = await select_chapters(question, outline)  # 第一次检索：挑相关章节
    chunks = []
    for c in chapters:
        if c.title not in picked:
            continue
        for part in split_by_heading(c.text, size=800, overlap=120):
            chunks.append(f"{c.heading_path}\n{part}")  # 标题路径前置，边界落在小节
    best = await vector_search(question, chunks, k=5)  # 第二次检索：块级 Top5
    return await llm.astream(build_prompt(question, best))
```

### 表格数据检索

表格是纯向量检索的天然克星，因为向量把整张表压成了一个平均语义。具体算一笔账：一张 12 行 5 列的季度报表，转成 Markdown 后每行文本大约 60 字，12 行总共 720 字，在 800 字的块大小下会被合并成一块。用户问"华东区 Q3 毛利率最高吗"，这块的向量是十二行数字的平均值，召回极不稳定。

解法三步：把表格按行切，每行单独成块；把列名拼进每一行的文本（写成"季度=Q3；区域=华东；营收=1280万；毛利率=34.2%"，这样"华东区 Q3"这类查询才抓得住）；把年、季度、区域这类筛选维度写进元数据，让检索时可以硬过滤而不是靠向量猜。

```python
def table_to_chunks(table: dict) -> list[dict]:
    """把二维表转成'每行一块、列名前置'的检索单元"""
    columns = list(table["columns"])          # 例如 ["季度", "区域", "营收", "毛利率"]
    base = {"source": table["source"], "table_id": table["table_id"]}
    chunks = []
    for row in table["rows"]:
        cells = [f"{col}={val}" for col, val in zip(columns, row)]
        chunks.append({
            "text": "；".join(cells),            # 列名进正文，向量才抓得住
            # 年/季度/区域进元数据，供检索层做硬过滤
            "metadata": {**base, "quarter": row[0], "region": row[1]},
        })
    return chunks
```

### 图片内容检索

图纸、扫描件、产品照片这类内容没有可切分的文本。主流做法是把图片内容整体编码成一个向量，与文本编码进同一个空间，这样"带密封圈的法兰"就能召回那张法兰照片。库规模通常在两万张量级：纯文本检索在这个库上等于零命中，因为入库时根本没写文本。

另一个可选信号是 OCR（光学字符识别）抽出的文字，它能覆盖约四成含文字的扫描件。关键纪律是：**文本向量和图像向量不要混在同一个索引里**。两种模态的向量尺度不同，混检会互相拉低相似度，表现为"文字查询召回了图片、图片查询召回了文字"。要么分两个索引，要么在同一库里用模态前缀（给文本和图像的向量各拼一段固定的标记串再归一化）隔开。

## 三、多轮对话与两个真实场景

资料侧的坑填完，接下来是交互侧。多轮对话的失败几乎都来自"这轮的检索词根本不是用户说的话"，而两个实战场景要处理的是业务边界——什么时候必须转人工，什么时候必须拒答。

### 多轮检索对话

用户第三轮说的往往不是完整问题，而是"那它多少钱""那要多久"。这类查询直接送进向量库必然失手，因为"它"在向量空间里没有指代对象。本章的会话统计（合成数据）显示，从第二轮起含指代或省略的提问占全部提问的六成，而改写后 Top1 命中率能从 54% 提升到 81%——这是单次投入产出比最高的一个改动。

改写要做三件事，都比想象中朴素：把指代补成实体（"它"→上一轮问的那个型号）、带上上一轮已引用的块 id 作为候选补充（避免重复召回，也保证答案连贯）、以及检测冲突（同一实体两轮答案矛盾时，在新一轮提示词里显式提醒模型以更新后的资料为准）。

```python
async def multi_turn_search(question: str, session_id: str):
    turns = await load_turns(session_id, k=3)         # 最近 3 轮原始消息
    standalone = await rewrite_query(question, turns)  # 补全指代与省略
    fresh = await vector_search(standalone, k=50)      # 本轮重新召回
    prev_ids = await load_cited_ids(session_id)       # 上一轮已引用的块
    # 合并去重后重排：老块能提连贯性，新块能提时效性
    merged = merge_and_rerank(standalone, fresh, prev_ids, top_n=5)
    return await llm.astream(build_prompt(question, merged))
```

### 客服问答实战

场景取最常见的电商售后。日均 12000 张工单，用户问法极口语，答案错误的后果是直接的资损和客诉。做法是先做五分类意图识别，再按意图决定检索哪个数据源、能不能自己答：

| 意图 | 检索源 | 能否自动答复 | 拒答或转人工条件 |
|---|---|---|---|
| 订单查询 | 订单库实时查询 | 能 | 订单号不存在时让用户核对，不猜 |
| 物流异常 | 物流接口实时查询 | 能 | 轨迹为空或状态矛盾时转人工 |
| 退换货 | 退换政策文档 | 能 | 超过 7 天无理由期时转人工 |
| 发票 | 发票政策文档 | 能 | 需要个体化税号时转人工 |
| 优惠与投诉 | 无 | 不能 | 一律转人工，绝不自动答复 |

业务上的三个数字目标：把电商售后这一个场景的一轮自助解决率从 48% 提到 62%，对应的转人工率从 52% 降到 38%；但转人工率不能低于 18%——低于 18% 不是好事，说明该转人工的场景被自动答复硬扛住了，风险从客服工单转移到了客诉和赔付。

```python
HUMAN_INTENTS = {"compensation_promise", "modify_order", "complaint_escalate"}
HUMAN_HINT = "这个问题需要人工客服处理，已为您转接，请稍候。"

async def answer_ticket(question: str, user: dict):
    intent = await classify_intent(question)          # 上表五分类
    if intent.name in HUMAN_INTENTS:                  # 承诺赔付、改订单、投诉升级
        return await handoff_to_human(user, question)  # 绝不自动答复
    source = SOURCES[intent.name]
    facts = await source.fetch(user)                   # 订单库或物流接口，带真实单号
    policy = await vector_search(question, k=50, filter={"doc_type": "policy"})
    evidence = await rerank(question, merge(facts, policy), top_n=5)
    if not evidence or evidence[0].score < 0.62:
        return HANDOFF_SAME_REASON                     # 与阈值共用一条口径
    return await llm.astream(                        # 答案必带出处：单号或条款号
        build_ticket_prompt(question, facts, evidence))
```

### 企业文档问答实战

第二个场景是制造企业内部知识助手：8 个部门、12000 份文档，覆盖规章制度、工艺文件、设备手册和质量报告。和客服最大的不同是权限——这里答错一条密级文件，代价是合规事故而不是客诉。

单次问答如果不做检索，全量候选资料的规模在 42 万 token 量级（近三个月各部门文件叠加），而检索收敛到 Top5 块后只有约 4000 字、约 2700 token。这就是检索的全部价值：省下 99% 的上下文，同时把越权内容挡在模型之外。

关键纪律只有一条：**权限过滤必须在检索层用元数据完成**。如果先全库召回再在生成层筛掉越权内容，等于把用户无权查看的内容塞进了模型提示词——它可能不会输出，但内容已经离开了你的系统，不合规。

```python
def build_acl_filter(user: dict) -> dict:
    """把用户身份翻译成向量库的元数据过滤条件"""
    return {"$and": [
        {"department": {"$in": user["allowed_depts"]}},      # 例如 eng、quality
        {"clearance_level": {"$lte": user["clearance"]}},    # 密级上限，public 到 secret
    ]}

async def ask_internal(user: dict, question: str):
    # 50 条候选全部在授权范围内，越权内容从未离开索引层
    hits = await vector_search(question, k=50, filter=build_acl_filter(user))
    evidence = await rerank(question, hits, top_n=5)
    return await llm.astream(build_prompt(question, evidence))
```

## 四、把成本、扩展性和安全压住

前四节做完了效果，剩下三节决定这套系统能不能长期活着：钱花得冤不冤、接入方能不能自己接、敏感数据会不会漏。

### 检索缓存优化

客服和企业文档两类场景里，重复问题占比都很高，本章取客服场景的合成数据 38%——超过三分之一的问题在最近几分钟内刚被同样地问过。缓存要分三层，各自解决不同的重复：答案级缓存（归一化后的查询哈希到最终答案，适合客服的重复问法）、召回级缓存（查询向量到候选块 id 列表，TTL 短，60 秒）、块级缓存（文档 URL 加内容哈希到块文本，内容不变就长期有效）。

缓存键归一化是命中率的关键。同一个问题"这个能便宜点吗？"和"这个能便宜点吗?"在哈希眼里是两个键，去掉标点、去语气词、统一数字和型号写法之后才是同一个。不做归一化，答案级命中率只有 11%，做完归一化能到 23%——翻倍来自一个几行的正则。

```python
import hashlib, random

def cache_key(question: str) -> str:
    norm = re.sub(r"[，。？！、,.?!]", "", question)   # 去标点
    norm = re.sub(r"(那个|请问|一下|呢|嘛)", "", norm)  # 去语气词
    norm = re.sub(r"\s+", "", norm)                   # 去空白
    return hashlib.sha1(norm.encode()).hexdigest()[:16]

async def cached_answer(question: str, session_id: str):
    key = f"rag:ans:v3:{session_key(session_id)}:{cache_key(question)}"
    if (hit := await redis.get(key)) is not None:
        return hit.decode()                            # 命中，连重排和生成都省掉
    answer = await rag_answer(question, session_id)
    # 600 秒基础 TTL 加 0 到 120 秒随机抖动，防止同一时刻集体失效
    await redis.setex(key, 600 + random.randint(0, 120), answer)
    return answer
```

缓存键里必须带版本号（本例 `v3`）：改过提示词或切分逻辑后升版本，旧缓存自然失效，比逐条删 key 可靠。带 `session_key` 是为了让跨用户会话隔离；需要跨会话共享时把它换成租户键，但那时必须确认答案里不含用户私有数据。

### 检索网关封装

随着接入方增多，检索逻辑会散落到每个业务方的代码里。第二章说过的"从 Demo 到服务封装"，在检索侧的具体形态是一个网关：所有检索请求从它进，由它路由到具体后端（向量库、BM25、图谱、业务查询接口），并在这一层统一执行四件事——元数据与 ACL 过滤、限流、缓存、埋点。

封装的直接收益可以量化：4 个业务方、3 类检索后端时，切换或新增一个后端从平均 2 天降到 15 分钟，因为业务方只认网关的一个接口。代价是多一跳延迟（约 2 毫秒）和一层需要自己运维的组件，这个代价在接入方超过两个之后就是净赚。

每个路由上还带一个灰度比例字段，含义是"这个场景有多少比例的流量走新版本"，具体怎么放量见第五节的灰度发布策略。

```yaml
# 检索网关路由配置：场景 -> 后端组合，统一在这里挂过滤、缓存与灰度开关
routes:
  - name: faq_hybrid          # 客服 FAQ：向量 + BM25 混合
    backends: [vector_pg, bm25_es]
    acl_filter: true          # 元数据过滤与权限在这一层强制执行
    cache_ttl_s: 60           # 召回级缓存 60 秒
    canary_percent: 5         # 灰度比例，与总流量开关相乘
  - name: policy_manual       # 制度手册：块层 + 图谱双路
    backends: [vector_pg, graph_neo4j]
    acl_filter: true
    cache_ttl_s: 300
    canary_percent: 5
limits:
  qps: 40                     # 网关自身入口限流
  embedding_rps: 120          # 下游 embedding 服务的独立配额
telemetry:
  emit: [latency_ms, recall_hits, rerank_top_score, cost_cny]
```

### 敏感信息脱敏

RAG 知识库里的敏感信息有三个来源：文档本来就含个人信息（客户名单、合同）、解析阶段引入的噪声（OCR 把页脚混进正文）、以及对话过程中的临时内容。防护要做三层，但第一层最关键。

入库前脱敏的规则表要按"先窄后宽"的顺序排列，否则 16 位到 19 位的银行卡规则会先把手机号吃掉。本章的扫描结果：6 类 PII（pattern）规则扫 10000 个块，命中 143 块，命中率 1.43%；其中 9 块是误报（订单号被当成了手机号），误报率 6.3%。误报不致命但必须治理——宁可漏掉一条提示，也不要让运营同学每天被几百条假报警淹没。

最容易做错的是"脱敏就检索不到了"这个顾虑。正确做法是用带盐哈希替换而不是打码：同一个手机号永远映射到同一个占位符，"查一下 13800138000 的订单"和文档里"客户 13800138000"哈希成同一个串，向量依然能对上；而打码成 `138****8000` 会让这类查询彻底失效。

```python
import hashlib, re

# 入库前脱敏：规则按顺序应用，先窄后宽（身份证优先于手机号）
PII_RULES = [
    ("id_card",   re.compile(r"\b\d{17}[\dXx]\b")),
    ("bank_card", re.compile(r"\b\d{16,19}\b")),
    ("phone",     re.compile(r"\b1[3-9]\d{9}\b")),
    ("email",     re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+")),
    ("address",   re.compile(r"[一-龥]{2,6}(省|市|区|县)[一-龥]{0,10}(路|街|号|室)")),
    ("contact",   re.compile(r"(联系人|收货人)[：: ]\s*[一-龥]{2,4}")),
]

def make_sub(field: str):
    def sub(m):
        # 带盐哈希：同一敏感值映射到同一占位符，检索能力得以保留
        h = hashlib.sha256((SALT + m.group()).encode()).hexdigest()[:8]
        return f"[{field}#{h}]"
    return sub

def mask(text: str) -> str:
    for field, pattern in PII_RULES:
        text = pattern.sub(make_sub(field), text)
    return text
```

### 灰度发布策略

RAG 的每次改动都可能同时影响质量、延迟和成本，所以不能整量替换。标准阶梯是：内部员工先跑（dogfood）→ 5% → 20% → 50% → 100%，每档停留至少一天且有效样本达标才推进。三条硬约束必须写进发布单：每档有效样本不少于 500 次、必须经过 50% 档、五个工作日内到达 100%。

"有效样本"要打个折扣，因为并非每个请求都会走完整链路（提前拒答、客户端取消都算无效）。按日均 12000 次请求、有效问答完成率 84% 计算，5% 档有 600 次请求、约 504 次有效，恰好压在 500 的线上。这个"恰好过线"不是巧合，而是把最小样本量换算成可执行规则的结果。

同一用户必须固定命中同一版本，做法是对 `user_id` 取模哈希决定走老版还是新版，否则用户会在两轮对话之间遇到答案不一致的诡异体验。回滚也要自动化，两个触发器任一命中即刻回滚：错误率相对基线上升 50% 以上，或端到端 P95 延迟上升 50% 以上。判断答案质量的变化靠离线回归评测，不靠线上抽样——线上只看硬指标。

!!! mascot-thinking "小流量看硬指标，大流量看质量"
    ![墨墨思考中](../../img/mascot/thinking.png){ class="mascot-admonition-img" }
    5% 档跑不满一天，答案质量的微小差异在统计上根本看不出来，硬看只会逼出一堆噪声结论。所以低档位只盯错误率、拒答率、延迟这类一两次就能判定的硬指标；真正的质量判断交给离线评测集的回归。这条分界线划错了，要么误回滚，要么把问题放过了 50% 档。

### 知识保鲜机制

知识库会腐烂：制度改了、报价过期了、设备换了型号，但向量库里那块文本一动不动，于是系统开始自信地引用三个月前的旧政策。保鲜不是定期重建索引，而是给每篇文档三个字段：有效期、最后复核时间、责任人。

具体数字：3600 篇文档，月度变更率 8%（约 288 篇），默认有效期 180 天。到期前 30 天生成待复核任务；到期仍未复核的文档自动标记为"待复核"，并且——这是最有用的一步——在引用它的答案末尾加一句时效提示，把不确定性交给用户而不是替知识运营隐瞒。

```bash
#!/usr/bin/env bash
set -euo pipefail

# 知识保鲜巡检：找出 30 天内到期、但没有任何复核记录的文档
DAYS=30
OUT=$(psql "$DATABASE_URL" -tA -F'|' -c "
  SELECT doc_id, title, expires_at
  FROM knowledge_doc
  WHERE expires_at <= now() + interval '${DAYS} days'
    AND last_reviewed_at IS NULL
  ORDER BY expires_at;
")
[ -z "$OUT" ] && { echo "没有 ${DAYS} 天内到期的待复核文档"; exit 0; }
echo "$OUT" | while IFS='|' read -r doc title expires; do
  echo "待复核: ${doc} (${title}) 到期 ${expires}"
done | tee -a /var/log/ai-app/knowledge-freshness.log
```

注意这个巡检只查"到期且未复核"，不重建索引。重建索引是重活，只对实际改动过的文档做增量更新（第三章的 RagFlow 提供了这个能力），全量重建留到季度级别。
