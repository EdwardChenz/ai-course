#### 1. 幻觉抑制的第一道防线"证据门槛"取的重排分数阈值是多少？

<div class="upper-alpha" markdown>

1. 0.50
2. 0.75
3. 0.62
4. 0.85

</div>

??? question "Show Answer"
    The correct answer is **C**。阈值取 0.62，拿重排后的 Top1 分数当闸门：低于阈值直接拒答，连提示词都不给模型看。算例是某次 Top5 分数 0.71、0.66、0.63、0.58、0.55，按 0.62 卡掉后只剩 3 条进上下文；Top1 就低于 0.62 则整轮拒答。而且 0.62 不是拍的——把 500 条线上查询的 Top1 分数画成直方图，看双峰之间的谷底在哪，换模型换业务必须重算。

#### 2. 本章基线的用户反馈量级与闭环时限，正确的是哪一组数字？

<div class="upper-alpha" markdown>

1. 日均 1200 次会话、负反馈率 6%，每周约 500 条待归因，闭环周期不超过 7 天
2. 日均 1200 次会话、负反馈率 0.6%，每周约 50 条待归因，闭环周期不超过 30 天
3. 日均 1200 次会话、负反馈率 6%，即每天约 72 条、每周约 500 条负反馈待归因，目标闭环周期不超过 7 天
4. 日均 12000 次会话、负反馈率 6%，每周约 5000 条待归因，闭环周期不超过 3 天

</div>

??? question "Show Answer"
    The correct answer is **C**。闭环的运转节奏是定死的：负反馈进归因队列 → 人工归到资料缺失、切分断裂、检索失配、生成漂移四类之一 → 修复 → 回归评测 → 进评测集固化成回归用例。7 天是硬目标，超过这个周期反馈就变成了抱怨而不是数据。四类信号（赞踩、追问、转人工、结束原因）都要挂在同一个 `trace_id` 上，否则无法回放当时的召回结果。

    **Concept Tested:** 用户反馈闭环

    **See:** [章节首页](../04-rag-advanced/index.md)

#### 3. 入库前的脱敏规则表，规则之间应该按什么顺序排列？

<div class="upper-alpha" markdown>

1. 先宽后窄，先跑覆盖面大的规则，避免同一条文本被反复匹配
2. 先窄后宽，身份证规则必须排在手机号与银行卡之前
3. 按规则历史命中率排序，命中最多的先跑，扫描性能最优
4. 按规则名的字母顺序排列，保证每次扫描的结果完全一致

</div>

??? question "Show Answer"
    The correct answer is **B**。规则按"先窄后宽"排列，否则 16 位到 19 位的银行卡规则会先把手机号吃掉。本章的扫描结果是 6 类规则扫 10000 个块命中 143 块，命中率 1.43%，其中 9 块误报、误报率 6.3%——误报不致命但必须治理，宁可漏一条提示，也不要让运营同学每天被几百条假报警淹没。

    **Concept Tested:** 敏感信息脱敏

    **See:** [章节首页](../04-rag-advanced/index.md)

#### 4. 灰度放量的低档位为什么只盯错误率、拒答率、延迟这类硬指标，答案质量要交给离线回归评测？

<div class="upper-alpha" markdown>

1. 因为线上环境根本采集不到答案质量数据
2. 因为硬指标的统计误差更小，所以更可靠
3. 因为离线评测集的标注工作还没做完
4. 因为 5% 档跑不满一天，答案质量的微小差异在统计上根本看不出来，硬看只会逼出一堆噪声结论

</div>

??? question "Show Answer"
    The correct answer is **D**。这条分界线划错的后果很实际：要么误回滚，要么把问题放过了 50% 档。低档位只盯一两次就能判定的硬指标，真正的质量判断靠冻结的评测集回归。灰度的三条硬约束也要记牢：每档有效样本不少于 500 次、必须经过 50% 档、五个工作日内到达 100%。

    **Concept Tested:** 灰度发布策略

#### 5. 为什么说表格是纯向量检索的天然克星？本章给出的解法是哪三步？

<div class="upper-alpha" markdown>

1. 向量把整张表压成一个平均语义——12 行共 720 字在 800 字的块大小下合成一块，查询只能撞上十二行数字的平均值；解法是每行单独成块、列名拼进每行正文、年与季度与区域写进元数据做硬过滤
2. 因为表格里的数字转成 Markdown 时会丢失精度
3. 因为向量库不支持二维结构化索引，表格只能降级成纯文本处理
4. 因为表格块算出的 embedding 维度和其他块不一致

</div>

??? question "Show Answer"
    The correct answer is **A**。一张 12 行 5 列的季度报表转成 Markdown 后每行约 60 字、12 行共 720 字，在 800 字的块大小下必然合并成一块，这块的向量是所有行的平均值，问"华东区 Q3 毛利率最高吗"自然召回不稳。解法三步缺一不可：列名必须前置写成"季度=Q3；区域=华东；营收=1280万；毛利率=34.2%"，否则向量抓不住；筛选维度必须进元数据做硬过滤，不能靠向量猜。

    **Concept Tested:** 表格数据检索

    **See:** [章节首页](../04-rag-advanced/index.md)

#### 6. 图片内容检索中，文本向量和图像向量必须遵守什么纪律？

<div class="upper-alpha" markdown>

1. 应该混在同一个索引里，一次查询同时命中两种模态，召回更全
2. 不要混在同一个索引：两种模态的向量尺度不同，混检会互相拉低相似度，表现为文字查询召回了图片；要么分两个索引，要么用模态前缀隔开
3. 应该只保留图像向量，文本查询一律改走 OCR 通道
4. 混检没有问题，只要库规模控制在两万张以内就不会出问题

</div>

??? question "Show Answer"
    The correct answer is **B**。混检的典型症状很有迷惑性：文字查询召回了图片、图片查询召回了文字，看着像召回不准，实际是两套向量尺度互相拉低了相似度。修法是分两个索引，或在同一库里给两种模态各拼一段固定的标记串再归一化。另一个可选信号是 OCR，能覆盖约四成含文字的扫描件，但纯文本检索在这个库里等于零命中——入库时根本没写文本。

    **Concept Tested:** 图片内容检索

    **See:** [章节首页](../04-rag-advanced/index.md)

#### 7. 从第二轮起含指代或省略的提问占全部提问的六成，改写后 Top1 命中率从 54% 升到 81%。多轮改写具体要做哪三件事？

<div class="upper-alpha" markdown>

1. 只把指代补成实体，其余部分交给模型自由理解
2. 只带上上一轮已引用的块 id 作为候选补充，避免重复召回
3. 把最近 3 轮全部塞进提示词，让模型自己去找指代对象
4. 补全指代与省略、带上上一轮已引用的块 id 作候选补充、检测同一实体两轮答案矛盾时显式提醒模型以更新后的资料为准

</div>

??? question "Show Answer"
    The correct answer is **D**。三件事都比想象中朴素，但缺一件就掉效果：只补指代不带上轮引用块，会重复召回且答案不连贯；不检测冲突，则同一实体在新旧资料矛盾时模型会两边都答。选 C 是把负担全推给模型——"那它多少钱"这类省略句连人类都要看上下文，模型自己找指代没有可靠依据。

    **Concept Tested:** 多轮检索对话

    **See:** [章节首页](../04-rag-advanced/index.md)

#### 8. 客服场景的重复问题占 38%，缓存键归一化前后答案级缓存命中率分别是多少？

<div class="upper-alpha" markdown>

1. 不做归一化 11%，做完归一化能到 23%，翻倍来自一个几行的正则
2. 11% 提到 14%，归一化的收益很小
3. 23% 降到 11%，归一化反而让命中率变差
4. 归一化前后都是 23%，但缓存命中的延迟降了一半

</div>

??? question "Show Answer"
    The correct answer is **A**。归一化的内容是去标点、去语气词、去空白——"这个能便宜点吗？"和"这个能便宜点吗?"在哈希眼里是两个键，不归一化就永远命中不了彼此。另外缓存键里必须带版本号（本例 `v3`），改过提示词或切分逻辑后升版本，旧缓存自然失效，比逐条删 key 可靠得多。

    **Concept Tested:** 检索缓存优化

    **See:** [章节首页](../04-rag-advanced/index.md)

#### 9. 电商售后的一轮自助解决率从 48% 提到 62%、转人工率从 52% 降到 38% 之后，转人工率还有一个下限，这个下限是多少？低于它说明什么？

<div class="upper-alpha" markdown>

1. 不能低于 18%；低于 18% 不是好事，说明该转人工的场景被自动答复硬扛住了，风险从客服工单转移到客诉和赔付
2. 不能低于 38%；低于 38% 说明自助解决率没做上去
3. 不能低于 5%；低于 5% 说明人工坐席大量闲置
4. 不能低于 30%；低于 30% 属于灰度还没放量完

</div>

??? question "Show Answer"
    The correct answer is **A**。转人工率不是越低越好——低于 18% 说明承诺赔付、改订单、投诉升级这三类意图被自动答复硬扛住了，风险只是从客服工单转移到了客诉和赔付。所以意图表里"优惠与投诉"这一类的检索源直接写"无"、能否自动答复写"不能"、转人工条件写"一律转人工"。成本类指标和风险类指标必须一起看，只盯着自助解决率会把系统调进沟里。

    **Concept Tested:** 客服问答实战

    **See:** [章节首页](../04-rag-advanced/index.md)

#### 10. 运营看板上四项指标越线，但当天只能处置三项。必须立即处置的是哪三项，被淘汰的那一项又为什么出局？

<div class="upper-alpha" markdown>

1. 召回命中率、忠实度、自助解决率，因为它们的绝对跌幅最大
2. 每次成功问答成本（+50.0%）、端到端 P95 延迟（+44.1%）、拒答准确率（−12.1%）；召回命中率虽然也越线，但相对变化只有 −3.3%，与第三名差 8.8 个百分点
3. 凡是越线的指标都必须处置，所以是拒答准确率、召回命中率、忠实度
4. 每次成功问答成本、召回命中率、忠实度，成本和效果两条线都要抓

</div>

??? question "Show Answer"
    The correct answer is **B**。越线不等于紧急，比的是相对变化幅度：成本 +50.0%、延迟 +44.1%、拒答准确率 −12.1% 是前三名。召回命中率从 91% 掉到 88% 同样越线，但相对变化只有 −3.3%，把绝对跌幅当紧急度就会误选。还要记住这张看板最常见的误读：自助解决率掉是效果问题去看负反馈归因，每次成功问答成本涨是架构问题去看缓存命中率和重排档位，两件事画在同一张折线图上最容易读错。

    **Concept Tested:** 知识库运营指标
