#### 1. MCP 的三类原语分别对应哪组方法名前缀？本章的 `order-mcp` 导出了多少项？

<div class="upper-alpha" markdown>

1. 工具 `tools/*`、资源 `resources/*`、提示模板 `prompts/*`；本章导出 8 个工具、3 个资源、1 个提示模板，共 12 项
2. 工具 `functions/*`、资源 `files/*`、提示模板 `templates/*`；本章导出 8 个资源、3 个工具、1 个提示模板
3. 工具 `tools/*`、资源 `resources/*`、提示模板 `templates/*`；本章共导出 12 项
4. MCP 只有工具一种原语，资源与提示模板属于 A2A 协议的范围

</div>

??? question "查看答案"
    正确答案是 **A**。这三组方法名不是术语游戏，它们决定了客户端能不能自动发现能力，也决定了服务端的方法论——写工具按"有没有副作用"归类，写资源按"能不能只读"归类。归错类的后果不是报错，而是模型的调用轨迹变得无法复现。选 B 的数量正好说反：8 个工具、3 个资源、1 个提示模板才是这一套服务的真实规模。

    **考查概念：** MCP协议总览

    **参见：** [章节首页](../06-mcp-tools/index.md)

#### 2. 错误码 `-32001` 与 `-32004` 分别代表什么？客户端该不该重试？

<div class="upper-alpha" markdown>

1. `-32001` 是限流，退避后重试；`-32004` 是资源不存在，不重试
2. `-32001` 是参数非法，重试一次通常就好了；`-32004` 是内部错误，最多重试 1 次
3. `-32001` 是参数非法（Schema 校验失败，重试无用）；`-32004` 是限流（超出单租户配额，退避后重试）
4. `-32001` 是鉴权失败，`-32004` 是上游超时

</div>

??? question "查看答案"
    正确答案是 **C**。MCP 沿用 JSON-RPC 2.0 的错误码体系，前五个 `-32700` 到 `-32603` 是协议保留段位，自定义段位是 `-32099` 到 `-32000`。分好类的意义在于客户端要靠它决定**要不要重试**，所以"能不能重试"是第一分类原则。选 B 看着像折中说法，其实害处最大：同一个错误码给出两种指令，客户端只能选一种实现，选错就会出现无限重试。

    **考查概念：** 错误码规范

    **参见：** [章节首页](../06-mcp-tools/index.md)

#### 3. 代码执行工具的沙箱至少要达到第几层？第三层里哪几条设置不能省？

<div class="upper-alpha" markdown>

1. 至少第一层，语言级的 try/except 与黑名单就够了
2. 至少第三层（进程与命名空间：非特权容器、只读根文件系统、禁 `ptrace`）；另外 `network` 默认 deny 再按白名单放行、`no_new_privs`、容器用完即销毁
3. 至少第四层（微型虚拟机），因为容器迟早会被逃逸
4. 不需要分层，在工具里包一层异常捕获即可

</div>

??? question "查看答案"
    正确答案是 **B**。能跑代码的工具必须有沙箱，这不是可选项——一个没隔离的 `exec_python` 等于把生产数据库口令递给了模型。选 C 的成本判断也不对：第四层每个执行独立内核与网络命名空间，成本太高；但第三层配齐只读根文件系统、网络默认 deny 加白名单、`no_new_privs`、用完即销毁这四条，已经能挡住宿主文件、提权和逃逸尝试。

    **考查概念：** 工具沙箱隔离

    **参见：** [章节首页](../06-mcp-tools/index.md)

#### 4. MCP 和第一章的 function calling 到底差在哪一层？

<div class="upper-alpha" markdown>

1. MCP 是 function calling 的替代品，后者已经废弃
2. function calling 天然跨进程，MCP 只在同进程内使用
3. 两者能力面完全一致，MCP 只是把 JSON 报文换成了 YAML
4. function calling 是模型与代码之间的一次握手，MCP 是工具与进程之间的长期契约；MCP 的工具照样用 function calling 报给模型

</div>

??? question "查看答案"
    正确答案是 **D**。边界很清晰：工具在 10 个以内、只服务一个应用、迭代频繁，用 function calling 更省事；一旦工具要跨应用复用、或者维护权在别的团队，MCP 的收益才盖过成本。本章 `order-mcp` 选 MCP 的核心理由是第二条——维护在订单团队，调用方有 4 个。选 A 会误判成"新协议淘汰老协议"，实际两者是叠加关系。

    **考查概念：** MCP与函数调用对比

    **参见：** [章节首页](../06-mcp-tools/index.md)

#### 5. 工具描述的质量分公式是什么？为什么质量分最高的版本不一定是选对率最高的版本？

<div class="upper-alpha" markdown>

1. \(Q = 0.30 \cdot w_{时机} + 0.30 \cdot w_{边界} + 0.25 \cdot w_{参数} + 0.15 \cdot w_{长度}\)；版本 F 四项齐全但 412 字超出 80 到 200 字的区间，长度项记 0，质量分 0.85 高于 D 的 0.75，选对率 0.83 却低于 D 的 0.85
2. 四项权重各占四分之一；版本 F 因字数超长被整体判零
3. 四项权重相等；版本 F 的质量分与选对率都是六个版本里最高的
4. 长度项只按字数线性给分，写得越长分越高，所以 F 最优

</div>

??? question "查看答案"
    正确答案是 **A**。可用区间是 80 到 200 字：低于 80 字说明信息不足，高于 200 字说明模型要在一堆废话里找信号。F 就是这条规则与实际效果之间的缺口——四项标准全齐却因为塞了 412 字而被长度项归零，选对率反而掉到 0.83。选 D 的"越长越好"正是要避免的误解：description 是写给模型的说明书，不是给人看的注释。

    **考查概念：** 工具Schema设计

    **参见：** [章节首页](../06-mcp-tools/index.md)

#### 6. 租户身份与 JWT 解码的正确做法是什么？

<div class="upper-alpha" markdown>

1. 把租户身份做成工具参数，由模型填写 `tenant_id`，服务端只做格式校验
2. 只要走了 HTTPS 就不需要令牌，租户身份从请求体里取
3. 租户身份只能从服务端解析出的令牌里取；JWT 解码必须显式指定算法白名单，写类工具单独校验 `scopes` 而读类工具不需要
4. `algorithms` 参数可以省略，省略等于接受令牌自己声明的算法，配合 HTTPS 依然安全

</div>

??? question "查看答案"
    正确答案是 **C**。如果 `query_order` 带一个 `tenant_id` 参数，模型只要填错或被诱导填别人的值就是一次越权——等于把越权开关交给模型。`algorithms` 白名单也不能省，省略它等于接受令牌自声明的算法，这是 JWT 最经典的漏洞。选 D 看着有 HTTPS 兜底，但算法协商漏洞发生在签名校验环节，传输层加密救不了。

    **考查概念：** 工具鉴权机制

    **参见：** [章节首页](../06-mcp-tools/index.md)

#### 7. 单次失败率 0.30、每次超时上限 800 毫秒、退避基数 200 毫秒倍数 4。在 5000 毫秒的用户等待预算下应该选哪个方案？

<div class="upper-alpha" markdown>

1. 方案 C：成功率 0.973 最高，多等一会儿也值得
2. 方案 B：总耗时上限 3400 毫秒、成功率 0.910；方案 C 虽成功率 0.973，但总耗时 7400 毫秒已超预算 2400 毫秒
3. 方案 A：不重试，800 毫秒，0.700，把等待时间全部留给用户
4. 方案 D：熔断联动时 800 毫秒、成功率可以做到 0.973

</div>

??? question "查看答案"
    正确答案是 **B**。最终成功率 = 1 − 0.30 的 (k+1) 次方，总耗时上限 = 调用次数 × 800 毫秒 + 退避等待之和。第三次重试还能再捞 0.063 的成功率，却要多花 4000 毫秒，这笔买卖在任何交互式场景里都不划算。记住那句结论：**超时的意义是保护服务，不是提高成功率**。选 D 的问题在于熔断省的是等待不是成功率，它不会把 0.910 变成 0.973。

    **考查概念：** 工具超时熔断

    **参见：** [章节首页](../06-mcp-tools/index.md)

#### 8. 客户端接入 2 个 MCP 服务器、共 34 个工具时，必须做哪两件事？

<div class="upper-alpha" markdown>

1. 把 34 个工具的全量描述原样塞进上下文，靠模型自己挑
2. 加命名空间 `server__tool` 防撞名，但不做预算裁剪，因为裁剪一定会漏工具
3. 按工具名字母序排列，让模型按名字猜用途
4. 加 `order__search`、`knowledge__search` 这样的命名空间防撞名，再按服务器相关性把 34 个工具裁到 12 个、描述从约 21,000 token 降到约 7,400 token

</div>

??? question "查看答案"
    正确答案是 **D**。命名空间解决撞名——两个服务器都提供 `search`，模型选哪个就是抛硬币；预算裁剪解决上下文——工具描述是要进模型上下文的，全量 21,000 token 超出了可接受范围。选 B 把裁剪当成纯粹的损失，其实它是让更多相关工具能被看见的手段；真正的做法是按服务器相关性裁，而不是平均砍。

    **考查概念：** MCP客户端集成

    **参见：** [章节首页](../06-mcp-tools/index.md)

#### 9. 把 `order-core` 的 11 个 HTTP 接口封装成 MCP 工具，正确的拆法是什么？

<div class="upper-alpha" markdown>

1. 按业务动作收敛成 3 个工具；参数只暴露模型需要判断的，上游要什么由服务端补全；物流接口挂了就把 `available` 置 false 降级返回，而不是整次调用失败
2. 11 个接口一一对应导出 11 个工具，把 OpenAPI 的字段原样倒给模型
3. 把所有查询合并成 1 个万能工具，参数全塞进一个 `args` 对象由模型自由填写
4. 保留 11 个接口，只在 description 里写清"请传形如……"，靠提示词约束格式

</div>

??? question "查看答案"
    正确答案是 **A**。按"一次业务动作"切工具而不是按"一个接口"切——`query_order` 合并了 4 个读接口，模型选错工具的概率随之下降。降级而非失败尤其重要：物流接口挂了就把 `available` 置 false，让模型告诉用户"物流信息暂不可用"，比整次调用失败好。选 B 的后果很具体：模型面对一个 40 个字段的接口不知道该传哪些，绝大多数调用都缺参数。

    **考查概念：** 内部API转MCP

    **参见：** [章节首页](../06-mcp-tools/index.md)

#### 10. 灰度两周 41.3 万次调用、总成功率 0.964，其中 `-32001`（参数非法）占全部失败的 38%。这个结果指向哪一项优先动作？

<div class="upper-alpha" markdown>

1. 优先扩容服务端，因为参数错误偏多说明模型侧压力大
2. 优先改 description 与收紧 Schema，因为模型调错参数才是工具失败的第一大原因，比服务端故障高出 3 倍
3. 优先给 `-32001` 加自动重试，一般重试几次就好了
4. 优先下线调用量最低的那个工具，先缩小暴露面

</div>

??? question "查看答案"
    正确答案是 **B**。按错误码分组统计失败率，正是为了区分"模型调错了"（`-32001`、`-32003` 偏高）和"服务端不稳"（`-32005`、`-32006` 偏高）——这两类修法完全不同，一个改 description 和 Schema，一个查上游。选 A 是把结果读反了：参数错误偏多恰恰说明失败发生在模型与服务端契约的接缝上，加机器解决不了契约问题。

    **考查概念：** 工具可观测埋点

    **参见：** [章节首页](../06-mcp-tools/index.md)
