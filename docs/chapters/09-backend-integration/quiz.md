#### 1. 建表时必须守住的三条纪律是什么？

<div class="upper-alpha" markdown>

1. 主键用数据库默认生成、时间戳一律 `timestamptz`、金额一律 `numeric` 不要 `float`
2. 主键用自增整数、时间戳用 `timestamp`、金额用 `float` 以便计算
3. 主键用 UUID、时间戳用 `datetime`、金额用 `decimal` 但统一小数位
4. 主键手工指定、时间戳用字符串、金额也用字符串以彻底避免精度问题

</div>

??? question "Show Answer"
    The correct answer is **A**。浮点数在金额上迟早差一分钱，而差一分钱就等于财务对不上账。另一条容易事后补不回来的是幂等键：消息表的 `client_msg_id` 必须在写接口那一步就留好，等线上发现重复对话再补是补不回来的。选 C 看着规范，但把时间戳用 `datetime` 存会在跨时区时留下隐患。

    **Concept Tested:** 数据表建模

    **See:** [章节首页](../09-backend-integration/index.md)

#### 2. RLS 要正常工作，依赖哪三样东西？

<div class="upper-alpha" markdown>

1. 前端在请求里传 `tenant_id`，服务端做一次比对
2. 在服务端中间件里统一拼过滤条件
3. 表上开启 RLS、至少一条策略、一个能取到身份的函数；三样缺一不可，只写策略不开开关是最致命的配置
4. 每个业务接口单独调用权限校验 SDK

</div>

??? question "Show Answer"
    The correct answer is **C**。策略写在开启之前是合法的，但开启之前策略不生效——`create policy` 成功不代表隔离生效，最典型的表现是全表对该角色可见，而你的功能测试用自己的数据跑得好好的。验证也不能靠"我测过了"，要靠一条用别人令牌执行的查询，返回非 0 就阻断发布。选 A 把越权开关交给了客户端，只要前端参数被改就是一次泄漏。

    **Concept Tested:** 行级安全策略

    **See:** [章节首页](../09-backend-integration/index.md)

#### 3. 会话持久化的读侧裁剪，本章的三个数字是什么？

<div class="upper-alpha" markdown>

1. 单条消息平均 620 个 token，14 轮历史约 4,340 个 token，只是略微超出预算
2. 单条消息平均 620 个 token，14 轮会话历史约 17,360 个 token，是 4,000 预算的 4.34 倍；裁剪后保留最近 3 轮共 6 条消息、3,720 个 token
3. 14 轮历史约 2,100 个 token，本来就落在预算内，不需要裁剪
4. 裁剪按轮数保留最近 14 轮，与 token 预算无关

</div>

??? question "Show Answer"
    The correct answer is **B**。超窗时模型侧的自动截断丢的往往正是开头那句关键上下文，所以裁剪规则是"最近 3 轮无条件保留，更早的从新到旧按预算回填，放不下就跳过"——第 4 轮放不下（3,720 + 620 = 4,340 超预算），所以实际回填 6 条。超过 30 轮的长会话不靠裁剪硬扛，而是在第 30 轮追加一条 `role='system'` 的摘要消息压到 300 个 token 左右。

    **Concept Tested:** 会话持久化

    **See:** [章节首页](../09-backend-integration/index.md)

#### 4. "认证"与"授权"在这个平台上是怎么交汇的？租户归属应该存在哪里？

<div class="upper-alpha" markdown>

1. 存在前端本地存储里，方便组件直接判断
2. 由业务代码在查询时拼接，只要拼对就行
3. 前端本地解码令牌后可以直接据此判定权限，省掉服务端校验
4. 认证决定令牌里有哪些声明，RLS 与存储策略只读这些声明；租户归属只应存在于令牌里，而令牌签发后无法收回，归属一变必须立刻作废旧令牌

</div>

??? question "Show Answer"
    The correct answer is **D**。理解了这个结构，"租户归属"就不该存前端、不该存会话变量、更不该由业务代码拼接。选 C 的错误在于解码不等于验签：前端解码只供界面控制用，任何权限判定都必须以服务端验签后的声明为准。更隐蔽的是选 A 那类做法——令牌一旦签发无法收回，租户归属一变更而旧令牌还在，刚换租户的用户就能读到旧租户数据，而且每一条策略都会认为他完全合法。

    **Concept Tested:** 认证与授权

    **See:** [章节首页](../09-backend-integration/index.md)

#### 5. 关于 pgvector 的余弦距离与维度，正确的说法是哪一个？

<div class="upper-alpha" markdown>

1. `<=>` 返回的是距离，取值 0 到 2，越小越近，相似度是 1 − d；所以"相似度不低于 0.75"就是距离小于等于 0.25
2. `<=>` 返回的是距离，取值 0 到 1，越小越近，相似度就是距离本身
3. `<=>` 返回的是相似度而不是距离，越大越近
4. 1024 维可以随时改，改完重建索引即可，历史向量不受影响

</div>

??? question "Show Answer"
    The correct answer is **A**。距离和相似度差一个 `1 −`，写过滤条件时错这一处会把"相似度不低于 0.75"变成"距离不低于 0.75"，结果是把最不相关的块全捞回来。选 B 同样是符号搞反。选 D 忽略了维度写死在列定义里这个约束——换嵌入模型就必须改这一处并重建索引，这也是它最大的约束同时是最省心的地方：不可能出现一半 768 维一半 1024 维的脏数据。

    **Concept Tested:** 向量扩展pgvector

    **See:** [章节首页](../09-backend-integration/index.md)

#### 6. 共享库加 RLS 与独立库之间，隔离强度与成本的真实关系是什么？

<div class="upper-alpha" markdown>

1. 两者隔离强度相同，因为策略都在数据库里执行
2. 独立库一定更划算，因为它没有固定费用
3. 共享库单租户 48.32 元、独立库 93.65 元；隔离强度是一条坡——共享库是"能防住手滑、挡不住误配"，独立库才连误配都越不过去，判断标准是这个租户出了事故你要赔多少钱
4. 混合方案永远是成本最低的，不需要分档

</div>

??? question "Show Answer"
    The correct answer is **C**。分档规则要写死成可执行的判断：合同年化超 50 万元、明确要求物理隔离、或属于金融医疗等强合规行业，走独立库；其余全走共享库。本章 3 个租户里澜海贸易是医疗器械供应商走独立库，账单变成 190.29 元，比全共享多 45.33 元——这笔钱不该按性价比评价，它是合规的价格。选 B 的错在忽略固定费用：68 元的数据库实例在 1 个租户时全额由它承担，到 12 个租户才被摊薄到每租户 5.67 元。

    **Concept Tested:** 租户隔离设计

    **See:** [章节首页](../09-backend-integration/index.md)

#### 7. 订单落库时金额字段的正确处理方式是什么？本章的自动入库比例是多少？

<div class="upper-alpha" markdown>

1. 允许模型直接给出 `amount_total`，只要是合法数字即可
2. 金额一律不采信模型输出：模型只抽 `sku` 与 `qty`，单价由商品主数据回填、总额由系统求和，再拿模型给的总额比一次；本月 4,200 张草稿自动入库 3,780 张（90.0%），转人工 420 张（10.0%）
3. 只校验必填与格式，业务合理性全部交给人工判断
4. `pay_method` 必须由模型给出明确枚举，不允许出现"待确认"

</div>

??? question "Show Answer"
    The correct answer is **B**。拿模型自己给的总额和系统求和的比一次是很好的自检：比不上就说明它编了数，这类幻觉占校验失败的 12%。选 D 反了——`pay_method` 无法判定时取"待确认"并转人工，枚举写进 Schema 并允许这个值，比逼模型猜好得多。转人工的 420 张原因分布也是稳定的，最大一项是 SKU 不存在或写错（34%），修法是把商品主数据清单放进提示词。

    **Concept Tested:** 订单业务落库实战

    **See:** [章节首页](../09-backend-integration/index.md)

#### 8. 最近一次恢复演练暴露了哪两件真事？为什么向量索引不单独备份？

<div class="upper-alpha" markdown>

1. `pg_dump` 的主要失败原因是磁盘空间不足，与恢复时长无关
2. 向量索引必须单独备份，否则恢复后检索结果会和表对不上
3. RPO 实测 5 分钟、恢复耗时 34 分钟，说明备份方案已经完美
4. `storage.objects` 的策略不在 `pg_dump` 范围内、恢复后必须重跑策略脚本，备份文件也不能放在同一个项目里；向量索引可以从 `knowledge_items` 重建，186,000 条约 2 分 40 秒，比备份索引文件更省事

</div>

??? question "Show Answer"
    The correct answer is **D**。演练的价值不在"测过了"，而在于它暴露真事：策略是代码不是数据，不在备份里；备份放在同一个项目里等于没备份。选 B 恰好搞反了——HNSW 索引可以重建，备份索引文件反而容易出现"索引文件和表对不上"的经典损坏。选 C 把一次演练当成了终点，演练只是把问题提前到有人盯着的时候发现。

    **Concept Tested:** 数据备份恢复

    **See:** [章节首页](../09-backend-integration/index.md)

#### 9. 换嵌入模型并迁移到新库时，正确的做法是什么？

<div class="upper-alpha" markdown>

1. 固定六步：建新库结构与策略并逐表验证 0 行泄漏 → 灌基础数据 → 全量导入历史且向量留空 → 开双写且一致率不低于 99.95% → 重算回填向量并校验检索条数一致 → 切读、观察 24 小时后停旧写；双写失败只入差异队列记账，绝不回滚主流程
2. 大爆炸切换，停机 20 到 40 分钟，窗口内的新数据人工补即可
3. 双写时新库写失败要回滚旧库，保证两边一定一致
4. 先切读到新库，失败再改回旧库读
</div>

??? question "Show Answer"
    The correct answer is **A**。双写方案最常见的翻车方式就是新库写失败去回滚旧库——那会把一次辅助迁移的失败放大成主业务的失败，正确的动作是记差异队列。选 B 的停机窗口内新数据要人工补，正是大爆炸方案的固有代价。算笔账也知道这笔钱不是问题：186,000 条向量、每条 400 个 token，全量重算 37.2 元、按 8 路并发约 5 分钟跑完，问题只在于排期——迁移窗口通常只有一小时，重算和校验必须分开跑。

    **Concept Tested:** 数据迁移方案

    **See:** [章节首页](../09-backend-integration/index.md)

#### 10. 后端账单里哪一项是真正的大头？三条降本动作该按什么顺序做？

<div class="upper-alpha" markdown>

1. 数据库实例是大头，应从降配实例开始优化
2. 边缘函数调用 26 万次是账单主体，应把模型调用搬进边缘减少后端开销
3. 出网才是大头：边缘函数出网 139.68 元占 48.7%，因为响应体被边缘节点完整转发了一遍；改成 302 跳转到对象存储的预签名地址可省 105.12 元；实时消息与边缘函数调用都在免费额度内，不该为省 0.14 元去改架构
4. 存储单价是出网的 16 倍，应优先压缩存储

</div>

??? question "Show Answer"
    The correct answer is **C**。用量最"热闹"的两项一分钱没花——实时出站 0.17 GB 远低于 2 GB 免费额度、边缘函数调用 26 万次远低于 50 万次；真正的账单在流量上。选 A 把固定成本当成可优化项，68 元的数据库实例优化后仍占优化后总价的 37.8%，但它换来的可靠性是任何优化都换不到的。做完后月度费用从 286.71 元降到 179.63 元、每会话 0.0100 元，加上模型成本 0.0125 元后，后端占了单会话总成本的 44.4%。

    **Concept Tested:** 后端成本估算

    **See:** [章节首页](../09-backend-integration/index.md)
