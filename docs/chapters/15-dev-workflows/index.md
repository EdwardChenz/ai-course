## 一、把编码从"写代码"改成"带判据地改代码"

### ORCA开发范式

ORCA 开发范式可以按"AI 时代开发利器"来定位：它不是又一个补全插件，而是一条独立的 Agentic 编码范式。核心主张是把编码重组成一条有分工、有机器可验证判据的流水线，人从"唯一的产出者"退到"设计者与放行者"。它的骨架是四条：角色分工、任务可验证、完成判据机器化、人工只保留两个介入点（方案确认、验收放行）。

一条最小的任务单长这样。注意它和普通待办清单的差别：每一项都带一个能被程序判定的完成判据，`done` 不由人说了算。

```markdown
# 任务：为订单查询接口补充分页参数

- [ ] 角色分工
      规划者产出接口签名草案；实现者只允许改 `api/orders.py` 与 `tests/test_orders.py`
- [ ] 完成判据（机器可判定）
      `pytest tests/test_orders.py -q` 通过
      `mypy api/orders.py` 无新增错误
      新增用例覆盖 page 与 page_size 越界两例
- [ ] 禁止事项
      不改数据库结构；不新增第三方依赖
- [ ] 人工介入点
      方案确认：接口签名草案先由人过一遍
      验收放行：三条判据全绿才允许合入
```

要诚实说明两点。第一，这条范式的名称缩写与官方定义以项目官方文档为准，本书只讲它代表的这条思路，不替任何项目做定义。第二，它真正可迁移的只有"判据机器化"这一条：只要你的完成判据还是"看着挺对"，Agent 必然产出你不敢合的代码，效率优势会被审查成本吃掉。

### Agentic编码总览

Agentic 编码有三种形态，混着用是效率损失的主要来源。判据很简单：这件事跨几个文件、错了能不能被测试逮到，就决定用哪一种。

| 形态 | 发起方式 | 作用域 | 完成判据 | 适合的任务 | 典型失败 |
|---|---|---|---|---|---|
| 补全 | 你在编辑器里按下触发 | 光标处的一小段 | 你看着顺眼 | 胶水代码、单个函数内的重构、注释与文档 | 补全的代码没有测试兜底，错了要到运行时才发现 |
| 代理 | 你给出任务，Agent 自行读文件、改代码、跑检查 | 跨文件的任务 | 类型检查加测试加 lint 全绿 | 跨模块功能、新增接口、批量改名与补测试 | 任务边界不清导致它顺手改了不该改的地方 |
| 重构 | 你给出不变量，Agent 在约束下重写 | 一个文件或一个模块 | 原有测试全绿加新增测试全绿 | 消除重复、拆分长函数、升级接口调用 | 不变量没写清，Agent 判断"顺手改一下"于是改了语义 |

与传统补全工具的差别集中在三点。**作用域**上，补全停在光标处，代理会自己去找相关文件并决定改哪几处。**输出形态**上，补全给的是候选片段，代理给的是带自证过程的改动——它跑过的检查会留下日志。**验收方式**上，补全的验收是"看着顺眼"，代理的验收只能是机器判据，因为你自己并不知道它会改出什么。

!!! mascot-thinking "形态选错，损失的是审查时间"
    ![墨墨思考中](../../img/mascot/thinking.png){ class="mascot-admonition-img" }
    对二十行胶水代码启动一次完整代理，等于派一个人先读三页需求再交两行代码，审查成本比手写还高。反过来用补全去改跨五个文件的功能，则必然漏改。这两种误用都会得到同一个体感：AI 编码"不太好用"。

三种形态的完成判据表述：补全是"类型检查通过加上你确认没有语义变化"；代理是"类型检查、测试、lint 三项全绿，且改动范围不超出任务单声明的文件"；重构是"原有测试全绿加新增边界用例全绿，且禁止顺手改语义"。

## 二、四种实践流派

这四套实践不是同一维度的四个选项，它们各自解决的是"Agent 编码往哪走"这个问题的不同侧面。本书按方法论介绍它们代表的思路，**具体用法、命令与版本以各项目官方文档为准**；本章不列任何未经文档确认的接口与参数。

### Superpowers实践

Superpowers 类实践的思路是**把编码能力打包成可复用的流程**，让 Agent 先按既定步骤做事——先确认需求、先写验收标准、先写测试、再写实现——而不是拿到需求就直接吐代码。可迁移的那一条是：**把团队的编码约定写成流程约束，而不是写进提示词里求 Agent 自觉**。约定写进提示词是软的，改一次提示词就可能绕过去；写进流程约束是硬的，绕不过去。

### Mattpocock工作流

Mattpocock 的实践代表另一种思路：**小步、强类型、每件事一个提交**。可迁移的有三条：把类型标注当文档也当测试，让编译器承担一部分评审；让 Agent 生成的是类型与测试，人负责语义；把改动切成小提交，使每一次评审的认知负担可控。第三条在 Agent 时代更值钱——大改动的评审本来就贵，Agent 让"一次提交只做一件事"更容易执行。

### Ponytail协作模式

Ponytail 协作模式的思路是**人机分工与两个介入点**：人出意图、审方案、放行，Agent 承接批量与重复。可迁移的是它的介入点设计——在动手前确认一次方案、完成后确认一次验收，中间不打扰。少一次打断，Agent 的单轮上下文就不会被人为切断，重试与跑偏的概率都跟着降。

### Ecc工程实践

Ecc 工程实践关注的是**把 Agent 的产出纳入常规工程约束并沉淀为资产**：产出的代码要过与人工代码相同的 CI、类型检查与评审清单；有效的提示词、可复用流程、批量脚本要提交进仓库，让个人经验变成团队资产。可迁移的是"资产化"这一步——不沉淀的技巧只存在于一个人的会话记录里，人一走就没了。

| 流派 | 核心机制 | 可迁移的一条做法 | 最容易踩的坑 |
|---|---|---|---|
| Superpowers 实践 | 把编码约定打包成流程约束 | 约定写成硬约束，不写进提示词里求自觉 | 流程写太细，Agent 每步都在等确认，效率反而更低 |
| Mattpocock 工作流 | 小步、强类型、单提交 | 一次提交只做一件事 | 把三个修复塞进一个提交，评审时谁也审不动 |
| Ponytail 协作模式 | 人机分工加两个介入点 | 动手前确认方案、完成后确认验收，中间不打断 | 介入点之外的事放手太多，错误要等验收才发现 |
| Ecc 工程实践 | Agent 产出走常规 CI，经验沉淀进仓库 | 把可复用的提示词与脚本提交进版本管理 | 只在个人机器上生效，团队其他人用不上 |

!!! mascot-tip "约定的强度决定了产出的稳定性"
    ![墨墨提示技巧](../../img/mascot/tip.png){ class="mascot-admonition-img" }
    判断一条约定该不该搬进 Skill 或工程约束，看它被违反时会不会有人发现。会有人发现的（lint 会红、测试会失败、CI 会挂）就硬起来；不会有人发现的（"代码要易读"）就留在代码评审里讨论，别指望 Agent 每次都记得。

## 三、把经验写成 Skill

### Skill机制设计

Skill 是把一次性提示词变成可复用资产的形式，核心结构是三层：**入口文件 `SKILL.md`**、**frontmatter 元数据**、**渐进式披露的 `references/` 附件**。渐进式披露的含义是：模型默认只读 `SKILL.md`，需要哪一部分再去读对应的引用文件，这样上下文里不会常年躺着一堆用不到的规则。

一条 Skill 该写什么、不该写什么，界线很干脆：

| 该写 | 不该写 | 理由 |
|---|---|---|
| 什么时候该用我这个 Skill | 通用的编程常识 | 使用场景写不清，模型会在无关任务里触发它 |
| 硬性规则（必须、禁止、量化阈值） | 需要时才查的细节清单 | 硬规则必须在入口，细节放引用文件按需加载 |
| 冲突时的优先级裁决 | 同一事实的第二份副本 | 两处副本必然漂移，改一处忘一处 |
| 一个可复制的最小示例 | 完整的参考手册 | 示例是为了让模型照着写，手册只会挤占上下文 |
| 指向 `references/` 的引用路径 | 把 references 内容抄进入口 | 抄进来等于取消渐进式披露，上下文立刻膨胀 |

关键原则是**单一事实源加引用而非复制**。下面这个例子是本书吉祥物放置规则的 Skill：入口只放触发条件与三条硬规则，合法类型名清单、计数判据与反例表全部推到 `references/`，入口只留路径。

```markdown
---
name: mascot-placement-rules
description: 判断一章该放几个吉祥物、放在哪、用哪个姿态。写或修改章节正文前必读。
---

# 吉祥物放置规则

## 何时使用
写或修改任何章节正文时使用。判断三件事：总数、位置、姿态类型。

## 硬性规则（必须满足）
```

## 四、把重复劳动脚本化

### 飞书CLI提效

飞书 CLI 的价值不在于"能在命令行发消息"，而在于**把文档、表格、多维表格与消息的批量操作脚本化**：一次导出、一次改名、一次按条件统计，都从两小时的点选变成一条命令。典型场景有三个：批量导出周报文档为 Markdown 供 Agent 检索、批量给表格补齐缺失字段、按条件统计并汇总成表。

```bash
#!/usr/bin/env bash
# 批量把指定空间的周报文档导出为 Markdown，供后续检索与复盘使用
# 子命令名、鉴权方式与参数以官方文档为准，下例为示意写法
set -euo pipefail

SPACE_ID="oc_xxxxxxxxxxxx"          # 空间标识
OUT_DIR="./weekly-reports"          # 导出目录
mkdir -p "$OUT_DIR"

# 先列出文档清单，导出前人工确认一次要拉哪些，避免把无关文档一起拉下来
lark-cli docs list --space "$SPACE_ID" --format json > "$OUT_DIR/_list.json"

# 逐篇导出；单篇失败不终止整批，失败项记进失败清单
: > "$OUT_DIR/_failed.txt"
while IFS= read -r doc_id; do
  if ! lark-cli docs export --doc "$doc_id" --format markdown \
        --output "$OUT_DIR/$doc_id.md"; then
    echo "$doc_id" >> "$OUT_DIR/_failed.txt"
  fi
done < <(jq -r '.items[].doc_id' "$OUT_DIR/_list.json")

echo "导出完成，失败 $(wc -l < "$OUT_DIR/_failed.txt") 篇，详见 _failed.txt"
```

### Office CLI提效

Office 文档这一类的痛点更具体：格式转换、批量替换、批量重算、以及从表格里抽数进报告。脚本化之后这些操作可重复、可回归，比在图形界面里手工做快几个数量级。

```powershell
# 批量把 xlsx 转成 csv，并把生成的 csv 汇总到一个目录，供后续分析与归档
# 参数名与可用格式以对应工具的官方文档为准，下例为示意写法
$ErrorActionPreference = "Stop"
$src = "C:\data\reports"
$dst = "C:\data\reports\csv"
New-Item -ItemType Directory -Force -Path $dst | Out-Null

Get-ChildItem -Path $src -Filter *.xlsx | ForEach-Object {
    $target = Join-Path $dst ($_.BaseName + ".csv")
    try {
        # 单个文件失败不影响整批，失败项集中记到 _failed.txt
        & soffice --headless --convert-to csv --outdir $dst $_.FullName | Out-Null
        if (-not (Test-Path $target)) { throw "未生成目标文件" }
        Write-Host "转换成功: $($_.Name)"
    }
    catch {
        "$($_.Name)`t$($_.Exception.Message)" | Out-File `
            -FilePath (Join-Path $dst "_failed.txt") -Append -Encoding utf8
    }
}
```

把这类脚本沉淀下来之后，它们还顺手产出了一份复盘骨架：批量任务跑完的日志、失败清单、耗时，本身就是复盘文档里"指标对比"与"踩坑"两节的原材料。
