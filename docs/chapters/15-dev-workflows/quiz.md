#### 1. ORCA 开发范式的骨架是哪四条？最小任务单和普通待办清单的差别在哪？

<div class="upper-alpha" markdown>

1. 角色分工、任务可验证、完成判据机器化、人工只保留两个介入点（方案确认、验收放行）；任务单上每一项都带能被程序判定的完成判据，`done` 不由人说了算
2. 角色分工、任务可验证、模型自评、人工随时介入
3. 模型一次性生成完整实现，人只做最终验收，其余环节全自动
4. 官方定义以本书给出的四条骨架为准，可以直接照搬

</div>

??? question "Show Answer"
    The correct answer is **A**。诚实说明两点：这条范式的名称缩写与官方定义以项目官方文档为准，本书只讲它代表的思路；但它真正可迁移的只有"判据机器化"这一条——只要你的完成判据还是"看着挺对"，Agent 必然产出你不敢合的代码，效率优势会被审查成本吃掉。选 D 把"讲思路"变成了"替项目做定义"，这正是本章反复提醒要避免的。

    **Concept Tested:** ORCA开发范式

    **See:** [章节首页](../15-dev-workflows/index.md)

#### 2. Agentic 编码的三种形态各自的作用域与完成判据是什么？

<div class="upper-alpha" markdown>

1. 补全、代理、自动化部署
2. 单文件编辑、跨文件代理、全量重构
3. 补全是光标处的一小段、判据是类型检查通过；代理是跨文件任务、判据是类型检查加测试加 lint 三项全绿；重构是一个文件或模块、判据是原有测试全绿加新增边界用例全绿
4. 代理、重构、全自动流水线

</div>

??? question "Show Answer"
    The correct answer is **C**。判据很简单：这件事跨几个文件、错了能不能被测试逮到，就决定用哪一种。选 A 和 D 把"部署"和"流水线"混进了形态分类——它们是交付环节，不是编码形态。选 B 的问题是把作用域和意图混为一谈：单文件编辑也可能是跨语义的重构，而全量重构这个说法本身与实际的重构形态不对应。

    **Concept Tested:** Agentic编码总览

#### 3. Skill 的核心结构是什么？最关键的那条原则怎么表述？

<div class="upper-alpha" markdown>

1. Skill 是单层的 `SKILL.md`，所有规则都写在入口里
2. Skill 入口应放完整的参考手册，模型需要时自己找
3. 同一事实应该在入口和 `references/` 里各存一份，方便查找
4. Skill 的核心是渐进式披露：入口只放触发条件、硬性规则与冲突裁决，细节清单推到 `references/`；关键原则是单一事实源加引用而非复制

</div>

??? question "Show Answer"
    The correct answer is **D**。渐进式披露的含义是模型默认只读 `SKILL.md`，需要哪一部分再去读对应的引用文件，这样上下文里不会常年躺着一堆用不到的规则。选 B 和 C 会让上下文立刻膨胀——把 references 内容抄进入口等于取消渐进式披露，两处副本则必然漂移。吉祥物放置规则那个例子把这个收益讲透了：姿态类型名和图片文件名是两套命名，混用会渲染成无样式，而合法清单只有一份。

    **Concept Tested:** Skill机制设计

    **See:** [章节首页](../15-dev-workflows/index.md)

#### 4. Superpowers 类实践的核心思路是什么？本章认为它可迁移的是哪一条？

<div class="upper-alpha" markdown>

1. 把编码能力打包成可复用流程，可迁移的一条是：把团队的编码约定写成流程约束，而不是写进提示词里求 Agent 自觉——写进提示词是软的，改一次提示词就可能绕过去，写进流程约束是硬的
2. 把编码约定写进提示词，因为提示词是唯一能被模型稳定读取的载体
3. 先写验收标准再写测试，这个顺序必须强制
4. 让 Agent 先输出方案再写代码，方案要人工逐行审

</div>

??? question "Show Answer"
    The correct answer is **A**。判断一条约定该不该硬起来的标准也很干脆：看它被违反时会不会有人发现。会有人发现的（lint 会红、测试会失败、CI 会挂）就硬起来；不会有人发现的（"代码要易读"）就留在代码评审里讨论，别指望 Agent 每次都记得。选 C 和 D 把顺序和审查粒度当成硬约束，但流程写太细会让 Agent 每步都在等确认，效率反而更低。

    **Concept Tested:** Superpowers实践

    **See:** [章节首页](../15-dev-workflows/index.md)

#### 5. "把一个 400 行函数拆成三个，行为必须一字不变"应该选哪种形态？完成判据怎么写？

<div class="upper-alpha" markdown>

1. 代理；判据是类型检查、测试、lint 三项全绿
2. 重构；判据是原有测试全部通过加新增边界用例通过，且禁止顺手改语义——一旦语义被改动，旧测试的通过就不能证明行为未变
3. 补全；判据是类型检查无新增错误
4. 重构；判据是"你确认语义没变"

</div>

??? question "Show Answer"
    The correct answer is **B**。这一题的关键在有没有旧测试当护栏——有，重构才有安全网。顺手修 bug 是禁止事项，不是加分项。选 A 是最容易犯的误判：代理形态会顺手扩大改动范围，而"行为必须一字不变"恰恰要求它别碰语义。选 D 的判据等于没写，和本书反复强调的"判据机器化"直接冲突。

    **Concept Tested:** Agentic编码总览

    **See:** [章节首页](../15-dev-workflows/index.md)

#### 6. 写一条 Skill 时，哪些该写进入口、哪些不该写？

<div class="upper-alpha" markdown>

1. 该写通用编程常识；不该写什么时候该用这个 Skill
2. 该写需要时才查的细节清单；不该写硬性规则
3. 该写把 `references/` 的内容抄进入口；不该写引用路径
4. 该写：什么时候该用、硬性规则（必须、禁止、量化阈值）、冲突时的优先级裁决、一个可复制的最小示例、指向 `references/` 的引用路径；不该写：通用编程常识、细节清单、同一事实的第二份副本、完整参考手册、抄进来的 references 内容

</div>

??? question "Show Answer"
    The correct answer is **D**。界线很干脆：使用场景写不清，模型会在无关任务里触发它；细节清单必须放引用文件按需加载，抄进入口就等于取消了渐进式披露。选 A 把使用场景这条最关键的触发条件剔掉了，选 B 把硬规则挪出了入口，选 C 则把渐进式披露彻底废除。

    **Concept Tested:** Skill机制设计

    **See:** [章节首页](../15-dev-workflows/index.md)

#### 7. 把 Office 文档的批量操作脚本化之后，除了"快几个数量级"之外还顺手得到了什么？

<div class="upper-alpha" markdown>

1. 批量任务跑完的日志、失败清单与耗时本身就是复盘文档里"指标对比"与"踩坑"两节的原材料，所以这类脚本沉淀下来是可重复、可回归的
2. CLI 只适合一次性任务，重复劳动仍然应该手工做
3. 文档格式统一之后就不需要再脚本化
4. 脚本化之后可以取消所有人工确认环节，直接批量执行

</div>

??? question "Show Answer"
    The correct answer is **A**。这就是"把重复劳动脚本化"的第二重收益：脚本的运行痕迹本身就是复盘的原材料，等于把复盘的成本也一并降下来了。选 C 的前提不成立——Office 文档的痛点恰恰是格式转换、批量替换、批量重算这些格式不统一带来的手工活。选 D 忽略了这类脚本最该保留的一步：导出前先列清单人工确认要拉哪些。

    **Concept Tested:** Office CLI提效

    **See:** [章节首页](../15-dev-workflows/index.md)

#### 8. Ponytail 协作模式的两个介入点怎么设计？少一次打断意味着什么？

<div class="upper-alpha" markdown>

1. 介入点越多越好，每个阶段都确认一次才安全
2. 介入点越少 Agent 越不容易跑偏：动手前确认一次方案、完成后确认一次验收，中间不打扰；少一次打断，单轮上下文就不会被人为切断，重试与跑偏的概率都跟着降
3. 人不应参与方案确认，只负责最后验收
4. 只保留"动手前确认方案"这一个介入点就够，验收交给自动化判据

</div>

??? question "Show Answer"
    The correct answer is **B**。前提是"介入点之外的事放手"也要有分寸——介入点之外放手太多，错误要等到验收才发现，那时已经浪费了一整轮。选 A 与 Agent 的工作方式相冲突：每阶段打断等于人为切断单轮上下文，跑偏概率反而升高。选 D 只保留了介入点里价值更高的那一半：动手前确认方案恰恰是防止整轮跑偏的最后一道人工关口。

    **Concept Tested:** Ponytail协作模式

    **See:** [章节首页](../15-dev-workflows/index.md)

#### 9. Ecc 工程实践关注的是什么？它最容易踩的坑是什么？

<div class="upper-alpha" markdown>

1. Agent 产出的代码应当比人工代码更宽松，因为它的产出速度快
2. 有效的提示词属于个人经验，不必提交进仓库
3. 只在个人机器上生效也没问题，团队暂时用不上
4. Agent 产出的代码要走与人工代码相同的 CI、类型检查与评审清单，有效的提示词、可复用流程与批量脚本要提交进仓库；不沉淀的技巧只存在于一个人的会话记录里，人一走就没了

</div>

??? question "Show Answer"
    The correct answer is **D**。"资产化"这一步是这一流派唯一可迁移的东西：走完常规 CI 只是不退步，把经验沉淀进仓库才产生复利。选 A 的代价极高——Agent 的改动速度快，审查也快，人更容易累，判据必须更硬而不是更松。选 B 和 C 描述的正是这一流派点名要避免的坑。

    **Concept Tested:** Ecc工程实践

    **See:** [章节首页](../15-dev-workflows/index.md)

#### 10. 飞书 CLI 的价值到底在哪里？三个典型场景是什么？导出时还有哪一步不能省？

<div class="upper-alpha" markdown>

1. 价值在于"能在命令行发消息"，省去打开客户端的步骤
2. 脚本化导出周报文档时直接批量拉取整个空间即可，不需要先列清单确认
3. 价值在于把文档、表格、多维表格与消息的批量操作脚本化——一次导出、一次改名、一次按条件统计，从两小时的点选变成一条命令；三个典型场景是批量导出周报供检索、批量补齐缺失字段、按条件统计汇总，且导出前必须先列清单人工确认要拉哪些
4. 只要脚本能跑通，就可以取消所有人工确认环节

</div>

??? question "Show Answer"
    The correct answer is **C**。"能在命令行发消息"只是表面，真正的价值是把批量操作从点选变成一条命令，而且这些操作可重复、可回归。选 B 和 D 取消的正是脚本化最该保留的一步——先列清单人工确认，避免把无关文档一起拉下来。选 A 是把工具的形态当成了价值。

    **Concept Tested:** 飞书CLI提效

    **See:** [章节首页](../15-dev-workflows/index.md)
