#### 1. 静态批处理与连续批处理的差别体现在哪几个数字上？

<div class="upper-alpha" markdown>

1. 静态批处理一批必须全部算完才能进下一批，批耗时由最长请求决定（2,000 除以 80 等于 25.0 秒）、吞吐 1.28 QPS、算力利用率仅 16%；连续批处理任何请求算完立刻出队、空出的位置立刻补新请求，吞吐 3.84 QPS（3.0 倍）、P50 从 25.0 秒降到 4.2 秒、利用率 89%
2. 静态批处理更公平，每个请求算完就立刻返回
3. 连续批处理能缩短单个长请求的生成时间
4. 连续批处理要求每批请求长度一致，否则无法调度

</div>

??? question "Show Answer"
    The correct answer is **A**。静态批处理的 84% 算力浪费来自一个无法回避的事实：同批请求的输出长度差异极大，平均 320 token、P90 900、最长 2,000，一个 2,000 token 的请求会让同批另外 31 个全部陪等 25 秒。选 C 是最需要警惕的误解：连续批处理解决的是"算力浪费"，不是"模型太慢"——逐 token 生成那一段与输出长度严格成正比，谁来调度都得一个 token 一个 token 算。

    **Concept Tested:** 连续批处理原理

#### 2. 量化到底压什么、不压什么？本章的三档并存结论是什么？

<div class="upper-alpha" markdown>

1. 量化会同时压权重、KV Cache 与激活值，所以能直接解决并发瓶颈
2. INT4 的正确率 0.85 高于 INT8 的 0.88，因为位数越少越省
3. 量化只压权重与 KV Cache、不压激活值；FP16 正确率 0.89、INT8 0.88（掉 0.01）、INT4 0.85（掉 0.04，恰好压在线上、余量归零）；因此量化是分层的：主生成模型 FP16、摘要与改写 INT8 副本、意图分类 INT4
4. 量化是无损压缩，量化后不需要复测正确率

</div>

??? question "Show Answer"
    The correct answer is **C**。因为不压激活值、也压不掉 KV，所以量化救不了并发瓶颈——70B 量化到 INT4 权重能从 140 GB 降到 35 GB，但 8 路并发的 KV 仍有 40 GB，单卡照样装不下。选 B 的方向错了：位数越少质量损失越大，质量损失量取决于任务难度而不是模型规模。

    **Concept Tested:** 量化选型

    **See:** [章节首页](../14-inference-deploy/index.md)

#### 3. 前缀缓存与语义缓存的区别是什么？各自的收益与风险是什么？

<div class="upper-alpha" markdown>

1. 语义缓存零质量损失，应当优先开启
2. 前缀缓存有质量风险，语义缓存没有
3. 两者收益完全相同，只是实现方式不同
4. 前缀缓存复用模型内部 KV Cache、零质量损失，命中率 0.94 时首 token P50 从 620 降到 390 毫秒；语义缓存复用最终答案、有误命中风险，阈值 0.92 时误命中 1.2%，降到 0.90 会升到 4.7%，所以只对只读问答启用

</div>

??? question "Show Answer"
    The correct answer is **D**。语义缓存的阈值不能靠感觉调——0.92 这个数字来自 200 条真实重复提问的实测，制度类问答错一条就是业务事故，所以宁可少命中也不放宽。选 A 和 B 都把两层的风险搞反了。还要注意前缀缓存的隐性纪律：2,700 token 的固定前缀必须不含时间戳、不含随机 ID、不含动态租户名，任何一个字节的漂移都会让整段缓存失效。

    **Concept Tested:** 缓存语义层

#### 4. 显存估算里权重与 KV Cache 的关系是什么？7B FP16 在 72 GB 预算下会发生什么？

<div class="upper-alpha" markdown>

1. 显存 = 权重 + KV Cache + 10% 的算子与碎片；KV 随并发与上下文线性增长而权重是常数，7B FP16 权重 14 GB、每 token KV 0.5 MB，所以 32 路并发配 4,096 上下文要 64 GB KV、合计 78 GB 超预算 6 GB
2. 只要权重装得下就能跑，并发可以上线后再调
3. KV Cache 只与并发有关，与上下文长度无关
4. 量化只降权重显存，KV Cache 完全不受影响

</div>

??? question "Show Answer"
    The correct answer is **A**。这两行的形状就是所有容量陷阱的来源：权重装得下，但并发一上来 KV Cache 就把预算撑爆。7B 权重只占 72 GB 预算的 19.4%，看起来宽裕，实际 32 路并发配 4,096 上下文就要 78 GB，进程在压测第二分钟就被 OOM 杀掉。任何显存估算表都必须包含那 10% 开销，漏掉它你会得到一个"刚好装下"然后在生产里 OOM 的结论。

    **Concept Tested:** 显存估算方法

    **See:** [章节首页](../14-inference-deploy/index.md)

#### 5. 容量规划的两个公式算出来，本项目的部署形状是什么？

<div class="upper-alpha" markdown>

1. 实例数等于峰值 QPS 直接除以单实例实测吞吐，安全系数 0.7 可按需临时调整
2. 实例数 = 3.2 除以 (3.84 乘 0.7) 向上取整 = 2 台；显存约束下最大并发 = (72.0 减 14) 除以每序列 2 GB = 29 路，所以 `--max-num-seqs` 设 24 留 17% 余量；结论是 2 台 2 卡实例、单台并发 24 路、峰值有效吞吐 5.38 QPS
3. 最大并发应直接设成 29，把显存预算用满
4. 实例数与显存无关，只按峰值 QPS 除以单实例吞吐向上取整即可

</div>

??? question "Show Answer"
    The correct answer is **B**。这两个数是纯算术，但两处取整都有理由：`--max-num-seqs` 设 24 而不是 29 是留给碎片与长短不均的余量；安全系数固定 0.7 不允许临时调，毛峰来了临时调系数等于拿可用性赌运气。算完再回看"要不要自建"：盈亏平衡在日均 27,313 次，当前 12,000 次差 2.28 倍，所以本章的顺序是先把网关和用量统计建起来。

    **Concept Tested:** 容量规划

#### 6. 多模型路由的判据应该依据什么？本章的三档路由与三条纪律是什么？

<div class="upper-alpha" markdown>

1. 应按模型自评决定，让模型判断自己能不能干；实测准确率只有七成，仍比请求特征可靠
2. 应把所有流量都发到大模型，靠提示词要求它对简单问题也简短回答
3. 路由判定不需要落日志，成本归因时事后补即可
4. 判据必须是请求侧特征而不是模型自评；三档为复杂规划 12%、常规问答 68%、简单分类 20%，加权成本 0.208 即全量走大模型的 20.8%；三条纪律是兜底链不能成环、路由判定结果必须落日志、路由规则变更要走灰度

</div>

??? question "Show Answer"
    The correct answer is **D**。让模型判断自己能不能干准确率只有七成，这不够支撑成本分摊。选 C 看着省事，实际会在成本归因时说不清某条请求为什么走了小模型——而分账的四维权重里部门占 40%。还有一个容易被忽略的细节：分类这步先用规则做一遍，本章 62% 的分类请求命中纯规则，根本不调模型。

    **Concept Tested:** 多模型路由策略

    **See:** [章节首页](../14-inference-deploy/index.md)

#### 7. 压测的三档各测什么？语料为什么不能用同一句固定输入？

<div class="upper-alpha" markdown>

1. 只测容量档就够了，因为容量档已经包含全部信息
2. 用同一句固定输入最稳定，缓存全命中说明系统健壮
3. 必记指标只有吞吐 QPS 一项，其余都是参考值
4. 三档各测一件不同的事：档一基线测裸延迟、档二容量找吞吐拐点（3.84 涨到 4.02 QPS 后持平，拐点在 24 路）、档三长尾测 P99 与稳定性；语料必须取真实 trace 的长度分位数，固定输入会把前缀缓存顶到接近全命中，测出的首 token P50 会比线上低 300 毫秒以上

</div>

??? question "Show Answer"
    The correct answer is **C**。选 B 是压测最贵的错：拿同一句话跑一万遍，前缀缓存几乎全命中，测出来的首 token P50 会比线上低 300 毫秒以上，门禁误判为通过，上线第二天全被打回来。档三的实测 P99 从 4.60 秒升到 5.10 秒、第 26 分钟首次出现 KV OOM 重试，这两件事在档一档二里根本测不出来——这就是三档不能省的原因。

    **Concept Tested:** 压测方法

    **See:** [章节首页](../14-inference-deploy/index.md)

#### 8. 灰度设计的重点为什么全在回滚？回滚该怎么预置？

<div class="upper-alpha" markdown>

1. 灰度的意义就是慢慢放流量，回滚可以临场再设计
2. 影子流量阶段应该返回真实结果给用户，否则测不出问题
3. 灰度的意义是放量的每一步都还能退回：回滚开关必须存在、能在 5 分钟内拨动、且必须演练过；做法是在网关路由层注册新旧两个模型名，灰度只改 `model_name` 的权重分布，回滚就是把权重改回 100%，本章实测 3 分 40 秒
4. 配置与模型版本应绑定成一个发布单元，回滚时一起退才干净

</div>

??? question "Show Answer"
    The correct answer is **C**。回滚开关先演练再灰度——开关本身坏掉的灰度等于一次真实故障。选 D 会让回滚退不干净：配置与模型版本必须能分开退。选 B 的影子流量阶段是 0% 只记录不返回，这是它的定义；真把影子流量返回给用户，就等于把未验证的版本放出去。记住每次回滚必须留记录，三个月后那次线上抖动才说得清。

    **Concept Tested:** 灰度与回滚

    **See:** [章节首页](../14-inference-deploy/index.md)

#### 9. "主备全不可用"时的降级应该返回什么？熔断的判定条件是什么？

<div class="upper-alpha" markdown>

1. 应返回一句抱歉，让用户稍后重试，保持接口形状统一
2. 降级不是一句抱歉而是一条有产出的路径——返回检索命中的 3 条制度原文加一句明确说明；四条动作按执行顺序是重试、退避、熔断、降级，熔断条件是同一后端连续 10 次失败、窗口 60 秒、期间全部流量走兜底后端
3. 熔断只应针对可重试故障，参数错误也要重试到成功为止
4. 故障转移与第一章的重试退避熔断是完全不同的机制，需要单独实现一套

</div>

??? question "Show Answer"
    The correct answer is **B**。降级要让用户拿到一半价值，也要让业务侧看到一条可统计的降级事件，而不是一次沉默的失败。选 A 丢掉了降级的全部意义。选 C 是本章反复强调的那一处真功夫：把"可重试的故障"和"不可重试的故障"分清楚，不然熔断器会对着一个参数错误重试到天荒地老。选 D 也不对——骨架就是第一章那一套，只是作用对象从函数换成模型后端。

    **Concept Tested:** 故障转移机制

#### 10. 限流与配额为什么必须分成两组阈值？超限后的处置有什么区别？

<div class="upper-alpha" markdown>

1. 两者应合并成一组阈值，因为它们的处置动作相同
2. 租户配额超限也应返回 429，让前端按 `Retry-After` 自动重试
3. 全局限流应直接设成单实例实测上限 25 QPS，不留余量
4. 限流是临时的（全局 24 QPS、桶容量 120，超限进队列最长等 30 秒）；配额是永久的（月度耗尽必须返回"本月财务部额度已用尽，请联系管理员"这类可读错误，而不是一个 429 让前端反复重试）

</div>

??? question "Show Answer"
    The correct answer is **D**。两个理由：限流等一会儿就好，所以要排队和退避；配额加钱才有，所以必须返回能让人读懂的错误——一个 429 会让前端在额度已经耗尽的情况下反复重试，把一次预算问题变成一场无效风暴。选 C 少了那 10% 给自身抖动的余量，桶容量 120 也就是 \(B = R \times\) 突发窗口 5 秒 的结果，不是随手取的整数。

    **Concept Tested:** 限流与配额

    **See:** [章节首页](../14-inference-deploy/index.md)
