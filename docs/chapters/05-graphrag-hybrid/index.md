图数据库和向量数据库解决的是两类问题。向量检索按语义相似度找块，擅长“这段话在讲什么”；图谱把实体和关系显式存下来，擅长“这个实体和那个实体怎么连着”。你的系统真正变好，不是因为加了图谱，而是因为把“关系”这一维从向量空间的隐式相似，变成了可查询、可计数、可沿边遍历的显式结构。

本章最贵的一课在第一节：判断该不该上图谱。判断错了，后面两周的抽取流水线和每个月的运维费用全是白花。

## 一、图谱建模与部署

### 图谱建模基础

建模是把业务里的“对象”和“对象之间的有向关系”翻译成节点标签（Label）与关系类型（Relationship Type），并规定每种节点和关系能带哪些属性。建模不是数据库设计练习，它决定了后面所有查询能不能写得出来——建模时没区分“供应商”和“承运商”，等你写“这批货走哪条航线”时就得回头洗数据。

判断要不要上图谱，看四条信号，任一条不成立就别上：答案在一段话里、问法措辞多变，是单文档语义检索；答案是“谁和谁有关系”，是关系密集；答案要沿关系链走两跳以上，是多跳推理；答案是一组计数或排名，需要去重与聚合。跨文档反复提及的实体也属于强信号——同一家公司在几十份研报里被提到，向量会把它的片段散落在各处的 Top20 里拼不回来。

反向信号同样要认：如果你 80% 的问题是“这份合同里违约金怎么算”，图谱只增加延迟和运维账单。判断方法不是拍脑袋，而是翻第四章那套评估集，统计问题里含“哪些”“谁”“多少”的比例，再人工数一遍答案需要跨几段原文才能拼出来。

| 你的问题长什么样 | 该用什么 | 判断依据 |
|---|---|---|
| 答案在一段话里，问法措辞多变 | 纯向量加关键词 | 单文档语义检索，第三章那套已经够 |
| 答案是“谁和谁有关系” | 图谱局部检索 | 关系密集，关系本身就是查询条件 |
| 答案要沿关系链走两跳以上 | 图谱 | 多跳推理，例如谁给谁供货、谁和谁有共同供应商 |
| 答案是一组计数或排名 | 图谱聚合 | 需要去重与聚合，向量无法计数 |
| 实体在几十份文档里被反复提及 | 图谱与向量并行 | 跨文档实体归一 |

建模的三条纪律。第一，节点只放“有独立业务含义、能用稳定 ID 指称”的对象，动作和事件不要单独建节点，挂成关系属性（`since`、`effective_date`）或独立事件节点。第二，每种关系必须带 `confidence` 和 `evidence`（指向原文证据块 ID），没有证据的边在排查和复核时是负债。第三，节点属性用扁平标量（字符串、数值、数组），嵌套结构放关系或单独属性表，别把整段 JSON 塞进一个属性里图谱就没法用了。

下面是一套金融场景的最小 Schema，作为后面章节的参照物：

| 节点标签 | 关键属性 | 关系类型 | 方向与关键属性 |
|---|---|---|---|
| `Company` | `id`、`name`、`ticker` | `BELONGS_TO` | Company 指向 Industry，带 `weight` |
| `Org` | `id`、`name`、`kind` | `COVERS` | Org 指向 Company，带 `weight`、`since` |
| `Industry` | `name`、`level` | `REPORTS` | Company 指向 Metric，带 `value`、`unit`、`year` |
| `Metric` | `name`、`unit` | `DOWNGRADE` | Analyst 指向 Company，带 `rating` |

### Neo4j部署与驱动

Neo4j 是原生图数据库：存储层就是图，不做“行存图再在应用层拼关系”的绕路，因此沿边遍历三跳和全表扫描是两回事。它的数据模型只有三种东西：节点、关系、属性，加上用来加速的属性索引（schema constraint）。

开发期永远先用 Docker 起单机，把内存调小，跑通再谈生产：

```yaml
# docker-compose.yml 图数据库开发实例，堆内存留出给文件系统缓存
services:
  neo4j:
    image: neo4j:5.20-community     # 钉死小版本，绝不用 latest
    container_name: neo4j-dev
    ports: ["7474:7474", "7687:7687"]   # 7474 是浏览器界面，7687 是 Bolt 协议
    environment:
      - NEO4J_AUTH=neo4j/your-password      # 首次启动后立刻改掉默认密码
      - NEO4J_server_memory_heap_max__size=2G
      - NEO4J_server_memory_pagecache_size=1G
    volumes:
      - neo4j-data:/data             # 命名卷：容器重建图谱不丢
volumes:
  neo4j-data:
```

Python 驱动用官方 `neo4j` 包，三条纪律：连接用单例 `GraphDatabase.driver`（内部有连接池，不要每次请求新建）、所有查询参数化（用 `$name` 传值，禁止字符串拼接）、批量写用事务或 `execute_write` 包起来而不是循环单发。

```python
import os
from neo4j import GraphDatabase

_driver = GraphDatabase.driver(
    os.environ["NEO4J_URI"], auth=(os.environ["NEO4J_USER"], os.environ["NEO4J_PASSWORD"]),
)

def upsert_company(tx, cid: str, name: str, ticker: str) -> None:
    # MERGE 保证幂等：同一条重复写入不会产生第二个节点
    tx.run(
        "MERGE (c:Company {id: $id}) SET c.name = $name, c.ticker = $ticker",
        id=cid, name=name, ticker=ticker,   # 参数化，杜绝拼接
    )

with _driver.session(database="neo4j") as session:
    session.execute_write(upsert_company, "C0001", "宁德时代", "300750")
```

参数化不只是防注入。在 Cypher 里用字符串拼 `id` 值时，计划缓存会失效——同一段模板因字面量不同被当成不同查询缓存十万条，这是很多 Neo4j 服务上线后突然变慢的真凶。社区版单机可承载约 200 万节点、5000 万关系；再往上就得读企业版的集群与在线备份能力，成本量级见第五节的运营成本表。

## 二、从文本到图：抽取管线

### 实体抽取流程

实体是有独立业务含义、能用稳定 ID 指称的对象；把它从一段文本里挑出来并落成节点，就是实体抽取。四条属性是刚性的：稳定 ID（跨文档能对上同一个东西）、名称、别名列表、置信度。`mention_count`（被多少文档提及过）和 `source_docs`（哪些文档）是后续消歧和排查的关键，别省。

抽取流程固定五步，每步都能单独测：

1. **切块**：沿用第二章的切分器，但块要比向量检索的块更大——800 到 1200 字符，因为关系常常跨句（主语在上一句、谓语在下一句）。
2. **提示词**：把上面的 Schema 表塞进提示词，给 2 个 few-shot 示例，要求只输出 JSON。
3. **结构化校验**：用第一章的 JSON Schema 卡住格式，不通过就带着错误信息重试，最多两次。
4. **归一化**：把同义写法映射到同一个 ID，这是下一节实体消歧的活。
5. **落库**：`MERGE` 按 ID 去重写入。

```python
import json
from pydantic import BaseModel, Field

class ExtractedEntity(BaseModel):
    name: str = Field(description="实体名称，与原文一致")
    type: str = Field(description="实体类型，必须取自 Schema：Company/Org/Industry/Metric")
    aliases: list[str] = Field(default_factory=list)
    confidence: float = Field(ge=0.0, le=1.0)
    evidence_chunk: str = Field(description="原文证据块 ID")

async def extract_entities(chunk_text: str, chunk_id: str, llm) -> list[dict]:
    """从单个块抽实体，返回待入库的候选记录"""
    raw = await llm.acall(build_extract_prompt(chunk_text), max_retry=2)  # 结构化输出 + 重试
    items = json.loads(raw)["entities"]
    out = []
    for it in items:
        try:
            ent = ExtractedEntity(**it)          # 校验先行，脏数据在这里就被挡住
        except Exception:
            continue
        out.append({**ent.model_dump(), "chunk_id": chunk_id})   # 证据块 ID 必须带上
    return out
```

### 关系抽取流程

关系是带方向、类型、置信度、证据三元组，第三要素是时间。它比实体抽取难，原因是自然语言里的关系表达经常不是“一个主语一个谓语一个宾语”：句子有并列、承前省略、条件从句、否定。关系抽取真正的工作量在这四种句式上，不在提示词调优上。

边的属性是刚性的：`type`（关系类型）、`confidence`、`evidence`（证据块 ID）、`since`（首次成立时间）、以及业务权重（下一节讲）。否定和条件句必须显式落成属性，不要丢在提示词里就算完：

```cypher
// 条件关系落成带门槛的边，查询时才能复现原文的条件
MERGE (d:Drug {id: 'N02BE01'})
MERGE (dz:Disease {id: 'I10'})
MERGE (d)-[r:CONTRAINDICATED {since: date('2024-05-01')}]->(dz)
SET r.confidence = 0.92,            // 抽取置信度
    r.grade = 'A',                  // 证据等级：医学域专用
    r.condition = 'eGFR < 30',       // 原文里的触发条件，原样保留
    r.evidence = 'chunk_88213';      // 指回原文块，出错时能追责
```

抽取量的账要提前算。金融研报场景（第六节展开）按每 800 字一块切、每块一次调用估算：

| 项 | 数值 | 口径 |
|---|---|---|
| 文档量 | 800 份研报 | 三年积累 |
| 原始字数 | 240 万字 | 平均每份 3000 字 |
| 切块数 | 3000 块 | 每块 800 字 |
| 抽取调用次数 | 3000 次 | 每块一次调用 |
| 单次调用成本 | 0.002 元 | 示意价，按小模型批量档估 |
| 首次全量耗时 | 40 分钟 | 串行，每次调用 0.8 秒 |
| 产出实体 | 1.2 万个 | 平均每块 4 个 |
| 产出关系 | 2.4 万条 | 平均每块 8 条 |

数字自洽关系可以这样验算：3000 块乘以 4 等于 1.2 万个实体，3000 块乘以 8 等于 2.4 万条关系；3000 次调用乘以 0.002 元等于 6 元，一次性抽取成本不到十块钱——这就是为什么图谱的瓶颈从来不是调用费，而是维护它的人力。

!!! mascot-warning "别让模型自由发挥关系"
    ![墨墨提醒注意](../../img/mascot/warning.png){ class="mascot-admonition-img" }
    提示词里不写死关系类型清单，模型就会自己发明“关联”“相关”“涉及”，然后你的图里出现上百种同义关系，任何一条查询都得写成几百个 `OR`。Schema 表要在提示词里贴全，并在校验层用枚举挡一道。

### 实体消歧方法

消歧要解决的是：同一个东西的不同写法归到一个 ID，不同的东西不能归到一起。中文场景里前者是主要矛盾——同一家公司有中文名、英文名、代码、简称（宁德时代 / CATL / 300750），指代同一个节点；后者是风险项，“新华书店”和“新华书店集团”合并错了会让后面所有聚合计数都偏。

三档策略，按投入从小到大：

- **别名表**（必备）：人工维护一张别名到 ID 的表，抽取出的名字先查表，命中即映射。这一档准确率最高、成本最低，能覆盖 60% 到 70% 的重复。
- **向量近邻**：把实体名向量化，同名同类型的候选里取余弦相似度最高且超过阈值的合并。阈值必须调高（0.95 以上），宁可漏合并不要错合并——错合并会静默污染计数。
- **模型裁决**：把候选混淆的少数几对丢给模型判断“是不是同一个”，只处理别名表和向量都没把握的边界情况。

```python
def resolve(name: str, etype: str, alias_map: dict, name_vec: dict, threshold=0.95):
    """先查别名表，再退到向量近邻；两者都不过就当作新实体"""
    key = f"{etype}:{name}".lower()
    if key in alias_map:                       # 第一档：别名表命中，直接返回
        return alias_map[key]
    best, best_score = None, 0.0
    for cand_id, vec in name_vec.get(etype, {}).items():   # 第二档：只在同类型里比，避免跨类误合
        score = cosine(name_embedding(name), vec)
        if score > best_score:
            best, best_score = cand_id, score
    if best_score >= threshold:                # 阈值高于此值一律不合并，宁可漏
        alias_map[key] = best
        return best
    return new_entity_id(etype, name)          # 新实体：建 ID 并登记别名，等人工抽检
```

### 关系权重设计

不是所有边都同等可信，权重就是用来表达这个差别的。三种成分，按重要度排：

1. **来源可信度**：来自已审核的结构化数据（如工商登记、主数据）权重 1.0，来自模型抽取的权重取 `confidence`。
2. **证据数量**：同一对实体被 5 篇独立文档提到，比只在一篇里提到可靠得多。取 `1 - (1 - p)^n`（n 是独立证据数，p 是单次可信度），n 越大越接近 1，增长很快。
3. **时效衰减**：关系会过期。用半衰期做衰减，`w = w_0 × 0.5^(Δt / H)`，H 是半衰期，Δt 是距今天数。

组合公式就是三者相乘，最终落在 0 到 1：

\[ w(r) = w_{source} \times \left(1 - (1 - p)^{n}\right) \times 0.5^{\Delta t / H} \]

算一个具体例子：某条边来自模型抽取，单次可信度 `p = 0.7`，被 3 篇独立文档提到，半衰期取 540 天，事实发生在 180 天前：

\[
1 - (1 - 0.7)^3 = 1 - 0.027 = 0.973, \quad 0.5^{180/540} = 0.5^{1/3} \approx 0.794
\]

\[
w = 0.7 \times 0.973 \times 0.794 \approx 0.541
\]

同一对实体的另一条边来自人工审核的数据库（`w_source = 1.0`）、只有 1 条证据（`1 - 0.3 = 0.7`）、同样 180 天，得到 `1.0 × 0.7 × 0.794 ≈ 0.556`——审核来源的小胜。查询里按权重过滤（`WHERE r.w >= 0.5`）时，这两条都过；而只有单条模型证据又比较老的边会被自然淘汰，省掉你手写的一堆例外规则。

!!! mascot-tip "权重先做成属性，别做成逻辑"
    ![墨墨提示技巧](../../img/mascot/tip.png){ class="mascot-admonition-img" }
    把“这条边算不算数”写成边上的一个数值属性，阈值放进配置。这样你改阈值不用重跑抽取，也能在排查时一条 Cypher 就捞出所有被淘汰的边。写在代码 `if` 里的规则，等你想调的时候已经改不动了。

### 冲突事实处理

图谱里同一个实体的同一个属性出现两个互斥值，是常态而不是异常：两份研报说 2025 年产能增速 35.2% 和 34.0%，可能都对（统计口径不同），也可能一条是错的。**冲突永远不要在抽取阶段悄悄丢掉一个**，丢了你就再也查不出图谱错在哪。

处理顺序是四步：先判性质（是时间不同、口径不同，还是真矛盾），再判权威度（来源可信度和发布时间），再决定动作（并存、择一、或标冲突挂人工），最后留痕。三个必须落成属性而不是删边的理由：删除不可逆、冲突往往是业务规则的信息（比如两家口径不同恰恰说明需要按口径分别检索）、人工复核队列需要知道有多少待处理。

```python
CONFLICT_RULES = [
    # 同一属性、同一时间、口径不同：并存，用 scope 区分，查询时按 scope 过滤
    ("CONFLICT_SCOPE",  lambda a, b: a.year == b.year and a.scope != b.scope),
    # 同一属性、时间不同：取较新的一条，旧值写入历史关系而不是覆盖
    ("SUPERSEDE",       lambda a, b: a.year != b.year),
    # 同一属性、同时间、同口径：真矛盾，标 CONFLICT 并进人工队列，谁都不删
    ("CONFLICT_REVIEW", lambda a, b: a.year == b.year and a.scope == b.scope),
]

def on_conflict(new_edge: dict, old_edge: dict) -> str:
    for name, pred in CONFLICT_RULES:                 # 顺序即优先级，别调换
        if pred(new_edge, old_edge):
            if name == "CONFLICT_REVIEW":
                flag_for_human_review(new_edge, old_edge)   # 两条都留，只打标记
            return name
    return "MERGE"
```

真矛盾的比例通常不高：3000 个块抽 2.4 万条关系，落到同实体同属性上的冲突大概几十条量级（示意数据）。用一张人工复核表兜住就行，不必上自动仲裁模型——把预算花在提高抽取精度上，收益更高。

## 三、图上的算法

### 社区发现算法

图的稠密度决定了不能整体遍历，社区发现把图按连接密度切成若干块，每块叫一个社区。算法上用 Louvain 或它的改良版 Leiden：交替执行“把节点搬到连接更密的社区”和“合并相邻社区”两步，直到模块度不再提升。模块度衡量的是“社区内部的边，比随机划分多了多少”，取值在 -1 到 1 之间，越大说明社区划分越符合图的内在结构：

\[ Q = \sum_{c} \left( \frac{l_c}{m} - \left(\frac{d_c}{2m}\right)^2 \right) \]

四个符号的意思：`l_c` 是社区 c 内部边的条数，`m` 是全图边数，`d_c` 是社区 c 内所有节点的度数之和，`2m` 是全图度数的两倍。后面那个平方项是“减掉随机也能凑出这么多内部边”的部分，所以社区大小不能无限增大——社区太大，平方项会把它拉回来。调节这个偏好的旋钮是 `resolution`，取 1.0 是默认起点，本章示例图谱取 1.0。

社区发现的价值在全局检索：把每个社区的内部事实压成一段摘要，再给摘要做向量，跨文档的“共性问题”就能被检索到。层级化做法分三层：level 0 是实体节点，level 1 是关系聚合，level 2 是社区摘要。本章示例图谱（1.2 万实体、2.4 万关系）在 `resolution = 1.0` 下分成约 96 个 level 2 社区，平均每社区 125 个实体，跨社区关系占 22%（以上为示意数据）。

| 层级 | 内容 | 存储位置 | 什么时候用 |
|---|---|---|---|
| level 0 | 实体节点及其属性 | Neo4j 节点 | 局部检索的事实来源 |
| level 1 | 社区内部关系的聚合摘要 | Neo4j 节点 `CommunitySummary` | 局部检索的上下文补充 |
| level 2 | 社区级跨文档摘要 | 向量库（可同步一份到 Neo4j） | 全局检索的召回单元 |

社区规模是运营指标，不是越小越好：单个社区实体数低于 5 说明切碎了，摘要里没有足够上下文；高于 200 说明摘要把不相关的事实搅在一起。按这个标准，上面的 96 个社区需要定期看碎片率，方法见本节的排查部分。

### 多跳推理查询

跳数是从种子节点出发走了多少条边，一跳是直接邻居，两跳是邻居的邻居。**多跳推理是图谱相对向量检索唯一的、不可替代的能力**——向量检索无论怎么调参，都不可能保证“走了且仅走了两条 COVERS 边然后回公司”这种带路径约束的查询。

跳数换来的代价是节点数增长。沿上面那套图谱算，从宁德时代出发：

| 跳数 | 本跳新增节点 | 累计节点 | 累计边 |
|---|---|---|---|
| 0（种子） | 1 | 1 | 0 |
| 1 | 5 | 6 | 5 |
| 2 | 15 | 21 | 28 |
| 3 | 42 | 63 | 96 |

（示意数据，按本节示例图谱的邻接结构估算）1 跳的 5 个邻居是 2 家研究所（入边）、1 个行业（出边）、2 个指标（出边）。从这里能读出两条硬约束：**跳数上限设 3，单种子每跳扇出上限设 50**。超过 3 跳的结果集对用户已经没有解释力（他记不住三层间接关系），超过 50 个邻居的子图塞进上下文会挤爆预算。

```cypher
// 显式写死两跳：可命中索引、可命中查询计划缓存，性能比变长关系稳定
MATCH (a:Company {ticker: '300750'})-[:COVERS]->(org:Org)
MATCH (org)-[:COVERS]->(peer:Company)
WHERE peer.ticker <> '300750'
RETURN DISTINCT peer.name AS 共同被覆盖公司, org.name AS 共同机构
ORDER BY 共同机构 LIMIT 20
```

这段查询回答“和宁德时代被同一家机构覆盖的公司有哪些”，结果是 2 跳：先从宁德时代逆着 `COVERS` 走到中信证券研究所，再顺着 `COVERS` 走到宁德时代（同一个起始机构分两条边，不构成路径）。真正要避免的是把跳数写成变量，见下一节的 Cypher 部分。

!!! mascot-warning "别图省事写变长关系"

### 子图检索策略

子图检索的产出不是“答案”，而是“答案所在的那一小块图”，再交给模型组织成话。所以策略的目标是**用最小的子图覆盖足够的事实**，而不是把图尽可能多地捞回来。四种手段按收益排：

1. **关系白名单**：先决定这条查询允许走哪些关系类型。比如“供应商风险”这条线只允许 `SUPPLIES`、`MADE_BY`、`BOM_PARENT`，`COVERS` 走进去只会带出噪声。
2. **权重剪枝**：`WHERE r.w >= 0.5` 砍掉低置信边，按上一节的公式口径，和手工维护黑名单相比省事且能自动适应数据变化。
3. **扇出封顶**：单种子每跳最多 50 个邻居，超出按权重降序取前 50 并在返回里标“已截断”，让模型知道信息不完整。
4. **社区子树**：问题落在某个社区内时，先取社区 ID 再取成员，一次查询拿到内聚的一组事实。

```python
# 子图检索的统一入口：白名单 + 权重剪枝 + 扇出封顶三件事在同一个查询里完成
CYPHER_SUBGRAPH = """
MATCH (seed:Company {ticker: $ticker})-[r:SUPPLIES|MADE_BY*1..2]-(n)
WHERE type(r) <> 'COVERS' AND coalesce(r.w, 0.6) >= $min_w
RETURN seed.ticker AS seed, collect(DISTINCT n)[..$cap] AS nodes,
       [x IN collect(r) WHERE x.w < 0.5 | coalesce(x.evidence,'?')][..3] AS 被剪掉的边
"""
# 变长关系只在“关系类型列表 + 跳数”都显式写清时使用，且节点数由 cap 强制封顶
```

返回格式也要定死，三选一：三元组列表（最省 token、模型最擅长推理）、邻接表（结构清楚但冗余）、自然语言摘要（最费 token，适合全局检索的社区层）。局部检索默认用三元组列表，一行一条，模型不容易把边读错方向。

## 四、图谱与向量的融合检索

### 图谱与向量融合

融合的前提认知：**向量库和图谱各有各的强项，应该并行召回而不是二选一**。向量库回答“这段话讲了什么”，图谱回答“这个实体和谁有关系”。把两者塞进同一个排序列表，需要一个可比的分数，这是下一节的事；这一节先解决更前面的问题——图谱侧产出的东西怎么变成可检索的文本。

三种形态，成本和噪声递增，按推荐顺序排：

| 形态 | 做法 | 噪声 | 适合 |
|---|---|---|---|
| 实体向量 | 把实体名加一句描述 embed，存进向量库 | 低 | 实体名与业务说法不一致时（CATL 对“宁德”） |
| 图增强块 | 检索到文本块后，把它的核心实体及其一跳邻居拼成上下文附加上去 | 中 | 需要答案里的关系也说清楚 |
| 路径向量 | 把一条路径序列化成文本再 embed | 高 | 路径模式高度固定且问法模板化 |

```python
async def hybrid_retrieve(question: str, k_vec: int = 20, k_sub: int = 5):
    """向量路召回 20 个文本块，图谱路召回 5 个子图，两者合并后交给排序层"""
    seeds = await llm.extract_entities(question)          # 问句先抽实体，作为图谱种子
    subgraphs, texts = [], []
    for ent in seeds:
        if not await graph.exists(ent.id):               # 图谱没有这个实体就退回纯向量
            continue
        sg = await graph.subgraph(seed=ent.id, hops=2, max_nodes=60, min_w=0.5)
        subgraphs.append(sg)
        texts.extend(sg.to_evidence_text())             # 子图转成三元组文本，补进向量候选
    hits_vec = await vector_store.similarity_search(question, k=k_vec)
    return {"vector": hits_vec, "subgraphs": subgraphs, "merged_texts": texts[:k_sub]}
```

注意 `if not await graph.exists(...)` 这个分支：图谱覆盖不到的问题必须能无声降级到纯向量，而不是报错。混合架构的一个隐性要求是**两条路都能单独工作**，任何一条路的故障都不能让服务不可用。

### 混合检索排序

三路候选（向量、关键词、图谱）合并后的排序，最稳的做法不是学一个权重，而是用倒数排名融合（RRF）。它的好处是无需归一化：不同检索器的分数分布差一个数量级，硬归一化会把长尾压成 0，而 RRF 只看名次：

\[ \text{RRF}(d) = \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)} \]

`R` 是候选集来自的检索路，`rank` 是文档在该路的名次（从 1 开始，没进前 20 记 0 分），常数 `k` 本章统一取 60——它压低头部优势的作用，取 10 到 100 之间都对，取 60 是社区里最常见的选择。

拿三个文档算一遍。文档 A 在向量路排第 3、关键词路排第 12；文档 B 只在向量路排第 1；文档 C 只在图谱路排第 2：

\[
\text{RRF}(A) = \frac{1}{63} + \frac{1}{72} \approx 0.0159 + 0.0139 = 0.0298
\]
\[
\text{RRF}(B) = \frac{1}{61} \approx 0.0164, \quad \text{RRF}(C) = \frac{1}{62} \approx 0.0161
\]

排序结果是 A > B > C。两个结论从这三个数字里直接读出来：**两路都命中的文档靠叠加占优**，哪怕它没有一路排第一；**单路第一名只值 0.016 左右**，所以图谱路必须能召回真正有价值的子图，否则它对排序毫无影响——图谱路排第一的 C 干不过向量路随便一个两路都中的文档，这不是 bug，是 RRF 的正常行为。

要控各路影响力就把权重复合进去，`w = 0.6, 0.3, 0.1` 对应向量、关键词、图谱（示意权重，按评估集调）。但调权重的顺序在后面：先确认三路的召回质量，再调权重。

!!! mascot-tip "融合先别学权重"
    ![墨墨提示技巧](../../img/mascot/tip.png){ class="mascot-admonition-img" }
    新手最常见的浪费是花一周调融合权重，而三路召回本身是坏的。用第四章的评估集先量每一路的召回命中率，哪一路低于 0.6 就先修那一路，权重放到最后调。

### 全局与局部检索

这是 GraphRAG 里最需要分清的一对概念。**局部检索**以问题里点名的实体为种子，沿边取 1 到 2 跳的子图，问题是“X 的供应商是谁”“X 今年的产能增速是多少”，答案在少数几条边里就能拼完。**全局检索**不指定起点，先按社区把整张图切块，每块压成一段摘要，再对这些摘要做向量检索，把命中的社区喂给模型汇总，问题是“过去一年行业的主要风险集中在哪些环节”“我们供应链有哪些单点故障”。

| 维度 | 局部检索 | 全局检索 |
|---|---|---|
| 起点 | 问题里的实体 | 没有，用社区摘要向量 |
| 图查询次数 | 1 到 2 次 | 1 次（取社区）+ N 次摘要 |
| 模型调用次数 | 2 次（1 次图查询 + 1 次生成） | 7 次（1 次图查询 + 5 次摘要 + 1 次汇总） |
| 延迟 | 0.4 加 0.8，即 1.2 秒 | 0.4 加 5 乘 0.6 加 1.1，即 4.5 秒 |
| 注入上下文块数 | 3 到 4 块 | 5 块（Top5 社区摘要） |
| 覆盖范围 | 种子实体的直接关系 | 跨文档、跨社区的共性 |
| 失败方式 | 图谱没覆盖到就答不出 | 摘要丢了细节，答得笼统 |

数字口径说清楚：1.2 秒的局部延迟是 0.4 秒图查询加 0.8 秒生成；4.5 秒的全局延迟是 0.4 秒图查询加 5 次社区摘要各 0.6 秒，再加汇总阶段 1.1 秒（输入更长，所以比一次普通生成慢）。**全局不是更准，只是问法不同**——问“宁德时代的产能增速”时用全局，等于用 96 份社区摘要去找一个数字，既慢又可能找不到。

选型判据只有一条：**问题里有没有点名一个起点实体**。有，走局部；没有，问的是结构性的共性问题，走全局。含“主要”“整体”“哪些环节”“画像”而没有具体公司名或药名的，一律全局。

### Cypher查询入门

Cypher 是图数据库的查询语言，写法接近自然语言，靠几个固定子句拼装：`MATCH` 匹配模式（`(a:Company)-[:COVERS]->(b)`），`WHERE` 过滤，`RETURN` 返回，`WITH` 把结果传给下一段，`UNWIND` 拆列表，`ORDER BY` 排序，`LIMIT` 截断。常用变体：反向遍历把箭头写成 `<-[:类型]-`，定长跳数写成 `-[:类型*2]-`，变长写成 `*1..3`。

五个必须掌握的写法，按踩坑频率排：

```cypher
// 1. 参数化：所有用户输入走参数，不拼进语句字符串
MATCH (c:Company {ticker: $ticker}) RETURN c.name AS 公司名

// 2. 变长关系慎用：*1..3 无法预知展开量，百万级图上会拖垮计划缓存
//    要跳数灵活就写成三条定长语句再 UNION ALL

// 3. 聚合与去重：COUNT(DISTINCT o) 才能数出机构数，COUNT(o) 会按路径重复计数
MATCH (c:Company)<-[:COVERS]-(o:Org)
RETURN c.name AS 公司, COUNT(DISTINCT o) AS 覆盖机构数

// 4. 短路与分页：LIMIT 必须配 ORDER BY，否则每次返回的行都可能不同
MATCH (o:Org)-[:COVERS]->(c:Company)
RETURN c.name ORDER BY c.name LIMIT 20 SKIP 40

// 5. 性能自查：先看 PROFILE 里的 rows 与 db hits，再看耗时
PROFILE MATCH (c:Company)-[:COVERS]->(org:Org) RETURN org.name LIMIT 20
```

两个性能事实要记住：属性索引（`CREATE INDEX ... FOR (c:Company) ON (c.ticker)`）只在查询起点能命中，别在遍历末端指望它；没有索引的属性过滤会退化成全图扫描，一条 3 跳变长查询在全图上的实测耗时是 4.7 秒，改成定长加索引后是 0.3 秒（示意值），差 15 倍。上线前的门槛很简单：单条查询 P95 不超过 200 毫秒，超了先加索引或改写，不要靠加机器硬扛。

## 五、图的运维生命周期

### 图谱增量更新

图谱腐坏的速度比向量库快得多：文档改了、事实过期了、分析师换所了，而向量库只需要重新 embed 一次。增量更新的目标是把单次变更的影响控制在“局部”而不是“全量”：示例图谱全量重建要 40 分钟，而单份研报变更影响 1 个实体加平均 6 个邻居，1 跳重算不到 5 分钟，快了 8 倍。

三个动作组成一次增量更新。第一，**按文档哈希跳过**：对每份文档取内容的 SHA-256 前 16 位，哈希没变直接跳过，这是最省事也最有效的一步。第二，**软删除加有效期**：删除时给旧边打 `valid_to = 今天` 而不是物理删，这样上月的问题还能复现，历史结论也能追责。第三，**幂等回填**：重抽完先清掉该文档贡献的 `mention_count`，再按新抽取结果重算，否则计数只增不减，去重会彻底失效。

```python
import hashlib

def on_document_updated(doc_id: str, text: str, pipeline) -> None:
    h = hashlib.sha256(text.encode()).hexdigest()[:16]
    prev = pipeline.hash_store.get(doc_id)
    if prev == h:
        return                                   # 内容没变，整条链路跳过
    # 先给旧边打有效期标记，不物理删除
    pipeline.graph.run("""
        MATCH (c)-[r {evidence_doc: $doc}]->()
        SET r.valid_to = date()
        REMOVE r.active                       // 旧边留库但不再参与检索
    """, doc=doc_id)
    entities = pipeline.extract(text, doc_id)          # 重抽
    pipeline.upsert_edges(entities, doc_id)            # MERGE 幂等写入
    pipeline.hash_store.set(doc_id, h)
    pipeline.recompute_mention_counts(doc_id)          # 计数重算，防止只增不减
```

别忘了**孤儿节点回收**：既无出边也无入边、且 `mention_count = 0` 的节点是抽取残留，按天扫一次删掉。上面的图谱每周约产生几十个孤儿节点，不清的话半年后图里会有一堆查不出所以然的空壳。

### 图谱可视化排查

图谱出问题时，`EXPLAIN` 只能告诉你查询慢在哪，告诉不了你数据脏在哪。可视化排查的价值在于**用肉眼看出模式**：一个孤零零飘在角落的点、三条线拧成一股绳、两片互不连通的图，都是肉眼一秒、脚本半小时的问题。开发期直接用 Neo4j Browser（7474），生产排查可以接一个只读的画布工具，把可疑节点附近的子图导出来看。

三类病灶，各配一条查询：

```cypher
// 病灶一：孤儿节点，抽取残留或实体被误删
MATCH (n) WHERE size([(n)--() | 1]) = 0 AND n.mention_count = 0
RETURN labels(n)[0] AS 类型, n.name AS 名称 LIMIT 50

// 病灶二：悬挂关系，指向已被删除的实体或文档
MATCH ()-[r]->(n) WHERE n IS NULL
RETURN type(r) AS 关系类型, count(*) AS 数量
// Cypher 里不会返回悬空节点，改查边指向的文档属性是否为空
MATCH (a)-[r]->() WHERE r.evidence_doc IS NULL OR r.valid_to IS NULL
RETURN type(r) AS 关系类型, count(*) AS 数量

// 病灶三：社区碎片，大量只有一两个实体的小社区，摘要里没有可用上下文
MATCH (c:Community) WHERE size(c.members) <= 2
RETURN c.id AS 社区, size(c.members) AS 实体数 LIMIT 50
```

抽查 100 个社区，其中 23 个实体数不超过 2，碎片率就是 0.23；把阈值定在 0.10，超过就要调 `resolution` 或合并碎片社区再重建摘要。这一步不做，全局检索会持续返回空泛的社区摘要——而且它不报错，只会安静地让答案变差。

### 图谱质量评估

图谱质量必须量化，因为它是唯一一个“你不测就一定会腐坏”的组件。四个指标，缺一不可：

| 指标 | 怎么算 | 上线门槛 | 不达标时的动作 |
|---|---|---|---|
| 实体 F1 | 人工标注 200 条抽取结果，算准确率与召回率的调和平均 | 大于等于 0.80 | 修提示词或补别名表，别急着上检索 |
| 三元组准确率 | 抽样 200 条边人工判定对错 | 大于等于 0.85 | 查关系类型枚举是否被模型绕过 |
| 覆盖率 | 已入图文档页数除以总页数 | 大于等于 0.60 | 补抽取覆盖，或明确拒答范围 |
| 图谱支撑率 | 端到端回答里引用了图谱子图的比例 | 大于等于 0.60 | 检索路由没生效，查意图分流 |

算一遍实体 F1 感受一下口径：200 条标注里，模型抽出的实体有 172 条正确、40 条错误（准确率 172/200 = 0.86）；标注集中实际有 200 个实体，模型抓到 158 个（召回率 158/200 = 0.79）：

\[ F1 = \frac{2 \times 0.86 \times 0.79}{0.86 + 0.79} = \frac{1.3588}{1.65} \approx 0.824 \]

0.824 高于 0.80 的门槛，允许图谱参与检索。安全攸真的领域门槛要抬到 0.90（医疗那一节的支撑率要求），因为答错一个人的用药禁忌不是扣分问题。

评估集要和第四章那套端到端评估集分开建：端到端评估集量“答案对不对”，图谱评估集量“事实抽对没抽对”。前者退化时你不知道该修抽取还是修检索，后者能直接指认。频率上，图谱评估集每两周跑一次全量，每天跑一次抽样 30 条的冒烟版。

!!! mascot-thinking "支撑率是图谱的体温计"
    ![墨墨思考中](../../img/mascot/thinking.png){ class="mascot-admonition-img" }
    如果支撑率长期低于 0.2，说明你花了钱建图谱却几乎没人在用它——多半是意图分流没做，问题全走了向量路。这时候该做的是调整路由和提示词，不是继续往图里灌数据。

### 图谱权限隔离

图谱把散落的文档变成了可串联的实体，这让权限问题从“按文档过滤”升级成“按关系过滤”——一个用户看不到 A 公司的研报，但如果图谱把 A 公司和 B 公司通过“共同覆盖机构”连了起来，用户就能推断出 B 公司的信息。Neo4j 没有开箱即用的行级安全，隔离必须自己在查询层做，这一点要提前和业务方说清楚。

| 方案 | 做法 | 隔离强度 | 成本 | 适合 |
|---|---|---|---|---|
| 查询层过滤 | 节点带 `tenant_id`，所有 Cypher 强制拼 `WHERE` 条件 | 中，漏写一处就泄漏 | 低 | 内部系统、租户数中等 |
| 一租户一库 | 每个租户独立 Neo4j 实例或独立 database | 强，物理隔离 | 高，实例数随租户涨 | 金融、医疗等强合规 |
| 分区 database | 同一实例内按租户分 database，账号级授权 | 强，账号隔离 | 中 | 租户数在几十量级 |

```cypher
// 查询层过滤：租户 ID 从会话注入，不从请求体取
MATCH (c:Company {ticker: $ticker})<-[r:COVERS]-(o:Org)
WHERE o.tenant_id IN $allowed_tenants        // 允许集合来自权限服务，不是用户输入
RETURN c.name AS 公司, collect(o.name) AS 覆盖机构
LIMIT 20
```

三条纪律配套：过滤条件写在**驱动层统一注入**而不是每个业务查询手写（手写一定会漏）；权限变更走**事件**而不是改数据（改数据会让历史查询结果无法解释）；跨租户的公共实体（行业、指标）放**独立的共享区**并标记 `scope = 'global'`，查询里按 `scope = 'global' OR tenant_id IN $allowed` 放行，既安全又不用把公共数据复制 N 份。

### 图谱运营成本

图谱的成本结构和向量库不同：向量库的成本几乎全是存储与检索，图谱的成本大头在**持续维护**。一份过期的边不会自己消失，它会安静地把答案带偏，直到有人发现。所以要按四项分别记账，别只看服务器账单：

- **存储与算力**：图遍历是内存操作，内存不够会退化成磁盘扫描，性能断崖式下跌。
- **抽取调用**：日常增量的模型调用费，按每天新增文档量线性增长。
- **质量维护**：每周抽检、人工复核冲突、消歧队列，这是最大也最容易被忽略的一项。
- **重建窗口**：全量重建要占用资源，通常安排在业务低谷。

按规模选硬件，下表是示意数据，不是厂商报价：

| 规模档 | 节点数 | 关系数 | 建议内存 | 可承载 | 全量重建耗时 |
|---|---|---|---|---|---|
| S 开发 | 10 万 | 100 万 | 16 GB | 本地与测试环境 | 1 小时以内 |
| M 生产 | 100 万 | 1000 万 | 64 GB | 生产单机 | 6 到 10 小时 |
| L 大规模 | 1000 万 | 1 亿 | 256 GB | 集群，需分片 | 需分片并行 |

把一张中等规模（100 万实体、1000 万关系）的月度账单算清楚（示意数据）：云主机 8 核 32 GB 约 700 元/月；增量抽取每天 200 篇研报、每篇 4 块，800 次调用乘以 0.002 元等于 1.6 元/天，30 天是 48 元/月；人工质量抽检按每周 0.2 人天算，约 160 元/月。合计约 900 元/月，其中模型调用费只占 5%——**决定图谱贵不贵的是人，不是 token**。这个比例是要写进立项汇报的数字，因为它决定了项目的真实瓶颈在哪。

降本的动作按性价比排：先提高抽取批处理吞吐（一次调用处理多块），再砍掉低价值边的维护（冷门关系季度更新而不是每日），最后才考虑降级图谱范围（只维护 Top 1000 实体的完整关系）。反过来先砍人，会让上面那 0.60 的支撑率门槛在两个月内崩掉。

### 图谱冷启动

冷启动的核心矛盾是：图谱的价值来自关系的密度，但关系密度只能从文档里抽出来，而文档还没处理。务实的解法不是“先把全部文档抽一遍”（那是几十小时的空转），而是三条路径里选一条：

| 路径 | 做法 | 周期 | 成本量级（示意） | 适用判断 |
|---|---|---|---|---|
| A 骨架先行 | 只建 50 到 200 个核心实体和它们之间最确定的关系，其余暂不抽 | 1 周 | 人力 1 到 2 人天，调用费不足 5 元 | 业务刚起步，先验证问题是否真是关系型 |
| B 结构化反灌 | 从已有的关系型数据库、工商主数据、CRM 反向生成实体与关系 | 2 到 3 周 | 人力 5 到 8 人天，调用费 0 | 关键实体在内部系统里已有权威数据 |
| C 高价值渐进 | 从第四章评估集里 Top 100 高频问题反推所需实体，只处理涉及这些实体的文档 | 4 周 | 人力 3 到 5 人天，调用费 20 元以内 | 已上线且问题分布可统计 |

路径 B 的性价比经常被低估：如果你的实体本来就存在于一个结构化的主数据表里，“抽取”这件事是多余的，直接映射更快也更准。路径 C 最适合已有评估集的系统，它把冷启动变成一个有终点的任务——Top 100 问题涉及的实体是有限集合，抽完就能上线。

冷启动期最容易做错的是**先上全局检索**。全局检索依赖社区摘要，社区摘要在实体数不足 5000 时全是噪声，答案会明显比纯向量还差。正确的顺序是：先让局部检索跑通（用路径 A 或 B 的骨架图），等实体数过万、社区规模稳定在 100 个量级，再开全局检索。

### 图谱演进路线

图谱不是一次性项目，是一条五级的路线，每一级由**触发条件**驱动而不是由时间驱动。跳过任何一级都能活，但会欠债。

| 级别 | 做什么 | 进入下一级的触发条件 | 大致工作量 |
|---|---|---|---|
| L0 纯向量加关键词 | 只优化混合召回与重排 | 关系型问题占比超过 30% | 0 |
| L1 只写不查 | 建图谱、跑抽取、做质量评估，但不参与在线检索 | 实体 F1 大于等于 0.80 且覆盖率大于等于 0.60 | 2 到 4 周 |
| L2 局部检索上线 | 意图分流，问题点名实体时走图谱 | 局部问题占比超过 50% 且支撑率大于等于 0.60 | 1 到 2 周 |
| L3 全局检索上线 | 社区摘要 + map-reduce 汇总 | 跨文档汇总类问题占比超过 20% | 2 周 |
| L4 自动化维护 | 抽取进队列、冲突自动分类、孤儿自动回收 | 图谱月漂移率超过 5% | 3 到 4 周 |

从 L0 到 L1 是不需要任何理由的那一步：先用离线任务把图建起来，用质量指标盯住，不接在线流量。它的好处是风险几乎为零，出问题只影响批处理；同时它给了团队时间去建立评估基线。**最常见的错误是跳到 L2 直接上线**，然后因为实体质量不过关导致答案比纯向量还差，团队得出“图谱没用”的错误结论。

从 L2 到 L3 的判断依据最实在：拿评估集统计，如果“主要”“整体”“共性”这类问题占比不到两成，全局检索的投入收不回来。反过来如果占比高，先别急着上全局，先试试把这类问题拆成两三个局部问题问，效果往往不差但成本低得多。

## 六、三种领域的图谱实战

### 金融研报图谱实战

金融研报是图谱最典型的适用场景，因为它的三个特征全中：实体跨文档反复出现（同一家公司出现在几十份研报里）、关系密集（覆盖、推荐、评级、上下游）、答案需要跨文档聚合（"有多少家券商同时覆盖了三家电池厂"）。

实体分六类：`Company`（带 `ticker`）、`Org`（研究所）、`Analyst`（分析师）、`Industry`（申万一级或二级）、`Metric`（指标名，带单位）、`Event`（评级调整、增发、诉讼）。关系有 `COVERS`（Org 指向 Company，边上带 `weight` 即去重后的研报篇数和 `since`）、`BELONGS_TO`、`REPORTS`（Company 指向 Metric，带 `value`、`unit`、`year`）、`DOWNGRADE`（Analyst 指向 Company，带 `rating`）、`SUPPLY_CHAIN`（Company 指向 Company，区分上游与下游）。

业务细节决定成败的三点：**简称必须归一**（宁德时代、CATL、300750 指向同一个节点，这是消歧那一节的活）；**指标要带单位和统计口径**（"营收"是单季还是累计，口径不同数值差一倍）；**分析师换所会造成关系漂移**，人从中信换到华泰，`COVERS` 的 `weight` 应当在时间窗内重算，否则计数虚高。

这套图谱的杀手锏是聚合查询，下面这题只有图谱能答：

```cypher
// 哪些电池厂被至少两家券商研究所覆盖，且 2025 年产能增速超过 30
MATCH (c:Company)-[:REPORTS {metric: '产能增速', year: 2025}]->(m:Metric)
WHERE m.value > 30
MATCH (o:Org)-[:COVERS]->(c)
WITH c, COUNT(DISTINCT o) AS 覆盖机构数
WHERE 覆盖机构数 >= 2
RETURN c.name AS 公司, c.ticker AS 代码, 覆盖机构数, m.value AS 产能增速
ORDER BY 产能增速 DESC
LIMIT 20
```

在本章示例图谱上执行，只有宁德时代同时满足两个条件（覆盖机构 2 家、产能增速 35.2）；比亚迪和亿纬锂能各只有 1 家机构覆盖，被 `覆盖机构数 >= 2` 过滤掉。纯向量检索做不出这个筛选——它不知道"去重后的机构数"是多少，而这个问题恰恰是研究员每天在问的。

### 医疗问答图谱实战

医疗问答是唯一**不能靠语义相似度兜底**的场景，因为关键事实往往是负面的："这个药高血压患者能不能用"的答案（禁忌）在原文里的措辞通常是"严重肝功能不全者禁用"，和问题里的"能不能用"毫无语义相似度，向量检索系统性地漏掉它。这类事实只有显式建成边、并在生成时作为硬约束注入，才能可靠。

实体五类：`Disease`（带 ICD-10 编码）、`Drug`（带 ATC 编码）、`Symptom`、`Exam`、`Department`。编码是关键——ICD-10 和 ATC 是现成的对齐键，让"同一个病"和"同一个药"不依赖字符串匹配。关系有 `CONTRAINDICATED`（Drug 指向 Disease，带 `grade` 证据等级与 `condition` 触发条件）、`FIRST_LINE`、`COMORBID`（Disease 指向 Disease）、`SYMPTOM_OF`、`EXAM_FOR`、`DEPT_TREATS`。

抽取量级（示意数据）：3000 篇指南与药品说明书，按每篇 6 个疾病、4 个药物、9 条关系算，产出 2.7 万条原始关系，疾病提及归并为 1.1 万个疾病实体、1.2 万个药物实体。证据等级按 GRADE 分布：A 级 18%、B 级 34%、C 级 48%。

质量控制是这个领域的核心工程量：**置信度低于 0.8 的边不参与在线检索**，直接进隔离区等人工复核，实测约 12% 的边会落在这里。生成时必须把 `grade` 和 `condition` 一起带进上下文，让模型回答成"在 eGFR 小于 30 时禁用（GRADE A 级）"，而不是只说"禁用"。

```python
# 禁忌链查询：疾病并发症 1 跳 + 药物禁忌 1 跳，置信度低于 0.8 的边直接不返回
CYPHER_CONTRA = """
MATCH (dz:Disease {icd10: $icd10})-[:COMORBID]->(c:Disease)
MATCH (c)<-[r:CONTRAINDICATED]-(d:Drug)
WHERE r.confidence >= 0.8
RETURN dz.name AS 主病, c.name AS 并发症, d.name AS 禁用药物,
       r.grade AS 证据等级, r.condition AS 触发条件, r.evidence AS 证据块
ORDER BY r.grade, r.confidence DESC
LIMIT 20
"""
# "糖尿病合并肾病的用药禁忌"就是 2 跳：糖尿病 →(COMORBID) 肾病 ←(CONTRAINDICATED) 某药
```

这个域的图谱支撑率门槛是 0.90，不是通用的 0.60——因为一旦回答依据了错误的边，代价不是回答变差，而是临床风险。这也是医疗域优先做路径 B（从结构化的药品数据库反灌禁忌关系）而不是纯模型抽取的原因：禁忌数据有权威来源时，没有理由让模型猜。

### 供应链图谱实战

供应链图谱的价值不在检索，在**影响面分析**："某地一家工厂停产，会影响哪些客户交付"这个问题，人工排查要两天，图谱一次查询几分钟。难点是 BOM 的层级展开会爆炸——单台设备 3 层展开有 1200 个物料，全量入图就是 1.2 万个物料节点，而真正的查询只需要前两层。

实体五类：`Material`（SKU，带 `tier` 层级 1 到 3）、`Factory`、`Supplier`、`Carrier`（承运商）、`Port`。关系有 `SUPPLIES`（Supplier 指向 Material，带 `lead_time_days` 交期天数、`price_index` 价格指数、`is_backup` 是否备选供应商）、`BOM_PARENT`（Material 指向 Material，自引用层级）、`MADE_BY`（Factory 指向 Material）、`CARRIED_BY`（Carrier 指向 Route）、`ORDER_OF`（Order 指向 Material）。

这里有三个纯检索场景不会遇到的业务细节。**备选供应商不另建关系类型**，用 `is_backup = true` 的 `SUPPLIES` 边表示，这样"主供 + 备供"的关系链一次查询就拿全。**交期参与加权**：延迟风险不是简单求和，而是 `sum(lead_time_days × w)`，上一节的关系权重直接复用。**层级只展开 2 层**，命中之后再按订单 ID 下钻，不做无界展开。

影响面分析走 3 跳，恰好用满跳数上限：

```cypher
// 第 1 跳：反查受影响物料；第 2 跳：BOM 父级展开；第 3 跳：挂上客户订单
MATCH (f:Factory {city: '苏州', status: '停产'})<-[:MADE_BY]-(m:Material)
WITH collect(DISTINCT m) AS hit1
MATCH (p:Material)-[:BOM_PARENT*2]->(child:Material)
WHERE child IN hit1
MATCH (o:Order)-[:ORDER_OF]->(child)
WITH p, count(DISTINCT o) AS 受影响订单数
OPTIONAL MATCH (s:Supplier)-[r:SUPPLIES]->(p)
WITH p, 受影响订单数, collect(DISTINCT CASE WHEN r.is_backup THEN s.name END) AS 备选供应商
RETURN p.sku AS 物料, 受影响订单数, size(备选供应商) AS 备选供应商数
ORDER BY 受影响订单数 DESC LIMIT 50
```

按本章示例数据算：某产线停产反查受影响物料 47 个，BOM 父级展开 2 层后命中 312 个物料，其中 198 个能找到备选供应商（`is_backup = true`），备选覆盖率是 198 除以 312 约等于 63.5%。剩下 36.5% 的物料只能靠加急调度，这 112 个物料就是风险清单本身——**图谱的产出是一份可执行的名单，不是一段话**，这是供应链场景和前两个场景最大的差别。

## 本章小结

| 主题 | 结论 |
|---|---|
| 什么时候上图谱 | 关系密集、多跳、跨文档实体、需要计数聚合，四条信号任一成立才值得 |
| 什么时候纯向量就够 | 单文档语义检索，且评估集里关系型问题占比不到三成 |
| 建模 | 节点放对象、关系带证据与置信度、Schema 贴在提示词里 |
| 抽取 | 五步流程，关系抽取的难点在否定句与条件句 |
| 社区 | 96 个 level 2 社区支撑全局检索，实体数过万再开全局 |
| 检索 | 三路召回用 RRF 融合，k 取 60；局部 1.2 秒，全局 4.5 秒 |
| 运维 | 哈希跳过、软删除、幂等回填；成本大头是人工质量维护，不是 token |
| 路线 | L0 到 L4 五级，按触发条件升级，跳级会欠债 |

本章最需要记住的其实只有一句话：**图谱补的是关系这一维，不是"更聪明"的检索**。判断该不该上它，靠的是评估集里的问题分布，不是趋势。
