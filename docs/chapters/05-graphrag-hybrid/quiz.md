#### 1. 图谱建模的三条纪律中，节点与关系分别要求怎么做？

<div class="upper-alpha" markdown>

1. 节点只放有独立业务含义、能用稳定 ID 指称的对象，动作和事件挂成关系属性或独立事件节点；每种关系必须带 `confidence` 和 `evidence`
2. 节点和关系都要尽量细粒度，把每个动作、每个状态都建成独立节点，这样查询最好写
3. 关系上只需带 `confidence`，`evidence` 可以事后补；节点属性可以随意存嵌套 JSON
4. 为了查询方便，供应商、承运商、代理商可以先合并成一个"交易方"节点，等有需要再拆

</div>

??? question "Show Answer"
    The correct answer is **A**。建模不是数据库设计练习，它决定了后面所有查询能不能写得出来：建模时没区分"供应商"和"承运商"，等你写"这批货走哪条航线"时就得回头洗数据。选 B 是把粒度做反了——节点越多边越密，遍历成本和噪声同步上升。选 D 看着省事，实际上抹掉了查询条件本身：承运商和供应商在交付链上的位置完全不同，合并之后关系就失去了区分度。

    **Concept Tested:** 图谱建模基础

    **See:** [章节首页](../05-graphrag-hybrid/index.md)

#### 2. 本章示例图谱（1.2 万实体、2.4 万关系）在 `resolution = 1.0` 下，社区发现分出多少个 level 2 社区？平均每社区多少实体？

<div class="upper-alpha" markdown>

1. 24 个 level 2 社区，平均每社区 500 个实体
2. 480 个 level 2 社区，平均每社区 25 个实体
3. 约 96 个 level 2 社区，平均每社区 125 个实体
4. 1,200 个 level 2 社区，平均每社区 10 个实体

</div>

??? question "Show Answer"
    The correct answer is **C**。社区规模是运营指标而不是越小越好：单个社区实体数低于 5 说明切碎了，摘要里没有足够上下文；高于 200 说明摘要把不相关的事实搅在一起。另外社区发现用的模块度 \(Q\) 取值在 -1 到 1 之间，`resolution` 取 1.0 是默认起点，它调节的是"社区别太大"的偏好——平方项会随社区变大而把划分拉回来。

    **Concept Tested:** 社区发现算法

#### 3. 关系权重的三种成分与组合公式，正确的是哪一组？

<div class="upper-alpha" markdown>

1. \(w =\) 抽取置信度 × \(0.5^{\Delta t / H}\)，只考虑时效，不看来源与证据数
2. \(w(r) = w_{source} \times \left(1 - (1 - p)^n\right) \times 0.5^{\Delta t / H}\)，其中 \(n\) 是独立证据数、\(H\) 是半衰期
3. \(w(r) =\) 来源可信度 + 证据数量 + 时效衰减，三项直接相加
4. \(w(r) =\) 证据数量 × \(0.5^{\Delta t / H}\)，来源可信度不参与计算

</div>

??? question "Show Answer"
    The correct answer is **B**。三成分相乘、结果落在 0 到 1。\(1-(1-p)^n\) 体现证据数量的增长很快——同一对实体被 5 篇独立文档提到，远比只在一篇里提到可靠。选 C 的加法组合有两个坏处：一是可能超过 1，二是任何一项为零都会让整条边归零，语义不对。最要紧的是把权重做成边上的数值属性而不是写死的 `if`，改阈值不用重跑抽取。

    **Concept Tested:** 关系权重设计

    **See:** [章节首页](../05-graphrag-hybrid/index.md)

#### 4. 为什么说"全局检索不是更准，只是问法不同"？选型判据到底是什么？

<div class="upper-alpha" markdown>

1. 因为全局检索用的是社区摘要，图谱里的实体数量永远比向量库少
2. 因为局部检索只要 2 次模型调用、全局要 7 次，所以局部更准
3. 因为全局检索只能回答"哪些环节"这类开放式问题，无法回答具体数值
4. 判据只有一条：问题里有没有点名一个起点实体。问"宁德时代的产能增速"用全局，等于用 96 份社区摘要去找一个数字，既慢又可能找不到

</div>

??? question "Show Answer"
    The correct answer is **D**。含"主要""整体""哪些环节""画像"而没有具体公司名或药名的一律走全局，反之走局部。延迟口径也要记住：局部是 0.4 秒图查询加 0.8 秒生成即 1.2 秒；全局是 0.4 秒图查询加 5 次社区摘要各 0.6 秒再加汇总 1.1 秒，即 4.5 秒。选 B 把"更快"当成"更准"，混淆了成本与效果两件事。

    **Concept Tested:** 全局与局部检索

    **See:** [章节首页](../05-graphrag-hybrid/index.md)

#### 5. 为什么不要图省事写 `-[*1..3]->` 这样的变长关系？本节给出的两条硬约束是什么？

<div class="upper-alpha" markdown>

1. 因为变长关系让查询计划无法预知最大展开量，也就用不上索引前缀，百万级图上能把 0.3 秒拖成几秒；硬约束是跳数上限设 3、单种子每跳扇出上限设 50
2. 因为变长关系无法同时表达关系类型白名单
3. 因为社区版 Neo4j 不支持变长关系语法
4. 因为变长关系返回的节点数不确定，子图里没法标注"已截断"

</div>

??? question "Show Answer"
    The correct answer is **A**。要跳数灵活就显式写出 1 跳、2 跳、3 跳三条语句再 `UNION ALL` 合并，别赌数据库的优化器。两条硬约束的依据也在这张累计表里：1 跳新增 5 个节点、2 跳累计 21 个、3 跳累计 63 个——超过 3 跳的结果集用户已经没有解释力，超过 50 个邻居塞进上下文会挤爆预算。

    **Concept Tested:** 多跳推理查询

    **See:** [章节首页](../05-graphrag-hybrid/index.md)

#### 6. 实体 F1 应该怎么算？门槛是多少？本章那批 200 条标注算出来的结果意味着什么？

<div class="upper-alpha" markdown>

1. 实体 F1 ≥ 0.80，不达标就先修意图路由和提示词
2. 实体 F1 ≥ 0.90，安全攸真的领域统一用这个门槛
3. \(F1 = 2 \times \text{准确率} \times \text{召回率} / (\text{准确率} + \text{召回率})\)；本章 200 条标注算出 0.824，高于 0.80 门槛，允许图谱参与检索
4. \(F1 = \text{准确率} + \text{召回率}\)；本章示例约 1.65，说明远超 0.80 门槛

</div>

??? question "Show Answer"
    The correct answer is **C**。算例是准确率 172/200 = 0.86、召回率 158/200 = 0.79，F1 ≈ 0.824，超过 0.80 的上线门槛，所以允许图谱参与检索；安全攸真的领域门槛要抬到 0.90，因为答错一个人的用药禁忌不是扣分问题。选 D 是把 F1 当成两项相加，而调和平均的特性恰恰是任一项低都会把整体拉下来。

    **Concept Tested:** 图谱质量评估

    **See:** [章节首页](../05-graphrag-hybrid/index.md)

#### 7. 三路候选里，文档 A 在向量路排第 3、关键词路排第 12；B 只在向量路排第 1；C 只在图谱路排第 2。按 RRF（k = 60）排序，结果是什么？这个结果说明什么？

<div class="upper-alpha" markdown>

1. B > C > A
2. A > B > C
3. A > C > B
4. B > A > C

</div>

??? question "Show Answer"
    The correct answer is **B**。手算三路：RRF(A) = 1/63 + 1/72 ≈ 0.0298，RRF(B) = 1/61 ≈ 0.0164，RRF(C) = 1/62 ≈ 0.0161。两个结论从这三个数字里直接读出来：两路都命中的文档靠叠加占优，哪怕它没有一路排第一；单路第一名只值 0.016 左右，所以图谱路必须能召回真正有价值的子图，否则对排序毫无影响——C 排第一却干不过 A，这不是 bug，是 RRF 的正常行为。

    **Concept Tested:** 混合检索排序

    **See:** [章节首页](../05-graphrag-hybrid/index.md)

#### 8. 混合检索时，用户问句抽出的实体在图谱里根本不存在，应该怎么处理？

<div class="upper-alpha" markdown>

1. 返回 502，让用户稍后重试
2. 返回空结果，明确告诉用户知识库里没有相关内容
3. 跳过图谱路，把这类问题统一标记为不回答
4. 无声降级到纯向量；混合架构的隐性要求是两条路都能单独工作，任何一条路的故障都不能让服务不可用

</div>

??? question "Show Answer"
    The correct answer is **D**。代码里那个 `if not await graph.exists(...)` 分支就是无声降级：图谱覆盖不到的问题必须能退回纯向量，而不是报错。选 B 的问题是白白丢掉了纯向量本来能答对的一批问题——图谱覆盖率永远不是 100%，把覆盖率当成可用性门槛会误伤大量正常请求。

    **Concept Tested:** 图谱与向量融合

#### 9. 医疗问答领域里，置信度低于多少的边不参与在线检索？这个领域的图谱支撑率门槛是多少？

<div class="upper-alpha" markdown>

1. 低于 0.8 的边不参与在线检索、直接进隔离区等人工复核（实测约 12% 的边落在这里）；支撑率门槛是 0.90，而不是通用的 0.60
2. 低于 0.6 的边不参与在线检索；支撑率门槛仍是 0.60
3. 低于 0.8 的边直接物理删除，不进隔离区；支撑率门槛是 0.95
4. 全部边都参与检索，靠生成阶段的二次校验兜底；支撑率门槛是 0.80

</div>

??? question "Show Answer"
    The correct answer is **A**。医疗是唯一不能靠语义相似度兜底的场景，因为关键事实往往是负面的——"严重肝功能不全者禁用"和"这个药高血压患者能不能用"毫无语义相似度，向量检索会系统性漏掉禁忌。生成时还要把 `grade` 和 `condition` 一起带进上下文，让模型答成"在 eGFR 小于 30 时禁用（GRADE A 级）"。支撑率抬到 0.90 的理由是：答错一条边的代价不是答案变差，而是临床风险。

    **Concept Tested:** 医疗问答图谱实战

#### 10. 中等规模图谱（100 万实体、1000 万关系）月度账单约 900 元，其中模型调用费只占 5%。这个成本结构说明什么？降本动作该按什么顺序做？

<div class="upper-alpha" markdown>

1. 说明图谱的大头是存储与算力，应该优先升级内存
2. 说明抽取调用是主要开销，应该把模型换成更便宜的
3. 说明决定图谱贵不贵的是人工质量维护而不是 token：先提高抽取批处理吞吐，再砍低价值边的维护，最后才降级图谱范围；反过来先砍人，0.60 的支撑率门槛两个月内就会崩
4. 说明成本完全可以忽略，不需要单独设预算

</div>

??? question "Show Answer"
    The correct answer is **C**。一份过期的边不会自己消失，它会安静地把答案带偏直到有人发现，所以质量维护是最大也最容易被忽略的一项。选 A 颠倒了主次：内存不够确实会让图遍历从内存操作退化成磁盘扫描、性能断崖式下跌，但账单的大头在每周抽检、人工复核冲突和消歧队列。降本的正确顺序是先把便宜的技术手段用尽，再考虑裁范围，最后才动人力。

    **Concept Tested:** 图谱运营成本
