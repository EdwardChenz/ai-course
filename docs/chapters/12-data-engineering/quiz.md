#### 1. Temporal 里 workflow 与 activity 的分工是什么？

<div class="upper-alpha" markdown>

1. workflow 承载编排逻辑（顺序、分支、等待、补偿），只做决策不碰外部世界且必须确定性；activity 承载业务动作（查库、跑 SQL、调 Spark、发通知），每一次都是可能失败或超时的外部调用
2. workflow 承载业务动作，activity 承载编排逻辑，两者可以互换
3. 两者实现方式完全自由，确定性要求也一样
4. workflow 不需要确定性，因为它的状态已经存在服务端了

</div>

??? question "Show Answer"
    The correct answer is **A**。这个分离不是风格问题而是可靠性问题：workflow 代码会被重放很多次，一旦在里面做随机数或读当前时间，重放结果就与第一次不一致，状态机直接崩掉。选 B 是彻底颠倒——本章 68 行 workflow、6 个各 20 到 40 行的 activity，规模本身就说明编排逻辑很薄、动作很厚。

    **Concept Tested:** Temporal编排入门

#### 2. 调度与重试配置里，两个最常被配错的参数是什么？

<div class="upper-alpha" markdown>

1. `timezone` 与 `cron`，两者必须写成相同时区才能生效
2. `maximum_interval` 与 `start_to_close_timeout`，两者不封顶就会各自无限增长
3. `maximum_interval` 不封顶会让退避序列在第 7 次跳到 24 分钟之后，运维早就以为任务死了，封顶到 60 秒后 8 次重试总共只花 200 多秒；`non_retryable_error_types` 必须把参数错误和权限错误列进去，重试不会让它们变合规
4. `catchup_window` 与 `overlap_policy`，报表类任务应该设成回填模式

</div>

??? question "Show Answer"
    The correct answer is **C**。选 D 把两条经验规则记反了：报表类选跳过，数据管道类选回填——月报补 3 次会发 3 份通知，而日管道漏 3 天不补，那 3 天的数据就永远缺了。退避倍数也有判断依据：2 倍适合本地资源竞争，3 倍以上适合外部依赖抖动，本章的 `dependency-default` 用 3.0、最大尝试 8 次，总退避 602 秒，正好覆盖一个 10 分钟级的依赖抖动窗口。

    **Concept Tested:** 定时与重试策略

    **See:** [章节首页](../12-data-engineering/index.md)

#### 3. Temporal 与 Dagster 的抽象对象分别是什么？为什么不能互相顶替？

<div class="upper-alpha" markdown>

1. 两者是同类工具，选一个就够了
2. Temporal 管数据资产，Dagster 管运行时
3. 两者可以互相顶替，用统一框架更简单
4. Temporal 的抽象对象是一次执行的运行时，Dagster 的抽象对象是一份数据资产及其血缘与新鲜度；前者回答"这次跑成功了吗"，后者回答"这份数据现在可信吗"

</div>

??? question "Show Answer"
    The correct answer is **D**。混账的典型症状是同一件事两边都做一半：Temporal 里手写了一个检查新鲜度的逻辑，Dagster 里又声明了一个用不上的新鲜度策略，两边都过期了但没人收到告警。用一个反例说清楚：Temporal 知道第 5 步成功了，但它不知道第 5 步产出的那张报表有没有被别人依赖、它的分区是不是最新的、它是不是在上游变更后悄悄变旧了。

    **Concept Tested:** Dagster资产管理

    **See:** [章节首页](../12-data-engineering/index.md)

#### 4. 断点续跑与"从失败处重试"的区别是什么？续跑能不能自动撤销已产生的副作用？

<div class="upper-alpha" markdown>

1. 续跑是"从完成的地方继续"而不是"从失败的地方重试"，以最近一个已成功完成的 activity 为界；续跑只保证 workflow 里的代码不重复执行，activity 的外部副作用必须自己用幂等键兜住
2. 续跑从失败的那一步重试，已完成的步骤不再执行，副作用也会自动撤销
3. 续跑就是从头重跑，只是由引擎自动触发
4. 只要接了编排引擎就不需要幂等键，引擎会替你处理

</div>

??? question "Show Answer"
    The correct answer is **A**。最后一行那个"会重复"必须点破：第 5 步已发出 1 个通知的场景下，从崩溃里续跑成功之后业务方会收到重复的月度通知，比崩溃本身更让人不信任系统。幂等键还必须由业务维度拼成（`monthly-report:{period}:{step}`），如果用 activity 的 attempt 序号或时间戳做键，每次重试都会生成新键，幂等完全失效——这是最常见的写法错误。

    **Concept Tested:** 断点续跑机制

    **See:** [章节首页](../12-data-engineering/index.md)

#### 5. "上周华东区各门店的毛利率趋势，和去年同期比"生成的 SQL 有哪三个关键点？

<div class="upper-alpha" markdown>

1. 自己在 SQL 里算毛利率、地区条件用 `LIKE '华东%'`、对比基准按日期对齐
2. 口径走 `ads.dws_store_week_gross_margin` 这张口径物化表而不是自己算；地区条件用 `IN` 列出五个省而不是 `LIKE '华东%'`；对比基准按自然周对齐
3. 自己在 SQL 里算毛利率、地区条件用 `IN`、对比基准按日期对齐
4. 口径走物化表、地区条件用 `LIKE '华东%'`、对比基准按自然周对齐

</div>

??? question "Show Answer"
    The correct answer is **B**。自己算毛利率会得到第二个数，因为它和口径表口径不同；用 `LIKE '华东%'` 会漏掉一半数据，因为 `region_code` 的实际值带下划线后缀（`华东_上海`）。选 A 和 C 各错一处，选 D 错在地区过滤。呈现也有纪律：答案里必须同时出现 19.8%、22.4%、2.6 个百分点和"数据截至 2026-10-05"，少任何一个都会产生歧义。

    **Concept Tested:** 报表Agent实战

#### 6. 自然语言转 SQL 的六条安全红线由谁强制？Schema 该怎么喂给模型？

<div class="upper-alpha" markdown>

1. 红线靠提示词里写明"请不要删表"；47 张表全量喂给模型
2. 红线只有只读账号与行数上限两条；Schema 喂列级明细
3. 红线是只读账号、30 秒、10,000 行三条；Schema 先表级目录再列级明细
4. 六条红线是只读账号、单条 SELECT 语句白名单、超时 30 秒、行数上限 10,000、扫描字节上限 50 GB、并发上限 4，全部由数据库角色与网关强制；Schema 先喂表级目录、模型选完再取列级明细，8,460 token 降到 2,450 token，选表准确率从 0.78 升到 0.91

</div>

??? question "Show Answer"
    The correct answer is **D**。关键是"由账号和网关强制"这五个字——`report_ro` 角色在数据库侧就没有增删改与建表授权，所以防线在最后一道而不是第一道。选 A 那种做法最危险，提示词层的权限是可以被绕过的。扫描字节上限还有一个坑：50 GB 的扫描即使最后被取消，钱和时间也已经花掉了，所以正确做法是先用 `EXPLAIN` 估算，估算超限就直接改写 SQL。

    **Concept Tested:** 自然语言转SQL

#### 7. 查询结果缓存的缓存键必须包含哪四样东西？漏掉哪一样最危险？

<div class="upper-alpha" markdown>

1. 用户身份、问题文本、口径版本、数据截至分区；口径版本最常被漏也最危险，因为改完口径当天 Agent 会拿新口径回答、缓存里却存着旧口径算出来的数
2. 只要包含问题文本即可，其余字段由服务端在执行前补上
3. 用户身份、问题文本、当前时间戳即可
4. 用户身份与问题文本，口径版本与数据截至分区可以在返回前校验

</div>

??? question "Show Answer"
    The correct answer is **A**。用户身份缺了会让 A 部门看到 B 部门的数；问题文本缺了会让问"上半年"和问"一季度"共用一个键；数据截至分区是新鲜度的显式编码，比用一个全局"数据版本号"更准，因为不同表的刷新时间不同。选 D 把校验放到事后，等于先把过期数字发出去再检查——缓存配错的后果是"发出过期数字，比不缓存更糟"。

    **Concept Tested:** 查询结果缓存

#### 8. 数据质量校验为什么必须是阻断式的？阈值怎么定才不会天天误报？

<div class="upper-alpha" markdown>

1. 校验应该做成告警式的，由值班人决定是否阻断，这样能保留灵活性
2. 校验必须阻断式，因为下游的报表 Agent 不会读你的告警、它只会读到数据；阈值还要按星期几分档——工作日 ±3%、周末 ±8%，因为周末行数高出 6 到 8%
3. 只要做行数波动一项校验即可，其他维度交给模型判断
4. 行数波动这类统计类检查可以放宽到 ±10%，只保留主键唯一与引用完整性两个阻断项

</div>

??? question "Show Answer"
    The correct answer is **B**。选 A 的后果很具体：一条没拦住的下游脏数据会变成一个自信的数字出现在用户面前，而那个数字没有任何地方标注它不可信。阈值分档来自实测——最近 90 天日行数标准差 1.1%，而周末会高出 6 到 8%，本章初版没分这一档，2026-08 连续 12 天每天告警，最后值班人把告警静音了，这是所有校验系统最常见的死法。

    **Concept Tested:** 数据质量校验

    **See:** [章节首页](../12-data-engineering/index.md)

#### 9. 五个降本措施按单措施收益排序是怎样的？收益接近时按什么标准排？集群小时与月成本的关系是什么？

<div class="upper-alpha" markdown>

1. 列裁剪 450 > 缓存命中率 440 > 小文件合并 260 > 查询合并 250 > 分区裁剪 1,500
2. 收益第一的分区裁剪应该最后实施，因为它最复杂、风险最高
3. 分区裁剪 1,500 > 列裁剪 450 > 提高缓存命中率 440 > 小文件合并 260 > 查询合并 250；列裁剪与缓存命中率只差 10 小时却要按收益稳定性排——列裁剪改了永远生效、缓存命中率会随业务习惯回落；集群小时降 50.3% 而月成本只降 39.4%，差的那段是省不掉的存储成本
4. 只做前三项与做完五项的月成本降幅成正比，可以按预算线性裁剪

</div>

??? question "Show Answer"
    The correct answer is **C**。收益第一的分区裁剪反而是最先做的——它几乎不需要判断力，任何一条不带分区条件的 SQL 都是 bug。选 B 把它当成最后一步，等于把最便宜、最稳定的收益推到后面。降幅与实施数量不成正比：边际收益在递减，而且存储 4,140 元与查询优化无关，优化到底也省不掉。基线 19,116 元、优化后 11,576 元、降幅 39.4%，这三个数要能当场算出来。

#### 10. 分区键、压缩等级与写入方式这三项决策，本章各选了什么？为什么？

<div class="upper-alpha" markdown>

1. 按 `region_code` 分区，因为地区是最高频的查询维度
2. 按月分区，单分区 25 GB 读放大 30 倍但目录操作更快，整体更优
3. 压缩用 ZSTD 级别 9，每天多花 25 秒换 4% 空间很划算
4. 分区键用 `days(dt)`、日粒度 1,095 个分区，压缩用 ZSTD 级别 3，写入方式选按分区覆盖写；级别 9 只省 4% 体积却慢 60%（写入 42 秒涨到 67 秒、每年多花 2.5 小时），而覆盖写天然幂等，是断点续跑能成立的前提

</div>

??? question "Show Answer"
    The correct answer is **D**。分区键必须与查询条件匹配——按 `region_code` 分区而查询不带地区条件等于没分区，所以本章查询必带日期，`days(dt)` 正好匹配日报查询。选 B 的方向恰好相反：月粒体会让单分区 25 GB、读放大 30 倍。选 C 忽略了一年的累计成本——每天 25 秒、每年 2.5 小时换 4% 空间，这笔账不划算。

    **Concept Tested:** 分区与压缩策略
