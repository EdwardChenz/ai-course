#### 1. RagFlow 的哪个配置项决定了解析引擎能不能识别标题层级、表格和图注？

<div class="upper-alpha" markdown>

1. `DOC_ENGINE=deepdoc` 做版面分析，`naive` 只抽纯文本会把版面拍平
2. `EMBEDDING_MODEL=zh-embed-base`，它决定版面还原的质量
3. Elasticsearch 的堆内存大小，越大版面分析越准
4. MinIO 的存储容量，它决定解析产物能放多少页

</div>

??? question "Show Answer"
    The correct answer is **A**。`DOC_ENGINE` 是解析引擎：`deepdoc` 做版面分析，能识别标题层级、表格和图注；`naive` 只抽纯文本，快但把版面拍平。制度文档一律用 `deepdoc`。选 B 是把两个正交的配置混为一谈——嵌入模型只负责向量化，对解析质量没有任何影响；而 Elasticsearch 和 MinIO 都不是解析器。

    **Concept Tested:** RagFlow流水线部署

    **See:** [章节首页](../03-rag-basics/index.md)

#### 2. 本章采用的 RRF 倒数排名融合中，平滑常数与两路权重是怎么设的？

<div class="upper-alpha" markdown>

1. \(k_{\text{r}}=20\)，稠密路 1.0、稀疏路 1.0
2. \(k_{\text{r}}=60\)，稠密路 0.6、稀疏路 1.0
3. \(k_{\text{r}}=60\)，稠密路 1.0、稀疏路 0.6
4. \(k_{\text{r}}=100\)，稠密路 1.0、稀疏路 0.5

</div>

??? question "Show Answer"
    The correct answer is **C**。平滑常数取 60，稠密路权重 1.0、稀疏路 0.6。稀疏路权重压低是有原因的：它常常返回几十条"沾边但没答到点"的候选，权重一高就会把噪声顶上来。选 B 是把两路权重说反了——那样恰好会放大稀疏路带来的噪声，这类"数值颠倒"的干扰项是本章最常见的送分陷阱。

    **Concept Tested:** 稠密与稀疏融合

#### 3. 四层层级索引里，真正入向量库的是哪两层，各有多少条？

<div class="upper-alpha" markdown>

1. 只有 L4 块，12,800 条
2. L2 章节摘要卡 320 张 + L4 块 12,800 条，合计 13,120 条向量
3. L1 文档 320 条 + L4 块 12,800 条
4. 四层全部入向量库，条数等于 L1 到 L4 累加

</div>

??? question "Show Answer"
    The correct answer is **B**。L1 文档层不入库，它只提供租户、版本这类元数据用于过滤与权限判定；L3 小节层也不入库，它只用来决定父块边界。入库的是 L2 章节摘要卡（320 张）和 L4 块（12,800 条），共 13,120 条向量，比平铺方案多约 35% 存储——换回来的是"小块检索、大块喂模型"：命中子块后能回溯到 1,200 字符的父块。

    **Concept Tested:** 层级索引构建

#### 4. 增量索引更新必须覆盖哪三种状态，漏掉哪一种会出生产事故？

<div class="upper-alpha" markdown>

1. 新增、重试、删除
2. 新增、修改、迁移
3. 新建、重建、销毁
4. 新增、修改（先删旧块再写新块）、删除（下线必须清干净）

</div>

??? question "Show Answer"
    The correct answer is **D**。漏掉"删除"最隐蔽：文档下线时旧块没清干净，已废止的制度会继续被引用，而且没人发现。判断修改还是删除的依据是内容指纹——只对正文取哈希，格式调整或元数据变动不触发重建，省下的就是真实的 embedding 成本。

    **Concept Tested:** 增量索引更新

    **See:** [章节首页](../03-rag-basics/index.md)

#### 5. 两路检索分数量纲不同，为什么要用 RRF 而不是归一化后加权相加？

<div class="upper-alpha" markdown>

1. 归一化加权对分数漂移毫无抵抗力：稠密分数整体抬高 0.1 就把候选挤进同一区间、名次乱掉，而 RRF 只看名次
2. RRF 的实现比归一化加权简单得多，代码量少一半
3. 归一化加权会让召回率下降，而 RRF 能保证每一类查询都拿到最优策略
4. BM25 分数本质上无法归一化到 0 到 1 区间

</div>

??? question "Show Answer"
    The correct answer is **A**。BM25 常见取值 0 到 12，余弦相似度接近 1，两种分数的量纲完全不同，这才是要融合就必须解决的问题。抗漂移是选 RRF 的真正理由。选 C 是个美好误解：编号精确匹配这一类上 BM25 的 0.95 高于混合的 0.90，融合的职责是保住纯稠密最弱的那一类，不是让每类都变好。

    **Concept Tested:** 混合检索架构

    **See:** [章节首页](../03-rag-basics/index.md)

#### 6. 权限过滤为什么必须做在召回阶段，不能等召回完再过滤？

<div class="upper-alpha" markdown>

1. 因为向量库不支持 `filter` 参数，权限只能在应用层过滤
2. 因为事前过滤能让召回率比事后过滤更高
3. 因为事后过滤时敏感块虽未显示却已进入模型上下文，模型用它推理出的信息已经出去了，等同泄漏
4. 因为事前过滤能把召回池从 12,800 缩到 4,300，检索耗时从 70 毫秒降到 25 毫秒

</div>

??? question "Show Answer"
    The correct answer is **C**。理由是合规而不是性能：事后过滤最骗人的地方是界面看着没问题，敏感块确实没显示，但模型已经拿它推理出了这句话，信息已经出去了。选 D 的数字本身没错——本库的示例用户可见 4,300 个块，检索耗时从 70 毫秒降到 25 毫秒——但那是顺带的意外收益，不能当作"必须事前过滤"的理由。

    **Concept Tested:** 权限过滤检索

    **See:** [章节首页](../03-rag-basics/index.md)

#### 7. HyDE 在编号类查询上出现负增益——"工单 SO-2024-0917 归谁处理"的命中数从 20 掉到 15，正确的工程修法是什么？

<div class="upper-alpha" markdown>

1. 直接关掉 HyDE，所有查询都用原始问题
2. 假文档只走稠密路，原问题保留在稀疏路做 BM25 检索，两路再 RRF 融合
3. 把假文档也拼进最终答案上下文，让模型自己判断哪个编号才对
4. 把 HyDE 的 temperature 从 0.7 降到 0，避免编号被改写

</div>

??? question "Show Answer"
    The correct answer is **B**。序号 5 是唯一负增益，原因是工单号必须精确匹配，假文档生成时把编号改写成了一个不存在的单号，稠密路被带偏；而原问题的 BM25 路仍能靠精确串命中。修法不是关掉 HyDE，而是做双路分工：假文档走稠密、原查询走稀疏、RRF 融合。其余五道口语化查询的增益都在 +4 到 +6 之间，整体仍然赚。

    **Concept Tested:** 假设性文档检索

    **See:** [章节首页](../03-rag-basics/index.md)

#### 8. 召回率 recall@20 是 0.80，而送模型 5 条的命中率只有 0.54，这组数字说明什么？该先动哪个旋钮？

<div class="upper-alpha" markdown>

1. 说明解析脏了，应该回去修解析与清洗规则
2. 说明生成模型不够强，应先把 3B 的生成模型换成 70B
3. 说明 0.80 已是召回天花板，应该接受 0.54 的准确率
4. 26 道题的正确块落在第 6 到第 20 名，进了候选却被重排判死；战场在召回与重排，换强模型只涨 0.02，换对重排能涨 0.1 以上

</div>

??? question "Show Answer"
    The correct answer is **D**。0.80 与 0.54 之间那 0.26 的缺口就是 26 道题卡在第 6 到第 20 名——它们进了候选，但重排阶段把它们判死了。这类系统的主要战场因此是召回和重排，不是生成模型。选 B 是最贵的误判：把生成模型从 3B 换到 70B，端到端答对率可能只涨 0.02。

    **Concept Tested:** 召回率与准确率

    **See:** [章节首页](../03-rag-basics/index.md)

#### 9. 本章的口径是 Top10 进上下文、压到 1,800 个 token。压缩后的单次上下文成本是多少？

<div class="upper-alpha" markdown>

1. 0.0045 元
2. 0.0072 元
3. 0.0090 元
4. 0.0128 元

</div>

??? question "Show Answer"
    The correct answer is **B**。原始 Top10 共 4,000 个 token，按第一章每千输入 token 0.004 元的示意价算是 0.016 元；压到 1,800 个 token 后是 1.8 × 0.004 = 0.0072 元，每次省 0.0088 元，压缩率 55%。压缩还有个看不见的收益：上下文越干净，模型首字延迟越低，本章端到端 P95 是 1.9 秒，其中生成占 1.6 秒。

    **Concept Tested:** 上下文压缩

    **See:** [章节首页](../03-rag-basics/index.md)

#### 10. 48 道失败题的归因里"召回"类占 34%、是占比最高的一类，为什么实践中却要先修占比只有 22% 的解析类？

<div class="upper-alpha" markdown>

1. 修复成本差异巨大：解析类改几行规则当天上线，召回类要动索引结构；先做便宜的归因，一轮通常能吃掉三成失败
2. 34% 的占比本来就不算高，不值得优先投入
3. 解析类失败无法在冻结的评测集上复现，必须现场手点
4. 召回那 34% 里其实大半是查询改写的问题，不该记在召回头上

</div>

??? question "Show Answer"
    The correct answer is **A**。归因解决的是"知道该修哪儿"，排序解决的是"先修哪儿"，两件事分开。实践中的顺序是先做便宜的归因、再做贵的：一轮归因做完，通常三成的失败案例能被同一处修复吃掉。选 D 恰好是归因要避免的错误——只记第一个出错的环节，后面的多半是连锁反应。

    **Concept Tested:** 失败案例归因

    **See:** [章节首页](../03-rag-basics/index.md)
