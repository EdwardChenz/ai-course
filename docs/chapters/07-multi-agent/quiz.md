#### 1. 角色卡片必须包含哪五个要素？

<div class="upper-alpha" markdown>

1. 角色、职责、输入、输出、禁止事项
2. 角色、职责、工具清单、模型选择、最大轮次
3. 身份、目标、提示词模板、示例、终止条件
4. 名称、系统消息、工具清单、温度、终止条件

</div>

??? question "Show Answer"
    The correct answer is **A**。五要素缺一项，角色就会在运行中越界。"职责"要写成三到五条可判定做完的事，否则会无限扩张互相侵占；"输出"必须带 schema，否则下游程序消费不了；"禁止事项"最容易被跳过也最值钱，它既是防越界的红线，也是下一节交接单校验的明确失败判据。选 C 和 E 这类"提示词要素清单"是照抄代码字段，不是角色设计。

    **Concept Tested:** 角色分工设计

    **See:** [章节首页](../07-multi-agent/index.md)

#### 2. 交接单的七个顶层字段里，哪个最容易被省掉、最不该省？为什么自然语言交接一定丢信息？

<div class="upper-alpha" markdown>

1. `usage`，它只用于成本归集，缺了不影响正确性
2. `provenance`，它只用于事后追责，缺了不影响流程
3. `acceptance_criteria`，它最难写，但缺了它下游就没有"做到什么算完"的判据；自然语言交接的坏处不是读不懂，是丢了还读得懂
4. `constraints`，它只是提醒性文字，不参与校验

</div>

??? question "Show Answer"
    The correct answer is **C**。自然语言交接丢的正是三类关键信息：上游说"缺一条关于配件来源的规定"，下游会漏掉这个缺口；说"客户信息已脱敏"，下游会当成有把握的事实；引用编号则干脆消失。换成结构化交接单，三样都是必填字段，缺一个就校验失败。代价是缺口被自然语言吞掉后整条链跑通、测试全绿，只有客户投诉时才发现。

    **Concept Tested:** 任务交接协议

    **See:** [章节首页](../07-multi-agent/index.md)

#### 3. 对话轮次控制的四个手段，本章取的参数是哪一组？

<div class="upper-alpha" markdown>

1. 硬上限 8、软提醒 12、内容终止 3 轮、停滞终止 12
2. 硬上限 `max_round=12`、软提醒 `warn_at_round=8`、内容终止命中 `TERMINATE`、停滞终止 `no_progress_rounds=3`
3. 硬上限 3、软提醒 8、内容终止 `max_round=12`、停滞终止 1
4. 只保留硬上限 `max_round=24`，其余全交给模型自觉

</div>

??? question "Show Answer"
    The correct answer is **B**。轮次控制是多 Agent 系统里唯一一个不算账就一定会烧钱的参数，四个手段要同时在位。软提醒最容易被忽略却是省钱的关键：第 8 轮注入"还剩 4 轮"后，实测平均轮次从 11.2 降到 9.4。停滞终止是防群聊死循环的最后一道闸——三个角色可以就同一个措辞来回客气十几轮，每轮都在消耗却没有新信息。

    **Concept Tested:** 对话轮次控制

    **See:** [章节首页](../07-multi-agent/index.md)

#### 4. 为什么审稿人必须是不参与写作的独立角色？

<div class="upper-alpha" markdown>

1. 因为 AutoGen 框架不允许同一个 Agent 先写后审
2. 因为独立角色只多花一份 token，预算更好控制
3. 因为审稿人的输出只允许问题清单，同一个角色无法产出这种格式
4. 因为同一角色先写后审等于自己给自己批改，模型会倾向于确认自己的判断；反思修正循环解决的正是这个自我确认偏差

</div>

??? question "Show Answer"
    The correct answer is **D**。审稿人与反思的本质区别是批判来自哪里：审稿人的批判来自另一个立场，反思的批判来自同一个角色的第二次审视。选 B 暴露了一个危险的省钱思路——把唯一的质量防线砍掉换预算。要防的是另外两种失效：橡皮图章（问题命中率低于 60% 说明审稿人在走过场，该换提示词而不是加轮次）和意见死循环（写作者按 A 改、审稿人又要求改回原样）。

    **Concept Tested:** 审稿人模式

    **See:** [章节首页](../07-multi-agent/index.md)

#### 5. 判断该不该上多 Agent 的四条标准是什么？多 Agent 的成本倍数由什么决定？

<div class="upper-alpha" markdown>

1. 四条标准命中任意两条就值得上；成本倍数不由角色数决定，而由调用总次数 \(T\) 和上下文重读倍数 \(R\) 两个乘数决定——群聊最贵不是人多，而是 \(R = 2.0\)
2. 只要命中"任务可并行分解"这一条就必须上多 Agent
3. 成本倍数与角色数成正比，人越多越贵
4. 角色数超过 5 个时成本曲线才会明显上升

</div>

??? question "Show Answer"
    The correct answer is **A**。只命中一条先把单 Agent 链做扎实，反模式只有一个：能一条链解决的就别拆。反模式里的成本不是线性涨的，是随交接次数翻的，而且每次交接都是一次丢信息的机会。参考基准是单 Agent 链 \(T=3\)、\(R=1.0\) 的 0.0348 元；群聊轮转 12 次调用、\(R=2.0\) 就要 0.2352 元，6.76 倍。

    **Concept Tested:** 多智能体编排总览

    **See:** [章节首页](../07-multi-agent/index.md)

#### 6. 群聊管理器为什么要独立成一个角色？`auto` 选人策略实测会出哪两个偏差？

<div class="upper-alpha" markdown>

1. 应该把群聊管理器合并进规划者，少一个角色就省一次调用
2. `auto` 策略没有偏差，交给模型自己选人即可
3. 群聊管理器只干选下一个发言者和判定收尾两件事，必须独立；`auto` 的两个偏差是发言不均（规划者拿到 47% 的发言次数）和串谋，要靠发言配额上限与相似度熔断治
4. `round_robin` 是唯一可用策略，其他策略都不可靠

</div>

??? question "Show Answer"
    The correct answer is **C**。"决定谁来说"和"决定任务怎么拆"是两种判断，混在一起会出现规划者一路点名自己发言的自我对话。串谋这一项尤其要治：三个角色连续讨论同一段话、措辞高度相似，看似三个视角其实是一个视角的复读，那多花的 6.76 倍就白花了。群聊的价值在发现分歧，不在达成一致——分歧暴露出来就该交给裁决机制。

    **Concept Tested:** 群聊管理器

    **See:** [章节首页](../07-multi-agent/index.md)

#### 7. 成本预算控制的三个硬闸门默认值是什么？各自越界后的行为是什么？

<div class="upper-alpha" markdown>

1. 步数 24、成本 0.5 元、token 50,000；任一越界一律抛异常丢弃结果
2. 步数上限 24 次调用、成本上限 0.10 元每任务、token 上限 120,000；步数越界立即收尾标"预算耗尽"，成本越界先降级执行者模型再考虑中止，token 越界触发上下文裁剪而不是截断历史
3. 步数 12、成本 0.05 元、token 8,000；越界后继续执行但发告警
4. 步数 24、成本 0.02 元、token 8,000；越界时把结果标记为部分成功并交付

</div>

??? question "Show Answer"
    The correct answer is **B**。三个硬闸门加一条降级路径，缺任何一样都会在深夜出事。成本越界之所以先降级而不是立刻中止，是因为换便宜执行者往往还能把任务做完；token 越界要触发上下文裁剪而不是截断历史，直接截历史会丢掉最早的任务背景。记账只有一个入口（`settle`），任何调用都必须过它，否则预算表和实际账单必然对不上。

    **Concept Tested:** 成本预算控制

    **See:** [章节首页](../07-multi-agent/index.md)

#### 8. 两个执行者对同一件事给出相反结论，裁决机制应该怎么定？

<div class="upper-alpha" markdown>

1. 一律按多数投票，票数多者胜
2. 一律由规划者最终裁定，不再看投票
3. 先多数投票，平局时随机选一个
4. 先加权投票，票差小于 1.5 判为未收敛并升级到上游仲裁，冲突详情随交接单一起送人工

</div>

??? question "Show Answer"
    The correct answer is **D**。裁决机制必须在开跑之前定好，等冲突了再决定，你的选择就会被"谁先说话"和"谁声音大"决定。多数投票的适用条件是角色同质且错误独立；票源同质时它只是把同一种偏见数三遍。选 B 看着果断，实际是把裁决权集中到一个角色上、失去交叉校验，而且仲裁者自己也会错，必须用角色卡片的判据去约束它。

    **Concept Tested:** 冲突裁决机制

    **See:** [章节首页](../07-multi-agent/index.md)

#### 9. 留存异动归因里，数值复算 Agent 的核心设计纪律是什么？

<div class="upper-alpha" markdown>

1. 数值复算 Agent 不看查询生成 Agent 的结论，只看原始表独立重算；实测 3 次归因里查询生成 Agent 有 1 次连表漏了 `WHERE` 条件，因为独立复算全部被拦下
2. 数值复算 Agent 必须复用查询生成 Agent 的结论，只做格式整理以保证口径一致
3. 数值复算 Agent 排在最后启动，等前面几个角色全部完成
4. 数值复算 Agent 与查询生成 Agent 用同一个模型，降低成本

</div>

??? question "Show Answer"
    The correct answer is **A**。这是本章最危险的一类错误的防线：两个渠道的用户数被算混，肉眼看两份结论是一致的。独立重算把它拦下来；如果复算 Agent 读的是上一个 Agent 的结论，它会顺着错误一起错，双保险就变成了互相背书。选 C 排序改变不了这件事——真正决定成败的是"复算者看的是原始数据还是别人的结论"。

    **Concept Tested:** 数据分析实战

    **See:** [章节首页](../07-multi-agent/index.md)

#### 10. 4 个子任务各约 9 秒，全串行 36 秒、带信号量的并发 11 秒（P95 14 秒）。为什么必须用带信号量的并发，而不是无脑全并发？

<div class="upper-alpha" markdown>

1. 因为无脑全并发会改变成本结构，让成本涨幅不可预测
2. 因为信号量能保证汇总结果按预定顺序拼接
3. 因为并发额度不等于任务数：无脑全并发墙钟同样是 11 秒但无限并发会打爆下游限流；带信号量的方案让一个失败只标记该项失败、其余正常入汇总，成本变化只是汇总多一次调用
4. 因为全串行时第一个失败会让后面三个全不跑，所以任何形式的并发都一定更好

</div>

??? question "Show Answer"
    The correct answer is **C**。并发额度应等于执行者数量，再多只是排队。第二个坑是失败隔离：`asyncio.gather` 要用 `return_exceptions=True` 收集异常而非抛出，让失败项在汇总里单列为 `failed`——失败不能拖垮整批，也不能被当成空结果跳过，那会掩盖问题。选 D 的推理不成立：全串行的失败影响面虽然大，但换成无限并发只是把问题从内部转移到下游限流上。

    **Concept Tested:** 并行任务调度

    **See:** [章节首页](../07-multi-agent/index.md)
