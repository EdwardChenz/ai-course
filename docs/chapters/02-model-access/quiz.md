#### 1. 本章示例中 `RecursiveCharacterTextSplitter` 的两个关键参数分别取了多少？

<div class="upper-alpha" markdown>

1. `chunk_size=800`、`chunk_overlap=120`
2. `chunk_size=120`、`chunk_overlap=800`
3. `chunk_size=8000`、`chunk_overlap=0`
4. `chunk_size=200`、`chunk_overlap=800`

</div>

??? question "Show Answer"
    The correct answer is **A**。`chunk_size` 是每块的目标字符数，`chunk_overlap` 是相邻块的重叠量，用来避免句子被拦腰切断——所以前者必然大于后者，选 B 这类"数值颠倒"的选项一眼就能排除。重叠量取块大小 15% 左右是常见起点。真正的坑不在参数本身：顺序永远是先确认解析出来的文本干净，再调块大小，最后才动重叠。

    **Concept Tested:** 文档加载与切分

#### 2. 重排（rerank）阶段使用的模型结构是下面哪一种？

<div class="upper-alpha" markdown>

1. 双塔结构，查询和文档各自编码，用速度换精度
2. 与召回阶段完全相同的 embedding 模型，只是换了个相似度函数
3. 交叉编码器，把（查询，文档）候选对一起送进去算相关性分数
4. 大语言模型，把全部候选文档拼进提示词让它逐条打星

</div>

??? question "Show Answer"
    The correct answer is **C**。召回用双塔（查询、文档各自编码，因此快而粗），重排用交叉编码器把候选对放在一起算相关性，因此准而贵。标准流水线是"粗召回 50 条 → 重排 → 取 Top5 给模型"。要区分清楚的是 B：重排换的是结构不是相似度函数，只换函数不会改变"粗筛"的上限，也就没意义了。

    **Concept Tested:** 重排序策略

    **See:** [章节首页](../02-model-access/index.md)

#### 3. 评估集初建时，最小可用版本的规模与标注要求是下面哪一组？

<div class="upper-alpha" markdown>

1. 至少 500 条，每条只标"对/错"即可
2. 50~100 个有代表性的问题，人工标注到"正确块在哪个文件哪一段"
3. 只收典型问题，边界问题和该拒答的问题等上线后再补
4. 20 条就够，小样本上召回指标更稳定

</div>

??? question "Show Answer"
    The correct answer is **B**。关键是标注粒度：要标到块，否则召回没命中时无法归因到底是解析、切分还是查询改写出的问题。规模上 50~100 条有代表性的问题就够起步。第三类必收的是"该拒答的问题"——库里没有答案时模型必须学会说不知道；漏掉这一类，评测集会奖励瞎编的模型。

    **Concept Tested:** 评估集初建

#### 4. 批量调模型时，限流必须同时定下的三个参数是下面哪一组？

<div class="upper-alpha" markdown>

1. 并发路数、单请求超时、重试次数
2. 线程池大小、队列长度、GC 阈值
3. QPS 上限、连接池大小、日志采样率
4. 并发路数、每分钟请求上限、每分钟 token 上限

</div>

??? question "Show Answer"
    The correct answer is **D**。只限并发是不够的，因为一次请求的 token 量可以差一个数量级：十个短问句和一个长文档总结占用完全不同的配额，所以请求数和 token 数要分别设上限。这就是令牌桶限流的用武之地。超限后的行为也要显式设计——等、快速失败还是降级，别让默认行为变成无限排队直到内存爆掉。

    **Concept Tested:** 并发与限流控制

    **See:** [章节首页](../02-model-access/index.md)

#### 5. 为什么生产系统基本都做"向量 + 关键词"混合检索，而不是只用向量？

<div class="upper-alpha" markdown>

1. 因为同义不同词、精确编号和日期这类硬事实上，向量检索反而不如关键词
2. 因为关键词检索的召回率天然高于向量检索
3. 因为向量库不支持元数据过滤，必须用关键词兜底
4. 因为混合检索的实现成本比纯向量检索低一个数量级

</div>

??? question "Show Answer"
    The correct answer is **A**。向量检索的本质是"找相似的文字块"，不是"找正确答案"，它有两个软肋：问法太短或太长时向量不稳定，而同义不同词、编号、日期这类硬事实恰恰是关键词的强项。选 C 是把两件事搞混了——元数据过滤是向量库的正统能力（`filter` 按 tenant 之类字段做结构化条件），跟要不要加关键词检索无关。

    **Concept Tested:** 向量库基础操作

    **See:** [章节首页](../02-model-access/index.md)

#### 6. 为什么说召回的 TopK 调得太小，"后面再强的重排也救不回来"？

<div class="upper-alpha" markdown>

1. 因为重排模型的输入长度上限低于召回条数，超了就直接报错
2. 因为重排只在语义层打分，看不见候选的原文
3. 因为 K 直接决定召回天花板，正确答案没进候选，重排只能在候选里排序
4. 因为 K 太小会触发向量库降级，返回一批无关结果

</div>

??? question "Show Answer"
    The correct answer is **C**。重排是候选集内部的"最后一公里"，它的上限被候选集锁死——答案压根没被捞进来，排第一也送不进模型。经验起点是 K = 20~50 再靠重排收敛到最终 3~5 条。正确的调法是在评测集上分别跑 K=10、20、50、100，看"正确块是否进入候选"这个指标何时饱和，饱和之后继续加 K 就是纯浪费。

    **Concept Tested:** TopK召回调参

    **See:** [章节首页](../02-model-access/index.md)

#### 7. 按 token 预算截断对话历史时，必须永远保留下来的是哪两条消息？

<div class="upper-alpha" markdown>

1. system 消息和模型上一轮的回复
2. system 消息和用户的第一个问题
3. system 消息和全部工具调用记录
4. system 消息和最近一轮的原文

</div>

??? question "Show Answer"
    The correct answer is **B**。用户的第一个问题常常含任务背景，丢了它模型就不知道自己在干什么，后面几轮的"它""那个方案"全成了悬空指代。system 消息则承载角色与边界，同样不能截掉。另一个要点是按 token 预算而不是按轮数截断——不同语言每轮的 token 数差异极大，按轮数会严重超支。

    **Concept Tested:** 对话历史管理

    **See:** [章节首页](../02-model-access/index.md)

#### 8. 代理循环里出现"同一个工具被反复调用"的死循环，正确的处理是下面哪一种？

<div class="upper-alpha" markdown>

1. 调高 `max_steps` 上限，给模型更多机会自己想明白
2. 干脆取消步数上限，让模型自己判断什么时候该结束
3. 换一个更强的模型重跑同样的任务
4. 记录已调用过的工具签名，重复三次就中止并让模型直接总结

</div>

??? question "Show Answer"
    The correct answer is **D**。死循环的止损靠显式检测而不是靠模型自觉：记录已调用过的工具签名，重复三次即中止，并要求模型基于已有结果直接收尾。选 A 会把一次 3 步的调用放大成一次 30 步的账单，而 B 直接拆掉了代理最关键的保险——步数上限、成本预算、工具超时熔断，缺一个就可能烧钱。

    **Concept Tested:** 代理执行循环

#### 9. 把 Notebook 改造成服务时，`/ask` 接口收到模型限流异常应该返回什么？

<div class="upper-alpha" markdown>

1. 返回 200，响应体里写 `{"error": "model busy"}`
2. 返回 429，状态语义要能指导客户端是否重试
3. 返回 500，因为限流属于服务端故障
4. 返回 400，因为请求里指定的模型名不合法

</div>

??? question "Show Answer"
    The correct answer is **B**。统一错误处理要求分三类语义返回：4xx 参数错、5xx 服务错、429 限流，而状态语义必须能指导客户端重试——429 让客户端退避后重试，500 让它报警。选 A 最危险：监控和网关都只认状态码，把错误混在 200 里，等于把限流事故变成一次"看起来完全成功"的调用。

    **Concept Tested:** 从Demo到服务封装

    **See:** [章节首页](../02-model-access/index.md)

#### 10. 本章的中级 RAG 流水线里，"候选为空"这个分支为什么不能省？

<div class="upper-alpha" markdown>

1. 因为检索不到候选时应该返回"资料库里没有相关内容"的拒答，硬答正是幻觉事故的主要来源
2. 因为空候选说明向量库故障，必须降级到固定间隔重试再查一次
3. 因为只要拒答，系统的可用性指标就会自动达标
4. 因为空候选说明查询改写写错了，应该把原问题原样再查一遍

</div>

??? question "Show Answer"
    The correct answer is **A**。RAG 的本质是把回答约束在指定的一小片资料里，资料没覆盖到的事它必然答错。示例代码里 `if not candidates` 直接返回一句换问法试试的提示，就是为了守住这个边界——拒答也是一种能力。选 B/D 都是在错误的层面排查：候选为空先分清是"库里真没有"还是"检索失灵"，两者要用失败归因区分，不能一律重查。

    **Concept Tested:** 中级RAG全流程

    **See:** [章节首页](../02-model-access/index.md)
