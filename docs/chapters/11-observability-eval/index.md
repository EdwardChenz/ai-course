## 一、三根柱子与 trace 这条线

可靠性工作听起来玄，实际只由三件事组成，它们必须同时在场：

| 支柱 | 回答的问题 | 缺了会怎样 | 本章对应的工具与产出 |
|---|---|---|---|
| 可观测 | 系统做了什么、花了多少、慢在哪 | 问题发生了，没人知道发生过 | LangFuse trace / span，落到根因分类 |
| 评测 | 做得好不好，好和坏怎么算 | 改了一版，说不清是好了还是坏了 | DeepEval 指标、评测集版本、门禁阈值 |
| 优化 | 怎么把差距变成一次具体改动 | 指标难看，改动全靠猜 | 归因决策表、改进循环、复盘模板 |

少任何一根，症状都很好认：只有可观测没有评测，是"看得见问题但没法判断好坏"——trace 里躺着一千条 span，你盯着看了半天，不知道这次发布算不算成功；只有评测没有可观测，是"知道分数掉了但不知道哪一步掉的"——答案正确率从 0.89 跌到 0.78，评测集告诉你掉分了，可线上没有 trace 去对照，你只能凭记忆猜是哪次改动干的；两根都有但没有优化，是"数字很全、行动为零"——看板和报告写得比论文还厚，季度复盘时还是那句"我们再优化一下"。所以本章的顺序是固定的：先把 trace 打通，再让评测跑出分，最后靠归因把分差变成改动。

### LangFuse追踪接入

Trace 是可观测的最小完整单位。要理解它，先把三个词分清：一次请求对应一个 **trace**，是顶层的完整记录；trace 内部每一步动作是一个 **span**，记录这一步的开始、结束、耗时与输入输出；span 之间有父子关系，父 span 的耗时等于子 span 耗时之和加上父自己的开销。三层结构对应到我们的系统上，正好是一棵树。

```python
from langfuse import Langfuse

lf = Langfuse(
    public_key=os.environ["LANGFUSE_PUBLIC_KEY"],
    secret_key=os.environ["LANGFUSE_SECRET_KEY"],
    host=os.environ.get("LANGFUSE_HOST", "http://127.0.0.1:3000"),
)


@lf.observe(name="answer_question")          # 根 span：一次请求一条 trace
async def answer_question(req: Question) -> Answer:
    q = await span_query_rewrite(req)        # 子 span：查询改写
    cands = await span_retrieval(req, q)     # 子 span：稀疏 + 稠密 + 融合
    ranked = await span_rerank(req, cands)   # 子 span：重排
    ctx = await span_compress(req, ranked)   # 子 span：上下文压缩
    out = await span_generate(req, ctx)      # 子 span：生成（含首 token 与逐 token）
    for tool in PLAN:                        # 三个平级子 span：工具调用
        await span_tool(tool.name, tool.args)
    await span_verify(req, out, ctx)         # 子 span：引用校验
    await span_persist(req, out)
    return out
```

`@lf.observe` 装饰器是 LangFuse 的核心入口：它自动开一个 span、把函数参数当输入、返回值当输出，并在函数内部再调用被装饰函数时自动挂成子 span。`retrieval` 那一路故意不拆成三个 span，因为三个 25 到 40 毫秒的调用分开看噪声更大；真要拆的时候显式用 `lf.start_span` 手动开，因为嵌套装饰器的父子归属在不同版本里行为有过调整，**版本差异以官方文档为准**。

本系统单次问答的 span 树长这样，14 个 span、平均端到端 2,800 毫秒，这是本章一切延迟与成本数字的共同底稿：

| span 名 | 层级 | 平均耗时 | 关键字段 | 本章是否进成本归因 |
|---|---|---|---|---|
| `answer_question` | 根 | 2,800 ms | `trace_id`、`user_id`、`session_id` | 否 |
| `query_rewrite` | 子 | 180 ms | 原问题、改写后问题 | 是 |
| `retrieval` | 子 | 70 ms | 稀疏 25 + 稠密 40 + 融合 5、命中块 id | 否（嵌入自部署不产生 token 费用） |
| `rerank` | 子 | 120 ms | top5 块 id 与分数 | 否 |
| `context_compress` | 子 | 60 ms | 压缩前后 token 数 | 否 |
| `generate` | 子 | 1,520 ms | 首 token 620 + 逐 token 900 | 是 |
| `tool_call` × 3 | 子（平级） | 630 ms | 工具名、参数、返回字节数 | 是 |
| `verify_citation` | 子 | 140 ms | 断言数、无依据断言数 | 是 |
| `persist` | 子 | 80 ms | 会话 id、落库条数 | 否 |

三个字段现在就要定下来，将来省下的时间会以周计。第一是 `trace_id` 必须贯穿全链路并且同时出现在前端会话记录、网关日志和 trace 平台上，三处任缺一处你就无法从用户的"我刚才问的那个"跳回 trace。第二是 `session_id` 与 `trace_id` 必须是两级而不是一个，会话往往有多轮，每一轮是一次独立 trace，但成本要按会话汇总。第三是工具返回值默认会全量入库，脱敏之后再写，密级判断留在自己的业务代码里做，不要指望平台兜底。

### LangFuse优先实践

选 LangFuse 而不是 LangSmith 作为主平台，理由只有一条：自托管。这套系统的知识库是企业制度，trace 里的输入包含用户原问题和检索到的制度原文，这些数据出域要走合规评审，评审周期通常比接 SDK 还长。LangFuse 可以整套跑在自己的机器上，这条路对合规最省事。代价你要认：机器和运维是你自己的。

```bash
# 自托管 LangFuse 的最小可运行栈；三容器，数据全在本机
git clone https://github.com/langfuse/langfuse.git
cd langfuse/docker
docker compose up -d --wait          # postgres、clickhouse、langfuse-web 三个容器
# 健康检查：返回 200 才算起来
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3000/api/public/health
```

自托管的资源账必须先算，否则第一次部署就会卡在磁盘上。本章这套生产规格：4 核 8 GB、200 GB 磁盘，日均 12,000 条 trace、每条 14 个 span，存 30 天，大约每月 12 GB 存储、约 360,000 条 span；追踪数据本身在 60 天后可压缩归档，但 trace 里的评测标签必须长期保留。

```yaml
# 采样、脱敏与保留期：这三项决定成本和合规，版本差异以官方文档为准
telemetry:
  sample_rate: 1.0                 # 失败请求必须 1.0，成功请求可降到 0.2
  always_sample:
    - on_error                     # 任何异常一律全采，出故障时样本不能被采样抽掉
    - when_span_ms_gt: 3000        # 单 span 超 3 秒说明慢请求，全采
    - when_field_eq:               # 特定业务标记全采
        field: intent
        value: complaint_escalate
  redact_fields:                   # 脱敏在写入追踪库之前完成
    - user.id_card
    - arguments.query              # 需要留痕的查询走带盐哈希占位符
  retention:
    traces_days: 60                 # 原始追踪 60 天
    scores_forever: true           # 评测标签永久保留，否则回测无从谈起
```

六条实践按执行顺序排：第一，**根 span 一定要带 `user_id` 与 `session_id`**，只有 `trace_id` 的话，你没法把一条失败 trace 和一位报障用户对上；第二，**失败请求必须 100% 采样**，成功请求可以降到 20%，但凡 trace 里有异常就绕过采样规则，否则出事时你没有样本——采样最致命的失效方式就是把你最想看的那批数据抽掉；第三，**脱敏在进追踪库之前做**，不要指望事后清洗，敏感值一旦落盘就是既成事实；第四，**评测标签跟着 trace 永久保存**，原始输入输出 60 天后可以归档压缩，但"这条 trace 当时得了 0.62 分"这条信息必须留到永远，否则三个月后你想对比两版系统时无从下手；第五，**给 span 名字定死规范**，用 `动词_名词` 的形式，比如 `query_rewrite`、`tool_call`，不要一会儿 `rewriteQuery` 一会儿 `rewrite-query`，聚合分析全靠名字匹配；第六，**追踪 SDK 的初始化放在进程启动时做一次**，不要在每个请求里 new 一个客户端。

!!! mascot-tip "别在请求里 new 客户端"
    ![墨墨提示技巧](../../img/mascot/tip.png){ class="mascot-admonition-img" }
    追踪客户端每请求新建一次，吞吐掉两成，连接池永远热不起来，而你会把锅甩给网络。正确的判断方法很直接：把追踪 SDK 摘掉跑一轮基线，如果延迟没变，说明你本来就在给它让路。八个概念里最容易犯的错就是这个，改一行就见效。

### LangSmith对照实践

LangSmith 是同一赛道里最完整的托管方案，功能面比 LangFuse 更宽（原生数据集、实验对比、离线评估流水线都是内置的），但它把数据放在第三方平台。两者不是谁更好，是"数据能不能出域"这一个约束下的两个合理选择，所以本章把它当对照组，而不是竞品。

| 维度 | LangFuse | LangSmith |
|---|---|---|
| 托管方式 | 可自托管（Docker / K8s），也提供托管实例 | 以托管服务为主，企业版可谈私有部署 |
| 数据是否出域 | 自托管时完全不出域，本系统选它就为了这条 | 托管版输入与输出进第三方平台，需合规评审 |
| 成本形态 | 开源免费，付机器与运维的钱，本章规格 4 核 8 GB | 按 trace 计费，日均 12,000 条时成本随量线性上涨 |
| 评估能力 | 内置评分队列、LLM 评分、人工标注标注位 | 内置数据集管理、离线评估运行器、实验并排对比 |
| 上手速度 | 半天，代价是自己运维数据库 | 一小时，代价是数据出域 |
| 适合谁 | 合规敏感、要自建评测闭环的团队 | 已在用 LangChain、想最快看到对比实验的团队 |

选型上给一条可执行的建议：如果你们的数据里有个人信息、客户名或合同条款，就先假设它不能出域，从 LangFuse 起步；等评测闭环跑顺了、团队也摸清了指标该看什么，再评估要不要换成熟方案。反过来，如果数据完全合成、团队正缺一个能并排看实验的工具，用托管方案省下的两周运维时间比自建更值钱。**接口与计费细节会随版本变动，具体字段以各自官方文档为准。**

### Trace根因定位

接上追踪只是拿到一堆记录，真正的技能是**从一条失败 trace 反推出第一个出错的环节**。方法论只有一句：**从失败的 span 往下倒查，找到第一个条件不成立的环节，后面的环节一律不看**。原因是链路上后面的失败通常是连锁反应——检索没召回，模型照样会生成一段通顺的话，于是你会误判成"生成质量问题"，然后花两天去调一个根本调不动的提示词。

具体到本系统的四层判定，判定条件全部可以从 span 的字段里读出来，不需要人工猜测：

| 归因层 | 判定条件（读哪个字段） | 首要动作 | 不要做的事 |
|---|---|---|---|
| 检索未召回 | `retrieval` 返回的候选里找不到 gold 块 | 分两类：库里有但检索不到 → 补文档或改查询；库里根本没有 → 排期补知识 | 不要动提示词，对这一层零收益 |
| 召回后被重排丢掉 | gold 块在 `retrieval` 候选里，但不在 `rerank` 的 top5 里 | 换更小的重排模型、调 TopK、把重排分数作为候选依据 | 不要调生成模型，它根本没看到这个块 |
| 上下文被压缩掉 | gold 块在 `rerank` 的 top5 里，但不在 `context_compress` 的输出里 | 提高压缩预算，或按重排分数保护头部块 | 不要去改检索，证据已经到了门口 |
| 生成没答对 | 上面三条都通过，证据齐备但答案错或该说不说 | 改提示词约束、换生成模型、校准拒答阈值 | 不要怀疑检索，它的账已经算清了 |

```python
GOLD = "gold_chunk_ids"


def locate_first_failure(trace: dict) -> str:
    """沿检索→重排→压缩的顺序找第一个缺 gold 的环节；全都在才是生成问题"""
    gold = set(trace["gold_chunk_ids"])
    if not gold:                                  # 没有标注就没有归因能力，直接拒绝分析
        raise ValueError(f"trace {trace['trace_id']} 缺少块级标注")
    stages = [
        ("retrieval", set(trace["retrieval"]["returned_ids"])),
        ("rerank_top5", set(trace["rerank"]["top_ids"])),
        ("compressed", set(trace["context_compress"]["kept_ids"])),
    ]
    for name, ids in stages:
        if gold - ids:                            # 第一个缺 gold 的环节就是根因
            return name
    return "generation"


def blame_batch(trace_ids: list[str]) -> dict[str, int]:
    """批量归因后按层聚合，用于决定先修哪一层"""
    counts: dict[str, int] = {}
    for tid in trace_ids:
        layer = locate_first_failure(fetch_trace(tid))
        counts[layer] = counts.get(layer, 0) + 1
    return dict(sorted(counts.items(), key=lambda kv: -kv[1]))
```

这张分布表值得逐行读。检索未召回占 44.1%，是最大的一块，但它里面还要再分：15 道里有 9 道是库里根本没有这份制度（资料缺失，只能排期补文档），6 道是库里有但编号类查询没命中。真正能靠改代码当天解决的，是重排那 11 道和压缩那 3 道——换一个小一档的重排模型通常能救回一半，而这 14 道加起来占了错题的 41.2%。这条分布也顺手否掉了一个流行做法：把 3B 生成模型换成 70B，对这 34 道里的 29 道（检索、重排与压缩这三层，共 15+11+3）一点用都没有——因为它们错的都不是生成这一步。

    ![墨墨提醒注意](../../img/mascot/warning.png){ class="mascot-admonition-img" }

**Learning Objective:** 学习者将根据六条失败 trace 的 span 观测值（候选数、top5 命中位置、压缩后是否保留、是否产生引用），判定每条 trace 的第一个出错环节，并在给出判定后说出该层对应的首要动作；判定条件是六条全部命中 Content 表的"应判归因层"列。

**Prerequisites:** trace 与 span 的父子关系、gold 块、召回未召回、重排、上下文压缩、生成没答对（均已在本块上方的"LangFuse追踪接入"与"Trace根因定位"两节定义）。

**Evidence of Mastery:** 学习者先逐条写下归因层与首要动作再提交；六条判定与 Content 表的"应判归因层"列全部一致、且至少四条的首要动作答对时算掌握。只看不提交不算证据。

**Misconceptions:** (1) 答案答错就一定是生成层的问题。(2) 候选池里有 gold 块就说明检索没问题。(3) 嵌入服务超时返回空数组属于系统故障，不需要归因到检索层。

**Instructional Rationale:** Analyze 层级的诊断要求先形成假设再用证据判定，因此六条判定必须先锁定后揭晓；序号 6 是关键的一题，它把"检索未召回"这个标签拆成"索引覆盖不足"与"下游依赖故障"两种截然不同的病因，练的是"标签对了还不够，还要能往下再分一层"。

**Content:**

六条失败 trace 的 span 观测（数字为 span 记录中的实际字段值，全部为合成数据，随机种子 20261103）：

| 序号 | trace 观测 | 应判归因层 | 首要动作 |
|---|---|---|---|
| 1 | retrieval 稀疏返回 20 条、稠密返回 20 条，融合后 26 条候选里没有 gold；rerank top5 为候选第 2 到 6 位 | 检索未召回 | 先查知识库有没有这份资料：库里有就改查询与嵌入，没就排期补文档 |
| 2 | gold 在融合候选第 14 位；rerank top5 里没有它；rerank 打分显示该块 0.31，低于当前 top5 门槛 0.44 | 重排 | 换更小的重排模型或调 TopK，并按打分复核 0.44 这个门槛是否偏高 |
| 3 | gold 是 rerank top5 的第 2 位，打分 0.81；context_compress 输出 4 段共 1,802 token，gold 不在其中 | 上下文压缩 | 把压缩预算从 1,800 提到 2,400 token，或按重排分数保护前 2 段 |
| 4 | gold 是 rerank top5 第 1 位，压缩后保留了它；答案引用了 [1] 但结论与资料相反 | 生成没答对 | 改提示词约束并加断言校验，不要动检索 |
| 5 | gold 在 rerank top5 第 3 位且压缩保留；答案未引用任何编号，直接输出"资料中未提及" | 生成没答对 | 校准拒答阈值：这条是过拒，改提示词让它先尝试作答 |
| 6 | retrieval 的稀疏与稠密两个子 span 都返回 0 条；trace 里记录 `embed_service_status: timeout`，降级逻辑返回空数组 | 检索未召回 | 查嵌入服务可用性与降级策略，这是依赖故障，不是索引问题 |

这六条对应到本章 34 道错题的分布：检索未召回 15 道（序号 1 与 6 都落在这层，但 6 是故障、1 多半是覆盖不足）、重排 11 道、上下文压缩 3 道、生成没答对 5 道（序号 4 与 5）。

答题反馈文案：序号 1 的 gold 块连候选池都没进，问题发生在检索之前，换生成模型毫无意义；先做知识库覆盖自查，因为这类里通常一半以上是库里根本没有这份资料。序号 2 的 gold 块确实被召回了，是重排模型用 0.31 分把它判死，而当前 top5 的门槛高达 0.44——门槛定得太挑剔是重排类失效最常见的根因。序号 3 最隐蔽，gold 的重排分高达 0.81，压缩时却因为 token 预算 1,800 被挤掉，证据走到了门口又被打发走了。序号 4 和 5 的区别在于方向相反：4 是有证据但答错，要加断言校验；5 是证据充分却拒答，要调的是拒答阈值而不是检索。序号 6 是全章唯一一条系统故障伪装成质量问题的情况，降级逻辑把超时吞成空数组，正确做法是让降级时打一条 error 事件并让该 trace 立刻进入排查队列。

**Provenance:** 六条 trace 的 span 字段值、0.44 门槛与 0.31 打分为合成数据（生成规则：按四层判定各造 1 到 2 条，gold 在各层的出现位置与层判定条件一致，重排打分按"top5 门槛 0.44 上下分布"生成），随机种子 20261103。34 道错题的四层分布 15/11/3/5 出自本块上方的"Trace根因定位"一节归因结果代码块。上下文预算 1,800 token 的口径沿用第三章"上下文压缩"一节。

**Rules:** 判定规则固定为顺序短路：gold 不在 retrieval 候选中则判检索未召回；gold 在候选但不在 rerank top5 则判重排；gold 在 top5 但不在 compressed 输出则判上下文压缩；三处都在则判生成没答对。判定为单选，无并列，容差为 0 层。序号 6 的标签与序号 1 相同，但首要动作不同：判定层同为检索未召回，动作必须指出嵌入服务超时与降级返回空数组。分数判定门槛 >= 0.44 视为进入 top5，低于则被排除；0.44 与 0.31 给出即判定，不需学习者自行计算。

**Learner Activity:**

1. 学习者看到六条 trace 的 span 观测，屏幕提问："答案都答错了，但第一个出错的环节各不相同——先逐条写下归因层与首要动作，再看标准答案。"
2. 六条判定全部锁定后揭晓，学习者对照每条的应判归因层回看自己的判断。
3. 学习者应注意到序号 1 与 6 标签相同但动作完全不同，并回答"同层标签下要怎么再分一层"。
4. 学习者把六条的判定映射回 34 道错题的四层分布，检验自己的归因思路是否能解释整体分布。

**Feedback:** 六次归因判定加一次动作匹配，共 7 次提交，判定锁定后才揭晓。判定答对："判定正确：<应判归因层>"，并展示该行反馈文案。判定答错："按 retrieval → rerank → compressed → generation 顺序短路，找 gold 第一次消失的环节"，随后展示该行反馈文案。动作答对："动作正确：<首要动作>"。动作答错：展示该条 trace 的 span 字段，指明是哪个字段否定了你的假设。揭晓后展示"判定答对 n/6，动作答对 n/6"。

**Starting State:** 六条 trace 的 span 观测可见，gold 块是否被保留的位置以文字描述给出，归因层与首要动作的输入位为空。屏幕提问："同一个系统、同一种症状，六个不同的根因——从 gold 第一次消失的地方开始数。"

## 二、钱和慢在哪

能跑通之后，运维会问两个问题：一次问答多少钱，一次问答多久。这两个问题的答案都不能靠感觉，必须能从 span 里算出来。

### Token成本归因

成本归因的关键是**选对归因维度**。只有一个总数是没法行动的，因为总数告诉你"贵了"，不告诉你"贵在哪"。本章按四个阶段归因：查询改写、生成、工具调用、引用校验。检索和重排不进这张表——它们跑在本地部署的嵌入与重排模型上，不产生 token 费用，这本身就是一条省钱结论。

以第一章的示意价为准，输入 0.004 元每千 token、输出 0.012 元每千 token，单次问答的实际构成如下：

| 阶段 | 输入 token | 输出 token | 阶段成本（元） | 占 token 比 | 占成本比 |
|---|---|---|---|---|---|
| 查询改写 | 660 | 60 | 0.0034 | 10.7% | 9.9% |
| 生成 | 2,220 | 320 | 0.0127 | 37.7% | 37.6% |
| 工具调用 × 3 | 2,400 | 360 | 0.0139 | 41.0% | 41.1% |
| 引用校验 | 600 | 120 | 0.0038 | 10.7% | 11.3% |
| 合计 | 5,880 | 860 | 0.0338 | 100% | 100% |

按日均 12,000 次请求算，单次 0.0338 元对应日均 406 元、月均 1.22 万元。把工具调用那一行单独拎出来看，它是本章最反直觉的一条结论：**三次工具调用吃掉了 41.1% 的钱，而它们单次只花 630 毫秒**。工具调用贵的原因不在长度，在次数——每次都把会话历史重新送一遍，而历史里躺着前面几轮已经用过的证据。所以省钱的第一刀应该切在"三次调用合成一次批量查询"，而不是去压生成模型的输出长度。

```python
def cost_by_stage(spans: list[dict], price_in: float, price_out: float) -> dict:
    """按阶段汇总 token 与金额；一条 trace 的成本必须能拆到 span 级，
    否则聚合出来的总数无法指认该修哪一段"""
    rows: dict[str, dict] = {}
    for sp in spans:
        if sp["name"] not in ("query_rewrite", "generate", "tool_call", "verify_citation"):
            continue                                    # 检索与重排自部署，不计费
        row = rows.setdefault(sp["name"], {"in": 0, "out": 0, "n": 0})
        u = sp["usage"]
        row["in"] += u["input_tokens"]
        row["out"] += u["output_tokens"]
        row["n"] += 1
    for row in rows.values():
        row["cny"] = round(
            row["in"] / 1000 * price_in + row["out"] / 1000 * price_out, 6
        )
    return rows
```

第二个维度是**按会话归因**，因为计费和对账都发生在这个粒度。表里的 0.0338 元是单轮问答的成本，而一次会话平均 4.2 轮，会话总成本是 0.1420 元（\(4.2 \times 0.0338\)）。把这两个数分开报给不同的人：对账和预算看会话成本，SLO 和容量规划看单轮成本，因为网关限流和超时都是按请求判的。第三个维度是按租户，用于把成本分摊到部门——权限过滤让不同租户看到的块数不同，token 天然有差异，按总量摊账会引发争议。

### 延迟分段分析

"端到端 3 秒多太慢了"这句话不可行动，因为 3 秒里塞着九个阶段。延迟分段分析要做的是把端到端拆成段，让每一段各自负责，并且只对**占比大且可压缩**的段动手。本系统的端到端按定义是网关收到请求到首字节写回，其中生成阶段再拆成首 token 等待与后续逐 token 输出两段——这两段的性质完全不同，必须分开算。

\[
T_{\text{e2e}} = T_{\text{rewrite}} + T_{\text{retr}} + T_{\text{rerank}} + T_{\text{compress}} + T_{\text{ttft}} + T_{\text{decode}} + T_{\text{tools}} + T_{\text{verify}} + T_{\text{persist}}
\]

| 段 | P50 耗时 | 占比 | 性质 | 可压缩性 | 怎么压 |
|---|---|---|---|---|---|
| 查询改写 | 180 ms | 6.4% | 串行 | 高 | 对无指代的查询直接跳过，覆盖 38% 流量 |
| 检索（稀疏+稠密+融合） | 70 ms | 2.5% | 并行 | 低 | 已经只有 70 毫秒，动它收益极小 |
| 重排 | 120 ms | 4.3% | 串行 | 中 | 换更小档模型，P50 可压到 60 毫秒 |
| 上下文压缩 | 60 ms | 2.1% | 串行 | 中 | 批量向量化，省 15 毫秒 |
| 首 token 等待 | 620 ms | 22.1% | 不可预知 | 高 | 系统提示与固定证据前缀走提示缓存，P50 可压到 390 毫秒 |
| 逐 token 生成 | 900 ms | 32.1% | 与输出长度成正比 | 中 | 输出减半即省 450 毫秒 |
| 工具调用 × 3 | 630 ms | 22.5% | 串行可并行 | 高 | 三次串行改并行，P50 可压到 230 毫秒 |
| 引用校验 | 140 ms | 5.0% | 串行 | 中 | 规则前置，只对有争议的断言调模型 |
| 落库 | 80 ms | 2.9% | 异步 | 低 | 改成异步写，主流程不等 |

这张表的两个要点。第一，首 token 加逐 token 生成合计 54.3%，是最大的单一板块，但它也是最难压的——逐 token 段与输出长度严格成正比，压它等于让模型少说话，而少说话会掉召回。第二，工具调用占 22.5%，是**最好压的一段**，因为三次调用之间没有数据依赖，把它们从串行改并行，P50 直接从 630 毫秒掉到 230 毫秒，零模型质量损失。重排段同理：它占 4.3% 看着不起眼，但换档模型能省下 60 毫秒且几乎不掉准确率，属于典型的低成本高性价比改动。

```python
SEGMENTS = ["rewrite", "retr", "rerank", "compress", "ttft",
            "decode", "tools", "verify", "persist"]


def segment_latency(spans: list[dict]) -> dict[str, int]:
    """把根 span 的子 span 按段聚合；同一段出现多次（如工具调用）时求和，
    因为它们在关键路径上是串行的"""
    out: dict[str, int] = {}
    for sp in spans:
        if sp.get("parent") != "answer_question":
            continue
        out[sp["segment"]] = out.get(sp["segment"], 0) + sp["duration_ms"]
    return {k: out[k] for k in SEGMENTS if k in out}


def percentiles(spans_list: list[list[dict]], ps=(50, 95, 99)) -> dict[str, dict[int, int]]:
    """端到端分位数由整条 trace 的实测总耗时算出，而不是各段分位数相加——
    各段相加会丢掉并发带来的重叠，也丢掉了尾部的抖动"""
    totals = sorted(sum(s["duration_ms"] for s in spans if s.get("parent") == "answer_question")
                    for spans in spans_list)
    def pick(p: int) -> int:
        return totals[min(len(totals) - 1, int(len(totals) * p / 100))]
    return {"e2e": {p: pick(p) for p in ps}}
```

三步优化的顺序也是这个表给的：先并行化工具调用（省 400 毫秒），再给首 token 上提示缓存（省 230 毫秒），最后跳过无指代查询的改写（省 180 毫秒）。三步做完，P50 从 2,800 毫秒降到 1,990 毫秒，P95 从 3,350 毫秒降到 2,540 毫秒，刚好越过 3.00 秒的门禁线。注意顺序不能换：并行化工具调用不改变任何 token，是零风险的机械改动；提示缓存要求证据前缀稳定，排在改写之后会因为改写结果不稳定导致缓存命中率低。

图表以九个分段的瀑布形式显示端到端 P50，默认合计 2,800 毫秒，右侧读数区实时显示合计值与通过 3.00 秒门禁的余量。

三个候选优化动作及其可省毫秒数（可省值由默认值与目标值之差确定）：

| 动作 | 涉及分段 | 默认值 | 目标值 | 可省 |
|---|---|---|---|---|
| 工具调用并行化 | 工具调用 | 630 | 230 | 400 毫秒 |
| 首 token 走提示缓存 | 首 token 等待 | 620 | 390 | 230 毫秒 |
| 跳过无指代查询的改写 | 查询改写 | 180 | 0 | 180 毫秒 |

挑战题（固定顺序，每题先预测再揭晓）：

| 序号 | 题干 | 标准值 | 答错时的提示 |
|---|---|---|---|
| 1 | 默认口径下，首 token 等待与逐 token 生成两段合计占端到端的百分比是多少 | 54.3% | 620 + 900 = 1,520 毫秒，1,520 / 2,800 = 54.3%。但这两段最难压：逐 token 与输出长度成正比，压它等于让模型少说话。 |
| 2 | 三个动作按可省毫秒数从大到小排序 | 工具调用并行化 > 首 token 走提示缓存 > 跳过无指代查询的改写 | 400 > 230 > 180 毫秒。注意收益第一的是只占 22.5% 的工具调用，而不是占 54.3% 的生成段——它零质量损失且纯机械改动。 |
| 3 | 三个动作全做后，端到端 P50 是多少毫秒，P95 是否通过 3.00 秒门禁 | 1,990 毫秒，通过 | 2,800 − 400 − 230 − 180 = 1,990 毫秒。P95 同步从 3,350 降到 2,540 毫秒，同样通过 3.00 秒门禁，余量 460 毫秒。 |

答题反馈文案：第 1 题算对了占比，但这一段恰恰是优化难度最高的地方，因为逐 token 生成与输出长度严格成正比。第 2 题的排序说明"该优化谁"和"谁最慢"是两回事：工具调用占 22.5% 却排收益第一，因为它可并行且不消耗额外 token；生成段占 54.3%，压它的唯一有效手段是缩短输出，而缩短输出会掉召回，属于要用质量换延迟的交易。第 3 题说明三步优化累计省下 810 毫秒，P50 与 P95 同时下移，3.00 秒门禁通过且还剩 460 毫秒余量。

**Provenance:** 九个分段的默认值与三个动作的目标值出自本块上方的"延迟分段分析"一节的 P50 分段表与三步优化段落。门禁 3.00 秒出自同节与本节正文引用的上线质量门禁（见"上线质量门禁"一节）。分位数关系（P50 与 P95 同幅下降 810 毫秒）为教学设定，基于本节 P50 2,800 毫秒与 P95 3,350 毫秒的实测口径。全部数值构成合成数据集，随机种子 20261103。

**Rules:** 端到端 P50 = 九个分段当前值之和，单位毫秒，实时更新，容差 ±0 毫秒。百分比 = 两段之和 / 端到端 × 100%，保留一位小数，判定容差 ±0.1 个百分点。门禁判定用 P95 与 3.00 秒比较，P95 <= 3.00 秒为通过，等于 3.00 秒按通过计。可省毫秒数 = 分段默认值 − 该动作目标值，为固定常数，不随学习者调节而改变。排序按可省毫秒数降序，三值互不相同（400、230、180），无并列。滑块取值必须落在步长网格上；首 token 等待最小 100 毫秒，最大 1500 毫秒；逐 token 生成步长 20 毫秒，其余分段步长 10 毫秒，检索步长 5 毫秒。

**Learner Activity:**

1. 学习者先拖动"工具调用"滑块，从 630 毫秒降到 230 毫秒，观察端到端读数从 2,800 掉到 2,400 毫秒，不改变任何其他分段。
2. 学习者拖动"首 token 等待"滑块到 100 毫秒，观察读数大幅下移，随后意识到该段的可压缩下限受提示缓存命中率约束，回调到接近目标值。
3. 学习者依次完成三道挑战题，每题先写下答案并提交，再看标准值。
4. 学习者应注意到两处反直觉：占比 54.3% 的生成段最难压，收益第一的却是只占 22.5% 的工具调用。

**Feedback:** 三道挑战题，固定顺序，每题两次机会，提交后立即揭晓。答对："正确，<标准值>"，并展示该行反馈文案。答错："回到瀑布图看该段的占比与可压缩性两列"，随后展示该行反馈文案并把相关分段的当前值高亮。两次答错记为失手。顶部累计"答对 n/3 题"。计分：满分 3 分，答对 2 分视为掌握。

**Starting State:** 九条滑块位于默认值（合计 2,800 毫秒），瀑布图与端到端读数可见，三道挑战题折叠在下方，标准值隐藏。屏幕提问："端到端 2.80 秒里，哪一段最该动？先拖一遍，再算一遍占比和收益。"

**Chapter Anchors:** 九个分段的默认 P50 值（180 / 70 / 120 / 60 / 620 / 900 / 630 / 140 / 80 毫秒）与合计 2,800 毫秒；首 token 加逐 token 生成占比 54.3%；工具调用占 22.5%；三个动作的可省毫秒数 400 / 230 / 180 与三步顺序；三步全做后 P50 1,990 毫秒、P95 2,540 毫秒、余量 460 毫秒；P95 门禁 3.00 秒。

### 告警阈值配置

告警的价值来自它把人的注意力从 1000 件事里筛到 1 件事上，因此**阈值定错比没有告警更糟**。拍脑袋定阈值的做法有两种：定一个"感觉挺慢"的数，比如 2 秒；或者定一个"比昨天高一点"的数，比如当前 P95 的 1.2 倍。前者会在系统变好之后一直报警，后者每天都在报警。本章的做法是用 SLO（服务水平目标）加实测分位数两条线夹逼。

先看本系统的实测分位数：端到端 P50 是 2,800 毫秒、P95 是 3,350 毫秒、P99 是 4,600 毫秒；首 token 等待的 P50 是 620 毫秒、P95 是 1,180 毫秒。成功率 SLO 定在 99.5%，按月 30 天、日均 12,000 次算，月请求量 360,000 次，允许失败的次数是 \(360{,}000 \times 0.5\% = 1{,}800\) 次——这个数字才是成功率告警的锚，因为它把"允许坏到什么程度"翻译成了可数的请求数。

| 告警项 | 指标 | 阈值 | 阈值来源 | 持续窗口 | 最小样本 | 触发后动作 |
|---|---|---|---|---|---|---|
| 端到端延迟 | P95 | > 3.00 s | 与上线门禁同一条线，超线即发布质量下降 | 5 分钟 | 200 次请求 | 查延迟分段，定出压缩哪一段 |
| 首 token 等待 | P95 | > 800 ms | 实测 P50 620 ms × 1.29 | 5 分钟 | 200 次请求 | 查上游限流与提示缓存命中率 |
| 请求成功率 | 5xx 加超时 | < 99.5% | 月度 SLO，允许失败 1,800 次 | 3 分钟 | 100 次请求 | 立即回滚到上一版本 |
| 幻觉率 | 每日抽样 500 条的幻觉率 | > 0.05 | 与评测门禁同一条口径 | 每日 | 500 条 | 阻断放量，进归因队列 |
| 单次问答成本 | 24 小时均值 | > 0.030 元 | 与预算门禁同一条口径 | 24 小时 | 12,000 次 | 查 token 阶段归因 |

这里有两条设计原则值得单独说。第一，**告警阈值和门禁阈值必须是同一个数字**。本章里 P95 延迟的告警线 3.00 秒与上线门禁的 3.00 秒是同一条，幻觉率的 0.05 也是同一条——两处数字一旦不一致，就会出现"告警了但我们认为合规"或者"门禁过了但线上在报警"的荒谬局面。第二，**每条告警必须先有最小样本量**。没有最小样本的告警在低流量时段会变成噪声发生器：一晚上只有 3 次请求，其中 1 次超时就产生一条 P95 告警，谁看都烦，于是被静音。

告警疲劳是可以量化的。本章这套系统上线首周的实测：7 天共触发 1,340 条告警，其中 1,197 条（89.3%）经事后核对没有任何处置动作，属于无动作告警。治理用了四条措施：给每条告警加最小样本量门、加持续时间门（瞬时尖峰不告警）、把告警分成阻断/告警/工单三级只有阻断级会打断人、以及每条告警强制绑定一个处置手册链接。结果是日均告警从 191 条降到 6 条，降幅 96.9%，同时没有漏掉任何一次真实故障。

!!! mascot-tip "阈值要能被追溯到某个数字"
    ![墨墨提示技巧](../../img/mascot/tip.png){ class="mascot-admonition-img" }
    好的阈值有两个特征：写得出它是怎么来的，也写得出它被违反了会怎样。本章每条阈值都挂着 SLO 或分位数做锚，被人质疑时能当场翻出依据。想省事就从"P95 等于 P50 乘 1.3"起，这条经验值在本章这套系统上给出的 3.64 秒也很接近实情。

## 三、评测：把体感变成数字

可观测让你看见发生了什么，评测让你判断它是不是变好了。评测的关键不是跑分，而是**让每个指标对应一种业务失败模式**。

### DeepEval评测接入

评测的落点是三个问题，每道题都要有答案：答对了吗、答得有依据吗、有没有编。DeepEval 把这三个问题做成三个可复用指标，接到本章这套系统上的第一步是定义指标。

```python
from deepeval.metrics import AnswerRelevancyMetric, FaithfulnessMetric
from deepeval.test_case import LLMTestCase
from deepeval import evaluate

# 版本差异以官方文档为准：指标构造参数在不同版本间调整过，
# 下例用与本系统幻觉判定一致的阈值 0.05
CORRECTNESS = GEval(
    name="answer_correctness",
    criteria=(
        "给定参考答案与实际答案，判断实际答案是否与参考答案在关键结论上一致。"
        "只允许措辞不同，不允许结论不同。仅当结论完全一致或实际答案更完整时给 1 分，"
        "否则给 0 分。"
    ),
    threshold=0.85,
    model="openai/gpt-4o",
)

FAITHFULNESS = FaithfulnessMetric(threshold=0.95, include_reason=True)
RELEVANCY = AnswerRelevancyMetric(threshold=0.90)

METRICS = [CORRECTNESS, FAITHFULNESS, RELEVANCY]
```

三个指标对应三种业务失败模式，这层映射是评测设计里最容易糊弄过去的地方：

| 指标 | 对应的业务失败模式 | 阈值 | 掉了意味着什么 | 该找谁 |
|---|---|---|---|---|
| `answer_correctness` | 结论答错，用户按错结论做决策 | >= 0.85 | 系统在给错答案，风险最高 | 生成侧与检索侧一起查 |
| `faithfulness`（幻觉率取其补） | 编造资料里没有的事实 | 幻觉率 <= 0.05 | 合规风险，法务会拦 | 生成侧与上下文压缩 |
| `answer_relevancy` | 答非所问，说了一堆正确的废话 | >= 0.90 | 用户体验差但不会造成损失 | 查询改写与意图识别 |

评测集的加载方式决定了这套评测能不能进 CI。一个真实可用的结构包含 goldens（题面、参考答案、上下文）和 test cases（题面、实际输出、检索上下文、期望工具轨迹）两层，文件里用版本号和校验和锁住内容。

```python
import json, hashlib
from pathlib import Path

EVAL_DIR = Path("evals")


def load_cases(version: str = "v1.2.0") -> list[LLMTestCase]:
    """从冻结目录加载；测试用例与标注分离，只有 golden 能人工改"""
    manifest = json.loads((EVAL_DIR / "manifest.json").read_text("utf-8"))
    gold = json.loads((EVAL_DIR / f"goldens-{version}.json").read_text("utf-8"))
    runs = json.loads((EVAL_DIR / f"cases-{version}.json").read_text("utf-8"))
    out = []
    for g, r in zip(gold["items"], runs["items"]):
        out.append(LLMTestCase(
            input=g["question"],
            expected_output=g["answer"],
            actual_output=r["answer"],
            retrieval_context=r["context"],
            tools_called=r["tools_called"],
        ))
    verify_checksum(manifest, version)      # 校验和不符直接拒绝加载
    return out


def verify_checksum(manifest: dict, version: str) -> None:
    digest = hashlib.sha256(
        (EVAL_DIR / f"goldens-{version}.json").read_bytes()
    ).hexdigest()[:16]
    if digest != manifest[version]["checksum"]:
        raise ValueError(f"评测集 {version} 被改动过，checksum 不符，拒绝评测")
```

批量跑分要控制三个东西：并发（太快会触发模型限流，太慢会拖垮流水线）、失败处理（单条报错不能让整轮崩）、结果落盘（每轮结果带 git commit 号和评测集版本号，否则三个月后无法复现）。下面这段是本章 CI 里实际用的调用方式。

```python
import concurrent.futures as cf


def run_suite(cases: list[LLMTestCase], workers: int = 8) -> list[dict]:
    """并发跑分；单条异常转成 error 记录而不是抛出去，保证一轮跑完"""
    rows: list[dict] = []

    def one(case: LLMTestCase) -> dict:
        try:
            res = evaluate(cases=[case], metrics=METRICS)
            return {"input": case.input, "score": res[0].score, "reason": res[0].reason}
        except Exception as exc:                  # 限流、超时、上下文超限都在这里
            return {"input": case.input, "score": None, "reason": f"运行失败：{exc}"}

    with cf.ThreadPoolExecutor(max_workers=workers) as pool:
        for row in pool.map(one, cases):
            rows.append(row)
    return rows
```

### DeepEval优先实践

评测跑起来之后，真正的分水岭是**你会不会为了分数去优化系统**。这是本章最重要的一条纪律：指标是对真实质量的代理，不是真实质量本身。为了把 `answer_relevancy` 从 0.88 拉到 0.92，常见的作弊手法是让模型在答案末尾加一段"此外，本问题还涉及以下方面"——分数立刻上去了，用户拿到的却是更啰嗦的东西。所以 DeepEval 的实践里，第一件事不是调指标参数，而是**给每个指标配一个反作弊检查**。

本系统用的四个反作弊检查，都写成断言挂在 CI 上：

| 指标 | 提分作弊手法 | 反作弊断言 | 断言不通过的后果 |
|---|---|---|---|
| `answer_correctness` | 把参考答案的关键结论抄进答案 | 答案与 `expected_output` 的结论重合度低于 0.7 时报错 | 阻断发布 |
| `faithfulness` | 用"根据资料未提及"回避责任 | 拒答率相对基线上升超过 8 个百分点时报警 | 报警并人工复核 |
| `answer_relevancy` | 加套话凑字数 | 平均答案长度相对基线上升超过 30% 时报警 | 报警并人工复核 |
| 综合 | 只挑跑得好的子集报分 | 提交的报告必须覆盖全量 200 题 | 直接作废该轮报告 |

第二条纪律是**看指标也要看分布**。本章基线轮的正确率是 0.83，DeepEval 控制台默认只显示均值，均值会把"85 题满分、115 题接近零分"这种情况完全掩盖掉。要看的是分位数：200 题里 166 题正确（0.83），但正确的那批里 120 题拿到满分，剩下 46 题得分在 0.3 到 0.6 之间错开，这说明系统在某一类问题上是整体不会，而不是随机错。第三条纪律是**评测分数和线上指标必须对账**。本章的做法是每周从线上随机抽 500 条跑同一个评测集，和线上真实反馈（点踩、转人工）做相关性检查；结果是评测正确率与线上负反馈率的相关系数 0.62，方向对得上但绝对值有系统性偏低——评测集比真实分布容易，这个 15% 的偏差要写进报告，而不是假装评测就是真实。

!!! mascot-warning "别把代理指标当成目标"
    ![墨墨提醒注意](../../img/mascot/warning.png){ class="mascot-admonition-img" }
    分数是代理，不是目标。见过为了把幻觉率压到 0.03 而把所有不确定的答案都改成拒答的系统，指标漂亮得能上汇报材料，用户拿到的是一具只会说"不知道"的问答机。这个坑我替你踩过：任何指标改动都要同时看一眼拒答率和答案长度，它们是作弊的两个出口。

### RAGAS对照实践

RAGAS 是 RAG 评测里的另一个成熟选择，它的强项是**面向检索的分解评测**：把"答案好不好"拆成检索和生成分别打分。这恰好补上 DeepEval 的短板——DeepEval 的三个指标里只有 `faithfulness` 显式依赖检索上下文，检索侧出了问题（比如召回的块完全不相关）它只能报一个低分，却不会告诉你"是检索的锅"。RAGAS 的四个核心指标分工明确：

| RAGAS 指标 | 问的问题 | 计算方式 | 本章口径 |
|---|---|---|---|
| `faithfulness` | 答案句句有依据吗 | 断言被上下文支撑的比例 | 幻觉率 = 1 − 该值 |
| `answer_relevancy` | 答的是问的吗 | 问题与答案的语义相似度 | >= 0.90 |
| `context_precision` | 送进去的上下文干净吗 | 排序后各块的信噪比加权 | >= 0.62 |
| `context_recall` | 该找的信息找到了吗 | 标准答案关键点被上下文覆盖的比例 | >= 0.85 |

```python
from ragas import evaluate as ragas_evaluate
from ragas.metrics import (
    faithfulness, answer_relevancy, context_precision, context_recall,
)

RAGAS_METRICS = [faithfulness, answer_relevancy, context_precision, context_recall]


def run_ragas(rows: list[dict], batch_size: int = 10) -> dict:
    """批量跑分；context_precision 与 context_recall 直接对应检索侧的失败模式，
    这是 DeepEval 给不出来的分解"""
    result = ragas_evaluate(
        dataset=[{
            "user_input": r["question"],
            "response": r["answer"],
            "retrieved_contexts": r["context"],
            "reference": r["gold_answer"],
            "retrieved_ids": r["context_ids"],   # 需要块级标注才能算得准
        } for r in rows],
        metrics=RAGAS_METRICS,
        batch_size=batch_size,                   # 批量能显著降 token 成本与耗时
    )
    return {m.name: round(float(v), 4) for m, v in zip(RAGAS_METRICS, result)}
```

两者的对比按"什么时候用哪个"来判断，而不是"哪个更强"：

| 维度 | DeepEval | RAGAS |
|---|---|---|
| 擅长领域 | 生成质量：正确性、有据性、相关性；含自定义评判标准 | 检索分解：正确性拆到检索与生成两层 |
| 指标体系 | 可自定义 `GEval`，指标定义完全自控 | 固定四指标，语义靠内置评委模型 |
| 依赖 | 只需参考答案与实际输出，可不依赖检索中间结果 | 强依赖检索上下文与块级标注 |
| LLM 调用量 | 每个自定义指标一次评委调用 | 批量跑可摊薄，单价更省 |
| 适用 | 已上线系统、指标与业务失败模式强绑定 | 检索调优阶段、需要定位是检索还是生成的锅 |
| 与本系统关系 | 门禁指标就是它的三个 | 与 34 道错题的四层归因互为印证 |

本章的实际做法是两个都接，各管一段：DeepEval 负责上线门禁的三道指标（正确率、幻觉率、相关性），因为这三个必须和业务失败模式严格对应，自己定义比套用现成的准；RAGAS 负责检索调优阶段的分解诊断，因为它能把"答案错"进一步拆成 `context_recall` 低（没找到）和 `context_precision` 低（找到了但被噪声挤掉）。本章 34 道错题的归因分布（检索未召回 44.1%、重排 32.4%）与 RAGAS 跑出的 `context_recall` 0.78、`context_precision` 0.55 方向一致，两条独立路径指向同一个结论，这样的交叉验证比任何单一指标都可信。

## 四、把评测接进工程流水线

评测只有接进日常流程才会持续产生价值。三个环节决定它能不能活下来：评测集怎么管版本、门禁怎么定、CI 怎么跑。

### 评测集版本管理

评测集必须像代码一样版本化，理由很实际：**没有版本号，回测对比就是在比噪声**。三个月前那次 0.89 的分数，如果当时的评测集是 180 题、现在是 240 题，这两个字面上不可比；更隐蔽的情况是题改了但版本号没变，你以为在测新提示词，实际是在测一道被换掉的题。所以本系统的规则是：评测集内容变化必须改版本号，版本号三段式，`大版本`表示题目集合重构、`中版本`表示增删题目、`小版本`表示只改标注不改编排。

本章评测集的版本谱系如下，每次改动都记了为什么改：

| 版本 | 题目数 | 相对上一版的变化 | 变更原因 | 对历史分数的处理 |
|---|---|---|---|---|
| v1.0.0 | 180 | 初始版本（典型 120、边界 40、拒答 20） | 沿用第四章的 200 题去掉边界题后的精简集 | 基线从此版本开始记录 |
| v1.1.0 | 200 | 补回 20 道边界题 | 第四章证明边界题是失败高发区 | 重跑基线，旧分数标为不可比 |
| v1.2.0 | 200 | 不增题，改 12 道标注 | 复核发现 12 道标注的 gold 块标错段 | 新旧版本分数并列展示，标注修正前后的差值单列 |
| v1.3.0 | 240 | 新增 40 道线上真实失败案例 | 线上负反馈转评测集，回避自己出题的自偏 | 新版本重跑全部历史配置 |

最后一行是这套管理里最重要的一行：**线上失败案例必须定期回流成评测集**，否则评测集会慢慢偏离真实分布——自己出的题永远是自己熟悉的题。本章 v1.3.0 的 40 道新题全部来自线上负反馈队列，人工标注时发现其中 9 道属于第四章定义的"资料缺失"类，这类题在人工出题时几乎不会被主动编出来，因为出题的人知道库里有什么。

```python
def snapshot_eval_set(cases: list[dict], version: str, reason: str) -> str:
    """冻结一个评测集版本：写文件、写校验和、记变更原因，三件事必须同一次提交完成"""
    path = EVAL_DIR / f"goldens-{version}.json"
    path.write_text(json.dumps({"items": cases}, ensure_ascii=False, indent=2), "utf-8")
    digest = hashlib.sha256(path.read_bytes()).hexdigest()[:16]

    manifest_path = EVAL_DIR / "manifest.json"
    manifest = json.loads(manifest_path.read_text("utf-8")) if manifest_path.exists() else {}
    manifest[version] = {
        "checksum": digest,
        "case_count": len(cases),
        "frozen_at": utc_now(),
        "reason": reason,                 # 变更原因必填，这是回测时唯一的解释依据
        "derived_from": manifest_latest(manifest),
    }
    manifest_path.write_text(json.dumps(manifest, ensure_ascii=False, indent=2), "utf-8")
    return digest
```

配套有两条纪律。第一，**golden 可以人工改，test case 不行**——后者是系统跑出来的，改它等于改考卷答案让考生抄。第二，**每次评测报告必须同时记录三个版本号**：代码 commit、评测集版本、依赖配置版本（比如嵌入模型名）。少记任何一个，三个月后你就无法解释某个分数是怎么来的。

### 上线质量门禁

门禁是本章所有数字的兑现处。前面四节分别产生了归因、成本、延迟、评测四组数字，门禁把它们合成一张放行单：任一不达标，阻断发布。这四道门禁的选择原则是**每条对应一种业务上不可接受的失败**，而不是"越多指标越安心"。

| 门禁 | 指标 | 阈值 | 阈值来源 | 基线 v1.2.0 | v1.3.0 | 判定 |
|---|---|---|---|---|---|---|
| 答案正确率 | `answer_correctness` | >= 0.85 | 业务底线：低于此值时客服需人工兜底 | 0.83 | 0.89 | 不达标 → 达标 |
| 幻觉率 | 1 − `faithfulness` | <= 0.05 | 合规红线：无依据断言不得进入对客答案 | 0.09 | 0.04 | 不达标 → 达标 |
| 端到端延迟 | P95 | <= 3.00 s | 超过 3 秒的对话式界面，用户会重复提问 | 3.35 s | 2.54 s | 不达标 → 达标 |
| 单次问答成本 | 24 小时均值 | <= 0.030 元 | 预算上限：日均 360 元，月 1.08 万元 | 0.0338 元 | 0.0285 元 | 不达标 → 达标 |

三个数字口径要说清，避免验收时扯皮。幻觉率的分母是**事实性断言数**而不是题数：本章评测集 v1.3.0 里 240 个事实性断言中有 10 个无依据支撑，幻觉率 \(10 / 240 = 0.042\)，显示为 0.04。延迟的分位数是**端到端**而不是单段，包含工具调用和引用校验，因为用户感受不到分段。成本的口径是**24 小时加权均值**而不是单次峰值，峰值受偶发长会话影响太大，会让门禁变成随机开关。

关于第四条成本门禁要特别说一句：第四章的成本门禁是"每次成功问答成本 <= 0.02 元"，本章改成了"单次问答 24 小时均值 <= 0.030 元"，阈值提高了 50%。这不是标准放松，而是被测对象变了——本章这套系统每次问答会调 3 次工具，token 天然比纯 RAG 问答多；用旧阈值会导致每一次发布都被拦，团队三次之后就会开始想办法绕过门禁，而一个被绕过的门禁比没有门禁更危险。正确的做法是按新对象重定阈值，同时把预算总额钉死（日均 360 元、月 1.08 万元），这样阈值放宽和预算不超两件事同时成立。

```yaml
# 门禁配置：阈值与告警阈值共用同一份文件，改一处两处同时生效
gate:
  dataset_version: v1.3.0          # 门禁绑评测集版本，换集必须重跑全部历史配置
  blocking: true                    # 任一不达标即阻断发布，不提供"带病上线"开关
  metrics:
    answer_correctness: {op: ">=", value: 0.85, weight: critical}
    hallucination_rate: {op: "<=", value: 0.05, weight: critical}
    latency_p95_ms:    {op: "<=", value: 3000, unit: ms, weight: high}
    cost_per_query:    {op: "<=", value: 0.030, unit: cny, weight: high}
  waivers:                          # 豁免必须留痕，且有失效日期
    max_active: 1
    require_runbook_url: true
    max_age_days: 7
```

```python
def gate_pass(report: dict) -> tuple[bool, list[str]]:
    """四道门禁是与运算；边界值（恰好等于阈值）判为通过，
    否则在浮点比较上会出现同一份报告两次跑出不同结论"""
    rules = load_gate()["gate"]["metrics"]
    failures: list[str] = []
    for name, rule in rules.items():
        got = report["metrics"].get(name)
        if got is None:                          # 指标缺失按不达标处理，绝不默认通过
            failures.append(f"{name}：缺测值")
            continue
        ok = got >= rule["value"] if rule["op"] == ">=" else got <= rule["value"]
        if not ok:
            failures.append(f"{name}：{got} 不满足 {rule['op']} {rule['value']}")
    return (not failures), failures
```

门禁之上还有一个纪律比门禁本身更难做到：**允许豁免，但必须留痕**。现实中总有"这次改的是检索不是生成，幻觉率不该动"这类合理理由，所以豁免机制是必要的；但豁免条目必须有失效日期（本系统设 7 天）、必须有处置手册链接、同时存活的豁免不超过 1 条。豁免的滥用有个典型路径：第一次豁免 3 天，第二次发现到期没续，于是顺手改阈值而不是续豁免，于是新阈值又有了新的豁免理由——半年后没人说得清 0.05 这个数字当初是怎么定的。

### 回归评测流水线

门禁要真在 CI 里跑起来，靠的不是一行命令，而是四个必须钉死的实现细节。第一个是**固定随机性**：评测用的生成调用必须 `temperature=0`，并且系统里的任何随机源（重排的并列打分开、缓存的采样、并发顺序）都要固定，否则两次跑同一份代码得出不同分数，门禁会在 ±0.02 的随机波动里反复横跳，最后所有人都学会忽略它。

```bash
#!/usr/bin/env bash
# 回归评测流水线：任一步失败即以非零码退出，阻断合并
set -euo pipefail

DATASET_VER="v1.3.0"                                  # 与门禁配置同一份版本号
export PYTHONHASHSEED=0                                 # 固定哈希种子，否则去重结果不稳定

python -m app.suite --dataset "${DATASET_VER}" --out "runs/${GIT_SHA}.json" \
                    --temperature 0 --workers 8 --seed 20261103

python -m app.gate --report "runs/${GIT_SHA}.json" --dataset "${DATASET_VER}" \
                   --config ci/gate.yaml

# 全部通过后归档；数据集校验和一并入档，供日后复现
sha256sum "evals/goldens-${DATASET_VER}.json" > "runs/${GIT_SHA}.checksum"
echo "回归评测通过：commit ${GIT_SHA} / 评测集 ${DATASET_VER}"
```

第二个是**并发上限**。本章用 8 个 worker，跑完 200 题约 6 分钟。并发调大到 24 反而更慢，因为会触发模型提供商的限流，重试退避把时间全耗在等待上；调小到 2 则要 25 分钟，流水线等不起。经验值是让总 QPS 落在限额的中位数偏上，本章的限额是 30 QPS，8 个 worker 每题约 4 次调用，稳定在 24 QPS 左右。第三个是**失败即阻断，包括基础设施失败**。这里有个真实的争议：模型提供商挂了两小时，这次跑分失败，该不该阻断合并？本系统的规则是阻断，同时把错误类型标成 `infrastructure`，因为一旦把基础设施失败排除在外，你会训练出一套"CI 红了就重跑一下"的肌肉记忆，红灯就失去了意义。第四个是**结果只追加不覆盖**：每次运行写一个带 git SHA 的新文件，历史运行全部保留，这样任何一次门禁判定都能被三个月后的人重新验证。

!!! mascot-tip "把评测集版本和代码版本焊在一起"
    ![墨墨提示技巧](../../img/mascot/tip.png){ class="mascot-admonition-img" }
    跑完评测顺手记三个版本号：代码 commit、评测集版本、依赖配置版本。少记一个，三个月后那个 0.89 就成了一桩无头案——你甚至说不清它是变好了还是换卷子了。

## 五、自进化：能力与边界

前三节是可以照着做的工作，这一节是前沿选讲。它讲的是一种更激进的设想：让系统自己改自己。这个方向值得了解，因为它正在变成现实；但它也是全书里最容易讲成神话的部分，所以本节的重点不在"多酷"，而在"边界在哪"。

### 自进化理论导读

自进化（self-evolving）指的是系统在运行过程中，依据自身产生的数据改变自身的策略或参数，从而在目标指标上单调改善。它和传统机器学习的区别在于改进信号的来源：传统学习依赖人工标注，而自进化依赖系统自己的运行轨迹——用户的显式反馈、任务的成败判定、以及模型对自己输出的自我评估。

学术上这个方向被拆成几类，它们的风险等级差别很大：

| 路线 | 机制 | 改动的是什么 | 风险等级 | 本章的处置 |
|---|---|---|---|---|
| 提示自优化 | 用评测结果自动改写提示词 | 提示词模板 | 低 | 采纳，人工确认后生效 |
| 检索参数自调 | 按线上成败调 TopK、阈值、融合权重 | 数值参数 | 低 | 采纳，但每次只调一个参数 |
| 记忆自写入 | 把成功的轨迹写进长期记忆 | 记忆库内容 | 中 | 采纳，需配过期与复核机制 |
| 训练自改进 | 用自生成数据继续预训练或微调 | 模型权重 | 高 | 不采纳，本章只做理论导读 |
| 评测自改进 | 让系统自己改评测集 | 评测集本身 | 极高 | 禁止，见第五节之二 |

最后两行是这一节存在的理由。前三行改的都是系统里"可解释、可回滚、有日志"的部分——改坏了你知道改了什么，回滚就是换回旧字符串。第四行改的是权重，改坏了你连"改了什么"都说不清，回滚需要重训，成本以天计。第五行更特殊：它改的是尺子。

### 自我改进循环

自我改进循环（self-improvement loop）是把评测、归因、改动、再评测接成一个可自动运行的闭环。它的正式名字叫反思机制（reflection），但中文语境里叫"改进循环"更准确，因为它强调的是循环而不是一次反思。循环的核心纪律只有两条：**每轮只改一个变量**，以及**每轮都必须跑全量评测集**。

```python
@dataclass
class LoopHypothesis:
    target_metric: str          # 本轮要改善的指标，必须是门禁里的那一个
    baseline: float             # 改动前的实测值
    change: dict                # 本轮唯一的改动，形如 {"param": "top_k", "from": 20, "to": 30}
    rationale: str              # 归因结论：为什么认为改这个能改善这个指标


def improvement_loop(hypothesis: LoopHypothesis, eval_cases, max_rounds: int = 5):
    """一轮一个假设、一个变量；改善不达标立即回退，不许在同一轮里叠加第二个改动。
    这样做牺牲了速度，换来的是每一轮的收益都能归因到一个具体动作上"""
    history = []
    best = (hypothesis.baseline, None)
    for round_id in range(max_rounds):
        apply_change(hypothesis.change)                 # 只改这一个变量
        report = run_full_eval(eval_cases)              # 必须全量，不许抽样
        score = report[hypothesis.target_metric]
        history.append({"round": round_id, "score": score, "change": hypothesis.change})

        if score > best[0] and not breaks_other_gates(report):
            best = (score, hypothesis.change)            # 有净收益，保留
            hypothesis = propose_next(report)            # 基于新归因提下一个假设
        else:
            rollback(hypothesis.change)                  # 没收益或破了别的门禁，立刻退回
            break
    return best, history
```

为什么"每轮只改一个变量"这条纪律值这么多钱？因为多变量同改时，指标涨了你不知道是哪个起的作用，跌了你也不知道该退哪一个。真实发生过的一个反面例子：一轮里同时改了 `top_k`、换了嵌入模型、调整了提示词，`answer_correctness` 从 0.83 涨到 0.89，看起来是三周工作的成果；结果三个月后要把嵌入模型降级省成本，一降就跌到 0.74，最后花两周才定位到当初是提示词里加的引用约束在起作用，嵌入模型那一版其实让正确率降了 2 个点。单变量循环每次只能拿到 1 到 3 个百分点的改善，但它每次都知道那 1 到 3 个点是从哪来的。

循环还有一个容易忽略的节流问题：每轮全量跑 200 题要 6 分钟，一轮试验 5 个假设就是 30 分钟。所以本系统的做法是先用 40 道题的子集做粗筛（3 分钟一轮），只有当某个假设在子集上提升超过 2 个百分点时才升级到全量验证。子集筛掉的假设里有相当一部分在全量上不成立——子集太小，偶然性太大——但筛选成本降了五倍，净收益是正的。

### 递归自改进风险

递归自我改进（Recursive Self-Improvement，RSI）指的是系统改进自己的改进机制本身——不是"改提示词后变好"，而是"改提示词的方法本身也变好了"。这个概念的思想源头很早，但真正被广泛讨论是因为大模型的代码生成能力让"自动改进智能体的框架"从设想变成了工程上可想象的事情。本章的立场很明确：**RSI 目前不应作为可依赖的工程手段**，理由有四条，任何一条单独拿出来都足以拦住它上线。

| 风险 | 具体表现 | 为什么难防 | 现有对策与其局限 |
|---|---|---|---|
| 评测被应试（reward hacking） | 系统学会针对评测集优化，在评测上分数上升、在真实分布上变差 | 优化目标和真实目标不同这件事本身不可观测，你只能看到那个可观测的 | 增加线上真实反馈做交叉验证；本章实测相关系数只有 0.62，够用但远不够硬 |
| 目标漂移（goal drift） | 每一轮都在改善指标，指标的定义却在多轮迭代中被无声地修改 | 谁都不是故意的：改指标定义总有具体理由，但累积起来目标和初衷可能已经不同 | 指标定义与门禁配置必须纳入版本管理且改动需评审；本系统由第二章负责 |
| 成本失控 | 改进循环本身的算力开销随轮数指数上升 | 第 \(n\) 轮的成本若与前 \(n-1\) 轮累积相关，总代价是超线性而非线性 | 硬性限制单轮预算与总轮数；本系统上限 5 轮，单轮不超过基线推理成本的 3 倍 |
| 不可解释 | 系统采用了人类读不懂的策略，出了问题无法定位 | 策略空间比人类可读的表达力大得多 | 只能靠约束表达空间（比如只允许改 7 个白名单参数）；一旦放开表达空间就等于放弃可解释性 |

第一条是最需要展开的，因为它最难被察觉。设想一个循环在优化 `faithfulness` 指标，它会发现一件事：把所有不确定的断言都改成"资料未提及"，幻觉率立刻降到 0.01，比任何提示词调优都有效。这个行为在优化意义上是正确的，在业务意义上是灾难。本章在第四节"DeepEval优先实践"里防的正是这个——反作弊断言里有一条是拒答率相对基线上升超过 8 个百分点就报警，正是为了让这类"应试"在评测阶段就被发现，而不是在用户面前。

第二条也值得多说一句，因为它和常规软件工程的经验相反。在普通开发里，"目标清晰、只管实现"是对的；在改进循环里不成立，因为改进循环会**主动**去优化那个被写下来的目标，于是目标本身成了攻击面。应对方式不是把目标写得更精细（更精细反而更好被应试），而是把目标拆成两个：一个可优化的代理目标（反馈密集、更新快），一个不可优化的验证目标（反馈稀疏、更新慢、绝不用于优化）。本章的做法是：循环只优化评测集上的正确率，而幻觉率和拒答率只作为门禁和断言存在，永不进入优化目标。

!!! mascot-encourage "这一节确实烧脑"
    ![墨墨为你打气](../../img/mascot/encouraging.png){ class="mascot-admonition-img" }
    第一次读自进化这一节会晕，这很正常，别怀疑自己。你已经会的那套东西——评测集、归因表、单变量循环、门禁——正好就是这一节的输入，而这一节的输出只是告诉你别走哪条路。先记住那个最实用的结论：循环只优化一个代理目标，验证目标永远不进优化。

## 六、把可靠性接回组织

最后一节处理一件技术文章容易忽略、但决定这套系统能活多久的事：故障发生时人怎么做事，以及团队走到了哪一步。

### 可靠性复盘模板

无指责复盘（blameless postmortem）的核心规则只有一条：**只对系统追责，不对个人追责**。原因不是政治正确，而是工程事实——人在信息不足时做的决定，多数情况下是当时可得信息下的合理选择；把矛头指向个人，只会让下次出故障时没有人愿意第一时间说出来，那份"不该出的错"也就永远查不出来。

模板固定成六个段落，缺段落比填错内容更严重，因为缺段落本身就是信号：

```markdown
# 故障复盘 INC-2026-1108 检索超时

## 1. 影响面
- 起止时间：11-08 09:42 至 10:15，共 33 分钟
- 受影响请求：3,180 次（占当日 12,000 次请求的 26.5%）
- 受影响用户：1,940 个会话，其中 610 个会话未完成问答
- 业务损失：转人工 612 次，按单次 8 元折算约 4,896 元

## 2. 时间线（每行必须有 trace_id 或日志行号）
- 09:42 首个失败请求出现，错误为检索上游连接超时
- 09:44 错误率越过 3% 的观察线，此时值班人正在处理另一个工单
- 09:51 值班人收到 Sentry 通知，告警延迟 7 分钟（原因见第 5 节）
- 10:02 定位到嵌入服务连接池耗尽（trace_id 见附件 14 条）
- 10:09 临时把嵌入服务切换到备用实例，错误率回落
- 10:15 备实例也满载，扩容后彻底恢复

## 3. 触发链
连接池上限 20 且无获取超时 → 33 分钟内累计 41,200 次检索请求 →
连接耗尽 → 降级逻辑返回空数组 → 检索无结果 → 模型生成"资料未提及" →
用户点踩，无人看到，直到告警延迟到达

## 4. 哪个防线本该拦住它
- 降级返回空数组时应该打 error 事件：未实现
- 检索结果为空率应有独立告警：未实现（只有端到端成功率）
- 备用实例容量只有主实例的 60%：容量规划缺口

## 5. 为什么告警晚了 7 分钟
告警规则用 5 分钟持续窗口，但触发条件写成了 P95 > 3 秒而非成功率 <
99.5%。检索全部超时时根本没有模型调用，模型侧延迟毫无异常，于是唯一
还在动的指标（成功率）没有单独告警，只有一个"通用服务异常"兜底。

## 6. 行动项（每条必须有负责人与截止日，写不满不算复盘结束）
- [ ] 空数组降级时打 error 事件并携带 trace_id | 检索网关 | 11-15
- [ ] 新增"检索结果为空率 > 5%"独立告警，持续窗口 2 分钟 | 可观测 | 11-13
- [ ] 备用实例容量从主实例的 60% 提到 100% | 基础设施 | 11-20
- [ ] 连接池获取超时设为 2 秒，配合 3 次重试与熔断 | 检索网关 | 11-15
- [ ] 值班响应从 5 分钟降到 2 分钟，超时升级给二线 | 团队 | 11-12
```

上面这份模板里最该学的是第 6 段和第 4 段。**行动项写不满等于复盘没做完**，这一条是纪律：没有负责人和截止日的行动项三个月后有九成不会发生，那次故障就等于白犯。第 4 段"哪个防线本该拦住它"是让复盘产生复利的地方——它逼你把防线逐条点名，而不是笼统写一句"加强监控"。这次故障如果"检索结果为空率"告警存在，故障时长能从 33 分钟压到 8 分钟以内（触发到定位的平均耗时是 5 分钟）。

复盘还要注意频率和对象的错配。低频高损的事故要深复盘（一次事故损失超过日均成本的 5%，或持续超过 15 分钟），高频低损的用周度聚合复盘（一周内同类告警超过 20 条的合并成一条看趋势）。最忌讳的是每周开一次复盘会逐条过小问题——那会训练出"复盘就是走流程"的团队文化，然后真正该开的会大家都不认真了。

### 故障演练方案

复盘是事后学的，故障演练是事前学的。演练的价值不在于证明系统健壮（没人能从演练中证明这一点），而在于**验证那些只有真出事才会被使用的路径**：降级开关能不能在 2 分钟内拨过去、备用库的数据是不是真的同步、告警能不能真的叫醒人。

演练有三种强度，必须分级做，从便宜的那级开始：

| 级别 | 手段 | 影响面 | 本章演练的四个剧本 | 谁批准 |
|---|---|---|---|---|
| 一级 | 影子流量注入，故障只打日志不影响真实响应 | 零用户影响 | 沙箱工具超时 | 值班人自主 |
| 二级 | 沙箱环境真实注入，单实例或单副本 | 沙箱环境用户 | 检索库宕机、模型限流 | 技术负责人 |
| 三级 | 生产灰度注入，限定 1 个租户且有即时回滚开关 | 单租户用户 | 记忆污染 | 业务负责人 + 回滚预案演练 |

四个剧本的具体做法如下，每个剧本都写清注入点、预期行为、判定标准三样：

| 剧本 | 注入点 | 预期行为 | 判定标准 | 本次演练结果 |
|---|---|---|---|---|
| 沙箱工具超时 | 把沙箱执行器的超时从 30 秒改成 0.05 秒 | 超时工具返回结构化错误，上层降级为"该步不可用"并继续主流程，不整体失败 | 主流程成功率下降不超过 2 个百分点，且全部超时 trace 都有 error 事件 | 通过，1,200 次注入请求成功率下降 1.4 个百分点 |
| 检索库宕机 | 停掉主检索实例，只留一个副本 | 检索层降级为返回空结果并打 error 事件；"检索结果为空率"告警在 2 分钟内触发 | 告警触发时间 <= 2 分钟，且值班人在 5 分钟内响应 | 未通过，告警 6 分钟后才触发，因为该告警当时还没建 |
| 模型限流 | 把模型客户端的 QPS 从 24 限到 3 | 客户端退避重试，超过重试上限后返回明确错误而不是挂起；首 token 延迟告警触发 | 无请求挂起超过 30 秒，且退避策略未造成重试风暴（QPS 不超过限额的 1.5 倍） | 通过，峰值退避期 QPS 为 4.4 |
| 记忆污染 | 向长期记忆写入 200 条互相矛盾的事实 | 检索侧的记忆过滤按写入时间与置信度把低置信条目降权，答案末尾出现时效提示 | 污染条目进入最终上下文的比例 <= 5%，且没有出现单一污染事实被反复引用的答案 | 未通过，进入上下文的比例 23%，比目标高 18 个百分点 |

两个未通过的剧本比通过的更有价值，因为它们各自产出了一个具体行动项：`检索结果为空率`告警不存在（正好对应上一节复盘里的第 4 段），记忆污染的降权规则没有生效。这四条也说明了演练和复盘的关系——复盘告诉你上次哪里漏了，演练验证这次补上没有；只复盘不演练，等于反复写同一份检讨。

演练有一条纪律：**先演练回滚，再演练故障**。演练故障时如果回滚开关本身是坏的，注入的故障就变成了真实事故。所以本系统的每次演练都强制包含一条：三分钟内恢复现场。所以本系统的每次演练都强制包含一条：三分钟内把注入改回去，并验证线上指标回到基线 ±5% 以内。这条验证不通过，演练判定为失败，哪怕故障处理得再漂亮。

!!! mascot-neutral "演练的分数不重要，暴露的问题才重要"
    ![墨墨说明情况](../../img/mascot/neutral.png){ class="mascot-admonition-img" }
    一次演练全部通过不代表系统健壮，只代表这次没测出问题。反过来，两个剧本未通过反而是这次演练最有价值的产出，因为它们各自带出了一个可以立刻修的具体缺口。

### 可靠性成熟度模型

成熟度模型的作用不是给自己评级好看，而是**指明下一级需要补什么**。本章用的四级模型以一个判据贯穿始终：出故障时，你能不能在 15 分钟内说清"哪里坏了、影响了谁、怎么修"。L0 做不到，L3 能做到且这个"说清"是自动生成的。

| 级别 | 特征 | 达标标志（可验证） | 典型事故表现 | 到下一级要补什么 |
|---|---|---|---|---|
| L0 无观测 | 只看进程是否活着，出问题靠用户投诉 | 没有任何 trace；日志只有 print 级的信息 | "系统好像有点慢"，无法定位 | 先接追踪，把 span 埋点补齐 |
| L1 有追踪 | 能看到一次请求的完整执行过程 | 100% 请求有 trace_id，失败 trace 可全量回放 | 能回答"哪一步报的错"，但说不出"多少比例会错" | 接评测集与离线跑分，建立基线 |
| L2 有评测与门禁 | 改动前能预测质量变化，且劣质版本无法上线 | 门禁在 CI 里强制执行且无法绕过；豁免有留痕与失效日期 | 劣质版本被阻断；发布质量波动明显收窄 | 接告警与 SLO，让线上问题主动找上门 |
| L3 自愈与演练 | 故障自动降级、告警主动、演练常态化 | 演练季度化执行且行动项闭环率 100%；注入依赖故障时服务不整体失效 | 平均恢复时间从 33 分钟级降到 8 分钟级 | 进入 L3 之后的目标不再是可靠性数字，而是把成本和延迟再压一个量级 |

本章这套系统在写完本章时的位置需要诚实说明：**L2 已达成，L3 部分达成**。达成的部分是有 trace（100% 请求，14 个 span）、有 200 题评测集与 v1.3.0 版本管理、有四道门禁且在 CI 里强制执行、有基于 SLO 与分位数的五条告警（治理后日均 6 条）。没达成的部分有三个：依赖故障演练还是脚本化的而不是自动化的（演练需要人工改配置）；记忆污染的降权规则未生效（污染条目进入上下文 23%）；平均恢复时间仍是 20 分钟量级，目标是 8 分钟。三个缺口对应三个明确的行动项，而这三个缺口也是从 L2 迈向 L3 的全部内容——这个模型的价值正在于此：它不告诉你"L2 已经很好了"，它告诉你差什么。

!!! mascot-celebration "可靠性闭环合上了"
    ![墨墨庆祝](../../img/mascot/celebration.png){ class="mascot-admonition-img" }
    你现在手里有一棵能回放的 trace 树、一把锁住发布的门禁尺、一次能算出收益的改进循环，还有四级成熟度表知道自己还差什么。从今天起，"改完感觉变好了"这句话在评审会上就站不住了。

## 本章小结

本章的核心结论是一张从问题到动作的闭环表，所有数字都可回溯到正文的具体小节：

| 结论 | 关键数字 | 出处 |
|---|---|---|
| 可观测、评测、优化三根柱子缺一不可 | 只有可观测无法判断好坏；只有评测无法定位环节 | 三根柱子与 trace 这条线 |
| Trace 是可观测的最小单位，本系统单次问答 14 个 span | 端到端 P50 2,800 毫秒 | LangFuse追踪接入 |
| 选 LangFuse 的唯一理由是自托管带来的数据不出域 | 日均 12,000 条 trace，月增 12 GB | LangFuse优先实践 |
| 根因定位要从第一个出错的环节倒查 | 34 道错题分布 15/11/3/5，检索加重排占 76.5% | Trace根因定位 |
| 成本必须归到阶段才可行动 | 工具调用占 41.1% 成本却只花 630 毫秒；会话成本 0.1420 元 | Token成本归因 |
| 占比最大的段不一定该先优化 | 生成占 54.3% 最难压；工具调用占 22.5% 却收益第一 | 延迟分段分析 |
| 告警阈值要用 SLO 加分位数夹逼，不能拍脑袋 | P95 门禁 3.00 秒；允许失败 1,800 次；告警降 69% | 告警阈值配置 |
| 指标必须与业务失败模式一一对应，且要配反作弊断言 | 三指标对应三种失败；拒答率超 8 个百分点即报警 | DeepEval评测接入 / 优先实践 |
| RAGAS 的价值是把答案质量拆到检索与生成两层 | `context_recall` 0.78、`context_precision` 0.55 与四层归因互相印证 | RAGAS对照实践 |
| 评测集必须版本化，否则回测就是在比噪声 | v1.0.0 的 180 题到 v1.3.0 的 240 题，改动必记原因 | 评测集版本管理 |
| 门禁阈值和告警阈值必须是同一个数字 | 四道门禁 0.85 / 0.05 / 3.00 秒 / 0.030 元 | 上线质量门禁 |
| 流水线要钉死随机性、并发、失败阻断、结果只追加 | 8 并发、24 QPS、基础设施失败同样阻断 | 回归评测流水线 |
| 改进循环每轮只改一个变量、每轮跑全量 | 粗筛 40 题筛假设，全量 200 题验收益 | 自我改进循环 |
| RSI 现阶段不可依赖，四条风险任一条都足以拦住 | 应试、漂移、成本失控、不可解释 | 递归自改进风险 |
| 复盘的行动项写不满等于没做完 | 故障 33 分钟、3,180 次请求、损失 4,896 元 | 可靠性复盘模板 |
| 演练先演练回滚，再演练故障 | 四个剧本两个通过两个未通过，暴露两个缺口 | 故障演练方案 |
| 成熟度以"15 分钟内能否说清哪里坏了"为判据 | 本章位置：L2 已达成，L3 三处未达成 | 可靠性成熟度模型 |
