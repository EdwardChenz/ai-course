检验本章 19 个概念的掌握情况。先作答，再展开答案。

#### 1. trace 与 span 是什么关系？本系统单次问答的 span 规模是多少？

<div class="upper-alpha" markdown>

1. 一次请求对应一个 trace，trace 内每一步动作是一个 span，父 span 耗时等于子 span 耗时之和加上自身开销；本系统单次问答 14 个 span、平均端到端 2,800 毫秒
2. 一次请求对应多个 trace，每个 span 就是一个 trace
3. span 之间一律平级，不存在父子关系
4. 父 span 耗时总是大于所有子 span 之和，因为要预留缓冲

</div>

??? question "查看答案"
    正确答案是 **A**。这套三层结构对应到系统上正好是一棵树，本章所有延迟与成本数字都以它为底稿。选 C 会让"总耗时"变成一堆无序数字，无法定位是哪一段慢。还要记住两个字段纪律：`trace_id` 必须贯穿全链路并同时出现在前端会话记录、网关日志和 trace 平台三处，`session_id` 与 `trace_id` 必须是两级——会话往往有多轮，每轮是一次独立 trace，但成本要按会话汇总。

    **考查概念：** LangFuse追踪接入

    **参见：** [章节首页](../11-observability-eval/index.md)

#### 2. Token 成本按哪四个阶段归因？最反直觉的结论是什么？

<div class="upper-alpha" markdown>

1. 检索、重排、生成、落库；生成占 37.7% 的成本
2. 查询改写、检索、生成、工具调用；工具调用占 20% 的成本
3. 查询改写、生成、工具调用、引用校验，检索与重排自部署不产生 token 费用故不进这张表；最反直觉的是三次工具调用吃掉 41.1% 的钱却只花 630 毫秒——贵在次数不在长度
4. 查询改写、检索、重排、生成；检索占成本的一半

</div>

??? question "查看答案"
    正确答案是 **C**。只有一个总数没法行动，总数告诉你"贵了"却不告诉你"贵在哪"，所以必须能归到 span 级。工具调用贵的原因是每次都把会话历史重新送一遍，而历史里躺着前面几轮已经用过的证据——省钱的第一刀应该切在"三次调用合成一次批量查询"。选 A、B、D 的问题都是把自部署的检索与重排算进了 token 费用，它们本身就是一条省钱结论。

    **考查概念：** Token成本归因

    **参见：** [章节首页](../11-observability-eval/index.md)

#### 3. 配置告警阈值的两条设计原则是什么？

<div class="upper-alpha" markdown>

1. 阈值可以拍一个"感觉挺慢"的数，比如 2 秒，简单好记
2. 告警阈值与门禁阈值必须是同一个数字；每条告警必须先有最小样本量
3. 阈值定得越严越好，宁可多报几次警
4. 每条告警单独定一条阈值，不与其他告警共用

</div>

??? question "查看答案"
    正确答案是 **B**。两处数字一旦不一致，就会出现"告警了但我们认为合规"或者"门禁过了但线上在报警"的荒谬局面；本章 P95 延迟的告警线与上线门禁都是 3.00 秒，幻觉率都是 0.05。没有最小样本的告警在低流量时段会变成噪声发生器。本章首周 1,340 条告警里 1,197 条（89.3%）没有任何处置动作，治理后日均从 191 条降到 6 条。

    **考查概念：** 告警阈值配置

    **参见：** [章节首页](../11-observability-eval/index.md)

#### 4. 从一条失败 trace 定位根因，方法论是什么？34 道错题的分层分布说明了什么？

<div class="upper-alpha" markdown>

1. 答案答错就一定是生成层的问题，改提示词即可
2. 候选池里出现了 gold 块就说明检索没问题
3. 应该从最后一个失败的环节倒查，因为那里的症状最明显
4. 从失败 span 往下倒查 gold 块第一次消失的环节，后面的失败一律当连锁反应；分布是检索 15、重排 11、压缩 3、生成 5，检索加重排占 76.5%，主要战场在检索侧而不在提示词

</div>

??? question "查看答案"
    正确答案是 **D**。顺序反了，你会把两天耗在一个永远不会被调用的参数上：检索没召回，模型照样会生成一段通顺的话，于是被误判成"生成质量问题"。分布表还要往下再分一层——检索那 15 道里有 9 道是库里根本没有这份制度，只能排期补文档；真正能靠改代码当天解决的是重排 11 道加压缩 3 道，占错题的 41.2%。

    **考查概念：** Trace根因定位

    **参见：** [章节首页](../11-observability-eval/index.md)

#### 5. 端到端 2,800 毫秒被拆成九段之后，哪一段该先优化？为什么？

<div class="upper-alpha" markdown>

1. 首 token 等待加逐 token 生成合计占 54.3% 但最难压；工具调用只占 22.5% 却是最好压的一段——三次调用之间没有数据依赖，改并行后 P50 从 630 毫秒掉到 230 毫秒，零模型质量损失
2. 占比最大的生成段必然最该优化，所以第一步就压生成
3. 工具调用与重排都是串行的，只能靠换更快的模型
4. 首 token 等待与逐 token 性质相同，可以合并成一类优化

</div>

??? question "查看答案"
    正确答案是 **A**。"该优化谁"和"谁最慢"是两件事：逐 token 段与输出长度严格成正比，压它等于让模型少说话，而少说话会掉召回，这是要用质量换延迟的交易。选 B 正好踩这个坑。检索段只有 70 毫秒、可压缩性低，动它收益极小；这类"占比大但压不动"与"占比不大但零损失能压"的判断，正是延迟分段分析要交付的东西。

    **考查概念：** 延迟分段分析

    **参见：** [章节首页](../11-observability-eval/index.md)

#### 6. 评测集版本管理有哪几条纪律？为什么线上失败案例必须定期回流？

<div class="upper-alpha" markdown>

1. 只要题目没变，版本号可以不写，反正内容一样
2. goldens 与 test case 都可以人工修改，只要改完重跑基线
3. 评测报告只要记录代码 commit 就够了
4. 内容变化必须改版本号；golden 可人工改、test case 不行；报告要同时记代码 commit、评测集版本与依赖配置版本；线上失败案例必须定期回流，否则自己出的题永远是自己熟悉的题，会慢慢偏离真实分布

</div>

??? question "查看答案"
    正确答案是 **D**。没有版本号，回测对比就是在比噪声——三个月前那次 0.89 如果当时是 180 题、现在 240 题，字面上就不可比。本章 v1.3.0 的 40 道新题全部来自线上负反馈队列，人工标注时发现其中 9 道属于"资料缺失"类，这类题人工出题时几乎不会被主动编出来，因为出题的人知道库里有什么。选 B 相当于改考卷答案让考生抄。

    **考查概念：** 评测集版本管理

    **参见：** [章节首页](../11-observability-eval/index.md)

#### 7. 四道上线门禁分别是什么？成本阈值为什么从第四章的 0.02 元提到 0.030 元？

<div class="upper-alpha" markdown>

1. 四道门禁是答案正确率、幻觉率、召回率与成本；成本阈值没有变化
2. 四道门禁为答案正确率 ≥ 0.85、幻觉率 ≤ 0.05、端到端 P95 ≤ 3.00 秒、单次问答成本 24 小时均值 ≤ 0.030 元；成本阈值提高 50% 是因为被测对象变了——这套系统每次问答调 3 次工具、token 天然更多，用旧阈值会让每次发布都被拦，团队三次之后就会开始绕过门禁
3. 四道门禁是与运算；成本阈值提高只是为了给团队更多弹性
4. 四道门禁只要三项达标即可，成本属于软指标

</div>

??? question "查看答案"
    正确答案是 **B**。被测对象变了尺子就得重定，这不是标准放松。选 A 和 D 都是在削弱门禁：门禁的选择原则是每条对应一种业务上不可接受的失败，"越多指标越安心"或"三项够用"都会开出绕过门禁的口子。另外要记住幻觉率的分母是事实性断言数而不是题数——v1.3.0 里 240 个断言有 10 个无依据，10 / 240 = 0.042，显示为 0.04。

    **考查概念：** 上线质量门禁

    **参见：** [章节首页](../11-observability-eval/index.md)

#### 8. 回归评测流水线要钉死哪四个实现细节？

<div class="upper-alpha" markdown>

1. 并发越大越快，应该直接开 24 个 worker
2. 并发应尽量小以避免限流，建议 2 个 worker
3. 生成调用可以用 `temperature=0.3`，更贴近线上表现
4. 固定随机性（`temperature=0`、固定哈希种子与并列打散顺序）、并发取 8 个 worker 稳定在约 24 QPS、失败即阻断（含基础设施失败）、结果只追加并带 git commit 与评测集版本号

</div>

??? question "查看答案"
    正确答案是 **D**。固定随机性是第一条：两次跑同一份代码得出不同分数，门禁会在 ±0.02 的随机波动里反复横跳，最后所有人都学会忽略它。选 A 的实测是并发调到 24 反而更慢，因为触发提供商限流、退避把时间全耗在等待上；选 C 属于用温度换随机，代价就是门禁不可复现。并发经验值是让总 QPS 落在限额的中位数偏上，本章限额 30 QPS、8 个 worker 每题约 4 次调用，稳定在 24 QPS。

    **考查概念：** 回归评测流水线

    **参见：** [章节首页](../11-observability-eval/index.md)

#### 9. 为防止"为了分数优化系统"，本章挂了哪四个反作弊断言？

<div class="upper-alpha" markdown>

1. 答案与 `expected_output` 的结论重合度低于 0.7 时阻断发布；拒答率相对基线上升超过 8 个百分点时报警；平均答案长度相对基线上升超过 30% 时报警；提交的报告必须覆盖全量 200 题否则作废该轮
2. 只要均值提升就放行，分布不重要
3. 只看正确率，拒答率与答案长度不必管
4. 反作弊靠人工评审代码，不写断言

</div>

??? question "查看答案"
    正确答案是 **A**。这些断言是"作弊的两个出口"：把参考答案的关键结论抄进答案、用"资料未提及"回避责任、加套话凑字数、只挑跑得好的子集报分。指标是对真实质量的代理，不是真实质量本身——见过为了把幻觉率压到 0.03 而把所有不确定答案改成拒答的系统，指标漂亮得能上汇报材料，用户拿到的是一具只会说"不知道"的问答机。所以任何指标改动都要同时看一眼拒答率和答案长度。

    **考查概念：** DeepEval优先实践

    **参见：** [章节首页](../11-observability-eval/index.md)

#### 10. 四个故障演练剧本两个通过两个未通过。为什么说"未通过的更有价值"？

<div class="upper-alpha" markdown>

1. 未通过说明系统不可靠，应该立刻停掉全部线上功能
2. 未通过是因为演练标准定得太严，应该放宽判定后再演练
3. 未通过的两个剧本各自产出了具体行动项——"检索结果为空率"告警当时还没建、记忆污染的降权规则没生效；复盘告诉你上次哪里漏了，演练验证这次补上没有，只复盘不演练等于反复写同一份检讨
4. 未通过说明团队能力不足，应加强培训而不是改代码

</div>

??? question "查看答案"
    正确答案是 **C**。演练的价值不在于证明系统健壮——没人能从演练里证明这一点——而在于验证那些只有真出事才会被使用的路径。检索库宕机那个剧本的判定标准是告警 2 分钟内触发，实际 6 分钟才触发，因为该告警当时还没建；记忆污染那个剧本污染条目进入上下文的比例是 23%，比目标高 18 个百分点。这两条都能立刻修，而且正好对应复盘模板第 4 段"哪个防线本该拦住它"。

    **考查概念：** 故障演练方案

    **参见：** [章节首页](../11-observability-eval/index.md)
