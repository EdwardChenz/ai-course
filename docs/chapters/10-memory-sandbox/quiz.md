#### 1. 短期记忆必须同时设哪两个上限？本章的起点取值是什么？

<div class="upper-alpha" markdown>

1. 轮数上限与 token 预算上限两个都要有；本章起点是最近 6 轮、4,000 个 token、Redis 键存活 7,200 秒
2. 只需要轮数上限 6 轮，token 用量会随轮数自动受控
3. 只需要 token 上限 4,000，轮数由 token 自然决定
4. 两个上限都设成 14 轮与 8,000 个 token，与会话长度对齐

</div>

??? question "Show Answer"
    The correct answer is **A**。只设轮数会被单轮超长拖爆——用户贴一段 8,000 字的表格就能击穿；只设 token 会让历史只剩几段互不相干的碎片，因为长轮会挤掉前面的轮子。生产上短期记忆必须落 Redis 而不是进程内存，因为记忆要跨进程、跨重启、跨机器，进程内的字典一条都满足不了。

#### 2. 记忆遗忘机制里的类型权重是哪四档？硬约束的特殊处理是什么？

<div class="upper-alpha" markdown>

1. 稳定事实 1.0 / 偏好 1.2 / 硬约束 0.3 / 噪声 0.9；硬约束照常参与时间衰减
2. 所有类型的记忆一律套用同一条时间衰减曲线，权重相同
3. 稳定事实 1.0 / 偏好 0.9 / 硬约束 1.2 / 噪声 0.3；硬约束的衰减项固定取 1、不参与时间衰减，只有显式覆盖能作废它
4. 回填次数越多分数越高，不做饱和处理

</div>

??? question "Show Answer"
    The correct answer is **C**。硬约束豁免是最容易漏的设计：把"这个账号只读"当成一条普通记忆，衰减半年后它就悄悄不见了，而 Agent 随后会在有写权限的路径上继续跑——没有时间衰减的约束，只有被用户改口这一种失效方式。选 D 的问题是不封顶：一条被反复命中的旧记忆可以靠刷次数把自己顶到第一位，而它三年前可能就过时了，所以频率项要用 \(1 + \ln(1+n)\) 做对数与饱和。

    **Concept Tested:** 记忆遗忘机制

    **See:** [章节首页](../10-memory-sandbox/index.md)

#### 3. 沙箱资源配额的四个维度，本章取值与越界行为分别是什么？

<div class="upper-alpha" markdown>

1. 内存 4 GiB / 2 核 / 60 秒 / tmpfs 8 GiB，越界统一返回同一个错误码
2. 内存 2 GiB / CPU 2 核 / 墙钟 30 秒 / tmpfs 4 GiB；内存分配失败即杀并标 `oom`，墙钟到点由运行时强杀并标 `timeout`，磁盘写入返回 ENOSPC
3. 内存 2 GiB / CPU 4 核 / 墙钟 120 秒 / tmpfs 16 GiB；越界一律放行并只发告警
4. 只设墙钟上限，其余维度交给运行时默认值，避免误杀正常任务

</div>

??? question "Show Answer"
    The correct answer is **B**。四个维度都要有上限值，而且越界行为必须显式定义——沙箱内存超了是启动失败还是运行中被杀，这两种现象在日志里长得很不一样，排查成本差十倍。选 C 的隐患最直接：墙钟一旦不设上限，挂死的沙箱会长时间占资源并计费，而时长恰恰是最贵的旋钮——单次执行从 12 秒涨到 45 秒，Daytona 的月成本就从 1,728 元涨到 5,688 元。

    **Concept Tested:** 沙箱资源配额

    **See:** [章节首页](../10-memory-sandbox/index.md)

#### 4. 为什么不能把整段对话原样存进记忆库？抽取环节的第一道关是什么？

<div class="upper-alpha" markdown>

1. 抽取就是把对话切块后入库，回填时按相似度取 Top 8 即可
2. 只要判断每句是不是完整的陈述句，不需要原文证据
3. 记忆条目由模型在运行时产生，所以可以直接把模型输出的结论当事实存起来
4. 原样入库的代价是三重的：噪声大、检索不准、成本高；抽取要输出带 `stability` 与 `evidence` 的 JSON，`evidence` 必须逐字出现在原文中，否则一律丢弃

</div>

??? question "Show Answer"
    The correct answer is **D**。三个代价都能量化：一句"好的"也是一条记录；Top 8 里塞满寒暄和确认语，真正的偏好被挤掉；本章 12 轮对话共 2,600 个中文字符约 1,900 个 token，全量回填会吃掉 4,000 token 预算的 48%，抽取后压到 3 条事实、约 320 token。选 C 尤其危险——模型不会自我怀疑，它只会自信地复述自己编的东西。

    **Concept Tested:** 长期记忆抽取

    **See:** [章节首页](../10-memory-sandbox/index.md)

#### 5. 记忆检索的三因子权重是多少？为什么不能只看相似度？

<div class="upper-alpha" markdown>

1. 权重 0.55 相关性 / 0.25 新鲜度（τ 取 45 天）/ 0.20 访问频率（10 次饱和）；算例中 A 得 0.747 排第 1，而只看相关性会把 C 排在 B 前面，但 B 是被验证过 9 次的稳定事实
2. 权重 0.55 / 0.30 / 0.15；只看相关性与综合排序一致
3. 三因子权重相等各 0.33；新鲜度与频率不参与排序
4. 频率项不封顶，回填次数越多分数越高

</div>

??? question "Show Answer"
    The correct answer is **A**。三个因子对应三种不同的"该信"：相似度说"对得上"，新鲜度说"还没过期"，频率说"被验证过很多次"。相关性权重最高因为它决定相不相关，频率只占 0.20 因为它不该推翻相关性——一条只被访问过一次但完全对题的硬约束，仍然该进上下文。算例里 B 与 C 分数只差 0.00006，远小于可接受噪声 0.01，工程上按并列处理，但名次交换本身就是教学点。

    **Concept Tested:** 记忆检索策略

#### 6. 用户画像与长期记忆是什么关系？`min_conf` 为什么取 0.60？

<div class="upper-alpha" markdown>

1. 画像是第四个独立存储层，有自己的一套抽取流程
2. 画像字段可以直接从对话里自由推断，不需要置信度门槛
3. 画像是长期记忆的投影，只做增量合并：同字段高置信度覆盖低置信度、新旧冲突时旧值记 `superseded` 留痕、历史版本进审计表；`min_conf` 取 0.60 是因为画像会被原样送进 system 提示词，污染范围比单条记忆更大
4. 业务归属类事实（如账号能碰哪些工单）置信度通常很高，也应该进画像

</div>

??? question "Show Answer"
    The correct answer is **C**。画像只回答一个问题——"这个用户稳定是什么样的人"，答案必须能整段塞进 system 提示词，所以要求字段化、稳定、无冗余。选 D 是个高频陷阱：`account_scopes` 置信度高达 0.92，但它描述的是"这个账号能碰哪些工单"而不是"这个人是怎样的人"，属于运行时授权，应该从工具侧校验读取，不进画像。本章画像 18 个字段进 system 约 320 token，加上 Top 8 回填约 640 token 是记忆层给每轮请求的固定开销。

    **Concept Tested:** 用户画像记忆

    **See:** [章节首页](../10-memory-sandbox/index.md)

#### 7. Daytona 沙箱的完整生命周期是哪四步？三条纪律是什么？

<div class="upper-alpha" markdown>

1. 创建 → 执行 → 销毁三步即可，审计是可选的
2. 创建 → 执行 → 落审计 → 销毁四步，销毁必须写在 `finally` 里；墙钟超时压在运行时一侧、输出必须截断、异常也要当返回值返回给模型；绝不复用实例
3. 可以复用实例以摊薄每次 2.4 秒的创建耗时
4. 墙钟超时交给调用方等待即可，运行时侧不必强制

</div>

??? question "Show Answer"
    The correct answer is **B**。销毁写在 `finally` 是因为一次超时或一次模型报错就会泄漏一个沙箱，而泄漏的沙箱会一直计费，直到 `auto_delete_interval` 兜底——那时账单已经产生了。绝不复用实例这一条要单独强调：复用等于让上一段模型生成的代码能读到这一段的 `envVars`，包括可能存在的密钥。快照可以复用，实例不行。异常当返回值返回，是因为一次 `ZeroDivisionError` 对模型来说是可纠正的信息，对调用方才是失败。

    **Concept Tested:** Daytona优先实践

    **See:** [章节首页](../10-memory-sandbox/index.md)

#### 8. 单次执行 12 秒时，Daytona 与 E2B 各多少钱？由此能不能得出"永远选 E2B"？

<div class="upper-alpha" markdown>

1. Daytona 0.0144 元、E2B 0.0088 元，E2B 在所有场景都更便宜，应统一选 E2B
2. 两者成本相同，选型只看自定义能力
3. Daytona 0.0144 元、E2B 0.0088 元；两条成本线在 5 到 60 秒区间始终不相交，但选型结论是"一次性短任务选 E2B，需要跨多次执行保留工作区与快照复用则接受 Daytona 的溢价"
4. 应优先看启动速度，E2B 启动只要 1.2 秒
</div>

??? question "Show Answer"
    The correct answer is **D**。关键在于两条线不相交的原因是量级差异：启动时间的差价只值 0.0008 元，而单价差是每分钟 0.02 元，所以单价一旦更高就永远更高。但"更便宜"不等于"该选"——真正该问的是我要不要跨多次执行保留工作区。选 A 把成本当成了唯一判据，会在需要持久工作区的场景里反复付溢价；选 C 的问题是用启动速度这个最小量级的优势去否决单价差。

    **Concept Tested:** E2B对照实践

    **See:** [章节首页](../10-memory-sandbox/index.md)

#### 9. 代码执行审计的字段设计里，`code_sha256`、`stdout` 与 `limits` 快照各自解决什么问题？采样率是多少？

<div class="upper-alpha" markdown>

1. `code` 只留前 2,000 字符、`code_sha256` 用来验明被截断部分的正身、`stdout` 留前 8 KB、`limits` 是本次生效的配额快照；执行类记录必须 100% 全采样，且代码与输出要先脱敏再落库
2. 这些字段都是为了省存储，可以按 10% 采样
3. 记 `execution_id`、`actor` 和 `status` 三项就够，其余字段只占空间
4. 代码正文与输出应原样入库，方便事后完整复现

</div>

??? question "Show Answer"
    The correct answer is **A**。`limits` 快照最常被省略，但它是事后归因的关键：同一个 `oom` 状态，内存给 2 GiB 是配额太紧，给 8 GiB 仍然 oom 就说明代码本身在无限吃内存，两者的修法完全不同。选 D 会把客户的真实姓名、订单号、邮箱、手机号和密钥原样写进审计库；脱敏规则要写成正则并固定"先脱敏再落库"的顺序，不能靠人工审阅。

    **Concept Tested:** 代码执行审计

#### 10. `add` 实测 0.0098 元（1,900 输入 + 180 输出 token、约 900 毫秒），`search` 0.0013 元。抽取的时机为什么这么重要？

<div class="upper-alpha" markdown>

1. 抽取应该每轮都做，保证记忆随时新鲜
2. 每轮做和每会话做一次的成本完全一样
3. 抽取必须发生在会话结束时而不是每轮——否则日成本会乘以平均 4.6 轮，从 23.52 元涨到 108 元；两项合计日成本 26.64 元
4. 抽取成本可以忽略，主要开销在检索侧

</div>

??? question "Show Answer"
    The correct answer is **C**。`add` 的输出 token 由记忆条数决定：一次会话平均抽出 3.2 条记忆、每条约 55 个 token，连同 JSON 包装约 180 个。这笔账真正提醒的是"记忆越多越糟"——写入永远比遗忘容易，而错误的记忆会持续污染后续每一次回答，模型不会怀疑记忆，它会把记忆当资料用而且用得很自信。所以本节的遗忘策略不是可选项。

    **Concept Tested:** Mem0记忆层总览

    **See:** [章节首页](../10-memory-sandbox/index.md)
