## 一、记忆层：从本轮上下文到跨会话记忆

### Mem0记忆层总览

Mem0 是一个独立于模型的记忆层，它的全部工作只有两件事：从一段对话里抽取事实存起来（写入），以及在提问时按相关性把事实取回来回填进上下文（检索）。这个形态和第三章的 RAG 是同一个骨架换了个数据源——RAG 检索的是文档块，记忆层检索的是从对话里抽出来的单条事实。差别在粒度与生命周期：文档块由你切分且相对稳定，记忆条目由模型在运行时产生，会被修正，也会被遗忘。

三条硬边界必须先知道。第一，记忆层不替你做窗口管理，短期记忆仍然要自己做，下一节讲。第二，记忆按 `user_id` 隔离，跨用户检索必须在服务端按 `user_id` 过滤，绝不能让前端传这个字段。第三，写入不是免费的：每次会话结束都会产生一次抽取调用，本章示例环境实测一次约 0.0098 元。

Mem0 的接口就两个方法：`add` 传消息列表让它自己决定抽什么、存不存、去重；`search` 传查询串加过滤条件拿回 TopK。底层是向量库加元数据过滤，`user_id`、`agent_id`、`run_id` 三个键决定隔离边界。

```python
from mem0 import MemoryClient          # 版本差异以官方文档为准

mem = MemoryClient(api_key=settings.MEM0_API_KEY)   # 密钥走配置注入，不进代码库


def remember(user_id: str, messages: list[dict]) -> dict:
    """会话结束调一次：Mem0 自己完成抽取、去重与合并"""
    return mem.add(
        messages=messages,
        user_id=user_id,                      # 隔离边界，服务端从会话取
        metadata={"tenant_id": ctx.tenant_id, "source": "chat"},
    )


def recall(user_id: str, query: str, top_k: int = 8) -> str:
    """提问前调一次：按相关性取回 TopK，拼成可直接进提示词的一段文本"""
    hits = mem.search(query=query, filters={"user_id": user_id}, top_k=top_k)
    return "\n".join(f"- {h['memory']}" for h in hits["results"])
```

本章示例环境的规模与开销：12 个用户，人均 380 条长期记忆，全库 4,560 条；每次检索回填 Top 8，约 320 个 token；`add` 实测约 900 毫秒，`search` 约 120 毫秒。单价沿用第一章的示意价（输入 0.004 元 / 千 token、输出 0.012 元 / 千 token），不是厂商报价。

| 操作 | 日调用量 | 输入 token | 输出 token | 单次成本 | 日成本 |
|---|---|---|---|---|---|
| `add` 抽取 | 2,400 次 | 1,900 | 180 | 0.0098 元 | 23.52 元 |
| `search` 检索 | 2,400 次 | 320 | 0 | 0.0013 元 | 3.12 元 |
| 合计 | — | — | — | 0.0111 元 | 26.64 元 |

`add` 的输出 token 由记忆条数决定：一次会话平均抽出 3.2 条记忆，每条约 55 个 token，连同 JSON 包装约 180 个。这笔账提醒一件事：抽取发生在会话结束时，而不是每轮都发生；否则日成本会乘以平均轮数（本例 4.6 轮），从 23.52 元涨到 108 元。

### 短期记忆设计

短期记忆处理的是“这一轮请求要带哪些历史”，和第二章的对话历史管理是同一件事，但生产上要落到 Redis 而不是进程内存——记忆必须跨进程、跨重启、跨机器，进程内的字典满足不了任何一条。

短期记忆有两个上限，缺一个都不行：轮数上限和 token 预算上限。只设轮数会被单轮超长拖爆（用户贴一段 8,000 字的表格）；只设 token 会让历史只剩几段互不相干的碎片，因为长轮会挤掉前面的轮子。本章的起点是最近 6 轮、4,000 个 token、Redis 键的存活时间 7,200 秒（2 小时无活跃即回收）。超预算时的动作不是硬截断，而是把最老的两轮折叠成 120 字摘要——对话前段往往是任务背景，背景被切掉的损失远大于细节被切掉。

三层结构的分工也在这里一次定清，后面四节都按这张表说话：

| 层 | 存储形态 | 典型内容 | 本章规模 | 检索方式 | 进上下文的方式 |
|---|---|---|---|---|---|
| 短期 | Redis ZSET，键 `mem:short:{user_id}:{session_id}` | 最近 6 轮原始消息 | 4,000 token / 会话 | 按时间戳取尾部 | 原文照贴 |
| 长期 | 向量库加元数据过滤 | 单条抽取事实 | 380 条 / 用户 | 相关性加时间衰减加访问频率 | Top 8 回填，约 320 token |
| 用户画像 | Postgres 单行 JSONB | 字段化的聚合视图 | 18 个字段 | 按 `user_id` 直取 | 快照进 system，约 320 token |

```python
import json
import time
from redis.asyncio import Redis

WINDOW_TURNS = 6          # 轮数上限
TURNS_PER_ROUND = 2        # 每轮两条消息：一条用户、一条助手
TOKEN_BUDGET = 4000       # token 预算上限，比轮数更要紧
TTL_SECONDS = 7200        # 2 小时无活跃即回收


async def push_turn(r: Redis, user_id: str, session_id: str, turn_msgs: list[dict]) -> None:
    """一轮写两条消息；score 叠一个微小的偏移，避免同毫秒写入互相覆盖"""
    key = f"mem:short:{user_id}:{session_id}"
    now = time.monotonic()
    pipe = r.pipeline()
    pipe.zadd(key, {json.dumps(m, ensure_ascii=False): now + i * 1e-6
                    for i, m in enumerate(turn_msgs)})
    pipe.zremrangebyrank(key, 0, -(WINDOW_TURNS * TURNS_PER_ROUND) - 1)  # 只留最近 6 轮
    pipe.expire(key, TTL_SECONDS)
    await pipe.execute()


async def build_context(r: Redis, user_id: str, session_id: str) -> str:
    """轮数不够用就折叠最老的两轮；绝不按 token 硬截——硬截会把任务背景切没"""
    key = f"mem:short:{user_id}:{session_id}"
    turns = [json.loads(s) for s in await r.zrange(key, 0, -1)]
    while count_tokens(render(turns)) > TOKEN_BUDGET and len(turns) > 2:
        folded = await summarize(turns[:2], max_chars=120)   # 折成 120 字摘要
        turns = [{"role": "system", "content": f"[早期对话摘要] {folded}"}] + turns[2:]
    return render(turns)
```

摘要必须自己带这句“早期对话摘要”的前缀，否则模型会把摘要当成用户说过的话，混淆事实与转述。

### 长期记忆抽取

先说不能做什么：不能把整段对话原样存进记忆库。这条错误的代价是三重的。噪声大——一句“好的”也是一条记录；检索不准——Top 8 里塞满寒暄和确认语，真正的偏好被挤掉；成本高——对话越长，回填越贵，本章示例里一段 12 轮对话共 2,600 个中文字符，按第一章换算约 1,900 个 token，全量回填会吃掉 4,000 token 预算的 48%。抽取的意义就是把这 2,600 字压成 3 到 5 条单句事实。

抽取规则只有四组，但每组都必须守住：

| 该存 | 不该存 | 判据 |
|---|---|---|
| 稳定事实：部门、邮箱、常用时区 | 本轮问题的措辞 | 下次还会为真，且与“这次问了什么”无关 |
| 明确偏好：语言、输出风格、图表偏好 | 一次性情绪：“今天好烦” | 跨越会话仍然成立 |
| 硬约束：“这个账号只读” | 知识库里能检索到的通用知识 | 会改变 Agent 要执行的动作 |
| 明确纠正：“是 Q3 不是 Q2” | 模型自己推测出来的结论 | 用户显式否定了某条旧记忆 |

抽取是一次结构化调用，不是自由生成。让模型输出带 `stability` 与 `evidence` 字段的 JSON，其中 `evidence` 必须逐字出现在原文里——没有原文片段支撑的候选一律丢弃，这是把“幻觉记忆”挡在库门外的唯一办法。模型不会自我怀疑，它只会自信地复述自己编的东西。

```python
EXTRACT_PROMPT = """从对话中抽取可跨会话复用的事实，只输出 JSON。
每条候选包含：text（单句事实）、stability（stable|volatile）、
evidence（原文片段，必须逐字出现在对话中）、action（add|update|delete）。
不要抽取：本轮问题的措辞、一次性情绪、通用知识、你的推测。
"""


async def extract_memories(messages: list[dict]) -> list[dict]:
    raw = await llm.chat_json(system=EXTRACT_PROMPT, messages=messages)
    kept = []
    for c in raw["candidates"]:
        # 证据校验：evidence 必须在原文里逐字找得到，否则这条是模型编的
        if not any(c["evidence"] in m["content"] for m in messages):
            continue
        # 稳定性判定：不稳的候选只能用来修正旧记忆，不能新增长期记忆
        if c["stability"] != "stable" and c["action"] == "add":
            continue
        kept.append(c)
    return [c for c in kept if c["action"] == "add"]
```

算例：一段 12 轮的会话共 2,600 个中文字符（约 1,900 个 token），模型给出 4 条候选，3 条通过证据与稳定性校验写入，1 条作为一次性情绪丢弃。写入调用的输入 1,900 个 token、输出 180 个 token，按第一章的示意价约 0.0098 元、约 900 毫秒。

### 记忆检索策略

检索排序不能只看相似度。相似度解决“说的是不是同一件事”，但记忆库里同时躺着三个月前的旧偏好和上个月被确认了八次的硬约束，两者的向量相似度可能一样高。所以本章用三因子加权：相关性、新鲜度、访问频率。

\[ \text{Score} = 0.55\,s + 0.25\,e^{-\Delta t / \tau} + 0.20\,\min\!\left(\frac{n}{10},\, 1\right) \]

其中 \(s\) 是余弦相似度归一化到 0 到 1，\(\Delta t\) 是距上次访问的天数，\(\tau\) 取 45 天，\(n\) 是累计回填次数。三个因子对应三种不同的“该信”：相似度说“对得上”，新鲜度说“还没过期”，频率说“被验证过很多次”。相关性权重最高，因为它决定相不相关；频率只占 0.20，因为它不该推翻相关性——一条只被访问过一次但完全对题的硬约束，应该排在被访问过八次的旧偏好前面。

算例，检索“我一般看什么格式的报表”，三条候选：

| 候选 | s | 新鲜度 | 频率 | Score | 纯相关性名次 | 综合名次 |
|---|---|---|---|---|---|---|
| A 偏好带趋势线的折线图 | 0.86 | 0.936 | 0.20 | 0.747 | 1 | 1 |
| B 报表统一走汇总页 | 0.80 | 0.135 | 0.90 | 0.654 | 3 | 2 |
| C 偏好先看结论再看明细 | 0.82 | 0.411 | 0.50 | 0.654 | 2 | 3 |

B 和 C 的分数差只有 0.00006，远小于可接受的排序噪声 0.01，所以工程上按并列处理，用 `last_accessed` 更新的 C 排在前面。真正的教学点是名次交换：只看相关性会把 C 排在 B 前面，而 B 是被验证过 9 次的稳定事实。

```python
import math

W_SIM, W_RECENCY, W_FREQ = 0.55, 0.25, 0.20
TAU_DAYS, SATURATION = 45.0, 10          # 半衰 45 天，频率在 10 次处饱和


def rank_memories(query_vec, candidates, tau: float = TAU_DAYS, k: int = 8):
    """三因子加权排序；只回填 Top k，其余留在库里不删——删除是遗忘策略的职责"""
    scored = []
    for m in candidates:
        s = max(0.0, min(1.0, cosine(query_vec, m["vector"])))  # 相似度归一化到 0~1
        recency = math.exp(-m["days_since_access"] / tau)      # 指数时间衰减
        freq = min(m["hits"] / SATURATION, 1.0)                # 饱和式，避免刷次数
        scored.append((W_SIM * s + W_RECENCY * recency + W_FREQ * freq, m))
    scored.sort(key=lambda x: -x[0])
    return scored[:k]
```

频率项必须做饱和：不封顶的话，一条被反复命中的旧记忆可以靠刷次数把自己顶到第一位，而它三年前可能就过时了。

!!! mascot-tip "三因子权重的起跑线"
    ![墨墨提示技巧](../../img/mascot/tip.png){ class="mascot-admonition-img" }
    0.55 / 0.25 / 0.20 是个能直接用的起点，但先别调它。顺序是先确认候选里确实有正确记忆，再用二十来条真实提问看排序错在哪，然后一周只改一个因子。这个坑我替你踩过，同时动三个因子，你会分不清是哪个在起作用。

### 记忆遗忘机制

本节是本章最有分量的一节，因为它是唯一一件“记忆越多越糟”的事。写入永远比遗忘容易：一句新事实写进去只要 900 毫秒，而错误的记忆会持续污染后续每一次回答——模型不会怀疑记忆，它会把记忆当资料用，而且用得很自信。

错误记忆有三个来源，处置方式各不相同：

| 来源 | 症状 | 处置 |
|---|---|---|
| 抽取幻觉：模型编了一条不存在的偏好 | 用户从没说过，Agent 却一口咬定 | 靠 `evidence` 校验挡在门外，见上一节 |
| 覆盖未完成：新旧事实并存，两条都能被检索到 | Agent 一会儿说 A 一会儿说 B | 显式覆盖：旧条目标 `superseded_by`，检索时跳过 |
| 时效性失效：项目结项、季度变更、岗位调整 | 拿过期状态做决策 | 时间衰减降到阈值以下即转归档 |

遗忘不是删除。三种策略分工不同：时间衰减决定“多久变得不可信”，访问频率决定“被验证过多少次”，显式覆盖与显式遗忘决定“立刻作废”。真正的删除只由两件事触发——用户说了“忘掉我住哪儿”，或者保留期 180 天到期。归档态的记忆仍在库里、仍可被检索，但不回填进上下文：既省了 token，又保住了“我们以前聊过这个”的审计能力。

留存规则只有一条公式，但它的取值要实测校准：

| 策略 | 规则 | 本章取值 | 说明 |
|---|---|---|---|
| 时间衰减 | 分数乘 \(e^{-\Delta t / \tau}\) | \(\tau = 45\) 天 | \(\tau\) 越大越念旧 |
| 访问频率 | 分数乘 \(1 + \ln(1 + n)\) | \(n\) 为累计回填次数 | 用对数，防止刷次数 |
| 类型权重 | 稳定事实 1.0 / 偏好 0.9 / 硬约束 1.2 / 噪声 0.3 | 四档 | 硬约束权重高，因为它过期会出事 |
| 硬约束豁免 | 约束类的衰减项取 1，不参与时间衰减 | — | 只有显式覆盖能作废它 |
| 回填阈值 | 分数大于等于 0.12 才回填上下文 | 0.12 | 低于阈值转归档 |
| 硬删除 | 仅显式遗忘或保留期到期 | 180 天 | 归档不等于删除 |

硬约束豁免这条是最容易漏的设计。把“这个账号只读”当成一条普通记忆，衰减半年后它就悄悄不见了，而 Agent 随后会在有写权限的路径上继续跑——没有时间衰减的约束，只有被用户改口这一种失效方式。

\[ S = \min\!\left(1.0,\; w \cdot R \cdot e^{-\Delta t / \tau} \cdot \left(1 + \ln(1 + n)\right)\right) \]

```python
import math

TYPE_WEIGHT = {"fact": 1.0, "preference": 0.9, "constraint": 1.2, "noise": 0.3}
TAU_DAYS, KEEP_THRESHOLD, RETENTION_DAYS = 45.0, 0.12, 180


def retention_score(memory: dict, now) -> float:
    """约束类不衰减：硬约束没有自然过期，只有被显式覆盖才作废"""
    days = (now - memory["last_accessed"]).days
    decay = 1.0 if memory["type"] == "constraint" else math.exp(-days / TAU_DAYS)
    raw = (TYPE_WEIGHT[memory["type"]]
           * memory["relevance"]
           * decay
           * (1 + math.log(1 + memory["hits"])))
    return min(1.0, raw)          # 上限 1.0：再重要的记忆也不会比满分更重要


def apply_forgetting(store, now) -> dict:
    """三态流转：回填、归档、删除；归档最容易被误当成删除"""
    stats = {"kept": 0, "archived": 0, "deleted": 0}
    for m in store.iter_all():
        if m.get("superseded_by"):                      # 显式覆盖：已被新事实顶掉
            store.archive(m["id"]); stats["archived"] += 1
            continue
        if retention_score(m, now) >= KEEP_THRESHOLD:
            store.touch(m["id"]); stats["kept"] += 1    # 回填并刷新访问时间
        elif (now - m["last_accessed"]).days > RETENTION_DAYS:
            store.delete(m["id"]); stats["deleted"] += 1   # 保留期到期才真删
        else:
            store.archive(m["id"]); stats["archived"] += 1
    return stats
```

拿本章示例库的 6 条记忆试一遍：\(\tau\) 取 45 天、回填阈值取 0.12，结果是 3 条保留回填、3 条转归档。被归档的三条恰好是最该忘的——210 天没确认的邮箱、300 天前就已结项的报表项目、上个月顺口提的一次“想学 Rust”。下面的模拟器把 \(\tau\) 和阈值做成可拖的量，你会看到不同的取值把哪条记忆判死。

### 用户画像记忆

画像是聚合视图，不是第四个存储层。它只回答一个问题：“这个用户稳定是什么样的人”，而答案必须能整段塞进 system 提示词，所以要求字段化、稳定、无冗余。每条长期记忆写入之后，向画像的对应字段做一次增量合并——画像没有独立的抽取流程，它只是长期记忆的投影。

增量合并的规则只有三条：同字段高置信度覆盖低置信度；新旧冲突时旧值记 `superseded` 留痕而不是直接删；画像里只保留当前生效的事实，历史版本进审计表。这三条和上一节的显式覆盖是同一套逻辑，只是作用对象从单条记忆换成了字段。

本章的画像是 18 个字段，其中 4 个是硬约束。这 4 个字段不参与时间衰减，也永远不会被自动覆盖，只能由用户显式改口。整份快照进 system 提示词约 320 个 token，与长期记忆的 Top 8 回填加起来约 640 个 token——这是记忆层给每轮请求增加的固定开销，值不值取决于任务是否真的需要个性化。

```python
PROFILE = {
    "locale": "zh-CN",              # 语言与地区
    "tz": "Asia/Shanghai",          # 时区
    "dept": "华东销售二部",          # 部门
    "output_style": "先结论后明细",   # 输出风格偏好
    "chart_pref": "带趋势线的折线图", # 图表偏好
    "constraints": [                 # 硬约束：不参与衰减，只能显式改口
        "订单接口只读",
        "导出文件必须带审批号",
    ],
    "version": 7,                    # 每次合并加 1，便于回滚
    "updated_at": "2026-10-06T09:12:00Z",
}


def merge_profile(old: dict, facts: list[dict], min_conf: float = 0.60) -> dict:
    """一条长期记忆进来只改它命中的字段；冲突时把旧值挂 _superseded 留痕"""
    new = {**old, "constraints": list(old["constraints"])}
    conf = dict(old.get("_conf", {}))
    for f in facts:
        field = f.get("profile_field")
        if not field or f["confidence"] < min_conf:
            continue                                    # 低置信度候选不写画像
        if field == "constraints":
            if f["text"] not in new["constraints"]:
                new["constraints"].append(f["text"])     # 硬约束只增不减
        elif f["confidence"] >= conf.get(field, 0.0):
            new.setdefault("_superseded", []).append({"field": field,
                                                     "old": new.get(field)})
            new[field], conf[field] = f["text"], f["confidence"]
    new["_conf"] = conf
    new["version"] = old.get("version", 0) + 1
    return new
```

`min_conf` 取 0.60 的理由和抽取那一节一致：低于这个置信度的候选大概率是模型推测的，而画像会被原样送进 system 提示词，污染范围比单条记忆更大。

## 二、执行沙箱

第六章给过一条硬规矩：能跑代码的工具必须有沙箱，并且至少做到第三层隔离——只读根文件系统、网络默认 deny 加白名单、`no_new_privs`、用完即销毁。那一节末尾的配置里写着 `runtime: daytona`，那是个占位符。本章把它换成真实部署，并补上第六、七章反复用到却一直没定义的两样东西：资源配额的具体数值，以及执行之后必须落库的审计记录。

### Daytona沙箱部署

Daytona 是一套专门跑 AI 生成代码的弹性运行时：每个沙箱是一个独立隔离的执行环境，可从快照秒级启动，生命周期可编程控制（到点停、自动归档、自动删），按运行时间计费。本章走托管服务，部署只有三步——装客户端、注入密钥、验证连通；自托管需要单独拉起控制面与运行时两套服务，最小规格与依赖请以官方部署文档为准，不要照抄本节的数字。

```bash
pip install "daytona"                              # 客户端 SDK，版本差异以官方文档为准
export DAYTONA_API_URL=https://app.daytona.io/api
export DAYTONA_API_KEY=dtn_xxx                     # 生产由密钥管理注入，绝不进代码库

# 验证连通：能列出已有沙箱就算通
python - <<'PY'
from daytona import Daytona
print([s.name for s in Daytona().list()])
PY
```

连通之后第一件事不是跑代码，而是把第六章那份隔离配置固化成可复用的档位，这样创建沙箱时不会出现“这次忘了关网络”的随机事故：

```yaml
# sandbox_profiles.yaml：把第三层隔离固化成两个档位
profiles:
  calc:                              # 纯计算与数据变换，本章默认档
    image: "debian-slim:3.12"
    language: python
    resources: {cpu: 2, memory: 4, disk: 8}      # 单位 GiB
    limits:
      wall_clock_s: 30                # 硬超时，到点由运行时强杀
      tmpfs_mb: 4096                   # 唯一可写区，用完即销毁
    network:
      network_allow_list: ["api.bank.example.com", "pypi.org"]
      network_block_all: true         # 主开关先关，再按白名单放行
    lifecycle:
      auto_stop_interval: 0            # 0 表示不自动停，用完由代码显式销毁
      auto_delete_interval: 300        # 兜底：5 分钟没人管就删，防止泄漏

  data:                              # 要读大 CSV 的重活档，配额高一档
    inherits: calc
    resources: {cpu: 4, memory: 8, disk: 20}
    limits: {wall_clock_s: 120, tmpfs_mb: 16384}
```

三个参数要说清含义。`auto_stop_interval` 设为 0 是刻意的：第六章要求“用完即销毁”，把销毁时机交给平台去猜，等于把上一段代码的环境变量留给下一段。`auto_delete_interval` 是第二道保险，专门兜住代码里漏掉 `delete` 的异常路径，它不替代 `finally`，只替你不小心。`network_block_all` 配白名单而不是黑名单，因为黑名单挡不住 DNS 重绑定——这一点第六章已经用一次事故讲过了。

本章示例环境的实测值：从快照创建沙箱约 2.4 秒，销毁约 0.5 秒且不计费，8 GiB 快照的首次构建约 4 分钟。快照的意义就在这里：第一次构建 4 分钟，之后每次启动都从快照拉，2.4 秒。

### Daytona优先实践

完整生命周期是四步：创建 → 执行 → 落审计 → 销毁。销毁必须写在 `finally` 里，否则一次超时或一次模型报错就泄漏一个沙箱，而泄漏的沙箱会一直计费，直到 `auto_delete_interval` 兜底——那时候账单已经产生。

三条纪律：墙钟超时要压在运行时一侧，不能只靠调用方的等待；输出必须截断，模型很容易写出打印一万行的代码，返回体膨胀会打爆上下文；异常也要当返回值返回给模型，让它自己决定换写法，而不是把整个工具调用打成失败——一次 `ZeroDivisionError` 对模型来说是可纠正的信息，对调用方来说是失败。

```python
import asyncio
from daytona import Daytona, CreateSandboxFromImageParams, Image, Resources

MAX_OUTPUT_BYTES = 8192          # 8 KB 输出上限，防止打爆模型上下文
WALL_CLOCK_S = 30


async def exec_code(user_id: str, code: str) -> dict:
    """创建 → 执行 → 审计 → 销毁；销毁写在 finally，异常路径同样回收"""
    daytona = Daytona()
    sandbox = await asyncio.to_thread(                     # SDK 是同步的，别堵住事件循环
        daytona.create,
        CreateSandboxFromImageParams(
            image=Image.debian_slim("3.12"),
            language="python",
            resources=Resources(cpu=2, memory=4, disk=8),
        ),
        timeout=40,                                        # 创建超时，不是执行超时
    )
    try:
        resp = await asyncio.wait_for(                      # 双保险：调用方超时 + 运行时强杀
            asyncio.to_thread(sandbox.process.code_run, code),
            timeout=WALL_CLOCK_S,
        )
        stdout = (resp.result or "")[:MAX_OUTPUT_BYTES]
        audit(user_id=user_id, code=code, stdout=stdout,   # 审计在返回前落库，见后文
              status="ok", elapsed_ms=resp.execution_time)
        return {"stdout": stdout,
                "truncated": len(resp.result or "") > MAX_OUTPUT_BYTES}
    except asyncio.TimeoutError:
        audit(user_id=user_id, code=code, stdout="", status="timeout")
        return {"stdout": "", "error": "超过 30 秒墙钟上限，已终止"}
    finally:
        await asyncio.to_thread(daytona.delete, sandbox)   # 用完即销毁，绝不复用实例
```

绝不复用实例这一条要单独强调：复用沙箱等于让上一段模型生成的代码能读到这一段的 `envVars`，包括可能存在的密钥。快照可以复用，实例不行。

本章示例环境的一次执行账：创建 2.4 秒加执行 18 秒等于 20.4 秒的计费窗口，销毁不计费；`code_run` 的返回带 `result` 与 `execution_time` 两个字段，取输出时必须自己截断。

### E2B对照实践

E2B 是同一类问题的另一家方案，用 Firecracker 微型虚拟机做隔离，启动更快、会话控制更细，但模板定制与持久工作区的路子不同。两家不是替代关系，按场景选就行。

| 维度 | Daytona（优先讲解） | E2B（对照） |
|---|---|---|
| 隔离方式 | 独立沙箱运行时，快照可复用 | Firecracker 微型虚拟机 |
| 启动速度（示例环境实测） | 2.4 秒 | 1.2 秒 |
| 单次执行会话时长 | 2.4 秒创建加 18 秒执行 | 1.2 秒启动加 18 秒执行 |
| 示意单价（2 vCPU） | 0.06 元 / 分钟 | 0.04 元 / 分钟 |
| 可定制性 | 自定义镜像加快照，可预装重依赖 | 自定义模板，本地构建后上传 |
| 状态管理 | 到点自动停、自动归档、自动删 | 暂停与恢复、分叉、快照 |
| 适用场景 | 需要持久工作区、多轮复用、预装重依赖 | 一次性短任务、快速原型、批量小任务 |

```python
from e2b import Sandbox


def exec_code_e2b(code: str, timeout_s: int = 30) -> dict:
    """同样的四步换一家运行时；网络用白名单，不整体放开"""
    sandbox = Sandbox.create(
        template="python",                        # 模板名或模板 ID
        timeout=timeout_s,                        # 会话级上限，到点沙箱自己结束
        network={"allow_out": ["api.bank.example.com"]},
        metadata={"pipeline": "chapter10"},
    )
    try:
        execution = sandbox.run_code(code, language="python", timeout=timeout_s)
        logs = execution.logs.stdout or ""
        return {"stdout": logs[:8192], "truncated": len(logs) > 8192}
    finally:
        sandbox.kill()                           # 与上下文管理器等价，异常路径同样回收
```

选型结论可以直接写成规则：一次性、单次执行在 30 秒内、不需要预装依赖，选 E2B；需要跨多次执行保留工作区、需要把运行环境固化成快照、依赖里已经有 pandas 之外的重家伙，选 Daytona。

这笔账要算清楚。单次执行 12 秒时，Daytona 是 \((2.4 + 12) / 60 \times 0.06 = 0.0144\) 元，E2B 是 \((1.2 + 12) / 60 \times 0.04 = 0.0088\) 元，E2B 省 0.0056 元、降幅 38.9%。而且在整个 5 到 60 秒区间里，Daytona 始终更贵——启动快的那 1.2 秒只值 0.0008 元，抵不过每分钟 0.02 元的单价差。所以选择依据不是启动速度，而是“要不要为持久工作区和可定制性付溢价”。

### 沙箱资源配额

配额不是“给多少算多少”。四个维度都要有上限值，而且越界行为必须显式定义——沙箱内存超了是启动失败还是运行中被杀，这两种现象在日志里长得很不一样，排查成本差十倍。

| 维度 | 本章取值 | 收紧的代价 | 放宽的风险 | 越界行为 |
|---|---|---|---|---|
| 内存 | 2 GiB | 用 pandas 读 200 MB 级 CSV 时 OOM 率从 2% 升到 11% | 本档无明显收益 | 分配失败即杀，审计标 `oom` |
| CPU | 2 核 | P95 执行 9.2 秒 | 换 4 核后 P95 降到 5.1 秒，单价从 0.06 升到 0.11 元 / 分钟 | 超时交给墙钟兜底 |
| 墙钟时长 | 30 秒 | 长任务被腰斩 | 挂死的沙箱长时间占资源并计费 | 运行时强杀，审计标 `timeout` |
| 临时磁盘 | 4 GiB tmpfs | 中间产物写不下 | 与内存同价，最容易被忽略 | 写入返回 ENOSPC |
| 网络出站 | 白名单 2 个域名 | 装包时要临时放行 `pypi.org` | 整体放开等于没有沙箱 | 未在白名单的连接直接拒 |

网络那一行值得单说。白名单里的 `pypi.org` 是妥协，装依赖确实需要出网，但它只在沙箱创建阶段有意义。执行阶段的正确做法是把依赖预装进镜像或快照，运行期把网络整体关掉——这正是上一节自定义镜像的价值所在：把依赖问题从运行时挪到构建时。

时长是最贵的旋钮。单次执行从 12 秒涨到 45 秒，Daytona 的日成本从 57.6 元涨到 189.6 元，月成本从 1,728 元涨到 5,688 元；同一场景下 E2B 从 35.2 元涨到 123.2 元，月成本 3,696 元。所以墙钟上限要按“正常任务 P99 时长乘二”来定，不是按“感觉差不多”定——设 30 秒时 P99 是 9.2 秒，还有一倍多的余量；设 120 秒时正常任务只占不到十分之一的窗口，剩下的时间全是风险敞口。

### 代码执行审计

沙箱解决的是“代码不能伤到宿主”，审计解决的是“出了事要能查清”。模型生成的代码被执行过无数次，出了问题你必须能回答三个问题：谁触发的、什么时候跑的、跑的是什么。三问答不上来，审计日志就是零。

审计对象不是业务日志，是“每一次执行”这一条记录。字段设计如下：

| 字段 | 类型 | 用途 | 是否脱敏 |
|---|---|---|---|
| `execution_id` | string | 一次执行一条主键，串联沙箱日志与业务日志 | 否 |
| `actor` | string | 谁触发的：`user_id` 或 `service_account` | 否 |
| `started_at` / `ended_at` | timestamp | 墙钟时长与并发统计 | 否 |
| `sandbox_id` | string | 定位到具体沙箱，查平台侧日志 | 否 |
| `code` | string | 代码正文，只留前 2,000 字符 | 需脱敏 |
| `code_sha256` | string | 全文指纹，被截断部分用它验明正身 | 否 |
| `stdout` | string | 输出前 8 KB | 需脱敏 |
| `status` | enum | `ok` / `timeout` / `oom` / `denied` | 否 |
| `limits` | object | 本次生效的四维配额快照 | 否 |

脱敏那一列是全表唯一容易被做错的地方。代码正文里会出现真实的客户名和订单号，输出里会打印出完整的邮箱、手机号和密钥。规则要写死成正则，而不是靠人工审阅；而且顺序不能反，必须先脱敏再落库。

```python
import hashlib
import re

PII = [
    (re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+"), "[邮箱]"),
    (re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)"), "[手机号]"),
    (re.compile(r"(?<!\d)\d{17}[\dXx](?!\d)"), "[身份证]"),
    (re.compile(r"(?<!\d)\d{16,19}(?!\d)"), "[卡号]"),
    (re.compile(r"(sk-[A-Za-z0-9]{8,}|ghp_[A-Za-z0-9]{20,})"), "[密钥]"),
]
CODE_KEEP = 2000          # 代码正文只留前 2,000 字符，其余靠指纹兜底


def redact(text: str) -> str:
    """先脱敏再落库；顺序不能反，落库后再脱敏等于没脱"""
    for pattern, placeholder in PII:
        text = pattern.sub(placeholder, text)
    return text


def write_audit(actor: str, sandbox_id: str, code: str, stdout: str,
                status: str, started_at, ended_at, limits: dict) -> dict:
    rec = {
        "execution_id": uuid4().hex,
        "actor": actor,
        "sandbox_id": sandbox_id,
        "code": redact(code[:CODE_KEEP]),
        "code_sha256": hashlib.sha256(code.encode()).hexdigest(),   # 截断部分的明证
        "stdout": redact(stdout[:8192]),
        "status": status,
        "started_at": started_at.isoformat(),
        "ended_at": ended_at.isoformat(),
        "limits": limits,                                          # 配额快照，便于事后归因
    }
    audit_store.append(rec)      # 独立的 append-only 表，永不 update、永不 delete
    return rec
```

一条审计记录约 1.4 KB，保留 180 天，采样率 100%。执行类记录不接受采样，因为出事的那一次不会提前打招呼。`limits` 快照常被省略，但它是事后归因的关键：同一个 `oom` 状态，内存给 2 GiB 是配额太紧，给 8 GiB 仍然是 oom 就说明代码本身在无限吃内存，两者的修法完全不同。
