## 一、把每章的小实战写下来

### 小实战写作规范

每个小实战都按同一份清单交付，四件缺一不可：可运行的仓库、可读的说明、可复现的复盘、可演示的脚本。小实战的价值在于覆盖面而不是深度，一章一个、章章有，才可能串成后面的集成项目。

```markdown
# 小实战交付清单（每章一份）

- [ ] 仓库结构
      `app/` 实现代码、`tests/` 测试、`prompts/` 提示词、
      `evals/` 评测集与 manifest、`README.md` 说明、`retrospective.md` 复盘
- [ ] 说明
      - [ ] 一句话说清这个系统解决什么问题、给谁用
      - [ ] 写明运行环境与依赖版本来源，不写"最新版"
      - [ ] 写明一条从零跑起来的命令，以及它成功时的输出长什么样
      - [ ] 写明当前已知的三条局限
- [ ] 演示脚本
      - [ ] 五条以内的固定演示路径，每条标注预期结果
      - [ ] 至少一条演示"失败长什么样"，用来证明错误处理是存在的
- [ ] 复盘
      - [ ] 按本节模板填写，指标对比一栏必须填真实数字，不填"效果变好了"
- [ ] 验收自检
      - [ ] 测试全绿、类型检查无新增错误、lint 无新增告警
      - [ ] 一次成功演示、一次失败演示都实际跑过并留下输出
```

仓库结构固定的好处是第三章到第十四章的东西可以横向堆叠——每章一个目录，最后合成项目时直接聚合，不用重新理结构。

### 复盘文档模板

复盘的价值在于留下"下次能用的判断"，而不是记录"这次做了什么"。下面这份模板可以直接复制，六段里第三段与第五段是复盘的真正产出，其余四段只是上下文。

```markdown
# 复盘：<项目或小实战名>

## 1. 背景
两到四句：这件事为什么现在要做，不做会怎样。

## 2. 目标
可量化的一到三条，写成指标而不是方向。
例：答案正确率从 0.83 提到 0.89；P95 端到端延迟压到 3.00 秒内。

## 3. 方案
改了什么，改在哪一层（检索 / 编排 / 生成 / 部署），每项一句话。

## 4. 指标对比
| 指标 | 改前 | 改后 | 差值 | 判定 |
|---|---|---|---|---|
| 答案正确率 | 0.83 | 0.89 | +0.06 | 达标（门禁 >= 0.85） |
| 幻觉率 | 0.09 | 0.04 | -0.05 | 达标（门禁 <= 0.05） |
| P95 端到端延迟 | 3.35 s | 2.54 s | -0.81 s | 达标（门禁 <= 3.00 s） |

## 5. 踩坑
每条写三件事：现象、根因、当时的判断错在哪。
1. 现象：改完提示词正确率没动。
   根因：34 道错题里 76.5% 出在检索与重排，提示词层根本没被调用到错误样本。
   判断错在哪：把"改了没变"当成改动无效，其实改动选错了层。

## 6. 下次改进
一到三条，每条带负责人与触发条件，写成可执行动作。
```

指标对比一栏必须留空重填而不是复制示例数字。没有真实数字的复盘在面试里一问就穿，这比没有复盘更糟。

## 二、把项目讲成故事

### 作品集讲述稿

讲述稿用 **STAR** 结构：情境、任务、行动、结果。四段各承担一件事，别混写——多数人把 STAR 写成一段流水账，结果每段都说不清。

| 段 | 回答的问题 | 长度占比 | 写错的样子 | 正确的样子 |
|---|---|---|---|---|
| 情境 | 当时的系统长什么样，难在哪 | 15% | 行业大趋势、公司背景 | 具体到一条 trace 或一个数字 |
| 任务 | 你负责哪一块，成功判据是什么 | 15% | "我们团队" | "我负责检索与评测这一段，判据是正确率 0.85" |
| 行动 | 你具体改了什么，为什么这么改 | 50% | 罗列用到的技术 | 每条行动都配一个被否掉的替代方案 |
| 结果 | 指标前后对比，以及没解决的 | 20% | "效果很好，上线了" | 指标、门禁口径、以及仍然存在的两条缺口 |

配套的 60 秒自述要写成能背下来的具体文本，空话在 60 秒里无处躲：

> 我做的是一个带知识库的企业制度助手。接手时它的答案正确率是 0.83，幻觉率 0.09，两项都过不了上线门禁。我负责检索与评测这一段。做法是先用 trace 做归因，把 34 道错题拆到四层，发现 76.5% 的错误出在检索召回和重排，而不是生成质量，所以没有去调提示词，而是换了重排模型并提高了召回上限，同时把一次服务调用合并成三次并行调用。结果是正确率 0.89、幻觉率 0.04、P95 从 3.35 秒降到 2.54 秒，四项门禁全过。没解决的是记忆污染的降权规则还没生效，污染条目进入上下文约 23%。

这段文本里有五个可验证的锚：0.83、0.09、0.85、76.5%、23%。面试官只要追问其中一个，你都能往下展开三层。

达标判定规则：总分大于等于 9 判为"直接进作品集"；总分 7 到 8 判为"补一项即可"；总分小于等于 6 判为"重写"。三段里两段达标、一段需补一项，没有三段全部直接达标的情况。

**交互规则：** 每维得分取 0 到 3 的整数，总分等于四维之和，满分 12，容差 0 分。达标判定：总分 >= 9 判"直接进作品集"；7 <= 总分 <= 8 判"补一项即可"；总分 <= 6 判"重写"。边界规则：总分恰为 9 按直接达标计，恰好为 7 按补一项计。最弱维度判定为四维中的最低分；最低分出现并列时（编号 2 的情境与结果并列 0 分）判定为"并列"，说出其中任一维度均算正确，但必须明确指出这是并列。三段无最弱维度并列之外的歧义。

**学习者活动：**

1. 学习者看到量表与三段讲述稿摘要，屏幕提问："12 分和 2 分的差别在结构上——先给每段四维打分，再判达标。"
2. 三段打分全部锁定后揭晓，学习者对照标准总分回看，确认加总是否正确。
3. 学习者为待补强的那一段指出最弱维度，并说明该补什么才算达标。
4. 学习者应注意到编号 3 的行动维拿满 3 分却仍不完美，差别全在结果维的口径与缺口。

**反馈文案：** 三次打分加两次判定，共 5 次提交，打分锁定后才揭晓。分数答对："分数正确，总分 <标准总分>"。分数答错："把四维逐项对照量表加一遍"，随后展示该段的标准四维。最弱维度答对："最弱维度正确：<维度>"。判定答对："判定正确：<标准判定>"。判定答错："总分不到 9 就不能说能直接用，先看是哪个维度拖的"，随后展示该行反馈文案。计分：满分 5 分，答对 4 分视为掌握。

**初始状态：** 四维量表与三段讲述稿摘要可见，三段打分位、最弱维度输入位与达标判定位均为空。屏幕提问："编号 3 拿 10 分却还要补一项——先打分，再判它能不能直接进作品集。"

**章节锚点：** 四维为情境、任务、行动、结果，各 0 到 3 分，满分 12；达标阈值为总分 >= 9 直接进作品集、7 到 8 补一项、6 及以下重写；三段讲述稿的总分为 12、2、10；编号 3 的最弱维度是结果（1 分），短板是缺门禁口径与未解决缺口；编号 2 的最弱维度为情境与结果并列 0 分。

### 项目深挖应对

深挖的本质是验证你是不是真的做过。四类问题几乎覆盖全部深挖，问之前先自问一遍，比被问到现场卡壳强。

| 问题类型 | 典型问法 | 你该给出的东西 | 危险信号 |
|---|---|---|---|
| 为什么这么做 | 为什么选这个编排方式而不是单 Agent | 决策依据加当时的约束条件（时延预算、语料规模、可用人手） | 只说"业界都这么做" |
| 替代方案 | 你考虑过什么别的做法，为什么否掉 | 至少一个被否的方案加否掉它的具体判据 | 说不出任何被否方案，说明没做过选择 |
| 失败过什么 | 讲一次你改错方向的经历 | 现象、根因、判断错在哪、后来怎么发现 | 只有成功案例，一次都没失败过不可信 |
| 数字怎么来的 | 这个正确率是怎么算的，评测集多大 | 指标定义、样本量、门禁口径与一次校验方式 | 数字来自个人印象或单次手工抽查 |

应对法可以固定成 **STAR-QA**：先给 STAR 的四段，再接一句 Q&A 预演——"如果你问我这个数字怎么来的，我会说……"。**把追问提前写进讲述稿**，面试时就不会因为答不上来而卡住整段。深挖问三层还站得住，才算真的懂；站不住的一层通常就在你最想说清楚的那个数字上。

## 三、面试怎么答

### 面试高频题精讲

先把话说在前面：**题目会变，考的是原理不是题库**。下面按六类给出代表题与答题要点，目的是让你知道每类题在考哪个原理；背标准答案是最没用的准备方式。

| 类别 | 代表题 | 答题要点（考什么原理） |
|---|---|---|
| Agent 架构 | 单 Agent 和多 Agent 怎么选？ | 先给可判定的分界：子任务是否可并行、是否共享不可分割的状态、失败是否需要独立重试；再给自己的判据（时延预算与语料规模），别给绝对结论 |
| 工具协议 | MCP 与 A2A 各自解决什么？ | 一个把工具暴露给模型，一个把 Agent 暴露给 Agent；讲清边界：工具的粒度是能力，Agent 的粒度是委托；能说出协议握手与权限边界会加分 |
| RAG 选型 | 什么情况下不上 RAG 而用长上下文？ | 语料总量与单次查询需要的证据量之比；长上下文的成本随 token 线性涨，且引用定位能力弱；给出你实测过的切换点而不是理论值 |
| 可靠性 | 幻觉怎么压，压到什么程度算够？ | 三层手段：约束（只依据给定证据）、校验（断言级引用校验）、兜底（拒答与转人工）；给出门禁口径（幻觉率 <= 0.05）与它对应的业务后果 |
| 多 Agent 编排 | 任务编排和事件编排怎么选？ | 长任务、断点续跑优先选可持久化的编排；批量任务优先选事件驱动；讲清各自的失败恢复粒度 |
| 推理部署 | 自建和调用 API 怎么选？ | 用盈亏平衡点回答：本章第十四章那套系统自建的盈亏平衡在日均 27,313 次；再叠加数据出域与运维能力两个非成本约束 |

每类的准备动作都一样：写一页纸，包含一个原理定义、一个你实测过的数字、一个你被否掉的方案。三样齐了，这类题你怎么问都答得动。

### 系统设计面试

设计一个 AI Agent 系统的答题框架是固定的七步，按顺序走完再回头补细节，面试官不会觉得你在绕。

```markdown
## 系统设计答题框架（七步）

1. 需求澄清：谁用、用来干什么、数据从哪来、量级多大、延迟要求多少
   —— 先问后答。不问就画图，画的必然不是你想要的的东西。

2. 数据层：语料从哪来、怎么切分、怎么保证可更新
   —— 答切分策略与更新机制，不要答具体框架版本。

3. 检索层：混合检索还是图检索、召回与重排怎么分工
   —— 答分工与 TopK 起点，并说明靠哪个指标判断需要调。

4. 编排层：单 Agent 还是多 Agent、编排选哪种、工具怎么接
   —— 给出可判定的选择判据，而不是偏好。

5. 可靠性层：怎么防幻觉、怎么兜底、失败怎么重试
   —— 至少给出两条手段和一个量化门禁。

6. 成本层：单次成本多少、瓶颈在哪、怎么降
   —— 用阶段归因回答，不要只给总数。

7. 监控层：上线后看哪几个指标、阈值从哪来
   —— 阈值必须能追溯到 SLO 或实测分位数。
```

被问到没准备过的部分时，标准答法是三句：我现在的判断是这样；我会先量哪个指标来验证；验证不通过我会退回哪一步。这三句比硬答更能拿分，因为它展示的是可用的决策习惯。

## 四、求职全流程

### 薪资谈判准备

谈薪的实质是**用可核对的数据换对方的确定性**，所以谈之前必须先把三类数据取到，取不到就去取而不是凭感觉报。

| 要取的数据 | 怎么取 | 取不到时的退路 |
|---|---|---|
| 岗位职责的市场区间 | 同城市、同年限、同方向的三到五个公开区间，取中位数 | 至少问两位在该岗位工作过的人，拿口头区间 |
| 自身可量化成果 | 从第十一章门禁与第十四章容量表里抄现成数字 | 没有数字的项目不要写进薪资论证 |
| 对方的预算结构 | 面评时问职责范围与团队阶段，据此判断区间 | 不问就按中位数报，留出上限空间 |

报数有三条纪律：**给区间不给单点**（"我看到类似岗位的区间在这个范围，希望在这个范围的上半段"）；**先问区间再报数**（过早报价会让你成为锚点）；**数字必须有出处**（"我的正确率是 0.89，门禁口径是 0.85"这类表述比"效果很好"值钱得多）。至于常见的"我们这里有 budget 上限""你期望多少"这类回应，务实处理只有一个：拿职责范围、团队阶段与晋升节奏去换，把僵局转成信息交换，而不是硬顶。

!!! mascot-tip "拿数字说话之前，先确认数字的口径"
    ![墨墨提示技巧](../../img/mascot/tip.png){ class="mascot-admonition-img" }
    同一个 0.89，可能是 200 题评测集上的分，也可能是 3 道题手测的结果。谈判里被追问一次口径，数字就会贬值一半。谈之前把每个数字的样本量与判定方式记在纸上，这是最便宜的一次准备。

### 一对一辅导规划

一对一辅导的价值随你的提问质量变化。一次有效会话按议题推进，事前准备比会话时长更重要。

```yaml
# 辅导会话准备单（每次会话前填写）
session:
  date: 2026-10-20
  duration_min: 60
topics:                      # 按优先级排序，前两项必须当场解决
  - name: 项目一的多 Agent 分工
    current_state: 能跑通，但角色边界靠硬编码切分
    evidence: 提供一段 trace 与分工配置
    my_hypothesis: 路由这一步不需要模型，用规则匹配意图更稳
    specific_ask: 请指出这个判断在什么情况下会失效
  - name: 评测集与线上分布的偏差
    current_state: 评测正确率比线上高约 15%
    evidence: 两组抽样结果各 500 条
    specific_ask: 这个偏差应该进评测集还是进报告
followups:                  # 上次会话遗留，本次要闭环
  - 给降权规则补一条反作弊断言
pre_read:                   # 让对方提前看的材料，最多两页
  - 项目一的分工配置（不含密钥）
```

纪律有三条：议题不超过三个，事前把假设写出来而不是等对方给答案，会后当天把结论落成待办。少了第三条，辅导就退化成聊天。

## 五、两个集成项目的验收标准

### 集成项目验收标准

验收标准要先写，再动手写。这是全书的收口——前面十四章的每一个数字在这里变成一条可以判是过的线。项目二的长报告生成走异步口径，这是第十一章"被测对象变了尺子就要重定"的同一原则，交互式部分仍用原四条阈值。

**项目一：带知识库、多 Agent 分工、可观测可评测、Supabase 落库的业务 Agent**

| 验收项 | 判定方式 | 通过标准 |
|---|---|---|
| 知识库问答 | 200 题冻结评测集 | 答案正确率 >= 0.85，幻觉率 <= 0.05 |
| 多 Agent 分工 | 三条固定任务各跑 20 次 | 分工路由正确率 >= 0.90，无跨角色越权调用 |
| 可观测 | 抽样 500 条请求 | 每条有完整 span 树，可从用户会话反查 trace |
| 评测 | 评测集版本与 manifest | 版本号与校验和入仓，改评测集必须重跑门禁 |
| Supabase 落库 | 抽查 100 条会话 | 会话、消息、检索块引用、指标四类数据齐全 |
| 引用校验 | 逐条断言级检查 | 无依据断言数与总断言数之比 <= 0.05 |

| 技术指标门槛 | 阈值 | 阈值来源 |
|---|---|---|
| 答案正确率 | >= 0.85 | 第十一章上线质量门禁，同一口径 |
| 幻觉率（分母为事实性断言数） | <= 0.05 | 第十一章上线质量门禁，同一口径 |
| 端到端 P95 延迟 | <= 3.00 秒 | 第十一章上线质量门禁，含工具调用与校验 |
| 单次问答成本（24 小时加权均值） | <= 0.030 元 | 第十一章上线质量门禁，同一均值口径 |
| 门禁强制执行 | 阻断且不可绕过 | 基础设施失败同样阻断，豁免最多 1 条且 7 天失效 |

交付物清单：`README.md`（含一条从零跑通的命令与成功输出）、`demo-script.md`（五条成功路径加一条失败路径）、`retrospective.md`（按第二节模板填写，指标对比填真实数字）、`quality-gate.yaml`（阈值与第十一章同一份文件）、`evals/manifest.json`（评测集版本与校验和）、追踪面板访问方式与脱敏说明。

**项目二：企业数据分析 Agent，含 Temporal 编排、Polaris/Iceberg 数据湖、Trino 查询与自然语言分析报告**

| 验收项 | 判定方式 | 通过标准 |
|---|---|---|
| 自然语言转查询 | 100 条真实分析意图 | 查询结果与人工核对一致的比例 >= 0.85 |
| Temporal 编排 | 任务运行中强杀工作进程 | 从上次检查点续跑，不重复已完成步骤 |
| 数据湖写入 | 连续三天增量写入 | 分区、快照与时间旅行可回溯，任务可重放 |
| Trino 查询 | 30 条高频分析查询 | 交互式 P95 <= 3.00 秒 |
| 分析报告 | 报告断言逐条校验 | 报告幻觉率 <= 0.05，数字须能追到查询 id |
| 异步长任务 | 完整报告生成 | P95 <= 120 秒，按异步口径判定，不适用 3.00 秒 |

| 技术指标门槛 | 阈值 | 阈值来源 |
|---|---|---|
| 数值正确率 | >= 0.85 | 沿用第十一章正确率门槛，指标换成"查询结果与人工核对一致" |
| 报告幻觉率 | <= 0.05 | 沿用第十一章幻觉率门槛，分母仍为事实性断言数 |
| 交互式 P95 延迟 | <= 3.00 秒 | 沿用第十一章门禁，指澄清与出查询计划两段 |
| 报告生成 P95（异步） | <= 120 秒 | 被测对象为异步长任务，按第十一章重定原则单独定 |
| 编排幂等性 | 重复触发不产生重复副作用 | 同一 workflow id 重放结果一致 |

交付物清单：`README.md`、`demo-script.md`、`retrospective.md`、`quality-gate.yaml`、Temporal 工作流定义与重放验证脚本、数据湖表结构与快照策略文档、30 条查询的基线耗时表。

验收纪律三条：阈值写在与第十一章同一份配置文件里，任一项不达标即判不通过；豁免必须有失效日期与处置手册链接，同时存活不超过 1 条；验收报告里的每个数字都能指认它的评测集版本或采样口径，指认不了的数字按缺失处理，缺失按不达标。

## 本章小结

本章的核心结论是一组"交付与讲述的判据"，所有阈值都能回溯到前十四章：

| 结论 | 关键做法或数字 | 出处 |
|---|---|---|
| 写下来才算学过 | 小实战四件套：仓库、说明、复盘、演示脚本 | 小实战写作规范 |
| 复盘的产出是判断不是记录 | 第三段方案与第五段踩坑是真正产出，第四段必须填真实数字 | 复盘文档模板 |
| 讲述稿按 STAR 四段分工 | 行动占 50% 且每条配被否方案，结果占 20% 且必须给口径与缺口 | 作品集讲述稿 |
| 讲述稿的分数由结构决定 | 满分 12 分，>= 9 直接进作品集，编号 3 拿 10 分仍需补结果口径 | 作品集讲述稿 |
| 深挖考的是真做过 | 四类问题各配一种回答材料，提前写进讲述稿（STAR-QA） | 项目深挖应对 |
| 面试考原理不是题库 | 六类题各准备一页纸：定义、实测数字、被否方案 | 面试高频题精讲 |
| 系统设计按七步走 | 需求、数据、检索、编排、可靠性、成本、监控 | 系统设计面试 |
| 谈薪靠可核对的数据 | 三类数据加三条报数纪律，数字必须有出处 | 薪资谈判准备 |
| 辅导的价值取决于提问 | 议题不超过三个，事前写假设，会后当天落待办 | 一对一辅导规划 |
| 验收标准先写再动手 | 两个项目各一张功能验收表加一张指标门槛表 | 集成项目验收标准 |
| 阈值与第十一章同一份文件 | 0.85 / 0.05 / 3.00 秒 / 0.030 元，项目二长报告按异步口径单定为 120 秒 | 集成项目验收标准 |
